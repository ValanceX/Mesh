# MESH v0.5 — Outline

Date: 2026-09-25
Status: Draft outline, written after an audit of v0.4.0 and a reading of
NEXUS and PORT. It is not an implementation plan.
- The audit's findings are recorded below, F1–F12.
- The invariants I1–I10 carry over from v0.3 and v0.4 unchanged.
  I11–I15 are new, and **proposed**.
- Decisions D1–D10 are **proposed**. Five questions are open, under
  "Open decisions", each with a recommendation. Pass 0 can start once
  open decisions 1 and 2 are answered.
- Nothing here is a Rust or TypeScript API, or a file-level design;
  that belongs to each pass's plan.

Repo: `mesh`. Read, not changed: `nexus` at `4d4554e` and `port` at
`782ee84`.

## Where v0.4 left off

v0.4.0 (released 2026-09-25) took MESH outside Rust. Seven packages are
on npm under `@valancex`, each at 0.4.0 with provenance:
`@valancex/mesh-compiler`, the compiler in WebAssembly, returning exactly
the diagnostics `mesh check --format json` prints; and
`@valancex/mesh-lsp` with its five platform packages.

MESH still stops at diagnostics. Its IR never leaves Rust: v0.4 kept it
out on purpose (E2), to design its serialized form with NEXUS and PORT.
That is v0.5.

## What NEXUS and PORT expect

Both repositories are read at the commits above. What they say about
MESH:

- **NEXUS** (v0.1 primitives implemented, UI-free) is the application
  core: State, Selector, Command, Event and six more primitives, on
  Effect. Its §9: "Commands are the primary application boundary for
  MESH." Its §15: MESH reaches NEXUS through a UI-facing API of state
  reads, selector reads, command invocation and UI-relevant environment
  state, and nothing else. Its §16 and resolved decision 4: **PORT never
  depends on NEXUS**; "everything PORT needs (state, selector values,
  command bindings) must already be resolved into the IR before it
  reaches PORT", by "a MESH runtime adapter". Its dependency directions
  include "MESH → NEXUS interfaces" and "PORT → MESH (Semantic IR only)".
  Its next milestone is "connecting NEXUS to MESH through the runtime
  adapter".
- **PORT** (scaffolding only: three empty packages) renders "compiled,
  validated, renderer-independent UI". A renderer "maps each node onto
  the target's native API" and handles mount, update and unmount. It
  never sees MPRX, runs no business rules, and silently drops nothing.
  Its first slice: `user-card.mprx → MESH compiler → MESH IR → NEXUS
  runtime → PORT (Web) → browser`.

So there are **two** formats, not one, and MESH owns both:
1. what the compiler produces from a template: structure, expressions,
   command intents, all resolved against the manifest. The runtime
   adapter consumes it.
2. what the runtime adapter produces from that and the app's current
   values: a tree of components with concrete prop values and opaque
   event handlers, and no expressions. PORT consumes it.

## Theme

**v0.5: MESH that renders.** A template that checks clean compiles to a
versioned, published format. One evaluator, in Rust, runs it against
the app's current values and produces a render tree that any PORT
renderer can draw, with events that come back as command intents for
NEXUS. MESH ships the formats, the evaluator (native and in
WebAssembly) and a runtime package; NEXUS's adapter and PORT's renderers
are built against them, in their own repositories.

## Architecture and invariants

```text
            compile (check, then emit)            evaluate
MPRX ───────────────────────────────▶ template ─────────────────▶ render tree ──▶ PORT
 + manifest                           (template-v1)  ▲   (render-v1)      │
                                                     │                    │ event
                                        scope values │                    ▼
                                              ┌──────┴──────────┐   dispatch(handler, payload)
                                              │  host (NEXUS    │◀── command intent
                                              │  adapter)       │    (command + arguments)
                                              └─────────────────┘
```

- **The compiler** (`mesh-compiler`) checks a template and, only if it
  has no errors, emits it in the template format.
- **The runtime** (a new crate, and the same code in WebAssembly)
  evaluates a template against scope values and produces the render
  tree; on an event, it evaluates the handler and produces a command
  intent. It has no I/O and no NEXUS dependency.
- **The host** gives the runtime scope values and receives command
  intents. For a NEXUS app, that's the NEXUS adapter: selectors and
  state in, commands out (NEXUS §15).
- **PORT** receives only render trees and a dispatch callback.

**New invariants (proposed).**
- **I11. One evaluator.** MPRX expressions are evaluated in exactly one
  place: the Rust runtime, compiled natively or to WebAssembly. No
  TypeScript, and no renderer, evaluates an expression, coerces a value,
  or decides what a text node says. I6 extends to the runtime's
  JavaScript package.
- **I12. Only what checked, runs.** The compiler emits a template only
  when its check has no errors. The runtime runs only templates of its
  own format version, and refuses one compiled against a different model
  than the one it's given. There is no path from unchecked source to a
  render tree.
- **I13. PORT sees values, never MPRX.** A render tree holds component
  names, concrete values, text, and opaque event handlers. No
  expression, scope name, command or `$event` reaches a renderer.
- **I14. The host is checked, not trusted.** Every scope value is
  checked against its declared type when it enters the runtime, and
  every event payload against its event's payload type. A mismatch is a
  runtime diagnostic, and nothing is rendered or dispatched from it.
- **I15. MESH doesn't need NEXUS to run.** The runtime depends on a
  host interface MESH defines, not on NEXUS. Any program can be a host,
  and MESH's own tests use one. (ARCHITECTURE rule 6, extended from the
  compiler to the runtime.)

## Goals

- **The template format** (`schemas/template-v1.schema.json`): a checked
  template, with every name already resolved, emitted by the Rust API,
  `mesh compile`, and `@valancex/mesh-compiler`'s `compile()` (D1, D2).
- **MPRX's evaluation, specified:** numbers, arithmetic, text, absence
  (D8).
- **The runtime:** a Rust crate that evaluates templates into render
  trees and handler invocations into command intents, checking the
  host's values (D3, D5, D6).
- **The render-tree format** (`schemas/render-v1.schema.json`), with
  TypeScript types PORT renderers import (D4).
- **Composition:** templates that use other templates' components
  (D7).
- **`@valancex/mesh-runtime`:** the runtime in JavaScript, over the same
  WebAssembly module (D9).
- **An integration guide** for the two sides MESH doesn't build: a NEXUS
  adapter (a host) and a PORT renderer; and an end-to-end example in
  MESH's tests, with a test host and a reference renderer.

## Non-goals (v0.5)

- **Building NEXUS's adapter or PORT's renderers.** They live in their
  repositories; MESH ships what they build against, and proves it with a
  test host and a reference renderer (Definition of Done).
- **Incremental evaluation or diffing.** Each change of values
  re-evaluates the whole template; render trees carry stable keys so a
  renderer can update in place (D6). A template evaluates in well under
  a millisecond.
- **New syntax,** unless open decision 3 chooses composite events or
  slots.
- **Styling, layout, focus, animation, routing, forms.** None is in
  MPRX, and none is added.
- **Editor features and a VS Code extension,** unless open decision 4
  says otherwise.

## Definition of Done

**Checked means runnable (I12).** For every template that checks clean
against its model, `compile` emits a template that validates against
`template-v1`; for every template with an error, it emits none and
returns the diagnostics `check` returns. The CLI and the JS API emit
equal templates for the same inputs.

**Well-typed values never fail at runtime.** A property test: for every
clean template in the corpus, and for generated scope values of exactly
the declared types (absent where optional), evaluation succeeds and
yields a render tree that validates against `render-v1`. The only
runtime errors are I14's, and a test shows each one.

**One evaluator (I11).** The native runtime and the WebAssembly one give
equal render trees and command intents for the same template, values
and events, over the corpus and generated values. `@valancex/mesh-runtime`
contains no evaluation code (review, and a test that its bundle has no
expression walker).

**The semantics are written, and followed.** Every rule D8 adds to the
spec has a test that pins it: `1.50` and `1.5` equal, `7 % -2`, division
by zero, how `{count}` and `{flag}` render, and absent values in content
and props.

**PORT sees only values (I13).** `render-v1` has no expression, scope,
command or `$event` in it; a test walks every render tree the corpus
produces and finds none.

**The slice works.** `examples/` gains a composite `user-card` template
and a page that uses it. With the test host supplying a user, the
runtime's render tree for the page is the committed expected tree; the
reference renderer prints it as the committed expected HTML;
dispatching the avatar's click produces the command intent
`selectUser` with the event's payload, exactly; and changing the host's
user changes only the nodes that depend on it (by key).

**It's documented.** The template and render-tree formats in the
manuals; the evaluation rules in the spec; "Integrating MESH with
NEXUS" (a host) and "Rendering MESH output" (a renderer) guides, each
with an example a test runs.

## Decisions (proposed)

### D1. The template format: the IR, resolved, as JSON

- **A template** is one component's checked template: its element tree,
  every attribute, event binding, child and expression, and for every
  name, what it resolved to: each tag to its component, each attribute
  to its prop, each event binding to its event, each reference to its
  scope name, each command to its command. The runtime never looks a
  name up in the manifest to find out what it means.
- **It carries what I12 needs:** its format version (`1`), the compiler
  version, the component it's the template of, and a fingerprint of the
  model it was checked against (the pass plan chooses what's hashed: the
  manifest's meaning, not its formatting).
- **Spans are kept,** as byte and UTF-16 offsets, so runtime diagnostics
  and developer tools can point at source. They cost little and nothing
  depends on them for meaning.
- **Numbers are numbers** (F6): the compiler converts a literal once,
  under D8's rules, and the template holds the value.
- **Published as `schemas/template-v1.schema.json`,** under the same
  promise as the diagnostics document: properties may be added; removing
  one or changing its meaning is a new version.
- **Rejected:** serializing `mesh_semantic` types directly with `serde`.
  That would make Rust field names and enum layouts the public format,
  and leave resolutions out. The format is written as a schema first,
  and the Rust side implements it.

### D2. Compiling is checking, then emitting

- `mesh_compiler` gains a compile operation beside v0.4's check (D3 of
  v0.4): the same inputs, the same diagnostics, and, when there are no
  errors, the template. Warnings don't stop it.
- `mesh compile --model <manifest> --component <name> <file>` writes the
  template as JSON; with errors, it prints the diagnostics as `check`
  does and exits 1.
- `@valancex/mesh-compiler` gains `compile()`, returning the diagnostics
  document and, when clean, the template. I7's agreement extends to it.

### D3. The runtime: one Rust crate, native and in WebAssembly

- A new crate, `mesh-runtime`, depends on `mesh-syntax` for spans and on
  the template format's Rust types, not on the parser or the analysis:
  it runs templates, it doesn't check them. Its whole surface is two
  operations:
  - **render**: a template, the model, and scope values in; a render
    tree, or runtime diagnostics, out;
  - **dispatch**: a handler from a render tree and the event's payload
    in; a command intent (the command's name and its evaluated
    arguments), or runtime diagnostics, out.
- It's pure: no I/O, no clock, no randomness, no global state. The same
  inputs give the same outputs (I9 extended).
- `mesh-wasm` exports it beside the compiler, so there is one module and
  one version handshake (I10).

### D4. The render-tree format

- **A node** is a component name, its props as concrete values (an
  absent value is a missing property, never `null`: the spec's rule for
  absence), its events as opaque handler identifiers, its children, and
  a **key**: a stable path from the template's root, so a renderer can
  match nodes across renders.
- **Text** is a string: the runtime decides what a value looks like as
  text (D8). Text and interpolations next to each other are one string.
- **Handlers** are opaque to PORT. A renderer that sees an event calls
  the dispatch callback it was given, with the handler and the payload.
  It never learns what command runs.
- Published as `schemas/render-v1.schema.json`, with TypeScript types in
  `@valancex/mesh-runtime` (D9) that a PORT renderer imports.

### D5. Scope values: supplied by the host, checked at the boundary

- **The host supplies every scope name's value** for the template's
  component, as JSON-compatible data: the manifest's types are all
  data (strings, numbers, booleans, `null`, lists, records, optional,
  `any`).
- **Each value is checked against its declared type** before anything
  renders (I14). A missing required name, an extra name, or a value of
  the wrong type is a runtime diagnostic, with a stable code in a new
  `runtime-*` family and a path to the value (`user.name`), and the
  render returns no tree.
- **Event payloads are checked the same way** at dispatch.
- The host interface is MESH's: a function from scope name to value (or
  a snapshot), and a function that receives command intents. NEXUS's
  adapter implements it with selectors and commands.

### D6. Updates: re-evaluate, keep keys

- A change of values is a new render: the whole template is evaluated
  again. That's the simplest model that's obviously correct, and cheap
  at MPRX's scale.
- Keys (D4) are stable across renders for the same template, so a
  renderer can update in place. Lists, where keys would need identity
  from data, don't arise: MPRX has no loops.

### D7. Composition: a program of templates

- **A program** is a set of compiled templates, all against one model.
  An element whose component has a template in the program is expanded:
  its template is evaluated in place, and the render tree holds what it
  produced. Any other component is a **primitive**, left for PORT to
  draw. No manifest change: which components are composites is a fact
  of the program, not of the model.
- **A composite's scope** is bound from its props: a scope name with the
  same name as one of its props gets that prop's value, and the
  compiler checks, when a program is assembled, that every scope name
  is bound by a prop (or reports it). Names that aren't props come from
  the host only at the root.
- **Composite events and children** need syntax MPRX doesn't have
  (F8c). v0.5 doesn't add it, unless open decision 3 chooses to: a
  composite with declared events, or used with children, is rejected
  when the program is assembled, with a diagnostic saying so.

### D8. MPRX's evaluation, written down

In a new spec section, §9.7, before the runtime is built:
- **Numbers** are IEEE 754 doubles. A literal is converted once, by the
  compiler, with round-to-nearest. `/` by zero and `%` follow IEEE 754
  (infinities, NaN), and a non-finite number is a runtime diagnostic
  wherever it would reach a render tree or a command argument, so no
  renderer ever receives one. The pass plan fixes `%`'s sign rule.
- **Text:** a `string` renders as itself; a `number` in the shortest
  round-tripping decimal form (`1.5`, `100`, `0.1`); a `boolean` as
  `true`/`false`; `null` as `null`. An absent value in content renders as
  nothing. A list or record in content is a check-time error in v0.5
  (a new diagnostic), since no text form of one is obviously right.
- **Absence** in a prop is a missing property in the render tree.
- Every rule gets a test (Definition of Done).

### D9. Packages

- `@valancex/mesh-compiler` gains `compile()` (D2).
- **`@valancex/mesh-runtime`**, new: `render()`, `dispatch()`, the
  render-tree types (D4), and the host interface's types (D5), over the
  same WebAssembly module (D3). Like the compiler package, it's boring
  (I6, I11).
- Whether the module ships once, in one package the other depends on,
  or in both, is the pass plan's, within D2 of v0.4's size budget.
- Versioned in lockstep, published by the v0.4 release workflow.

### D10. The evidence is in MESH

- **A test host** supplies scope values from JSON fixtures and records
  command intents.
- **A reference renderer**, test-only, prints a render tree as HTML-like
  text, so an expected rendering is a committed file.
- The slice (Definition of Done) runs through both, natively and in
  Node.

## Sequencing

- Pass 0 comes first: the formats and the semantics are the contracts.
- Pass 1 and Pass 2 can overlap once the schemas are settled: the
  runtime's tests can use hand-written templates at first.
- Pass 3 needs both. Pass 4 needs everything.
- NEXUS's adapter and PORT's Web renderer can start as soon as Pass 0's
  schemas are published, in their own repositories.

## Risks

- **Formats harden early.** Once NEXUS and PORT build on `template-v1`
  and `render-v1`, changing them costs three repositories. Mitigation:
  schemas first (Pass 0), reviewed against both repositories' needs,
  and the additive-only promise, which leaves room to grow.
- **A second evaluator creeping into JavaScript** (formatting a number
  in a renderer, defaulting an absent prop). I11, I13 and the review
  checklist are the defence; the render tree holds final values, so
  there's nothing left to compute.
- **The host boundary is only as strict as its checks.** I14 checks
  every value on every render. If that shows up in profiles, the answer
  is to make it faster, not to skip it.
- **NEXUS and PORT move independently.** MESH can't change them. The
  integration guides, the test host and the reference renderer make
  MESH's side checkable without them.

## Open decisions

1. **Where does evaluation happen?**
   - (a) **In Rust, one runtime, native and WebAssembly** (D3).
     **Recommended:** it keeps one semantics (I1, I11), reuses the
     WebAssembly module v0.4 ships, and the JSON boundary already exists.
     A render crosses it once: values in, tree out.
   - (b) In TypeScript, in the runtime package. Faster to iterate on,
     and no boundary crossing per render, but it's a second
     implementation of MPRX's semantics, which every invariant so far
     rules out.

2. **Who writes the NEXUS adapter, and what does it depend on?**
   - (a) **MESH defines the host interface (D5); the adapter lives in
     NEXUS**, depending on `@valancex/mesh-runtime`. **Recommended:** it
     matches NEXUS's own "MESH → NEXUS interfaces" direction without
     making MESH depend on NEXUS (I15), and the adapter is mostly NEXUS
     code (selectors, commands).
   - (b) MESH ships `@valancex/mesh-nexus`, depending on NEXUS. It keeps
     the integration in one place, but MESH would depend on a package
     that isn't published yet, and on Effect.

3. **How far does composition go in v0.5?**
   - (a) **Composites without events or children** (D7). **Recommended:**
     it covers the PORT slice (`user-card` in a page) with no new syntax.
   - (b) Also composite events: a way for a composite's template to
     raise its own declared events. New syntax, with its own design.
   - (c) Also children and slots. The largest language change yet; it
     deserves its own release.

4. **Do editor items ride along?** The VS Code extension, the project
   file, and v0.3's editor limitations (E11).
   - (a) **Not in v0.5; a later editor-focused release.** **Recommended:**
     v0.5 is already three formats and a runtime.
   - (b) The VS Code extension only: small, and independent of the rest.

5. **NEXUS's and PORT's npm scope (F9).** Both still name `@valence/*`.
   Renaming them is those repositories' change, not MESH's; the question
   is whether to do it before they depend on `@valancex/mesh-runtime`.
   **Recommended: yes**, while nothing of theirs is published.

## After v0.5

- Composite events and slots (open decision 3), with their own design.
- Editor work (open decision 4): the VS Code extension, the project
  file, definitions for closing tags and record fields, related spans, a
  debounced manifest.
- The remaining language questions: a presence test or optional
  chaining, and unions.
- Incremental evaluation, if a real app ever needs it.
