## Where v0.4 left off

v0.4.0 (released 2026-09-25) took MESH outside Rust. Seven packages are on npm under `@valancex`, each at 0.4.0 with provenance:
- `@valancex/mesh-compiler`, the compiler in WebAssembly, which returns exactly the diagnostics `mesh check --format json` prints;
- `@valancex/mesh-lsp` with its five platform packages.

MESH still stops at diagnostics. Its IR never leaves Rust. v0.4 kept it out on purpose (E2), so its serialized form could be designed with NEXUS and PORT. That is v0.5.

## What NEXUS and PORT expect

Both repositories are read at the commits above. Their READMEs and architecture documents say the following about MESH. Neither implements any integration with MESH yet.

- **NEXUS** is the application core. Its README says "v0.1 primitives implemented": nine primitives, State, Selector, Command and Event among them, on Effect, with a UI-free vertical slice. It has no UI, and no MESH integration.
  - §9: "Commands are the primary application boundary for MESH." A NEXUS command has its own identity (`"users.select"`) and one structured input.
  - §15: MESH reaches NEXUS through a UI-facing API of state reads, selector reads, command invocation and UI-relevant environment state, and nothing else. MESH should not gain arbitrary access to NEXUS internals.
  - §16 and resolved decision 4: **PORT never depends on NEXUS**. "Everything PORT needs (state, selector values, command bindings) must already be resolved into the IR before it reaches PORT", by "a MESH runtime adapter".
  - Its dependency directions include "MESH → NEXUS interfaces" and "PORT → MESH (Semantic IR only)". In this outline, what PORT receives is the render tree (D4), not the Semantic IR.
  - Its README's next milestone is "connecting NEXUS to MESH through the runtime adapter". That adapter doesn't exist yet.
- **PORT** is "early scaffolding": three packages whose sources are empty, and no renderer. Its architecture says:
  - a renderer receives "compiled, validated, renderer-independent UI", "maps each node onto the target's native API", and handles mount, update and unmount;
  - it never sees MPRX, runs no business rules, and silently drops nothing;
  - its first slice is `user-card.mprx → MESH compiler → MESH IR → NEXUS runtime → PORT (Web) → browser`.

So there are **two** formats, not one, and MESH owns both:
1. **The template** (`template-v1`): one component's checked MPRX, with every name resolved and no values. The runtime consumes it.
2. **The render tree** (`render-v1`): what the runtime produces from a program of templates and the host's values. It holds concrete values and no expressions. PORT consumes it.

Nothing in either repository requires the host to supply exactly the names a template reads (D5). Nothing gives PORT a reason to know a command's identity (D4).

**Who owns what.**

| | Owns |
|---|---|
| MESH, in v0.5 | the formats; the compiler's compile and program-check operations; the runtime (render and dispatch); the host interface; `@valancex/mesh-compiler` and `@valancex/mesh-runtime`; a test host, a reference renderer, and the guides |
| NEXUS, later, in its repository | the adapter: a host built on `@valancex/mesh-runtime` that supplies snapshots from state and selectors, re-renders on change, and maps command intents to NEXUS commands; its `@valancex` rename |
| PORT, later, in its repository | renderers that draw render trees, reconcile them by key, and report events with handler identifiers; its contract package over `render-v1`; its `@valancex` rename |
| MESH's evidence (D10) | MESH's side of both boundaries, tested without NEXUS or PORT existing |

## Terms

Each term below has exactly this meaning everywhere in this outline.

- **Manifest:** the JSON document in the manifest format (v0.2).
- **Model:** the validated meaning of a manifest. It is used in exactly two roles:
  - checking source and programs, which is the compiler's role;
  - validating values at runtime, which is the runtime's role (D3).

  It is never used at runtime to resolve a name.
- **Model fingerprint:** a value computed from a model's meaning (D1). Two models with the same meaning have the same fingerprint.
- **Component, prop, event, command, scope name:** declarations in the model (§9.1).
  - A **scope name** is a name a component's own template may read.
  - A **handler** is the command invocation written in an event binding (`on.click={selectUser(user.id)}`).
- **Template:** a `template-v1` document. It is one component's MPRX, checked clean against a model and compiled (D1).
- **Program:** a root component and a set of templates, at most one per component, that together satisfy the assembly rules (D7).
  - A program is a concept, not a document: v0.5 defines no serialized form of it.
  - **Assembly** is the checking of a program against those rules.
- **Occurrence:** one element in one template, at one position.
  - Relative to a program, an occurrence is a **composite occurrence** if its component has a template in the program, and a **primitive occurrence** otherwise.
  - A **composite** is a component with a template in the program; a **primitive** is any other component.
- **Host:** whatever calls the runtime. It supplies snapshots, relays events, and receives command intents. The NEXUS adapter is one host; MESH's test host is another.
- **Snapshot:** the host's scope values for the program's root template, as one mapping from scope name to value (D5).
- **Runtime:** the Rust evaluator, compiled natively or to WebAssembly (D3).
- **Render:** the runtime's operation that turns a program, model and snapshot into a render tree. **A render** (the noun) is one successful result: the tree, together with the program, model and snapshot it came from.
- **Render tree:** the `render-v1` document PORT draws (D4). It is made of **nodes** (primitive occurrences) and **text runs**, each with a **key**.
- **Handler identifier:** an opaque token in a render tree that names one handler at one node (D4).
- **Dispatch:** the runtime's operation that turns a render, a handler identifier and a payload into a command intent (D3).
- **Command intent:** a command's identity and its evaluated arguments (D4). The host receives it; a renderer never sees one.
- **Boundary:** a place where values leave or enter the runtime. Inputs are snapshots and payloads. Outputs are primitive props, text runs and command arguments. The **boundary data model** is the set of values allowed there (D5).
- **Diagnostics:** there are three kinds.
  - **Check diagnostics:** v0.4's, plus two new codes (D8).
  - **Assembly diagnostics:** a new family (D7).
  - **Runtime diagnostics:** a new `runtime-*` family, reported in three phases (D3).

## Theme

**v0.5: MESH that renders.**
- A template that checks clean compiles to a versioned, published format.
- A program of such templates is run by one evaluator, in Rust, against the host's snapshot. It produces a render tree any PORT renderer can draw.
- Events come back through MESH as command intents for the host.
- MESH ships the formats, the evaluator (native and in WebAssembly) and a runtime package. NEXUS's adapter and PORT's renderers are built against them later, in their own repositories.

## Architecture and invariants

```text
 MPRX source + model ──compile──▶ template (template-v1) ─┐
   (one component)   check, then emit                    │   program =
                                                         ├── root component
 MPRX source + model ──compile──▶ template ... ──────────┘   + templates
                                                                  │
                                        model ─────────────┐      │
                                                           ▼      ▼
  host ── snapshot ────────────────────────────────▶  render (runtime) ──▶ a render
                                                                            │  │
                                                                 render tree│  │ kept by the host
                                                                 (render-v1)▼  │
                                                                         PORT  │
                                                   event: handler id, payload │
  host ◀── command intent ── dispatch (runtime) ◀── host ◀──────────────┘   │
          (command identity                  ▲                                 │
           + evaluated args)                 └──────── the same render ────────┘
```

- **The compiler** (`mesh-compiler`) checks one component's source against the model. Only if the check has no errors does it emit a template, with every name resolved. It also **checks programs**: given a root and templates, it reports the assembly diagnostics (D7). It produces no program artifact.
- **The runtime** is the Rust evaluator, compiled natively or to WebAssembly. Its operations are validation, render and dispatch.
  - **Validation:** given a program and a model, it validates both, including the assembly rules, before it evaluates anything.
  - **render:** it evaluates the root template, and every composite occurrence under it, against the snapshot, and yields a render.
  - **dispatch:** it takes the render the event came from, a handler identifier and a payload, and yields a command intent.
  - It has no I/O and no NEXUS dependency.
  - It resolves no names: every resolution is in the templates. It uses the model only to validate values (D3).
- **The host** supplies snapshots, keeps each render while its tree is on screen, relays events to dispatch with that render, and receives command intents.
- **PORT** receives render trees, and reports events as a handler identifier and a payload. It never learns what an event does.

**New invariants.**
- **I11. One evaluator.** MPRX's semantics are implemented exactly once: in the Rust runtime.
  - Outside it, no code may evaluate an MPRX expression, convert a value to text, coerce a value between kinds, normalize a number, substitute anything for absence, decide whether a component is a composite, resolve a handler identifier, or judge whether a value is valid at the boundary.
  - Code outside the runtime *may* transport values, encode and decode them losslessly, walk their structure to encode it, and read render trees and intents as given.
  - A renderer mapping a render tree's strings and values onto its target (setting a DOM attribute, drawing text) is drawing, not evaluation.
  - v0.4's I6 applies to `@valancex/mesh-runtime` unchanged: it performs no MESH validation of its own (D5).
- **I12. Only what checked runs.**
  - MESH's tools emit a template only from source whose check has no errors.
  - The runtime accepts no MPRX source, only templates. It runs a program only after its own validation, which checks every template's structure, format version and model fingerprint, and the assembly rules.
  - The runtime fails closed on any value that doesn't fit where it's used (D8). So even a template MESH didn't produce can't make it emit a value of the wrong type, or one outside the boundary data model.
  - There is no path from unchecked source to a render tree.
- **I13. PORT sees values, never MPRX.** A render tree contains exactly:
  - primitive component names;
  - prop names, with values from the boundary data model;
  - text runs, as strings;
  - event names, each with a handler identifier;
  - keys.

  It contains nothing else: no expression, scope name, command identity, argument, composite name, template, span or `$event`. Keys and handler identifiers are opaque, and don't reveal those in recoverable form to a party without the program's templates (D4). They are not secret, and I13 doesn't make them so.
- **I14. The host is checked, not trusted.** Every host-controlled input is validated before the runtime uses it:
  - the model, as a manifest;
  - every template, and the program as a whole;
  - the snapshot, against the root template's scope;
  - every payload, against its event's payload type;
  - every handler identifier, against the render it is dispatched with;
  - the render itself, which passes through the host's hands.

  A failure is a runtime or assembly diagnostic, and nothing is rendered or dispatched from it.
- **I15. MESH doesn't need NEXUS to run, and dependencies point one way.**
  - No MESH crate or package depends on NEXUS, PORT or Effect.
  - The NEXUS adapter depends on `@valancex/mesh-runtime`. PORT renderers depend on MESH's render-tree types (D9).
  - NEXUS and PORT don't depend on each other.
  - The runtime depends on a host interface MESH defines. Any program can be a host, and MESH's own tests use one. (ARCHITECTURE rule 6, extended from the compiler to the runtime.)

## Goals

- **The template format** (`template-v1`): one checked component, with every name resolved into executable expressions. The Rust API, `mesh compile` and `@valancex/mesh-compiler`'s `compile()` emit it (D1, D2).
- **Programs:** a root and templates, with assembly rules checked by the compiler and enforced by the runtime (D7).
- **MPRX's evaluation, specified in the spec:** values and absence, numbers, non-finite values, equality and comparison, evaluation order, text, runtime checks, and the boundary data model (D5, D8).
- **The runtime:** render and dispatch, validation of every host-controlled input, and diagnostics in three phases (D3, D5, D6).
- **The render-tree format** (`render-v1`) and the command intent, with TypeScript types that PORT renderers and NEXUS adapters import (D4, D9).
- **`@valancex/mesh-runtime`:** the runtime in JavaScript, over the WebAssembly build (D9).
- **Two integration guides**, one for each side MESH doesn't build: a NEXUS adapter (a host) and a PORT renderer. Also an end-to-end example in MESH's tests, run by a test host and a reference renderer (D10).

## Non-goals (v0.5)

- **Building NEXUS's adapter or PORT's renderers,** or changing either repository. They live in their own repositories, and the MESH release neither includes nor waits on them. MESH ships what they build against, and proves it with a test host and a reference renderer (D10).
- **Incremental evaluation, dependency tracking or diffing in the runtime.** Every render evaluates the whole program and returns a complete render tree (D6). Runtime evaluation is expected to be inexpensive at MPRX's scale; v0.5 imposes no formal latency target.
- **Composite events, and children or slots for composites.** They are rejected for v0.5, not left open (D7), and are kept for a later language-design release.
- **Other new syntax,** and any language feature listed under "After v0.5". v0.5 adds two check-time diagnostics (D8) and no syntax.
- **Styling, layout, focus, animation, routing, forms.** None is in MPRX, and none is added.
- **Editor work:** the VS Code extension, the project file and v0.3's editor limitations (E11). They are deferred to a later editor-focused release.
- **A NEXUS integration package in MESH.** The adapter is NEXUS's (resolved decision 2).

## Decisions

### D1. The template: resolved, executable, value-free, and self-describing

A template separates MPRX's three stages: **source syntax → semantic resolution → runtime evaluation.** It is the product of the first two, and holds nothing from the third.

**A template contains exactly:**
- **Its format version.** This is `1`, and describes the serialized structure. It is the template's only compatibility version.
- **Its component,** the one whose template it is.
- **The model fingerprint** of the model it was checked against.
- **Its compiler version,** for provenance and debugging only. It must never affect whether a template runs.
- **Its element tree, as checked.**
  - Only the attributes §3's duplicate resolution keeps are included.
  - Whitespace-only text is omitted (§3).
  - Every attribute, event binding, child and expression is included.
- **For every name, what it resolved to:**
  - each element to its component;
  - each attribute to its prop;
  - each event binding to its event;
  - each reference to its scope declaration;
  - each command invocation to its command, identified by the command and the component whose template declares it;
  - each `$event` to the payload of the event its handler is bound to.
- **Literal values:** each number literal as the binary64 value D8 converts it to, and quoted attribute values and literal text as their strings.
- **Spans,** as byte and UTF-16 offsets, for diagnostics and developer tools. Nothing depends on them for meaning.

**A template does not contain:**
- values of any scope name, prop or payload;
- evaluated props or text;
- anything that depends on other templates.

A reference identifies the scope declaration it reads. Its value is supplied only at runtime: by the snapshot for the root template, or by the occurrence's props for a composite (D7).

**What belongs to the template, and what to the program:**

| Information | Where it lives |
|---|---|
| format version | each template |
| component identity | each template (its own); each occurrence (what it's an instance of) |
| model fingerprint | each template. A program has no fingerprint of its own: its fingerprint is the one all its templates share (D7). |
| composite or primitive | the program only: an occurrence is composite exactly when the program has a template for its component. A template never records it. |
| template lookup | the program only, by component identity. The model is never consulted. |
| root component | the program only |
| cross-template references | none inside a template. An occurrence names a component, and the program supplies the template, if any. |
| handler lookup | each handler lives in its template. The runtime finds it through the handler identifier, which the program determines (D4). |

**Why every template carries the fingerprint:**
- a template is self-describing, so a stray one can be rejected on its own;
- assembly can detect templates checked against different models;
- the runtime checks each template against the model it's given, instead of trusting a claim about the whole program.

**The model fingerprint** is determined by the model's meaning, and by nothing else.
- **What counts:**
  - the set of components;
  - for each component, its props (name, type, requiredness), its events (name, and payload type or none), its commands (name, and parameter types in order), and its scope (name and type);
  - types as their full structural expansion, since named types are structural (§9.3).
- **What doesn't count:**
  - JSON formatting, whitespace and number spelling;
  - the order of object keys (every declaration map is a set);
  - the `$schema` property and the manifest format's `version`;
  - the names of named types, and named types nothing uses;
  - parameter names, which appear only in messages.
- Pass 0 specifies the canonical form and the digest. The runtime requires every template's fingerprint to equal its model's.

**Compatibility is decided by exactly two things:** a supported format version, and an equal model fingerprint. A template runs under any runtime that supports its format version, whatever compiler version produced it.

**Published as a JSON Schema,** under the same promise as the diagnostics document: properties may be added; removing one or changing its meaning is a new format version.

**Rejected:** deriving the format from the Rust IR types. That would make Rust's field names and enum layouts the public format, and leave the resolutions out.

### D2. Compiling is checking, then emitting

- **`mesh_compiler` gains a compile operation** beside v0.4's check (v0.4's D3). It takes the same inputs and returns the same diagnostics, plus the template exactly when there are no errors. Warnings don't stop it.
- **`mesh compile`** does the same from the command line: with no errors it writes the template; with errors it prints the diagnostics as `check` does and exits 1.
- **`@valancex/mesh-compiler` gains `compile()`,** which returns the diagnostics document and, when the source is clean, the template. I7's agreement extends to it: for the same inputs, the CLI and the JS API return equal diagnostics and equal templates.
- **The compiler gains a program check:** given a model, a root and templates, it reports the assembly diagnostics (D7). It is available wherever compile is, and it produces no artifact.
- **Determinism:** identical inputs and compiler version give identical templates and diagnostics (I9 extended).

### D3. The runtime

(Resolved decision 1: an architectural constraint, not an implementation preference.)

**It is one Rust implementation,** compiled natively and to WebAssembly. It doesn't parse or check MPRX. A second evaluator in TypeScript was considered and rejected (I11).

**The model's role at runtime is validation, not resolution.**
- The model validates runtime inputs and outputs: the snapshot against scope types, payloads against payload types, prop values against prop types, and command arguments against parameter types.
- It is never used to resolve a name, find a template, or decide whether a component is a composite. Every semantic resolution evaluation needs is already in the templates.

**Operations.** The whole conceptual surface is two operations.
- **render:** a program, a model and a snapshot in. A render out, or runtime or assembly diagnostics.
- **dispatch:** a render, a handler identifier and a payload in. A command intent out, or diagnostics.

A handler identifier alone is never enough. Dispatch needs the render it came from: the program, model and snapshot that produced the tree (D5).

**Diagnostic phases.** Each operation runs these phases in order. A phase that reports any diagnostic ends the operation, and no later phase runs.
1. **Program validation.** Its steps run in order, and a step that reports anything ends the phase.
   1. The model must be a valid manifest (the existing `manifest-*` diagnostics).
   2. Every template must be well-formed and of a supported format version.
   3. Every template's fingerprint must equal the model's.
   4. The program must satisfy the assembly rules (D7).

   Each step reports every diagnostic it finds.
2. **Input validation.**
   - For render: the snapshot. Every mismatch is reported.
   - For dispatch: first the handler identifier. If it's invalid, that is the phase's only diagnostic, because the payload's type depends on it. Otherwise, every mismatch in the render's snapshot and the payload is reported.

   Diagnostics are ordered by path: segments compared in turn, names by code point, list indices numerically, and a path before its extensions. Snapshot paths start at the scope name, and payload paths at `$event`.
3. **Evaluation.** Exactly one diagnostic, the first in D8's evaluation order, is reported, and evaluation stops.

**Results.** A render or dispatch returns either its result and no diagnostics, or diagnostics and no result. The runtime has no warnings.

**Diagnostic identity.** Each diagnostic's identity is its **code** and its **location**.
The location has exactly one of six forms, and each code always uses the same one:
- **model:** a span in the manifest, for the model's own diagnostics;
- **program:** the program as a whole, where there is no template to point to (a missing root template);
- **template:** a template, by its position in the host's list, for template-level validation;
- **source:** a template's component and a span, for every other assembly diagnostic and for evaluation diagnostics;
- **input:** a path into the snapshot or the payload, for input diagnostics;
- **handler:** the handler identifier, for one dispatch can't accept, where there is no meaningful span or path.

Codes are stable and part of the contract. Pass 0 lists them. Message wording is not part of the contract.

**Purity.** The runtime has no I/O, no clock, no randomness and no global state. For each operation, identical inputs give identical results and diagnostics (I9 extended). An implementation may cache validation results, since they depend only on their inputs.

**One version handshake.** The runtime's WebAssembly build is subject to I10 like the compiler's.

### D4. The render tree, keys, handler identifiers and command intents

**A node** is a primitive occurrence. It has:
- its component's name;
- its **props**: each written prop's value. An absent value is an omitted prop, and `null` is `null` (D5, D8);
- its **events**: for each event binding, the event's name and a handler identifier;
- its **children**: nodes and text runs, in order;
- its **key**.

**Composites never appear.** A composite occurrence is replaced by what its template produced, which is exactly one node, since a template has one root element (D7).

**A text run** is one string, D8's text of a maximal sequence of adjacent literal text and interpolation children. A text run is present even when it's empty. So, with MPRX's lack of loops and conditional elements, **a program's render trees all have the same structure, whatever the snapshot.** Only prop values and text differ.

**Keys** are structural identities:
- **Derived only from the program.** Each node's and text run's key is determined by its position: the sequence of child positions from the root template's root, and the component at each step, composites included. Composite expansion is therefore part of every key below it.
- **Independent of values.** No snapshot or payload affects a key.
- **Unique:** no two nodes or text runs in one render tree share a key.
- **Stable within one program:** every render of a program has the same keys at the same positions. Keys are **not** stable across programs: a changed root or template may change every key. That is intentional, and keys carry no compatibility guarantee across programs.
- **Opaque:** a renderer may compare keys for equality, and must not interpret them. Their encoding must not reveal composite names, scope names or commands in recoverable form to a party without the program's templates, which is why the program identity is part of the hash. The encoding is Pass 0's. Keys are not a confidentiality or authentication mechanism: anyone holding the templates can compute them.
- **Not data identity,** and not application identity. A later list design may extend them.

**Handler identifiers** are opaque tokens:
- **What one names:** exactly one handler at one node. It is determined by the program's identity, the node's key and the event's name.
  - The **program's identity** is determined by the program's root and templates, and changes if they change.
  - A handler identifier is therefore unique within a program, the same in every render of it, and independent of values.
  - It is not the command, and must not contain the command's identity or arguments, or anything they can be recovered from. The encoding is Pass 0's.
- **How dispatch uses one:** it checks that the identifier was made by the render's program and names a handler there; otherwise it reports an input diagnostic. The runtime then finds the handler through the node's key and the event, in the template that produced that node.

**A command intent** contains exactly:
- **The command's identity:** the command's name, and the component whose template declares it. Two components may each declare `selectUser`.
- **One argument per parameter, in parameter order,** each either a boundary value or **absent**, where the parameter's type is optional. The intent must distinguish an absent argument from `null` and from every other value. Its representation is Pass 0's.
- The NEXUS adapter maps an intent to a NEXUS command (for example, `selectUser` to `"users.select"`) and its input. That mapping is the adapter's. A renderer never receives an intent.

**Published.** `render-v1` is published as a JSON Schema, and the command intent's shape is specified alongside it, both under the additive-only promise. Their TypeScript types are in `@valancex/mesh-runtime` (D9).

### D5. The boundary, and the host interface

(Resolved decision 2: MESH defines the host interface; the NEXUS adapter implements it, in NEXUS.)

**The boundary data model.** A value may cross a boundary, in either direction, only if it is one of these:
- `null`;
- a boolean;
- a **finite** number;
- a string of Unicode scalar values;
- a list of such values, with **no absent elements**;
- a record: a set of named fields, each such a value.

**Absence** crosses only as the omission of a named entry: a scope name, a record field, a prop, or a command argument position (D4). A record's absent field is the same as having no such field.

**How each value crosses:**

| Value | Into the runtime (snapshot, payload) | Inside evaluation | Out (primitive prop, text run, command argument) |
|---|---|---|---|
| absent | no entry for a scope name or record field. A payload that isn't given is absent. | allowed | omitted prop; omitted record field; empty text; absent argument |
| `null` | `null` | allowed | `null`; text `null` |
| boolean | as is | allowed | as is; text `true` or `false` |
| finite number | the nearest binary64 value (D8). A number out of binary64's range is an input diagnostic. `-0` is kept. | allowed | as is, except that `-0` becomes `0`; text per D8 |
| NaN, ±∞ | can't be expressed in JSON; from JavaScript, an input diagnostic | allowed | an evaluation diagnostic (D8) |
| string | must be Unicode scalar values; an unpaired surrogate is an input diagnostic | allowed | as is |
| list | every element present | may hold absent elements | an absent element, at any depth, is an evaluation diagnostic |
| record | exactly the declared fields (below) | allowed | absent fields omitted |

**Types at the boundary.**
- **`any`** accepts every present value, of any kind, at any depth; a value of type `any` is still subject to the boundary data model. **`any?`** also accepts absent.
- **An optional type `T?`** accepts absent, or a value that fits `T`.
- Types are checked with D8's *fits* relation, the one relation used everywhere.

**Open scope.** The root template's expected scope must be a subset of the snapshot.
- A scope name whose type isn't optional must be present.
- Each declared name that is present must fit its type.
- A declared name whose type is optional may be absent.
- **A name the root template doesn't declare is ignored entirely:** never validated, never retained, never readable, since references are resolved at compile time.

Nothing in NEXUS needs a closed scope. NEXUS §15's "no arbitrary access" limits what MESH reaches into, and MESH reads only what the template declares either way. An open scope lets one snapshot serve several programs.

**Exact records.** A record value must have only declared fields, because records are exact (§9.3) and equality compares all their fields. A missing field is absent, allowed only where the field reads as optional (§9.2).

**Payloads** are checked the same way, against the payload type of the event the handler is bound to. For an event declared without a payload, the payload must be absent.

**JavaScript encodes; Rust judges.** `@valancex/mesh-runtime` encodes host values structurally and losslessly, and performs no MESH validation (I6, I11). Every judgement is the runtime's. So a native host and a JavaScript host get the same diagnostics for the same values.
- A missing property, and a property whose value is `undefined`, are both encoded as absent.
- An array's `undefined` element or hole is encoded as such, so the runtime can reject it.
- A number keeps its exact binary64 value: NaN, infinities and `-0` included.
- A string keeps its UTF-16 code units, unpaired surrogates included.
- A value that is not a plain object, array, string, number, boolean or `null` is encoded as unsupported, with its kind. Examples: a function, a symbol, a `bigint`, a class instance, a `Map`, a `Date`.
- A cycle is encoded as unsupported, so encoding always terminates.
- The runtime rejects each of these where it would be read.
- The encoding is the pass plan's. It must not use a lossy conversion: `JSON.stringify` alone turns `NaN` and `undefined` in an array into `null`.

**The host interface, and the dispatch lifecycle.**
1. The host calls render with a program, model and snapshot. The result is a render.
2. The host gives the render's tree to the renderer, and keeps the render.
3. A primitive's event fires. The renderer reports the handler identifier from the tree it drew, and a payload.
4. The host calls dispatch with **the render whose tree the renderer had drawn** when the event fired, and with that identifier and payload.
5. The runtime runs program validation for the render's program and model.
6. Input validation follows: the handler identifier against the render's program, then the render's snapshot and the payload.
7. The runtime finds the handler, and re-derives the scope of each composite on the path to it by evaluating those occurrences' props against the render's snapshot, exactly as the render did.
8. It evaluates the handler's arguments, applying D8's checks.
9. The result is a command intent, or diagnostics.

**Rules of the lifecycle:**
- **The snapshot a dispatch evaluates against is the render's snapshot, never one supplied separately.** So an intent reflects exactly the values the user saw. A render must retain its snapshot as validated and encoded, so later changes to host objects can't alter it.
- The runtime re-validates what a render contains on each dispatch (I14), because a render passes through the host's hands.
- Which render the renderer had drawn is known only to the host. Keeping renders and pairing each event with its render is the host's obligation, and the guides say so.
- Dispatch with a render of an earlier program is valid; the result is that program's intent.

### D6. Updates: re-evaluate everything, keep structural identity

- **A change of values is a new render.** The whole program is evaluated again, and the result is a complete new render tree. That's the simplest model that's obviously correct.
- **Every render of a program has the same structure, keys and handler identifiers** (D4), so a renderer can match a new tree against the one it drew, node by node, and update in place.
- **Finding what changed is the renderer's job,** by comparing prop values and text at equal keys. The runtime does no dependency tracking, caching of evaluation or diffing in v0.5.

### D7. Composition: a program of templates

(Resolved decision 3: composites without composite events, children or slots.)

**A program** is a root component, plus a set of templates with at most one per component.
- Its model fingerprint is the one its templates share.
- It is given to the compiler's program check, and to the runtime, as those parts. It has no document of its own.
- Every template in the program is subject to the assembly rules, whether or not the root reaches it.
- An unreached template is valid, and ignored when rendering.

**Composite or primitive is decided by the program, and only by the program.**
- An occurrence whose component has a template in the program is a composite occurrence. The runtime expands it by evaluating that template in place.
- Any other occurrence is a primitive occurrence, and becomes a node.
- **A component with no template in the program is a primitive,** always. This is not an error, whatever the model declares for it.
- The manifest has no say in the matter: nothing in it marks a component as either.

**Binding a composite's scope.** For every composite `C` used as a composite occurrence in any template of the program:
- Every scope name `s` of `C`'s template must be bound by a prop of `C` with the same name.
- The binding must be sound: with the prop declared as type `P`, and the scope name `s` of type `S`:
  - if the prop is required, `is_assignable(P, S)` must hold;
  - if it's optional, `is_assignable(P?, S)` must hold (or `is_assignable(P, S)`, when `P` is already optional), because an unwritten prop binds absence.
- At runtime, each written prop's value is evaluated in the enclosing template. An unwritten prop binds absent.
- Props of `C` with no scope name of the same name are evaluated (D8) and then not used.
- Only the root template's scope comes from the snapshot. The root component's own props play no part.
- The root is exempt from the binding rules unless it is also used as a composite occurrence, which is then a cycle.

**Nesting.** A composite's template may contain composite occurrences, to any depth, provided the program has no cycle.

**Handlers inside a composite** invoke that composite's own commands. `user-card`'s avatar click invokes `user-card`'s `selectUser`. So the slice needs no composite events.

**Assembly rules.** Each broken rule is an assembly diagnostic. The compiler's program check runs steps 2–4 of the runtime's program validation (D3), with the same diagnostics, codes and locations. Rule 3 is steps 2 and 3; the others are step 4.
1. At most one template per component.
2. The root component has a template in the program.
3. Every template is well-formed, has a supported format version, and has the fingerprint of the given model. So all of a program's templates share one fingerprint.
4. Every scope name of every composite used as an occurrence is bound, and soundly (above).
5. **No cycles.** A composite may not expand itself, directly or through others. Every composite occurrence on a cycle is reported.
6. **No composite declares events** in the model. Composite events are rejected for v0.5.
7. **No composite occurrence has children,** text or elements. Whitespace-only text is not a child (§3). Children and slots are rejected for v0.5.

Assembly diagnostics are ordered by the template's component (by code point), then by span.

**What is an assembly error, and what a runtime one:**
- Every rule above is decided before evaluation, from the program and model alone: an assembly error.
- During evaluation, composition can fail only through D8's runtime checks. The only one specific to composition is a composite prop whose value, coming from an `any`, doesn't fit its declared type. That is a runtime evaluation diagnostic.

### D8. MPRX's evaluation semantics

Pass 0 writes these into the spec, as a new §9.7, before any runtime code exists. They are the language's definition.
- Where a rule matches IEEE 754 or ECMAScript, it says so, and the named standard is normative.
- Where it deliberately departs from what a host language happens to do, it says so too.

**Values.** A runtime value is exactly one of:
- *absent*;
- `null`;
- a boolean;
- a number;
- a string;
- a list of values;
- a record: a set of named fields, each a present value.

Absent is the lack of a value (§9.2), never a kind of `null`. It comes only from:
- a snapshot entry, field or payload whose type is optional;
- a record field read as optional;
- an unwritten optional prop bound into a composite's scope;
- an expression that yields one of these.

MPRX has no literal for absence. A record literal field whose value is absent is the same as no field. A list literal may hold an absent element inside evaluation. D5 says where values may cross.

**Fits.** One relation, *fits(value, T)*, decides every runtime type check. Named types are expanded first.
- `T?`: the value is absent, or fits `T`.
- An absent value fits no type that isn't optional.
- `any`: every present value.
- `string`, `number`, `boolean`, `null`: a value of that kind. Every binary64 value is a `number`, non-finite ones included; D5 governs the boundary.
- `list<U>`: a list whose every element fits `U`.
- A record type: a record with no field the type doesn't declare. Each declared field must be either absent, where it reads as optional (§9.2), or present and fitting its type.

**Numbers.**
- **Representation:** a number is an IEEE 754 binary64 value.
- **Literals:**
  - A literal is converted once, by the compiler, to the nearest binary64 value, with ties to even (IEEE 754 roundTiesToEven).
  - A literal whose nearest value would be infinite is a **check-time error**, a new diagnostic.
  - Literals are unsigned, so a literal is never `-0`.
  - `1`, `1.0` and `1.00` are the same value, and so are `1.5` and `1.50`.
- **Arithmetic:**
  - `+`, `-`, `*`, `/` and unary `-` are the IEEE 754 binary64 operations under roundTiesToEven. Overflow gives an infinity, and any NaN operand gives NaN.
  - `x / ±0` is `±∞`, with the sign of `x`'s sign times zero's sign. `±0 / ±0` is NaN.
- **`%` is the truncated remainder, not IEEE 754's `remainder` operation,** which rounds the quotient to nearest. MPRX deliberately chooses the truncated form, as C's `fmod`, JavaScript's `%` and Rust's `%` compute it.
  - For finite `x` and non-zero finite `y`, `x % y` is exactly `x − y × trunc(x / y)`, computed without rounding. It is always representable.
  - Its sign is `x`'s, and its magnitude is less than `|y|`. A zero result has `x`'s sign.
  - Examples: `7 % 2` is `1`, `-7 % 2` is `-1`, `7 % -2` is `1`, `-7 % -2` is `-1`, `7.5 % 2` is `1.5`, `-4 % 2` is `-0`, `-0 % 5` is `-0`.
  - Special cases: `x % ±0` is NaN; `±∞ % y` is NaN; `x % ±∞` is `x` for finite `x`; a NaN operand gives NaN.
- **Negative zero** exists inside evaluation, from IEEE 754 operations: `-0`, `0 * -1`, `-4 % 2`.
  - It is `==` to `0`, and not `<` it.
  - It is observable only through the sign of an infinity produced by division (`1 / -0` is `−∞`).
  - At every output it becomes `0`: a prop value or argument, at any depth, holds `0`, and text shows `0`.
- **Non-finite numbers** (NaN, `+∞`, `−∞`) may exist inside evaluation, and may be compared, discarded by a conditional, or passed into a composite's prop.
  - A non-finite number reaching an output, at any depth, is an **evaluation diagnostic**. The outputs are a primitive prop, a text run and a command argument.
  - No renderer and no host ever receives one.
  - All NaNs behave alike: no NaN's sign or payload is observable.

**Equality and comparison.**
- **`==` and `!=`** are strict: there is no coercion, and values of different kinds are unequal (§9.4). `!=` is exactly the negation of `==`.
  - Numbers compare by IEEE 754 equality. `0 == -0` is `true`. NaN equals nothing, itself included, so `x == x` can be `false`. `∞ == ∞` is `true`.
  - Strings compare by their sequence of Unicode scalar values. Booleans and `null` compare by value.
  - Lists are equal when they have the same length and are pairwise equal. Records are equal when they have the same fields, pairwise equal.
  - Absent equals absent, and nothing else; `null` is not absent.
  - A value of type `any` compares by its actual value.
- **`<`, `<=`, `>` and `>=`** are IEEE 754 comparisons: any comparison with NaN is `false`, and `-0 < 0` is `false`.

**Evaluation order.**
- Operands are evaluated left to right, and each operand before its operator.
- `&&` and `||` evaluate the left operand, then the right only if the left doesn't decide. The result is a boolean (§9.4).
- `c ? a : b` evaluates `c`, then exactly one branch.
- List elements and record fields are evaluated in source order.
- A **render** evaluates in document order, top down. For each occurrence, it evaluates the written attributes that §3 keeps, in source order, then the children in order.
  - At a composite occurrence, it evaluates the props, then the composite's template.
  - Event handlers are **not** evaluated at render.
- A **dispatch** evaluates the props on the path to the handler's node (D5, step 7), then the handler's arguments, left to right.
- Expressions have no side effects, so order decides only which evaluation diagnostic is reported: the first.

**Runtime checks.** These are the points where evaluation can fail. Every other operation is total.
- **Operands:**
  - `!`, `&&` and `||`, and a conditional's condition, need a boolean;
  - unary `-`, arithmetic and `<`/`<=`/`>`/`>=` need numbers.

  A clean check guarantees these, except where an operand has type `any` or `any?`.
- **Member access `a.f`** needs `a` to be a record. On a record type, an absent field gives absent. On `any`, the field must be present.
- **Content:** an interpolated value must not be a list or record.
- **Props:** each written prop's value, at primitive and composite occurrences alike, must fit the prop's declared type. An absent value is allowed only when that type is optional.
- **Arguments:** each argument must fit its parameter's type.
- **Outputs** (primitive props, text runs, arguments): no non-finite number and no absent list element, at any depth. `-0` becomes `0`.

At any one point, the type check comes first, then the output check.

**Text conversion.** This is used for each interpolation in content.
- A string is itself.
- A boolean is `true` or `false`.
- `null` is `null`.
- **Absent is the empty string.**
- A finite number follows ECMAScript's `Number::toString` with radix 10 (ECMA-262, Number::toString), with one choice made explicit. Where several shortest digit strings round-trip, the one nearest the exact value is chosen, and between two equally near, the one with an even last digit. Examples:
  - `1.5`, `100`, `0.1` and `-2.5`;
  - `0.000001`, `1e-7`, `123456789012345680000` and `1e+21`;
  - `-0` is `0`.

  This deliberately isn't a host's default formatting: Rust's `Display` for `f64`, for instance, never uses exponents.
- A non-finite number never reaches text (see Numbers).

**Number to text: the contract, and how it is verified.** This is the only rule in D8 where the reference MPRX cites (ECMA-262) doesn't determine the output on its own, and where no implementation MESH might use documents the behaviour it needs. So the rule, its implementation and its evidence are stated separately.
- **MESH's rule is the normative one.** ECMA-262's normative step for Number::toString requires the shortest digit string that round-trips. It says outright that the last digit "is not necessarily uniquely determined" by that, and only *recommends*, in a note, the nearest candidate with ties to even. MESH makes that recommendation normative. The layout of those digits (plain, leading zeros or exponent, and the thresholds) is ECMA-262's. So MESH's rule is determined where ECMA-262 isn't. A conforming ECMAScript engine may differ from MESH in the last digit without breaking ECMA-262, and V8 is never the authority for MESH output.
- **The normative table.** Pass 0 writes the rule's expected outputs as a committed table, part of the v0.5 contract beside §9.7. Each row gives an exact binary64 value, as its bit pattern, and the exact text MESH must produce, or, for NaN and the infinities, the evaluation diagnostic that stops them before text conversion. The rows cover:
  - ordinary values;
  - `0`, and `-0`, which gives `0`;
  - integers around representation boundaries: 2^53 and its neighbours, and 2^n where the gap below is half the gap above;
  - both sides of every layout threshold: 1e21, 1e-6 and 1e-7;
  - very large and very small magnitudes: the largest finite value, the smallest normal value, and subnormals, the smallest included;
  - values where several shortest candidates round-trip and the nearest must be chosen (the smallest subnormal, `5e-324`, is one: every single-digit candidate from `3e-324` to `7e-324` reads back as it);
  - equally near candidates, where the even one must be chosen, if binary64 has any. Pass 0 establishes whether it does, and records the evidence. The rule is normative either way.

  The table's values are computed from the rule alone, with exact rational arithmetic, by a reference generator committed beside the table. It runs no float formatter, whether Rust's, JavaScript's or Python's `repr`. Nothing in the table is taken from what an implementation happens to print.
- **The Rust implementation must not rely on undocumented behaviour.** The standard library's float formatting (`Display`, `Debug`, `LowerExp` for `f64`) documents no algorithm: neither shortest output nor which of several shortest candidates it prints. What it does today is an implementation detail that may change between toolchains. So the runtime does not use it to generate digits. It uses one of these, and Pass 0 names which, with the documentation it relies on:
  - a library, under a MESH-owned layer that lays its digits out by ECMA-262, but only if authoritative, citable evidence shows all three guarantees: shortest round-trip, nearest among several shortest candidates, and ties to even. Observed behaviour and source comments don't count;
  - or MESH's own exact digit generator, with the argument for its correctness in its documentation.

  **Pass 0's reviewed decision:** `std`/`core` formatting is rejected. It fails 4 of the table's 82 finite rows on the pinned 1.98.1, all exact ties. `ryu` is rejected for v0.5: its citable documentation states only shortest round-trip output. So **the runtime uses MESH's own exact digit generator**, the reference generator's algorithm over arbitrary-precision integers. If authoritative evidence for a library is obtained later, adopting it is an implementation change, recorded with its evidence and reviewed on its own, and the library must still pass the table.

  Either way, the implementation is correct because it passes the normative table, not because a library is trusted.
- **Pass 2 is the normative verification.** The runtime's number-to-text conversion must reproduce every row of the table exactly before Pass 2 is complete.
- **Pass 3's comparison with V8 is a differential test,** not a proof. It compares MESH's text for one million generated values with V8's `String(x)`, to catch regressions and implementation bugs the table's rows don't reach. A difference is investigated and classified, never resolved by adopting V8's output:
  - **a MESH implementation bug:** MESH's text breaks the rule. It isn't shortest, doesn't round-trip, or isn't the nearest candidate. Fix the runtime, and add the value to the normative table;
  - **an incorrect or underspecified MESH expectation:** the rule, or a table row, turns out wrong or ambiguous. Amend the rule through this outline and the spec, then the table, then the runtime;
  - **an intentional difference:** MESH follows its rule and V8 doesn't, for instance in the last digit ECMA-262 leaves open. Record the value, both outputs and the reason in a committed list of known differences, which the test then accepts, and which the release notes report.

Literal text is kept as the semantic model keeps it (§3). A text run is the concatenation of its parts.

**Lists and records in content.** An interpolation whose static type is a list, a record, `list<nothing>` or an optional of one is a **check-time error**, a new diagnostic: no text form of one is obviously right. An interpolation of type `any` or `any?` whose value turns out to be a list or record is an evaluation diagnostic.

**Every rule gets a test** (Definition of Done).

- **A test host** supplies snapshots from JSON fixtures, keeps renders, relays events to dispatch with their renders, and records command intents.
- **A reference renderer,** test-only, prints a render tree as HTML-like text, so an expected rendering can be a committed file. It also compares two trees key by key (D6).
- **Scope:** both run natively, and in Node over `@valancex/mesh-runtime`. They prove MESH's side of the NEXUS and PORT boundaries without either repository.

## Resolved decisions

The first draft left five questions open. They are resolved, and each one is written into the decisions above.

1. **Evaluation happens in Rust, in one runtime, native and WebAssembly** (D3, I11). This is an architectural constraint: MPRX's semantics are implemented once. JavaScript encodes and transports values; it doesn't evaluate them, judge them, or decide how they're presented.
2. **MESH defines the host interface; the NEXUS adapter lives in NEXUS** and depends on `@valancex/mesh-runtime` (D5, I15). MESH depends on neither NEXUS nor Effect, which matches NEXUS's "MESH → NEXUS interfaces" direction.
3. **Composition covers composites without composite events, children or slots** (D7). That is enough for the `user-card` slice. Composite events and children/slots are rejected for v0.5, and kept for a later language-design release.
4. **Editor work is deferred** to a later release: the VS Code extension, the project file and E11 (Non-goals).
5. **NEXUS and PORT move to `@valancex/*`** before either publishes (F9, D9). That is their change, outside the MESH release.

## Definition of Done

Each item is observable evidence for a contract above.

**Templates (D1, D2, I12).**
- For every source in the corpus that checks clean, `compile` emits a template that validates against `template-v1`.
- For every source with an error, it emits none, and returns the diagnostics `check` returns.
- The CLI and the JS API return equal templates and diagnostics for the same inputs.
- Compiling twice gives identical templates.
- Each of the two new check-time diagnostics has a test: a list or record in content, and a literal too large to be finite.

**Fingerprints and versions (D1, I12).**
- Two manifests that differ only in formatting, key order, `$schema`, unused or renamed named types, or parameter names have equal fingerprints.
- A change to any counted declaration changes the fingerprint.
- The runtime refuses a template of an unsupported format version, and a malformed template, each with its own diagnostic.
- It refuses a template whose fingerprint differs from its model's.
- A template whose compiler version differs, and nothing else, runs.

**Programs and assembly (D7).** Each assembly rule has a test that breaks it and shows the diagnostic, from the compiler's program check and from the runtime, with equal codes and locations. The tests cover:
- two templates for one component, and a missing root template;
- mixed fingerprints;
- an unbound scope name, and a binding whose types don't fit;
- an optional prop bound to a scope name that isn't optional;
- a direct cycle and an indirect one;
- a composite that declares events;
- a composite occurrence with children, including whitespace-only text, which is not a child and is accepted.

Also:
- An occurrence of a component with no template renders as a primitive.
- An unreached template is accepted and ignored.

**Inputs (D5, I14).** Each case below has a test:
- a missing required scope name, and an absent optional one;
- extra scope names, which are ignored even when their values are invalid or unsupported;
- a wrong-kind value at depth, with its path;
- a record with an undeclared field, and one missing a field that reads as optional (accepted) and one that doesn't (rejected);
- `null` where absence is expected, and the reverse;
- an out-of-range number;
- an unpaired surrogate;
- each unsupported JavaScript value, including `undefined` in an array, a hole, NaN and a cycle;
- a payload that doesn't fit, a payload given for an event with none, and a missing payload where one is required.

Also: every input mismatch in one call is reported, in D3's path order.

**Evaluation (D8).** Every rule D8 adds to the spec has a test that pins it, including:
- `1 == 1.0` and `1.50 == 1.5`;
- `7 % -2`, `-7 % 2`, `-4 % 2`, `x % 0`, `1 / 0`, `-1 / 0`, `0 / 0` and `1 / -0`;
- `0 == -0`, and `-0` rendered and passed as `0`;
- NaN in `==`, `!=`, `<` and in a list compared for equality;
- non-finite numbers inside evaluation that never reach an output (no error), and one reaching a prop, a text run and an argument at depth (an error each);
- short-circuiting that skips an erroneous right operand, and the conditional evaluating one branch;
- text for strings, booleans, `null` and absent;
- **number to text, normatively:** the runtime reproduces every row of the normative number-to-text table exactly (D8), covering every category D8 lists. The table's generator reproduces the committed table. This is checked in Pass 2, and Pass 2 isn't complete without it;
- an absent prop omitted, a `null` prop present;
- an absent list element reaching an output (an error);
- each `any` runtime check failing: an operand, member access, content, a prop and an argument;
- when several evaluation errors exist, the first in evaluation order is the one reported.

**The property test.** For every program in the corpus, and generated snapshots that fit exactly (absent only where the type is optional), every render either:
- yields a render tree that validates against `render-v1`; or
- stops with one of D8's evaluation diagnostics, whose source is present in that program: a non-finite number or absent list element reaching an output, or an `any` check.

A program with none of those sources renders every time.

**Structure, keys and handler identifiers (D4, D6).**
- For every program in the corpus, renders with different generated snapshots have identical structure, keys and handler identifiers.
- Within each tree, keys are unique, and so are handler identifiers.
- Two occurrences of the same composite, and of the same primitive, get distinct keys and distinct handler identifiers.
- A nested composite (a composite inside a composite) renders, with keys distinct from the same primitive outside it.
- No key or handler identifier contains a composite name, scope name or command identity in recoverable form, and keys can't be reproduced from the structure alone: the same structure in two programs with different templates gives different keys.

**Dispatch (D5).**
- Dispatch with a handler identifier from another program is an input-validation diagnostic, and so is one naming no handler; each is located at the `handler`, and they have different codes.
- Dispatch evaluates against the render's snapshot: after the host has rendered new values, dispatching with the earlier render gives the earlier values' intent.
- Mutating the host's snapshot object after render doesn't change the intent.
- An absent argument is distinguished from `null` in the intent.

**PORT sees only values (I13).** A test walks every render tree the corpus produces and finds only what I13 lists.

**One evaluator (I11).**
- Native and WebAssembly give equal render trees, keys, handler identifiers, command intents and diagnostics for the same inputs, over the corpus, generated snapshots and every input-validation case.
- **Number to text, differentially:** the WebAssembly build's text for one million generated values is compared with V8's `String(x)`. Every difference is classified as D8 requires. The test passes only when no difference is unclassified and none is a MESH implementation bug. Known differences are committed and reported in the release notes. This is compatibility evidence, and doesn't replace the normative table.
- A review of `@valancex/mesh-runtime` against I11's list finds no evaluation, coercion or validation.

**The slice.** `examples/` gains a composite `user-card` template and a page whose template uses it twice. With the test host supplying users:
- the render tree is the committed expected tree, primitives only;
- the reference renderer prints it as the committed expected HTML;
- dispatching the first avatar's click, with its payload, gives exactly the committed intent: `user-card`'s `selectUser`, with its evaluated arguments;
- re-rendering with one user changed gives a complete tree with the same keys, and the reference renderer's key-by-key comparison lists exactly the committed set of changed props and text runs;
- all of this holds natively and in Node.

**It's documented.**
- The template format, programs and assembly, the render tree and command intent, and the runtime diagnostics are in the manuals.
- The evaluation rules and the boundary data model are in the spec.
- Two guides, each with an example a test runs: "Integrating MESH with NEXUS" (a host, including the obligation to pair events with their renders) and "Rendering MESH output" (a renderer, including reconciling by key).

## Sequencing

- Pass 0 comes first: the formats, semantics and diagnostics are the contracts.
- Pass 1 and Pass 2 can overlap once Pass 0 is done. Pass 2 uses hand-written templates, and Pass 1's fingerprint computation.
- Pass 3 needs both. Pass 4 needs everything.
- NEXUS's adapter and PORT's Web renderer can start in their own repositories, on their own schedules, once Pass 0's specifications are published and after their `@valancex` rename. MESH's passes don't depend on them.

## Risks

- **Formats harden early.** Once NEXUS and PORT build on `template-v1` and `render-v1`, changing them costs three repositories. Mitigations:
  - specifications first (Pass 0);
  - the additive-only promise;
  - compatibility decided by format version and fingerprint, never by compiler version.
- **A second evaluator creeping into JavaScript,** for example formatting a number in a renderer, defaulting an absent prop, or validating in the runtime package. The defences are I6, I11, I13, "JavaScript encodes; Rust judges" (D5), and the review in the Definition of Done. The render tree holds final values, so there's nothing left to compute.
- **Number formatting borrowed from a host.** A runtime that trusts Rust's default float formatting, or treats V8's output as correct, would make MESH's text depend on undocumented behaviour of one toolchain or engine. The defences:
  - D8's rule is normative, and its table is computed from the rule alone;
  - digit generation is MESH's own code (Pass 0's reviewed decision); a library could replace it only on citable evidence of all three guarantees;
  - Pass 2 passes the table;
  - Pass 3's V8 comparison is only differential, and every difference is classified.
- **Hosts that pair an event with the wrong render.** Dispatch is only as faithful as the host's pairing (D5). The guides make it an explicit obligation, and the test host models it.
- **The host boundary is only as strict as its checks.** I14 validates every input on every call. If that shows up in profiles, the answer is to make it faster (D3 allows caching validation), not to skip it.
- **Exact records may chafe.** A NEXUS selector that returns a record with more fields than the manifest declares fails I14. That is intended, because open records are out of scope (§10). The adapter shapes its values to the manifest, and the integration guide says so.
- **Absent list elements can't cross the boundary** (D5, D8). A `list<T?>` holding an absent element, from an array literal, can't be rendered or passed as an argument. It's rare, it's fail-closed, and it's documented.
- **A missing template silently makes a composite a primitive** (D7). If a program omits `user-card`'s template, PORT receives a `user-card` node, which PORT's "nothing silently dropped" rule should then surface. Tests and the guides cover it.
- **Whole-model fingerprints** make every template incompatible after any change of meaning to the model, even to an unrelated component. That is conservative and correct; recompiling is the remedy.
- **NEXUS and PORT move independently.** MESH can't change them. The guides, the test host and the reference renderer make MESH's side checkable without them.

## After v0.5

None of these is needed by the v0.5 contract.
- Composite events, and children and slots for composites, with their own language design.
- Editor work: the VS Code extension, the project file, definitions for closing tags and record fields, related spans, and a debounced manifest.
- The remaining language questions: a presence test or optional chaining, unions, and open records.
- A boundary representation for absent list elements, or a rule that avoids them.
- A narrower model fingerprint, covering only what a program depends on.
- An assembly warning for a component used as a primitive that declares its own scope or commands (and so looks as if it should have a template).
- Incremental evaluation, and data-derived keys once MPRX has lists of elements.
