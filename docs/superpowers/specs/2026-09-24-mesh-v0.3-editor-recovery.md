# MESH v0.3 — Editor recovery (D3's design spec)

Date: 2026-09-24
Status: Design spec. The outline's D3 asks for this before Pass 3 is
planned, "written against real Tree-sitter recovery trees the way v0.2's
located syntax errors were". It chooses *how* recovery works. It doesn't
relax invariants I1–I3, and it doesn't change the canonical path.

Spec: `docs/superpowers/specs/2026-09-24-mesh-v0.3-outline.md`, D3, D4 and
I1–I3; findings B6 and B7 of the audit after Passes 0 and 1.

## Evidence

Every shape below was observed on 2026-09-24 by parsing real inputs with
the committed grammar (`tree-sitter-mprx` at `47950dd`, tree-sitter
0.27.0) and dumping the whole tree, anonymous tokens, `ERROR` and
`MISSING` nodes included. Pass 3 turns each row into a fixture, so a
grammar or Tree-sitter change that moves one fails a test instead of
silently changing an answer.

Offsets are bytes. `…` is a part of the tree that parsed cleanly.

Two conclusions shape everything below:

- **Recovery must be a forest, not a tree** (B6). S16 is the most common
  state while typing an expression without auto-closed braces, and it has
  no root element at all. What it does have is every complete element
  before the cursor.
- **Clean subtrees next to a mistake can be misparses** (S16). A clean
  `reference` `page` that is really a closing tag must never be answered
  as a name in scope. Recovery only trusts clean subtrees in places whose
  delimiters are real: an element whose tag name is real, or an expression
  block whose `{` and `}` are both present.

## What recovery produces

Recovery answers one question: *for a document whose canonical compile
has no IR, what do the parts that parse mean?* Its answer is a list of
**parts**, in source order, none overlapping another:

- **An element part:** an element, pruned of whatever doesn't parse, and
  its analysis as the template of the configured component.
- **An expression part:** a clean expression found in an expression block
  that was pruned from an element part, and its analysis as a value in the
  template's scope.

Its only queries are `resolution_at(offset)` and `typed_at(offset)`, with
`Analysis`'s own "at" rule, across all parts. It has **no** facts, and no
diagnostics accessor at all, so nothing can publish it by mistake (I2,
I3).

## The rules

**R1. When.** Recovery runs only when the canonical compile has no IR,
and only when the document is checked against a model (it has a
template). Without a model there is nothing to resolve against, and the
canonical state already answers "nothing". A file that parses never runs
recovery (D3: "When the canonical compile does have IR, navigation uses
canonical state only").

**R2. Parse.** Recovery parses the text with the same grammar as `parse`.
If the tree is nested deeper than `MAX_NESTING_DEPTH` anywhere, recovery
returns no parts: the limit exists so nothing recursive runs on such a
tree (A1), and recovery is recursive after this point. The depth check is
the existing iterative one, which works on trees with errors.

**R3. Element parts.** Walk the tree from the root, in source order.
- A `self_closing_element` or `container_element` node whose `name` field
  is a `tag_name` that isn't `MISSING` is an element. It becomes an
  element part, pruned as below, and the walk doesn't descend into it
  further.
- Any other node (the `source_file`, an `element` wrapper, a `child`, an
  `ERROR`) is walked into, so elements inside an `ERROR` are found (S16,
  S15).
- Loose tokens are never assembled into an element. S8's `<`, `avatar`,
  `s` are not an element; S16's root `<page …>` is not either.

**R4. Pruning an element.** An element part keeps:
- its tag name and its opening tag's span;
- each `attribute` and `event_binding` child that has no error (S2 keeps
  `alt`; S10 and S11 drop the `ERROR`);
- each `child` in order: text always; an `expression_block` only if it
  has no error; a nested element pruned by these same rules, whether or
  not it has an error;
- each element inside an `ERROR` among its children, found as R3 finds
  them, kept as a child at its position;
- its closing tag name only if both closing tokens are present and not
  `MISSING`.

A `MISSING` token never disqualifies an element by itself (S5, S6, S7
keep their elements).

**R5. Expression parts.** For each `expression_block` that R4 dropped (from
a child, an attribute value or a handler, but not from inside an
`ERROR`):
- if its `{` and its `}` are both present and not `MISSING`, and
- its `expression` field is a node with no error and not `MISSING`,

that expression becomes an expression part. S1, S2 and S3 give the parts
`user`, `user` and `!user`. S4 gives none (the conditional isn't clean),
S13 none (the expression is `MISSING`), S14 the reference `selectUser`,
and S16 none (no block exists; the braces are loose tokens of the `ERROR`).
The same rule never looks inside an `ERROR` for expressions, so S16's
misparses can't become parts.

**R6. Lowering and analysis.** Each element part is converted to a
`mesh_syntax::Element` by the parser's existing lowering functions, which
are only ever given clean subtrees, then to IR by `mesh_semantic::lower`,
and analyzed with `mesh_analysis::analyze` against the template. Each
expression part is lowered the same way and analyzed with a new
`mesh_analysis::analyze_expression`, which runs the same walker on one
expression in value position (not as a handler, not as a handler's
argument). Lowering diagnostics and every fact are discarded where they
are produced; nothing keeps them.

Analyzing each element part on its own gives the same resolutions and
types it would get inside its parent, because analysis of an element
depends only on the template, never on its ancestors (`check.rs`,
`Walker::element`). Pass 3 pins that with a test (P1 below).

**R7. Answers.** `resolution_at` and `typed_at` search every part and
return the innermost match across all of them, by `Analysis`'s rule.
Parts don't overlap, except that an expression part lies inside the span
of the element part it was pruned from; the innermost rule picks the
expression part there, which is what the cursor is on.

**R8. Where it runs.** On the compile thread, right after the canonical
compile of the same snapshot, with its 8 MiB stack. Its result is stored
beside that snapshot's canonical state, dropped with it, and never
compared with or merged into it.

## Properties Pass 3 must prove

- **P1. Recovery agrees with canonical analysis on files that parse.**
  For every `.mprx` file in the corpus that parses, recovery run directly
  (bypassing R1) gives exactly one element part, and its resolutions and
  types equal the canonical analysis's, in order.
- **P2. Recovery never touches canonical state.** For every fixture with a
  syntax error, and every prefix of the two example templates, with and
  without a model: `compile_with`'s result is identical whether or not
  recovery ran first, and the published diagnostics equal
  `mesh check --format json`'s (the Pass 1 agreement test, extended).
- **P3. Nothing recovered is published.** The recovery type has no facts
  and no diagnostics; a grep shows `mesh-lsp`'s publication path reads
  only `Compiled::diagnostics`.
- **P4. Misparses aren't answers.** On S16 and S17, hovering the misparsed
  names (`page` in `</page>`, `text` in `</text>`) gives nothing, even
  when the manifest declares a scope name `page`.
- **P5. Every shape is pinned.** S1–S18 are fixtures whose expected parts
  are written out; a change in Tree-sitter's recovery fails one.

## Rejected

- **Assembling elements from loose tokens** (S8, S16's root). It would
  mean writing a second parser for MPRX's broken states in `mesh-parser`,
  and it would guess. Completion reads loose tokens for *context* (D4),
  which is a smaller, syntactic question; recovery doesn't.
- **Keeping clean expressions from anywhere in the tree.** S16 shows why:
  after the mistake, clean-looking expressions are often closing tags.
- **Analyzing expression parts in their real place** (as a handler, or a
  handler's argument). The place is only known when the enclosing
  construct parses, and then the expression is usually in an element
  part already. An expression part is analyzed as a value; where that
  gives no answer (a command, `$event`), hover gives nothing, which is
  less, never wrong.
- **Recovering against an older good snapshot.** Rejected by D3 already.
