## Context

Pass 3b (Array/Object/Command/EventValue expressions) shipped and merged to
`master` (HEAD `827c3bd`). Per the v0.1 roadmap
(`docs/superpowers/specs/2026-09-22-mesh-v0.1-pass-3-5-outline.md`), Pass 4
is next and is the highest cross-cutting-risk pass in the roadmap: it
touches every crate in the workspace (`mesh-syntax`, `mesh-parser`,
`mesh-semantic`, `mesh-compiler`) and changes two public function
signatures that every caller, including all existing tests, depends on.

This spec splits Pass 4 into two sequential plans:

- **Pass 4a** — mechanical, breaking plumbing: the diagnostic-plurality
  API change to `mesh_parser::parse` / `mesh_semantic::lower` (including
  relocating `Diagnostic`/`Severity` to `mesh-syntax`), the
  `Child::Element` nested-element addition, and the `Element.closing_name`
  field that captures close-tag text for Pass 4b to validate. No new
  validation logic.
- **Pass 4b** — built on top of 4a: event-binding grammar/AST/IR, and the
  structural validation rules that need plural diagnostics to report.

4a lands first as its own plan; 4b starts only once 4a is merged, since
4b's validation diagnostics need 4a's `LowerResult` type to exist.

mesh-syntax     — zero workspace-internal dependencies
mesh-parser     — depends on: mesh-syntax
mesh-semantic   — depends on: mesh-syntax
mesh-compiler   — depends on: mesh-syntax, mesh-parser, mesh-semantic
mesh-cli        — depends on: mesh-syntax, mesh-compiler

`mesh-syntax` is the only crate with no workspace-internal dependencies,

already depend on it. This fact drives the diagnostic-ownership decision
below.

## Architecture: Change Containment

This section formalizes, as durable architectural principles rather than
Pass-4-specific advice, the constraints this spec's design already
follows. It does not add functionality — it states, explicitly, the
reasoning that already shaped every decision above and below, so future
passes (and future contributors to this codebase) can rely on it rather
than re-deriving it. Nothing in this section changes any already-approved
Pass 4a/4b behavior.

> **MESH must optimize for change containment, not merely current
> implementation simplicity.** A feature should have a bounded,
> traceable implementation surface. An old feature should be removable
> or replaceable without forcing unrelated compiler internals to change.
> **Adding a feature should have a bounded blast radius, and removing or
> replacing a feature should have a bounded blast radius.**

A feature should have: an explicit owner; explicit representations at
each compiler boundary where the feature is actually required; explicit
semantic responsibilities; explicit diagnostics; explicit tests; explicit
documentation. Features must not leak implementation-specific knowledge
into unrelated components. Shared abstractions must represent stable
language concepts, not temporary implementation similarities. Adding a
feature must not require speculative changes to unrelated infrastructure.
Removing or replacing a feature must not require redesigning unrelated
features or compiler infrastructure. Compatibility and migration logic
(when it exists at all) must live at explicit boundaries and must be
removable once the compatibility period ends. The architecture prefers
localized feature handling over globally distributed conditionals,
feature flags, compatibility branches, or historical representations.

### Compiler architecture invariants

These are binding invariants for Pass 4a/4b and every pass after it, not
informal recommendations:

**Source order is authoritative.** Ordered `Vec` collections preserve
source order unless the language specification explicitly defines
normalization. Maps and sets may be used internally for lookup or
duplicate detection, but their iteration order must never determine
observable AST ordering, IR ordering, diagnostic ordering, emitted
output, or semantic behavior. If both lookup and source ordering are
required, use a lookup structure *in addition to* the authoritative
ordered representation, never instead of it. (Already applied above: see
"Deterministic diagnostic ordering" and the duplicate-resolution rules,
which explicitly forbid `HashMap`/`HashSet` iteration order from
determining diagnostic order.)

**AST field lifecycle must be explicit.** Every AST field has one of
four dispositions: (1) preserved into semantic IR; (2) consumed only
during semantic validation/lowering, then discarded; (3) retained only
for source/diagnostic purposes (e.g. `Span`); (4) intentionally
discarded after lowering with no IR trace at all. Do not copy an AST
field into IR merely because it exists; do not remove an AST field
merely because IR does not need it. Every new AST field's lifecycle
must be stated where the field is introduced. (Applied below: see the
per-field lifecycle table in "Pass 4 Feature Ownership and Removal
Surface".)

**Lossy transformations require explicit justification.** Any
information discarded during CST → AST or AST → IR must be intentional
and documented — whitespace-only text, closing-tag information, source
delimiters, syntactic redundancy, and parser-only recovery information
are all examples already present in this spec. Do not introduce implicit
information loss merely for implementation convenience.

**Source fidelity belongs to the CST unless promoted.** The CST is the
authoritative source-fidelity representation. AST and IR preserve
formatting, trivia, delimiters, or other syntactic information only when
that information has an explicit semantic, diagnostic, tooling, or
source-mapping purpose. Do not force source-fidelity concerns into
semantic IR. (Applied below: the whitespace-only-text filter moved to
`mesh-semantic`, not `mesh-parser`, so the AST stays a full structural
mirror of the CST and only the IR narrows toward meaning — see
"Whitespace-only text children" below.)

**Diagnostics are data, not presentation.** `mesh_syntax::Diagnostic`
represents diagnostic data only — it must not know about terminal
formatting, CLI output, LSP protocol structures, IDE rendering, colors,
source-code snippets, or any renderer-specific formatting; those
concerns belong at the consumer boundary (`mesh-cli`, `mesh-lsp`, or
whatever renders diagnostics next). Diagnostic messages are presentation
text, not diagnostic identity — do not treat `message` as something code
branches on. This does not make future machine-readable diagnostic codes
impossible, but Pass 4 does not add them (see "Explicitly Out of Scope").
This invariant is the reasoning behind the "Scope constraint on
`mesh_syntax::Diagnostic`" above, stated generally.

**Severity does not determine recoverability.** Diagnostic severity and
compiler recoverability are separate concepts. `Error`-severity plus
usable IR is valid whenever semantic lowering can continue without
producing structurally misleading output — exactly the tag-mismatch
recovery rule above (`Error` diagnostic, `ir` still `Some`). Do not
introduce logic equivalent to "if severity == Error, discard IR" unless
a future language specification explicitly requires it; Pass 4 does not.

**Grammar defines syntax; semantic analysis defines language meaning.**
The parser is responsible for syntactic validity; semantic analysis is
responsible for meaningful-tree and structural constraints. Do not
encode semantic uniqueness or relationships into grammar merely to
simplify semantic validation — duplicate attributes, duplicate event
bindings, and matching opening/closing names all remain semantic
concerns for Pass 4, exactly as already decided (see "Validation
location" below).

**Semantic namespaces are explicit.** Two constructs conflict only when
the language specification places them in the same semantic namespace.
For Pass 4, `attributes` and `events` are separate namespaces —
`<div id="a" on.click={handler} />` is not a duplicate merely because
both are `element_modifier`s syntactically (already stated under
"Duplicate event bindings" below; restated here as the general
invariant it's an instance of). Do not unify semantic namespaces merely
because their parser representation is similar.

**Compiler output must be deterministic.** Given identical source and
compiler configuration, MESH must produce deterministic AST, semantic
IR, diagnostics, and diagnostic ordering. Observable behavior must never
depend on hash-map/hash-set iteration, filesystem iteration order,
thread scheduling, or any other incidental/unstable traversal. Pass 4
introduces no concurrency, no filesystem iteration, and no hash-based
ordering dependency anywhere in `lower` or `parse` — verified directly
against both crates' current implementations, which use only `Vec`
iteration throughout.

### Dependency direction is protected

The verified dependency graph above (`mesh-syntax` ← `mesh-parser`,
`mesh-semantic` ← `mesh-compiler` ← `mesh-cli`/`mesh-lsp`) must never
gain a reverse edge. Feature implementation problems are never solved by
moving feature-specific logic into a lower-level crate that does not own
that concept — e.g. event-binding duplicate-detection logic belongs in
`mesh-semantic` (which owns semantic validation), never pushed down into
`mesh-syntax` (which owns only AST *shape*) merely because that would be
convenient for some caller. If an implementation appears to require
violating this direction, that is an architecture problem to raise, not
a workaround to apply silently.

### Avoid speculative shared abstractions

Do not introduce a generic abstraction merely because two
implementations currently look similar. A shared abstraction must
represent a stable concept, justified by: **at least two independent
consumers that require the same stable concept** — otherwise keep the
implementation feature-local. Concretely for Pass 4: attributes and
event bindings are *not* unified into a generic `Vec<ElementModifier>`
despite sharing a grammar production (`element_modifier`), because they
have distinct, independent semantic roles (declarative state vs.
behavioral intent) — this is already the approved design (see "Rationale
for keeping attributes and event bindings as separate fields" below). No
generic diagnostic abstraction beyond the already-approved `Diagnostic`
is introduced. No feature registries, plugin systems, visitor
frameworks, or extension interfaces are introduced — none is required by
Pass 4.

### Feature removal is a first-class design requirement

For every non-trivial feature, this spec states which layers
(grammar/CST, AST, semantic rules, IR, diagnostics, tests, docs) own the
feature and which layers intentionally do not — see "Pass 4 Feature
Ownership and Removal Surface" below. This does not mean every feature
must appear in every layer; it means the boundary is explicit, so
removing a feature later does not require redesigning unrelated
infrastructure, and replacing a feature is possible by changing its
boundary representation rather than spreading compatibility logic
through the compiler.

### Compatibility logic has a deletion point (not needed in Pass 4)

If an old and new representation ever need to coexist, compatibility
logic must live at an explicit boundary (old representation →
compatibility adapter → current representation), never distributed as
`if old_feature { ... }` through unrelated compiler code, and every such
layer must have a stated removal condition. **Pass 4 introduces no
compatibility layer** — this invariant is recorded now, before any
migration exists, precisely so a future migration doesn't retrofit one
badly. Nothing in Pass 4a/4b requires this machinery.

### Public API changes must be intentional

v0.1 permits public API changes between passes, but every one must be
intentional and documented, not incidental churn from internal
refactoring. Pass 4a's two public signature changes are both
intentional and both documented above with their motivation:
`mesh_parser::parse`'s `Result<Element, ParseError>` → `ParseResult`
(motivated by needing plural parser diagnostics) and
`mesh_semantic::lower`'s `Element` → `LowerResult` (motivated by needing
plural, partial-success-capable semantic diagnostics). No other public
signature changes anywhere in the workspace — `mesh_compiler::compile`'s
own signature and `CompileResult`'s fields are unchanged (see
"Explicitly Out of Scope").

### Partial output is a deliberate philosophy

MESH prefers recoverable compilation when continuing produces
structurally sound output. A semantic diagnostic does not automatically
imply IR must become unavailable — but partial output must never be
produced when continuing would make the resulting IR structurally
unsound or misleading. Pass 4's explicit instance of this: tag mismatch
→ diagnostic + continue lowering + IR remains `Some` (see the five-point
recovery rule below). This is not generalized into unrestricted error
recovery — Pass 4 defines exactly these recoverable cases (duplicate
attributes, duplicate events, tag mismatch) and no others; a parser-level
`ParseError` remains a hard stop for the element it applies to (see "On
`ParseError`'s severity" below).

## Pass 4a: Diagnostic Plurality + Nested Elements

### Diagnostic-plurality API

Today, `mesh_parser::parse` returns `Result<Element, ParseError>` (zero or
one error) and `mesh_semantic::lower` is fully infallible (`-> Element`,
no diagnostics at all). `mesh_compiler::CompileResult` already has the
target shape (`ir: Option<Element>`, `diagnostics: Vec<Diagnostic>`) but
today only ever holds 0 or 1 diagnostic, because neither crate underneath
it can produce more. `Diagnostic` and `Severity` are currently defined in
`mesh-compiler` (`crates/mesh-compiler/src/lib.rs`), verified directly in
the source.

Replace both signatures with dedicated named result structs, one per
crate, structurally mirroring `CompileResult`:

```rust
// mesh-parser
pub struct ParseResult {
    pub ast: Option<Element>,
    pub errors: Vec<ParseError>,
}

pub fn parse(source: &str) -> ParseResult
```

```rust
// mesh-semantic
pub struct LowerResult {
    pub ir: Option<Element>,
    pub diagnostics: Vec<mesh_syntax::Diagnostic>,
}

pub fn lower(ast: &mesh_syntax::Element) -> LowerResult
```

A plain `Result<T, E>` cannot express "usable partial output plus
non-fatal diagnostics" — Pass 4b's duplicate-attribute/duplicate-event
warnings need `lower` to keep producing IR while also reporting a
diagnostic. Dropping `Result` in favor of named structs sidesteps this
without inventing a new shape at each layer — it's the same pattern
`CompileResult` already established.

#### When is `LowerResult.ir` `None`?

Verified against the current `mesh-semantic::lower` implementation
(`crates/mesh-semantic/src/lib.rs`): today `lower(ast: &mesh_syntax::Element)
-> Element` is fully infallible — it is not even `Option`-wrapped, and
every one of its match arms is a total structural mirror of the AST with
no failure path anywhere.

All Pass 4b validation rules are recoverable and IR-preserving by
design: duplicate-attribute and duplicate-event warnings still produce
IR (the winning occurrence survives), and tag-mismatch is an `Error`
diagnostic that still produces IR (recovery rule step 5, above). Pass 4
introduces no rule under which lowering an existing AST fails to produce
IR. Accordingly:

> When `ast` exists, Pass 4 semantic lowering produces `Some(ir)` even
> when `diagnostics` contains warnings or errors. `None` remains part of
> the API to represent the absence of a lowerable AST and/or future fatal
> semantic failures; Pass 4 does not introduce a new fatal semantic
> validation rule.

Concretely, for Pass 4: every call to `lower()` (which, like today, is
only ever invoked on an `ast: &mesh_syntax::Element` that already
exists) returns `LowerResult { ir: Some(..), diagnostics }`. `ir: None`
is not reachable through any Pass 4 code path — it exists in the type
purely so `LowerResult` mirrors `CompileResult`'s established
partial-success shape and leaves room for a later pass to add an actual
fatal semantic rule without another breaking signature change. Do not
add a mechanism that produces `None` merely to exercise the `Option`.

#### Diagnostic ownership and dependency direction

`LowerResult.diagnostics: Vec<Diagnostic>` as originally drafted was a
layering contradiction: it would require `mesh-semantic` to depend on
`mesh-compiler`, which currently owns `Diagnostic`/`Severity` — and
`mesh-compiler` already depends on `mesh-semantic`, so that edge would be
a dependency cycle. Rust would refuse to compile it.

**Fix: move `Diagnostic` and `Severity` from `mesh-compiler` into
`mesh-syntax`.** Per the verified dependency graph above, `mesh-syntax`
is already the workspace's zero-dependency base crate, already holds
`Span` (which `Diagnostic` embeds), and is already a dependency of
`mesh-parser`, `mesh-semantic`, and `mesh-compiler` — so this requires no
new crate and no new `Cargo.toml` dependency edges anywhere. This is the
smallest change consistent with the existing crate boundaries.

`ParseError` does **not** move — it stays defined in `mesh-parser` and
crate-local to it. It is not part of the shared diagnostic model; see
"On `ParseError`'s severity" below for why.

Resulting dependency direction:

```text
                    mesh-syntax
                (Span, Diagnostic, Severity)
                    ^     ^      ^
                    |     |      |
          mesh-parser  mesh-semantic  mesh-compiler
        (ParseError)   (LowerResult)  (CompileResult,
                                        orchestration)
```

`mesh-parser` and `mesh-semantic` depend only on `mesh-syntax`, exactly
as they do today — neither gains a dependency on `mesh-compiler`.
`mesh-compiler` continues to depend on all three, as it already does, and
is where `ParseError` values get converted into `mesh_syntax::Diagnostic`
values (in `compile()`'s glue code) — that conversion needs no crate to
depend on `mesh-compiler`, since it happens inside `mesh-compiler` itself,
which already sees both types.

`ParseError` and `Diagnostic` remain distinct types — do not merge them
into one shared error type. `Diagnostic` is the semantic/compiler-facing
type, carrying `Severity`; `ParseError` is `mesh-parser`'s own
parse-failure type. Keeping them separate matches their different
homes and different purposes (see below).

**Scope constraint on `mesh_syntax::Diagnostic`.** Moving `Diagnostic`
into `mesh-syntax` must not turn `mesh-syntax` into a miscellaneous
shared-types dumping ground. `mesh_syntax::Diagnostic` must remain
renderer-, compiler-, and parser-agnostic: it may contain only generic
diagnostic information (`severity`, `message`, `span`) and must not
accumulate layer-specific concepts (no parser-only fields, no
compiler-orchestration fields, no renderer/codegen fields). Any future
diagnostic need that is specific to one layer belongs on a type local to
that layer, not as an addition to `mesh_syntax::Diagnostic`.

#### On `ParseError`'s severity

`ParseError` represents parser-level failures in the current parser API.
Pass 4 does not introduce parser diagnostic severity or parser-level
recovery semantics — every `ParseError` in `ParseResult.errors` is, for
Pass 4's purposes, a hard failure of the specific construct it applies
to. This is deliberately phrased narrowly rather than as a permanent
architectural invariant: it describes Pass 4's parser API, not a claim
that parser errors can never become recoverable or gain severity levels
in a future pass. Pass 4 does not add parser recovery — a future pass
remains free to add it later without requiring another architectural
rewrite of this design.

Layering stays:

```text
MPRX source
    -> mesh-parser -> AST + ParseError[]              (mesh-syntax types only)
    -> mesh-semantic -> IR + Diagnostic[]              (mesh-syntax::Diagnostic)
    -> mesh-compiler -> CompileResult { ir, diagnostics }  (thin orchestration)
```

#### Parser-to-compiler diagnostic conversion — exact mapping

Verified today's `compile()` (`crates/mesh-compiler/src/lib.rs`):
`mesh_parser::ParseError { message: String, span: Span }` (confirmed
field names, `crates/mesh-parser/src/lib.rs`) is converted 1:1 into a
`Diagnostic` on the `Err` branch of the current `match
mesh_parser::parse(source) { Ok(ast) => ..., Err(err) => ... }`. Under
Pass 4a's `ParseResult { ast: Option<Element>, errors: Vec<ParseError> }`,
`compile()`'s shape changes from a `match` on `Result` to unconditional
field access, but the conversion itself is unchanged:

```rust
pub fn compile(source: &str) -> CompileResult {
    let parsed = mesh_parser::parse(source);
    let mut diagnostics: Vec<mesh_syntax::Diagnostic> = parsed
        .errors
        .into_iter()
        .map(|err| mesh_syntax::Diagnostic {
            severity: mesh_syntax::Severity::Error,
            message: err.message,
            span: err.span,
        })
        .collect();

    let ir = match parsed.ast {
        Some(ast) => {
            let lowered = mesh_semantic::lower(&ast);
            diagnostics.extend(lowered.diagnostics);
            lowered.ir
        }
        None => None,
    };

    CompileResult { ir, diagnostics }
}
```

This confirms and preserves, exactly:

- `ParseError.message` maps to `Diagnostic.message` unchanged;
  `ParseError.span` maps to `Diagnostic.span` unchanged; every
  `ParseError` becomes a `Diagnostic` with `severity: Severity::Error`
  (matching the "On `ParseError`'s severity" framing above — this is
  Pass 4's mapping, not a permanent invariant).
- `mesh-parser` and `mesh-semantic` do not depend on `mesh-compiler` —
  this conversion happens entirely inside `mesh-compiler`, which already
  depends on both (see the verified dependency graph above). No crate
  gains a new dependency to perform it.
- All parser diagnostics (from `ParseResult.errors`) and all semantic
  diagnostics (from `LowerResult.diagnostics`) land in the single
  `CompileResult.diagnostics` list — `mesh_compiler::compile` remains the
  one place that aggregates diagnostics from every stage, unchanged from
  today's aggregation role.
- Diagnostics are preserved even with partial stage output: if `parsed.ast`
  is `Some` but lowering also reports diagnostics, both the parser's and
  the semantic stage's diagnostics appear together in
  `CompileResult.diagnostics`. If `parsed.ast` is `None` (a fatal parse
  failure), lowering never runs, but the parser's diagnostics are still
  present — `CompileResult.diagnostics` is never silently dropped.

`CompileResult`'s own fields (`ir: Option<mesh_semantic::Element>`,
`diagnostics: Vec<Diagnostic>`) are unchanged by Pass 4 — only the glue
that populates them changes, matching today's shape exactly.

Existing tests migrate mechanically: `crates/mesh-parser/tests/parse.rs`
(~36 `.expect(...)`/`.expect_err(...)` sites), `crates/mesh-semantic/tests/lower.rs`,
`crates/mesh-compiler/tests/compile.rs` (~13 sites) all destructure the new
struct instead of a `Result`. No test logic changes — this is pure call-site
mechanics, suitable for a single implementer task.

### `Child::Element` (nested elements)

Add a third variant to the existing `Child` enum in `mesh-syntax`:

```rust
pub enum Child {
    Text(Text),
    Expression(Expression),
    Element(Box<Element>),
}
```

`Box` is required — `Element` contains `Vec<Child>`, so an unboxed variant
makes `Child` infinitely-sized.

Ripple-through (confirmed exhaustively via grep across all four crates —
no other match sites exist):

- `grammar/tree-sitter-mprx/grammar.js`: add `$.element` as a third
  alternative to the `child` rule's `choice(...)`.
- `mesh_syntax::Child`: add the variant (above).
- `mesh-parser`'s child-lowering dispatch: add an `"element"` kind arm
  that recurses into the existing element-lowering function, boxed.
- `mesh_semantic::Child`: mirror with `Element(Box<Element>)` (semantic
  `Element`, IR-side).
- `mesh-semantic`'s child-lowering function: this match is exhaustive
  today (no catch-all) — add the corresponding arm, recursing into
  `lower`.
- Existing test call sites: none use exhaustive matches on `Child`, so
  none break at compile time, but none exercise the new variant either.
  New tests are needed for nested-element parsing and lowering.

### Explicitly deferred: recursion-depth guard

Nested elements introduce a second mutually-recursive lowering path
(`lower_element -> lower_child -> lower_element -> ...`) alongside the
pre-existing, already-parked recursion risk in expression lowering
(deeply nested/parenthesized expressions, flagged at the Pass 3b final
review with no depth limit anywhere in the lowering layer).

Pass 4a does **not** add a depth-limit mechanism. This remains a known,
tracked concern for a later hardening pass — not silently dropped.
Verified via repo-wide search: this repository has no existing
known-issues/deferred-work/backlog file or convention today. Given
that, the spec does not prescribe a specific tracking mechanism:

> **The Pass 4a implementation plan must record the recursion-depth
> limitation in the repository's existing deferred-work/known-issues
> mechanism, if one exists. A local code comment may additionally be
> used where useful. No recursion guard is implemented in Pass 4.**

The underlying concern is unchanged regardless of where it is recorded:
expression lowering (pre-existing, parked at the Pass 3b final review)
and, as of Pass 4a, element lowering (`lower_element -> lower_child ->
lower_element -> ...`) both share the same unguarded-recursion gap.

### Whitespace-only text children — v0.1 policy

MPRX is a UI language, not an HTML-compatibility implementation. Adopt a
deliberately minimal whitespace policy rather than inheriting
HTML/Vue/Svelte whitespace semantics:

> **Whitespace-only text children are formatting and are omitted from the
> semantic model. Text containing any non-whitespace character is
> preserved verbatim — no trimming, no collapsing, no normalization.**

"Whitespace-only" is defined precisely as Rust's standard library
`str::trim().is_empty()` — i.e., Rust's built-in, Unicode-aware
definition of whitespace (`char::is_whitespace`), not a custom or
MPRX-specific character class. This is a deliberate choice to reuse the
standard library's existing, already-correct Unicode handling rather
than inventing a bespoke definition.

**Exact site: `mesh-semantic`'s `lower_child`, not `mesh-parser`'s.**
Per the Change Containment invariant that source fidelity belongs to the
CST unless explicitly promoted (§ "Source fidelity belongs to the CST
unless promoted", below), the AST should stay a faithful structural
mirror of the CST and not itself start making meaning-vs-formatting
judgments. Verified against the current `mesh-parser::lower_child`
(`crates/mesh-parser/src/lib.rs`): it already lowers every `"text"` CST
node into a `Child::Text` unconditionally, with no filtering — that
stays true after Pass 4; `mesh-parser` gains no new whitespace-awareness.
The filter belongs in `mesh-semantic::lower_child`
(`crates/mesh-semantic/src/lib.rs`), which already owns "does this
content mean anything" judgments (the same crate that owns
duplicate-attribute and tag-mismatch meaning-judgments). Concretely,
`mesh-semantic::lower`'s `children: ast.children.iter().map(lower_child).collect()`
becomes `filter_map` instead of `map`, since a whitespace-only text child
now lowers to no `Child` at all rather than to `Child::Text`:

```rust
// mesh-semantic::lower_child, AST -> IR only — mesh-parser is unchanged
fn lower_child(child: &mesh_syntax::Child) -> Option<Child> {
    match child {
        mesh_syntax::Child::Text(text) if text.value.trim().is_empty() => None,
        mesh_syntax::Child::Text(text) => Some(Child::Text(text.value.clone())),
        mesh_syntax::Child::Expression(expression) => {
            Some(Child::Expression(lower_expression(expression)))
        }
        mesh_syntax::Child::Element(element) => Some(Child::Element(Box::new(lower(element)))),
    }
}
```

So: the **AST** (`mesh_syntax::Element.children`) retains every text
node exactly as parsed, whitespace-only or not — no change to
`mesh-parser` at all. Only the **IR** (`mesh_semantic::Element.children`)
omits whitespace-only text children. This was implicit in the prior
revision's "AST/IR" phrasing; this revision makes the AST/IR split, and
which crate performs the filter, explicit.

Examples:

```xml
<div>
    <span>A</span>
    <span>B</span>
</div>
```

produces no text nodes for the indentation/newlines between `<span>`
elements.

```xml
<div>
    Hello <strong>world</strong>
</div>
```

preserves the text child between `<div>` and `<strong>` verbatim exactly
as it appears in the source (including any leading/trailing whitespace
that is part of that same text run, since the run as a whole is not
whitespace-only) and preserves `"world"` verbatim as its own text
child.

```text
"Hello     world"
```

is never collapsed or altered — internal whitespace within a
non-whitespace-only text node is always preserved verbatim.

Explicitly **not** implemented in v0.1: leading/trailing trim of
meaningful text, whitespace collapsing, HTML-style block/inline
whitespace rules, any normalization beyond the single
discard-if-entirely-whitespace rule above.

This is a semantic-IR-only policy, not a lexer, CST, or AST change — the
CST and the AST both retain full source fidelity (including
whitespace-only text) for tooling/source-location/diagnostic purposes;
only the semantic IR omits formatting-only text nodes, per the exact
site described above.

**Action for the Pass 4a implementation plan: document this policy in
`docs/MPRX-SPEC.md` §3, replacing the current "open question, deferred to
Pass 4" note.**

## Pass 4b: Event Bindings + Structural Validation

Depends on Pass 4a being merged (`LowerResult`, `Child::Element` both
need to exist first).

### Event binding grammar / AST

Extend the grammar's element-modifier surface from attributes-only to a
choice between attributes and event bindings:

```text
element_modifier ::= attribute | event_binding
event_binding ::= 'on' '.' identifier '=' expression_block
```

`self_closing_element` and `container_element` both change their
`repeat($.attribute)` to `repeat($.element_modifier)`. `'on'` is used as
a plain string token in the grammar — this coexists with a legal plain
attribute literally named `on` (e.g. `on="x"`) with no ambiguity, since
the two productions diverge at the token immediately following the
shared prefix (`=` continues as `attribute`, `.` continues as
`event_binding`). This is analogous to the technique the grammar already
uses for `boolean_literal`'s `'true'`/`'false'` and `null_literal`'s
`'null'` string tokens coexisting with the general `identifier` rule with
zero `prec`/`conflicts` declarations (verified directly in
`grammar/tree-sitter-mprx/grammar.js` — neither `boolean_literal` nor
`null_literal` carries any precedence annotation).

That existing precedent is suggestive, not proof, for a new token in a
new position (`element_modifier`, not `expression`) — so the
implementation must not assume no `prec`/`conflicts` declarations are
needed by analogy alone. **Grammar acceptance criteria (must be verified
via grammar generation and parser tests, not asserted by design
argument):**

1. `<div on="x" />` — an ordinary attribute literally named `on` — must
   parse as `self_closing_element` with one `attribute` (name `on`,
   value `"x"`).
2. `<div on.click={handler} />` — an event binding — must parse as
   `self_closing_element` with one `event_binding` (name `click`,
   handler `handler`).
3. `<div on="x" on.click={handler} />` — both together on the same
   element — must parse as `self_closing_element` with one `attribute`
   and one `event_binding`, in that source order.

All three must be exercised as parser/grammar tests in the Pass 4b
implementation plan. Only add `prec`/`conflicts` declarations to
`element_modifier`/`event_binding` if the generated parser actually
reports a conflict for one of these three cases — do not add them
preemptively.

AST gets a dedicated type, not folded into `Attribute`:

```rust
pub struct EventBinding {
    pub name: String,
    pub handler: Expression,
    pub span: Span,
}
```

```rust
pub struct Element {
    // ...
    pub attributes: Vec<Attribute>,
    pub event_bindings: Vec<EventBinding>,
}
```

`mesh-semantic`'s IR mirrors this with a span-free `EventBinding { name,
handler }` and `Element.event_bindings: Vec<EventBinding>`, following the
same AST-to-IR mirroring pattern already used for `Attribute`/`Child`.

Rationale for keeping attributes and event bindings as separate fields
(not a unified `Vec<ElementModifier>`): they have distinct semantic
roles — attributes are declarative element/component state, event
bindings are behavioral/event intent — and keeping them separate gives
semantic analysis, validation, codegen, and future tooling a clean
distinction without needing to filter a tagged-union wrapper.

### Structural validation rules

All validation below runs in `mesh-semantic::lower` (see "Validation
location" section) and reports via `LowerResult.diagnostics`.

#### Deterministic diagnostic ordering

Today's codebase has no precedent to follow here directly: verified
against `crates/mesh-compiler/tests/compile.rs`, existing tests only
ever assert `result.diagnostics.is_empty()` or (via the `Err` branch)
exactly one diagnostic — there is no existing multi-diagnostic ordering
convention anywhere in the repo, since `Vec<Diagnostic>` with more than
one element has never existed before Pass 4. This section defines the
rule fresh.

`LowerResult.diagnostics` order is **source traversal order**, produced
by a straightforward depth-first walk that falls directly out of
`lower`'s natural recursive structure — no separate sorting pass is
required or permitted:

1. For the element currently being lowered, diagnostics for that
   element's own duplicate attributes are emitted in the shadowed
   occurrences' source order (see the worked example below), followed by
   diagnostics for that element's own duplicate event bindings, in their
   shadowed occurrences' source order, followed by that element's own
   tag-mismatch diagnostic, if any (there is at most one: an element has
   exactly one close tag to compare).
2. Then, `lower` recurses into the element's `children: Vec<Child>` in
   their existing source order (unchanged from today's `children.iter()`
   traversal). For each `Child::Element(child)` encountered, that child
   element's own diagnostics (computed recursively via steps 1-2) are
   appended next, before moving on to the next child in the `Vec`.
   `Child::Text` and `Child::Expression` children contribute no
   diagnostics under Pass 4b.
3. This composes into one rule: **diagnostics appear in the order their
   underlying source construct appears in a depth-first, pre-order walk
   of the source tree** — a parent element's own diagnostics precede its
   children's, and children's diagnostics appear in the children's source
   order, recursively.

This ordering is a property of the traversal itself, not of any
intermediate data structure — nothing in this design collects
diagnostics into a `HashMap` or `HashSet` at any point (deduplication
below operates on the source-order `Vec<Attribute>`/`Vec<EventBinding>`
directly). **`HashMap`/`HashSet` iteration order must never be allowed to
determine diagnostic order** — any implementation that groups
occurrences by name for the duplicate-detection rule must do so with an
order-preserving structure (e.g. grouping indices while retaining the
original `Vec`'s order, or a linear scan) and must emit diagnostics by
walking that grouping back out in original source order, not in
whatever order a hash-based structure happens to yield.

For duplicate-attribute/duplicate-event diagnostics specifically:
**the diagnostic's span is the shadowed (non-winning) occurrence's own
span**, and diagnostics are ordered by that shadowed occurrence's
position in the source, not by the winning occurrence's position (see
the worked example below). For the tag-mismatch diagnostic: **the span
is the element's own span (`ast.span`)** — i.e., the opening element's
span, since the recovery rule (above) treats the opening tag as
authoritative identity and the diagnostic is fundamentally about that
element, not the close-tag token in isolation.

**Duplicate attributes — exact resolution rule.** The grammar allows
`<div class="a" class="b" />` today (verified: `mesh_syntax::Attribute`
carries no uniqueness constraint, and `mesh_syntax::Element.attributes`
is a plain `Vec<Attribute>` in source order — no uniqueness constraint is
expressible in the CFG either, and none exists there).

Semantic policy: for each attribute name that appears more than once,
the semantic IR's `attributes: Vec<Attribute>` keeps exactly one entry —
the value and span of that name's **final source occurrence** — and
every other (shadowed) occurrence of that name is dropped from the IR
entirely. The surviving entries appear in the IR in order of their own
winning occurrence's original source position (not the position of the
name's first occurrence). Equivalently: filter the source-order attribute
list down to, for each name, only its last occurrence, preserving the
relative order of the surviving entries. (This ordering rule itself is
unchanged from the prior revision — only the worked example and
diagnostic-ordering statement below are new, to make it unambiguous.)

Emit one `Warning`-severity diagnostic per shadowed (non-winning)
occurrence — e.g. `duplicate attribute "class"`, spanning the shadowed
occurrence — not one per winning occurrence and not one aggregate
diagnostic per element. This is not a fatal error — lowering still
produces IR. Per "Deterministic diagnostic ordering" above, these
warnings appear in the shadowed occurrences' own source order.

**Worked example:** `<div class="a" id="x" class="b" id="y" />`. Source-
order attributes: `[class="a" (pos 0), id="x" (pos 1), class="b" (pos 2),
id="y" (pos 3)]`.

- Winning occurrences: `class` → `class="b"` (pos 2, the last `class`);
  `id` → `id="y"` (pos 3, the last `id`).
- Surviving IR, in winning-occurrence source order: `[class="b", id="y"]`
  — `class`'s winning occurrence (pos 2) comes before `id`'s winning
  occurrence (pos 3), so `class="b"` precedes `id="y"` in the IR.
- Diagnostics, in shadowed-occurrence source order: first a `Warning`
  for the shadowed `class="a"` (pos 0), then a `Warning` for the shadowed
  `id="x"` (pos 1) — `class`'s warning precedes `id`'s warning because
  the shadowed `class="a"` occurs before the shadowed `id="x"` in the
  source, independent of the winning entries' relative order.

The identical rule applies to event bindings (below), independently,
within their own `Vec<EventBinding>`.

**Duplicate event bindings.** The identical rule, applied independently
within `event_bindings: Vec<EventBinding>` (its own `Vec`, its own
namespace — never merged with `attributes` for this purpose): two
`on.click={...}` bindings resolve to the value and span of the last
occurrence, in the surviving entries' winning-occurrence source order,
with one `Warning` diagnostic per shadowed occurrence. An attribute and
an event binding never collide with each other (e.g. an attribute named
`click` and `on.click` are unrelated) since `element_modifier` is a
tagged union of two semantically distinct productions, and each of
`attributes`/`event_bindings` is deduplicated only against entries of
its own kind.

**Tag mismatch.** The grammar does not enforce that a `container_element`'s
open and close tag names match — `<div>...</span>` parses successfully
today (verified: `grammar.js`'s `container_element` rule captures the
open tag name as the fielded `name` and the close tag name as a plain,
unfielded `$.tag_name` with no back-reference tying the two together).

Verified gap this reveals: `mesh_syntax::Element` today has only a single
`name: String` field, populated in `mesh-parser::lower_element` from the
open tag's fielded `name` node — the close tag's `tag_name` node is
currently matched by neither the attribute filter nor the child filter
in `lower_element`, so its text is read nowhere and is effectively
discarded during lowering. Since validation must live in
`mesh-semantic::lower` (per the "Validation location" section below) and
`mesh-semantic` only ever sees the already-lowered `mesh_syntax::Element`
— never the raw CST — the AST as it exists today cannot carry the close
tag name forward for `mesh-semantic` to compare it against.

**Required AST addition:** `mesh_syntax::Element` gains one new field to
carry the close tag's text through lowering:

```rust
pub struct Element {
    pub name: String,
    pub closing_name: Option<String>,
    pub attributes: Vec<Attribute>,
    pub event_bindings: Vec<EventBinding>,
    pub children: Vec<Child>,
    pub span: Span,
}
```

**Why `closing_name` exists, and where it stops.** It exists solely
because structural (tag-mismatch) validation runs post-parse, in
`mesh-semantic::lower` — the AST is `mesh-semantic`'s only input, so any
data `mesh-semantic` validates must survive into the AST first. Without
this field, the close tag's text is parsed by the grammar (`grammar.js`'s
`container_element` rule captures it as a bare `$.tag_name` node) but is
read nowhere in `mesh-parser::lower_element` today and is effectively
discarded during lowering — verified directly against the current
`crates/mesh-parser/src/lib.rs` and `crates/mesh-syntax/src/lib.rs`,
which today defines only `pub struct Element { pub name: String, pub
attributes: Vec<Attribute>, pub children: Vec<Child>, pub span: Span }`
with no closing-tag field at all.

`closing_name` is AST-only, scoped narrowly:

- `None` means the element is self-closing (`self_closing_element` — no
  close tag exists in the source to capture).
- `Some(value)` means the element is a container element
  (`container_element`) whose close tag was present, and `value` is that
  close tag's parsed identifier text, captured verbatim as written in
  source (the same `tag_name` token kind — `/[a-zA-Z_][a-zA-Z0-9_-]*/` —
  as the open tag's `name` field, per `grammar.js`).
- Comparison against `ast.name` (performed by Pass 4b's tag-mismatch
  rule) uses exact Rust string equality (`closing != ast.name`) only —
  no case-folding, no Unicode normalization, no namespace-aware
  comparison. Two tag names that differ only in case or Unicode
  normalization form are a mismatch, not a match; MPRX v0.1 has no
  case-insensitive or namespaced tag-name concept (see "Explicitly Out
  of Scope").
- **`closing_name` is AST-only — the Semantic IR does not retain it.**
  The close tag is structural syntax (parse-time bookkeeping for the
  parser and, via this field, for `mesh-semantic`'s validation pass), not
  semantic element data: an element's *meaning* is fully captured by its
  (opening) name, attributes, event bindings, and children, so
  `mesh_semantic::Element` gains no corresponding field. `closing_name`
  is consumed by `mesh-semantic::lower`'s tag-mismatch check and then
  discarded — it does not appear anywhere in `LowerResult.ir`.

This is not new validation logic — it is the minimal data-capture change
needed for the already-approved "tag mismatch is a `mesh-semantic`
concern" decision to be implementable at all, surfaced by verifying the
actual `Element` definition rather than assuming it already retained
this. `mesh-parser::lower_element` is the only place `closing_name` gets
populated, reading the previously-ignored close-tag `tag_name` node.

**Scope placement:** this field addition (`mesh-syntax`/`mesh-parser`
only, no validation behavior) ships as part of **Pass 4a**, alongside
`Child::Element` — both are mechanical AST/lowering additions with no new
validation logic, matching 4a's stated scope. The `Error`-diagnostic
comparison logic that *reads* `closing_name` and reports a mismatch is
the Pass 4b work described below.

**Recovery rule.** When `mesh-semantic::lower` finds `ast.closing_name`
is `Some(closing)` and `closing != ast.name`:

1. Emit an `Error`-severity `mesh_syntax::Diagnostic` identifying both
   the opening name (`ast.name`) and the closing name (`closing`).
2. Continue lowering the element — do not abort or discard it.
3. Use the **opening tag name** (`ast.name`) as the resulting IR
   `Element`'s name — the element's identity is never taken from the
   close tag.
4. The close tag contributes nothing else to the IR; it is only ever a
   structural terminator, matched or not.
5. Do not treat the mismatch as fatal to the whole `LowerResult` —
   `ir` is still `Some(..)` for this element (and any ancestor that
   contains it), consistent with `LowerResult.ir: Option<Element>`
   allowing `Some` alongside non-empty `diagnostics`, the same
   partial-success shape the duplicate-attribute/duplicate-event
   warnings rely on. A caller wanting strict behavior can still inspect
   `diagnostics` for any `Severity::Error` entries and treat the whole
   result as failed itself.

`self_closing_element`s (`closing_name: None`) are never subject to this
check — there is no close tag to mismatch against.

**Malformed event bindings — scope kept minimal.** No separate semantic
validation subsystem for arbitrary malformed `on.*` syntax. Malformed
event-binding *syntax* (e.g. an empty event name, `on.={...}`) is
rejected by the parser as an ordinary parse error, because the grammar's
`identifier` production requires at least one character — there is no
syntactically-valid-but-semantically-malformed case left to define once
the grammar rule above exists. The only Pass 4b semantic validation rule
for event bindings is duplicate detection (above). Do not invent
additional semantic rules for event bindings beyond this without raising
a new design question first.

### Validation location: `mesh-semantic::lower`

Validation (duplicate attributes/events, tag mismatch) runs in
`mesh-semantic`, not `mesh-parser`. This is a boundary-of-responsibility
decision, not a spans-availability workaround — `mesh-semantic::lower`'s
*input* (`&mesh_syntax::Element`) already carries full spans regardless
of the span-free IR it produces, so span-accurate diagnostics need no
special plumbing either way.

The boundary:

- **mesh-parser** answers "is this syntactically valid MPRX?" — unexpected
  tokens, missing `>`, invalid expression syntax, malformed event-binding
  *syntax*.
- **mesh-semantic operates on the parsed tree and determines whether that
  tree makes semantic/structural sense** — duplicate attributes, duplicate
  event bindings, tag-name mismatch, and future name-resolution or
  binding/type validation.

This is deliberately not phrased as "semantic lowering only runs on a
syntactically valid tree" or "only runs when there are zero parser
errors" — verified against today's `compile()` (see "Parser-to-compiler
diagnostic conversion" above), `mesh-semantic::lower` is only invoked
when `ParseResult.ast` is `Some`, which is the actual, narrower
precondition. `ParseResult.ast` can be `Some` even when
`ParseResult.errors` is non-empty in a future parser-recovery pass (see
"On `ParseError`'s severity" above); Pass 4 does not add that recovery,
so today `ast: Some` and `errors: []` coincide in practice, but the
precondition `mesh-semantic` actually depends on — and the one this spec
preserves — is "an AST exists," not "there were no parser errors."

Both duplicate-detection and tag-matching are meaningful-tree questions,
not grammar questions — the grammar accepts both malformed cases fine —
so all non-syntax validation stays in one crate rather than being split
by kind across two.

## Pass 4 Feature Ownership and Removal Surface

Per "Feature removal is a first-class design requirement" above, this
section makes each Pass 4 feature's layer ownership explicit: which
layers own it, which intentionally do not, what each transformation
discards, and what would disappear if the feature were later removed.
This is documentation of decisions already made elsewhere in this spec —
nothing here introduces new behavior.

### Diagnostic plurality (`ParseResult` / `LowerResult` / `Diagnostic`)

- **Owner:** `mesh-syntax` owns `Diagnostic`/`Severity` (the data);
  `mesh-parser` owns `ParseResult`/`ParseError` (parser-local, never
  shared); `mesh-semantic` owns `LowerResult` (semantic-local). The
  shape mirrors an already-established pattern (`CompileResult`).
- **Representation:** exists in `mesh-parser` (`ParseResult.errors`),
  `mesh-semantic` (`LowerResult.diagnostics`), `mesh-compiler`
  (`CompileResult.diagnostics`, aggregated). Does not exist in CST or
  AST/IR — diagnostics describe the tree, they are not part of it.
- **Transformation:** `ParseError` → `Diagnostic` is a lossless 1:1 field
  mapping (see "Parser-to-compiler diagnostic conversion"); intentional,
  documented, deterministic.
- **Ordering:** source-traversal order, `Vec`-based throughout; no
  hash-based structure anywhere in the pipeline (see "Deterministic
  diagnostic ordering").
- **Dependencies:** no new crate; no reverse dependency; `Diagnostic`'s
  home in `mesh-syntax` was the one dependency-direction fix this spec
  required (see "Diagnostic ownership and dependency direction").
- **Removal surface:** if plural diagnostics were later removed (e.g.
  reverted to single-error `Result`), only `ParseResult`/`LowerResult`'s
  shape and `mesh_compiler::compile`'s aggregation loop change — no
  AST/IR representation depends on diagnostic plurality, so nothing
  downstream of diagnostics is affected.

### Nested elements (`Child::Element`)

- **Owner:** `mesh-syntax` owns the `Child::Element(Box<Element>)`
  variant (AST shape); `mesh-parser` owns CST→AST recursion into it;
  `mesh-semantic` owns AST→IR recursion into it (mirrored
  `Child::Element(Box<Element>)` on the IR side too — nesting is
  semantically real, not just syntactic).
- **Representation:** exists at every layer (grammar, CST, AST, IR) —
  this is the one Pass 4 feature that is fully mirrored end-to-end,
  because nesting itself is both a syntactic and a semantic fact.
- **Transformation:** lossless recursive mirror, `Box`ed only because
  `Element` contains `Vec<Child>` (sizing requirement, not a design
  choice).
- **Ordering:** children preserve `Vec` source order at every layer,
  unchanged from today's non-nested traversal.
- **Dependencies:** none beyond existing `mesh-syntax`/`mesh-semantic`
  ownership of `Child`/`Element`.
- **Removal surface:** removing nested elements would mean deleting the
  `Element` variant from `Child` in both `mesh-syntax` and
  `mesh-semantic`, plus the grammar alternative and the two recursive
  match arms — it does not touch attributes, event bindings, or
  diagnostic plurality, none of which depend on nesting existing.

### Whitespace-only text (IR-level omission)

- **Owner:** `mesh-semantic` alone. `mesh-parser`/`mesh-syntax` have no
  awareness of this policy — the AST retains every text node.
- **Representation:** exists in CST and AST (all text, unfiltered); does
  not exist in IR for whitespace-only nodes (omitted, not represented as
  e.g. an empty string).
- **Transformation:** intentionally lossy at AST→IR only, per
  `str::trim().is_empty()`; documented above; deterministic (a pure
  per-node predicate, no ordering dependency).
- **Ordering:** n/a beyond the surrounding `Child` `Vec` order, which
  this feature does not alter — it only removes some elements from the
  iteration, doesn't reorder the rest.
- **Dependencies:** none.
- **Removal surface:** reverting to "preserve all text" touches only
  `mesh-semantic::lower_child`'s one `filter_map` predicate — no AST
  representation change, no grammar change, no other feature's code.

### Event bindings (`EventBinding`, `element_modifier` grammar)

- **Owner:** grammar/`mesh-parser` own the `element_modifier` choice and
  `EventBinding` AST construction; `mesh-semantic` owns duplicate-event
  validation and the IR-side `EventBinding` mirror.
- **Representation:** exists in grammar, CST, AST
  (`Element.event_bindings: Vec<EventBinding>`), and IR (mirrored,
  span-free). Intentionally kept as its own field/type rather than
  folded into `attributes` — a distinct, non-speculative abstraction
  boundary (see "Avoid speculative shared abstractions").
- **Transformation:** structural AST→IR mirror identical in shape to
  `Attribute`'s existing mirror; only lossy in the sense that `Span` is
  dropped, same as every other IR type.
- **Ordering:** `Vec<EventBinding>` preserves source order; deduplicated
  independently of `attributes` (separate namespace, see "Semantic
  namespaces are explicit").
- **Dependencies:** none beyond existing `mesh-parser`/`mesh-semantic`
  ownership boundaries; grammar acceptance criteria (above) gate whether
  any `prec`/`conflicts` declaration is needed — none assumed
  preemptively.
- **Removal surface:** removing event bindings means deleting
  `element_modifier`'s second alternative, `EventBinding` from both AST
  and IR, and the duplicate-event validation rule — attributes,
  nesting, and tag-mismatch validation are entirely unaffected, since
  event bindings share no representation with them beyond the unrelated
  `element_modifier` grammar choice point.

### Structural validation: duplicate attributes / duplicate events / tag mismatch

- **Owner:** `mesh-semantic` exclusively — these are meaningful-tree
  questions, not grammar questions (see "Grammar defines syntax;
  semantic analysis defines language meaning").
- **Representation:** the *conditions* being validated exist in the AST
  (repeated names in `Vec<Attribute>`/`Vec<EventBinding>`;
  `Element.name` vs. `Element.closing_name`). The *validation logic and
  its diagnostics* exist only in `mesh-semantic` — neither the grammar
  nor `mesh-parser` encode any uniqueness or matching constraint (see
  "Required AST addition" and "Duplicate attributes — exact resolution
  rule").
- **Transformation:** shadowed attribute/event occurrences are
  intentionally dropped from IR (last-one-wins); `closing_name` is
  intentionally dropped from IR entirely after the comparison runs (see
  "`closing_name` is AST-only" above) — both are documented, intentional
  losses, not incidental ones.
- **Ordering:** shadowed-occurrence source order for warnings;
  winning-occurrence source order for surviving IR entries; see the
  worked example above.
- **Dependencies:** none beyond `mesh-semantic`'s existing dependency on
  `mesh-syntax`.
- **Removal surface:** removing duplicate-detection removes one
  `mesh-semantic` helper per collection (`attributes`,
  `event_bindings`) and its `Warning` diagnostics — no AST/grammar
  change. Removing tag-mismatch validation removes one `mesh-semantic`
  comparison and its `Error` diagnostic; `closing_name` would then have
  no remaining consumer, at which point *removing the AST field itself*
  becomes a valid, isolated follow-up (touching only `mesh-syntax` and
  `mesh-parser`'s population of it) — it was never referenced by
  anything else, per its AST-only lifecycle stated above.

### AST field lifecycle summary (`mesh_syntax::Element`)

| Field | Disposition | Notes |
|---|---|---|
| `name` | (1) preserved into IR | Element identity, always the opening tag's name. |
| `closing_name` | (2) consumed only during semantic validation, then discarded | New in Pass 4a; read once by the Pass 4b tag-mismatch check; never appears in IR. |
| `attributes` | (1) preserved into IR, transformed | Deduplicated (last-one-wins) during AST→IR. |
| `event_bindings` | (1) preserved into IR, transformed | New in Pass 4b; deduplicated identically to `attributes`, independently. |
| `children` | (1) preserved into IR, transformed | Whitespace-only `Child::Text` entries omitted during AST→IR (new in Pass 4b); `Child::Element` recurses (new in Pass 4a). |
| `span` | (3) retained only for source/diagnostic purposes | Never copied into IR (IR has always been span-free); consumed by `mesh-semantic` to build diagnostic spans, then discarded. |

## Guiding Principle

> Keep MPRX syntactically expressive enough to recover a useful AST/IR,
> keep the semantic model clean and renderer-independent, and make
> semantic validation deterministic without prematurely introducing
> language complexity.

> Adding a feature should have a bounded blast radius, and removing or
> replacing a feature should have a bounded blast radius — see
> "Architecture: Change Containment" above, and each feature's stated
> ownership and removal surface in "Pass 4 Feature Ownership and Removal
> Surface" above.

## Explicitly Out of Scope for Pass 4a/4b

- Recursion-depth guards (tracked as a deferred concern, not fixed here).
- Any whitespace policy beyond the single discard-if-whitespace-only rule.
- Any semantic validation for event bindings beyond duplicate detection.
- Any change to how `mesh-cli` or `mesh-lsp` consume `CompileResult` — its
  shape is unchanged by this pass; only `mesh-parser`/`mesh-semantic`'s
  internal signatures change, and `mesh_compiler::compile`'s own
  signature and `CompileResult`'s fields stay as they are today.
- Splitting `mesh_compiler::compile`'s aggregation logic beyond the thin
  glue described above.
- Any general architecture infrastructure beyond what's stated above:
  no plugin systems, dynamic feature registries, generalized compiler
  pipelines, generic visitor hierarchies, trait-object-heavy extension
  mechanisms, diagnostic code registries, versioned ASTs, migration
  frameworks, feature flags, or compatibility layers. Pass 4 keeps
  today's implementation small; "Architecture: Change Containment"
  above keeps tomorrow's change localized — it is not a request to
  build a framework for every feature MESH might ever have.

Do not expand Pass 4a/4b beyond the decisions in this spec without
surfacing a new architectural question first.

   occurrence's), and the exact diagnostic-emission rule (one `Warning`
   per shadowed occurrence).
3. **Tag-mismatch recovery was underspecified**, and verifying the actual
   `mesh_syntax::Element` definition surfaced a real gap: it has no field
   to carry a close tag's name at all today, so `mesh-semantic` could not
   have validated tag matching as originally written. Added the
   `Element.closing_name: Option<String>` field (Pass 4a, plumbing only)
   and the exact five-point recovery rule (error + continue + open-tag
   identity + close tag is terminator-only + non-fatal to the whole
   result) as Pass 4b behavior.
4. **`ParseError`'s "fatal by construction" framing was too strong** as a
   permanent architectural claim. Reworded to describe Pass 4's parser
   API specifically, leaving room for parser-level recovery/severity in
   a later pass without contradicting this spec.

No previously-approved decision changed: `ParseResult`/`LowerResult`
(not `Result<T, E>`), `Child::Element(Box<Element>)`, the deferred
recursion-depth guard, the whitespace-only-text policy, the dedicated
`EventBinding` type with separate `event_bindings: Vec<EventBinding>`,
and validation living in `mesh-semantic::lower` are all unchanged.

**2026-09-23 (same day) — final determinism/testability review
corrections.** Ten issues found in a final pre-`writing-plans` review, all
fixed without changing any previously-approved decision or expanding
scope:

1. **`closing_name`'s ownership/purpose was implicit.** Made explicit:
   it exists only because tag-mismatch validation runs post-parse in
   `mesh-semantic`; it is AST-only and never appears on
   `mesh_semantic::Element`; `None`/`Some` meaning and exact-string-only
   comparison semantics are now stated explicitly, verified against the
   actual `mesh_syntax::Element`/`grammar.js` definitions.
2. **Diagnostic ordering across multiple/nested diagnostics was
   undefined.** Added an explicit depth-first, pre-order source-traversal
   rule (own diagnostics, then children's, recursively, in source order),
   with an explicit prohibition on `HashMap`/`HashSet` iteration order
   ever determining diagnostic order.
3. **Duplicate-resolution ordering lacked a worked example.** Added the
   exact `<div class="a" id="x" class="b" id="y" />` example showing
   both the surviving-IR order and the diagnostic-emission order
   (shadowed-occurrence source order). No change to the underlying
   last-one-wins rule itself.
4. **Parser-to-compiler diagnostic conversion was described, not
   specified.** Added the exact `ParseError { message, span }` →
   `Diagnostic { severity: Error, message, span }` mapping with real
   field names, verified against `crates/mesh-compiler/src/lib.rs` and
   `crates/mesh-parser/src/lib.rs`, and confirmed diagnostics from both
   stages always land in `CompileResult.diagnostics`, including under
   partial output.
5. **Parser/semantic boundary wording implied a "zero parser errors"
   precondition.** Reworded to "operates on the parsed tree and
   determines whether it makes semantic/structural sense," and stated
   the actual, narrower, verified precondition: `mesh-semantic::lower`
   runs whenever `ParseResult.ast` is `Some`, independent of
   `ParseResult.errors`.
6. **`LowerResult.ir == None` conditions were unstated.** Verified
   today's `lower()` is fully infallible; since every Pass 4b rule is
   recoverable and IR-preserving, stated that Pass 4 never produces
   `ir: None` in practice — `None` remains theoretical/forward-looking
   API surface only, matching `CompileResult`'s shape, without inventing
   a new failure mechanism to justify it.
7. **Whitespace-only classification wasn't tied to a concrete
   definition.** Stated explicitly that it is Rust's standard
   `str::trim().is_empty()` (Unicode-aware via `char::is_whitespace`),
   not a bespoke definition — no change to the preserve/discard rule
   itself.
8. **Recursion-depth tracking prescribed a mechanism the repo doesn't
   have.** Verified via repo-wide search that no known-issues/
   deferred-work convention exists today; relaxed the requirement to
   "use the repo's existing mechanism if one exists; a code comment may
   additionally be used" rather than mandating a specific artifact.
9. **Event-grammar acceptance criteria were argued by analogy only.**
   Added three concrete required parse-test cases (`on="x"` alone,
   `on.click={handler}` alone, both together) that the Pass 4b
   implementation must verify via actual grammar/parser tests;
   `prec`/`conflicts` declarations are now only added if a real
   generated-parser conflict appears, not preemptively.
10. **No explicit guardrail existed against `mesh-syntax` scope creep.**
    Added a constraint: `mesh_syntax::Diagnostic` must stay renderer-,
    compiler-, and parser-agnostic (severity/message/span only), so the
    diagnostic-ownership move in correction round 2 doesn't turn
    `mesh-syntax` into a general shared-types crate over time.

No previously-approved decision changed by this round either — all ten
items clarify determinism and verify claims against the actual
repository; none alter what Pass 4a/4b build.

**2026-09-23 (same day) — architecture-hardening pass (Change
Containment).** Added a formal "Change Containment" architecture
principle and a set of binding compiler architecture invariants (source
order authority, AST field lifecycle, lossy-transformation
justification, CST-vs-IR source fidelity, diagnostics-as-data,
severity-vs-recoverability, grammar-vs-semantics responsibility,
explicit semantic namespaces, and determinism), plus a per-feature
ownership-and-removal-surface breakdown for every Pass 4 feature. This
pass is architecture-hardening, not redesign — it identifies and states,
explicitly, principles this spec's decisions already followed; it
changed no previously-approved Pass 4a/4b behavior. One implementation
detail was newly pinned down (not previously one of the 12 approved
decisions, but left ambiguous by prior revisions): the whitespace-only-
text filter is now stated to run in `mesh-semantic::lower_child`
(AST → IR) rather than in `mesh-parser` (CST → AST) — the AST retains
all text nodes unfiltered; only the IR omits whitespace-only ones. This
follows directly from the new "source fidelity belongs to the CST unless
promoted" invariant and matches the current `mesh-parser::lower_child`
implementation, which already performs no such filtering today.
