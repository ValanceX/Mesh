# MESH v0.1 — Pass 3-5 Outline

Date: 2026-09-22
Status: Draft outline, not an implementation plan
Repo: `mesh`

## Purpose

This is a planning aid, not a bite-sized implementation plan. Passes 3-5's
exact grammar/AST shapes depend on decisions Pass 2 (expressions) actually
makes when implemented — the same reason Pass 1 needed a mid-implementation
fix (`named_child` for whitespace extras) and an unplanned adaptation to the
installed `tree-sitter-cli` version. Writing full TDD-level plans for three
passes ahead of that real experience would risk the same kind of rework.

Each pass below still needs its own brainstorming pass (informal or full,
depending on how much its risks section below reads as "settled" vs.
"genuinely open") and a `writing-plans` cycle before implementation starts.
This document exists so that planning cycle doesn't start from zero — it
carries forward the scope, anticipated file-level changes, and known risks.

See `docs/superpowers/specs/2026-09-21-mesh-v0.1-roadmap-design.md` for the
authoritative Definition of Done wording for each pass, and
`docs/MPRX-SPEC.md` for the authoritative grammar/semantics — several items
this outline originally marked TBD (operator set, precedence, event-binding
token shape, array/object syntax) are now resolved there. This document
only adds pass-sequencing and Rust-API-shape detail underneath both.

## Pass 3 — Full expression model

**Split into two plans (decided 2026-09-22, during Pass 3a brainstorming):**
this pass turned out to be, as anticipated below, too large for one plan.
It's now **Pass 3a** (Unary/Binary/Conditional — the precedence-ladder
operators) and **Pass 3b** (Array/Object/Command/EventValue — the
remaining literal-ish/call-shaped node kinds), each with its own grammar
test + semantic IR fixture DoD. 3b is deliberately deferred until 3a ships
so its Rust type shapes (still open — see `docs/MPRX-SPEC.md` §8) can be
set from real 3a implementation experience rather than fixed
speculatively alongside 3a. The rest of this section describes what was
originally scoped as one "Pass 3"; the subsections below now split it.

**Scope (from the spec):** grammar adds UnaryExpression, BinaryExpression,
ConditionalExpression, ArrayExpression, ObjectExpression, CommandInvocation
— the remaining node kinds from `docs/ARCHITECTURE.md` §5's expression
model, on top of Pass 2's Literal/Reference/MemberAccess.

### Pass 3a — Unary, Binary, Conditional

**Anticipated file-level changes:**
- Grammar: `expression` (currently `choice($.literal, $.reference,
  $.member_access)`) gains four more direct alternatives —
  `$.unary_expression`, `$.binary_expression`, `$.conditional_expression`,
  and a parenthesized-grouping form `seq('(', $.expression, ')')` (no new
  AST node kind for grouping; `mesh-parser` unwraps to the inner
  expression). This stays a **flat** choice, not a cascade of per-tier
  named rules mirroring §5's EBNF nesting literally — `binary_expression`
  is one rule covering every binary operator, disambiguated by a numeric
  `prec.left`/`prec.right` table, the standard tree-sitter idiom for
  operator-precedence grammars (e.g. tree-sitter-javascript's
  `binary_expression`). This is a deliberate deviation from transliterating
  §5's ladder rule-for-rule: nesting a named rule per tier (as originally
  sketched here) would make even `{user}` parse through ~8 always-present
  wrapper nodes (`conditional_expression` → `logical_or_expression` →
  ... → `primary_expression`) with no operator anywhere in the source,
  since tree-sitter doesn't inline a named rule's single-alternative
  pass-through case the way the EBNF's `(...)? ` / `(...)*` suffixes
  imply. The flat form matches how `expression` already behaves today
  (wraps only what's actually there) and keeps `mesh-parser`'s dispatch a
  single flat `match node.kind()`, same shape as the existing one, just
  with more arms. Precedence numbers, highest (binds tightest) to lowest,
  matching §5's ladder: unary → multiplicative → additive → relational →
  equality → `&&` → `||` → conditional. Unlike the nested-tier version,
  these numbers are **required for correctness here**, not defensive —
  `binary_expression`'s alternatives are genuinely LR-ambiguous without
  them (e.g. `a + b * c`: after parsing `a + b` and seeing `*`, the
  parser must know whether to reduce the `+` first or keep shifting into
  `*`'s operand — that's exactly what the prec comparison resolves).
  `conditional_expression` additionally needs `prec.right` for the
  dangling-`:`-style ambiguity in nested ternaries (`a ? b ? c : d : e`).
  This is genuinely new grammar technique for this codebase — Pass 2's
  `member_access` only had one operator (`.`), never needed `prec` or
  parenthesization. Trust `tree-sitter generate`'s conflict output over
  this plan's predictions if the two disagree, same as Pass 1/2's
  grammar tasks.
- Grammar: `number_literal`'s regex loses its leading `-?` (see
  `docs/MPRX-SPEC.md` §2's revised `number` token) — `/[0-9]+(\.[0-9]+)?/`
  instead of `/-?[0-9]+(\.[0-9]+)?/`. Negative numeric literals now parse
  as `unary_expression`'s `-` applied to a `number_literal`, not a signed
  token — resolves a real ambiguity, not a style preference.
- `mesh-syntax`: extend the `Expression` enum with three new variants —
  `UnaryExpression{operator: UnaryOperator, operand: Box<Expression>,
  span}`, `BinaryExpression{operator: BinaryOperator, left: Box<Expression>,
  right: Box<Expression>, span}`, `ConditionalExpression{condition,
  consequent, alternate: Box<Expression>, span}` — plus `UnaryOperator
  {Not, Negate}` and `BinaryOperator{Mul, Div, Mod, Add, Sub, Lt, Le, Gt,
  Ge, Eq, Ne, And, Or}`.
- `mesh-parser`: lowering for each new node kind; operator-token-to-enum
  mapping. One existing Pass 2 test needs its expectation rewritten, not
  just extended: `parses_a_negative_decimal_number_literal_expression_attribute`
  (`{-3.5}`) currently expects `Literal::Number("-3.5")` and must expect
  `Unary{Negate, Literal::Number("3.5")}` instead, per the `number` token
  change above. Its `mesh-compiler` integration-test analogue, if one
  exists, needs the same update.
- `mesh-semantic`: mirror the three new `Expression` variants (span-free,
  same pattern Pass 2 established) — but `UnaryOperator`/`BinaryOperator`
  are reused directly from `mesh-syntax` rather than redeclared, since
  they carry no span to strip (see `docs/MPRX-SPEC.md` §8's note).
- `mesh-compiler`: no signature changes expected — still structural-only,
  same reasoning as Pass 2.

**DoD (from the spec):** each of the three node kinds has a grammar test +
a semantic IR fixture — no single canonical integration example required
yet.

### Pass 3b — Array, Object, Command, EventValue (planning started 2026-09-22, after 3a shipped)

**Anticipated file-level changes:**
- Grammar: `expression`'s `choice` gains four more direct alternatives —
  `$.array_expression`, `$.object_expression`, `$.command_invocation`,
  `$.event_value` — following the same flat-alternative style Pass 3a
  already established (no precedence table needed here: none of these
  four compete with each other or with 3a's operators for the same input
  shape, so no `prec` is required anywhere in this pass). `array_expression`
  and `object_expression` both use the `optional(seq(item, repeat(seq(',',
  item)), optional(',')))` shape for comma-separated-with-trailing-comma
  lists (matching §5's EBNF `(x (',' x)* ','?)?` exactly); `command_invocation`'s
  argument list deliberately omits the trailing-`,'?`  — §5's EBNF has no
  trailing comma for command arguments, unlike arrays/objects, and that's
  not an oversight to "fix" for consistency, it's what the spec says.
  `object_member`'s `key` field is `choice($.identifier, $.string)`, its
  `value` field is `$.expression` — both fielded, since (unlike array
  elements/command arguments) each `object_member` is a single-slot child
  read via `child_by_field_name`, not a repeated same-kind sibling list.
  `event_value` is a **single atomic regex token**
  (`/\$[a-zA-Z_][a-zA-Z0-9_]*/`), not a `seq('$', $.identifier)` grammar
  rule — see `docs/MPRX-SPEC.md` §2's new note for why (a structural `seq`
  would let Tree-sitter's automatic whitespace-insertion between tokens
  accept `$ event` with a space, contradicting `event_value`'s placement
  in §2's *lexical* grammar). `mesh-parser`'s `lower_event_value` strips
  the leading `$` from the token text rather than reading a separate
  field, since there is no separate field — this is the one node kind in
  this pass without a `child_by_field_name` extraction step.
- `mesh-syntax`: `ArrayExpression{elements: Vec<Expression>, span}`;
  `ObjectKey{Identifier(String), String(StringLiteral)}`,
  `ObjectMember{key: ObjectKey, value: Expression, span}`,
  `ObjectExpression{members: Vec<ObjectMember>, span}`;
  `CommandInvocation{command: String, arguments: Vec<Expression>, span}`;
  `EventValue{name: String, span}` (grammar is general per §5's lexical
  rule, only `$event` is semantically meaningful in v0.1) — these shapes
  are now fixed in `docs/MPRX-SPEC.md` §8, decided during Pass 3b's own
  brainstorm rather than left provisional.
- `mesh-parser`: lowering for each new node kind, following the same
  `missing_expression`-reuse pattern Pass 3a established for any
  `Expression`-typed field fallback. Two field-fallback conventions,
  applied deliberately rather than uniformly (a direct lesson from Pass
  3a's post-merge rust-skills audit, which found `.unwrap_or(<arbitrary
  operator variant>)` was the wrong call for a closed enum with no
  harmless default): plain `String` fields (`command`, `EventValue.name`)
  keep the file's existing `.unwrap_or_default()` convention (an empty
  string is already a visibly-wrong, harmless sentinel, same spirit as
  `Reference{name: String::new()}`); `ObjectKey`'s fallback is the same
  kind of harmless sentinel (`ObjectKey::Identifier(String::new())`) for
  the same reason — unlike `UnaryOperator`/`BinaryOperator`, `ObjectKey`
  has no "every variant looks equally real" problem, since an empty
  identifier key is obviously bogus on inspection. `.kind()` dispatch
  (`lower_object_key`'s `identifier`/`string` match) uses `unreachable!()`
  like every other closed-set kind-dispatch already in the file — no new
  exception needed there.
- `mesh-semantic`: mirror `ArrayExpression` as `Array(Vec<Expression>)`,
  `ObjectExpression` as `Object(Vec<ObjectMember>)` with an IR-local
  `ObjectMember{key: String, value: Expression}` (`ObjectKey` flattens to
  a plain `String`, unlike the operator enums reused verbatim in 3a,
  since its two variants carry a span on one side and are semantically
  equivalent once lowered — see `docs/MPRX-SPEC.md` §8's note),
  `CommandInvocation` as `Command{command, arguments}`, `EventValue` as
  `EventValue(String)`. Variant style follows Pass 3a's own precedent:
  single-field variants stay tuple-style (`Array`, `EventValue`, matching
  `Literal`/`Reference`), multi-field variants use named fields (`Command`,
  matching `MemberAccess`/`Unary`/`Binary`/`Conditional`).

**Object-literal ambiguity — resolved, not just flagged:** `docs/MPRX-SPEC.md`
§5 adopts JSX's own resolution: `object_expression` (`{key: value}`) needs
doubled braces when used as an attribute/child value —
`data={{ key: "value" }}` — because the outer `{}` is `expression_block`
and the inner `{}` is the object literal itself. Traced through by hand:
`object_expression` is only reachable as an `expression` alternative,
never as a bare `attribute_value` (that's still exclusively `string |
expression_block`), so `data={{ k: "v" }}` unambiguously nests — no
`prec`/`conflicts` needed. The grammar corpus should still test this
explicitly (proving the nesting, not just asserting it), **and** should
test the negative case: `data={ k: "v" }` (single brace) must be
*rejected* — `k` parses as a bare `reference`, then `:` has no valid
continuation without a preceding `?`, so `mesh_parser::parse` returns
`Err`. That rejection test is the one that actually proves the
doubled-brace requirement is load-bearing, not just documented.

**DoD (from the spec):** each node kind has a grammar test + a semantic IR
fixture — no single canonical integration example required yet.

## Pass 4 — Bindings, structure, and errors

**Scope (from the spec):** grammar adds `on.eventName={...}` binding
syntax (now formalized: `docs/MPRX-SPEC.md` §4 —
`'on' '.' identifier '=' expression_block`, its own rule rather than
reusing `member_access`), nested elements/children, multiple attributes
(already trivially true via `repeat($.attribute)`, so this item is really
about nested children). `mesh-semantic` adds structural validation:
duplicate attributes, mismatched open/close tags, malformed `on.` bindings
— as diagnostics, not panics.

**Anticipated file-level changes — this is the highest cross-cutting-risk
pass in the whole roadmap:**

- **Children model change (narrower than originally scoped, still
  breaking):** Pass 2 already changes `Element`'s children from `Vec<Text>`
  to `Vec<Child>` where `Child = Text(Text) | Expression(Expression)` — see
  `docs/MPRX-SPEC.md` §3, which puts expression-children in Pass 2 rather
  than here (`<text>{user.name}</text>` is a content-position expression,
  not a nested element, and doesn't need to wait for this pass). What Pass
  4 actually adds to the `Child` enum is just one more variant,
  `Element(Box<Element>)` — still ripples through `mesh-syntax`,
  `mesh-parser`, `mesh-semantic`, `mesh-compiler`, but it's one variant
  addition to an enum that already exists by this point, not the whole
  enum's introduction from scratch.
- **Diagnostic-plurality change (breaking, ripples everywhere):** flagged
  explicitly by the Pass 0-1 final whole-branch review. Today,
  `mesh_parser::parse` returns `Result<Element, ParseError>` (zero or one
  error) and `mesh_semantic::lower` is infallible. Structural validation
  needs *multiple* diagnostics from *both* parsing and lowering. Likely
  shapes to evaluate as real options (not decided here): `parse` returning
  `(Option<Element>, Vec<ParseError>)` instead of a `Result`; or keeping
  `Result` but making the error variant hold `Vec<ParseError>`; `lower`
  changing from `-> Element` to `-> (Element, Vec<Diagnostic>)`.
  `mesh-compiler::compile`'s diagnostic aggregation then needs to merge
  parser + semantic diagnostics into one list instead of today's
  hardcoded 0-or-1.
- Grammar: the `event_binding` rule from `docs/MPRX-SPEC.md` §4 alongside
  `attribute` in `element_modifier`; `child` gaining an `element`
  alternative (`child ::= text | expression_block | element`, per §3 — the
  first two already exist from Pass 2, only `element` is new here).
- `mesh-semantic`: this is where the structural-validation *logic* itself
  gets written for the first time (Pass 1-3 only ever built representations,
  never validated them) — duplicate-attribute detection, open/close tag
  name matching (explicitly deferred from Pass 1's `mesh-parser` task),
  malformed-binding detection.

**Key risk:** two independent breaking type/signature changes (children
model, diagnostic plurality) landing in the same pass, each touching every
crate in the pipeline. This pass should get a full brainstorming cycle with
2-3 concrete architecture options presented and compared — not just an
outline — before it's planned, given the risk level. Consider whether the
children-model change and the diagnostics-model change can be sequenced as
two separate plans within this pass rather than one large one.

**DoD (from the spec):** a fixture corpus of malformed MPRX produces
correct diagnostics with accurate spans, not panics.

## Pass 5 — Canonical example and polish

**Scope (from the spec):** the full `user-card.mprx` example from
`docs/ARCHITECTURE.md` §3/§5 (`<user-card user={user} compact={layout.compact}
on.select={selectUser($event)} />`) parses and checks clean; diagnostic
rendering polished to rustc-style (source snippet + caret); example +
fixture corpus committed under `examples/`, with an integration test —
directly mirroring Pass 1's Task 8 pattern.

**Anticipated file-level changes:**
- No new grammar/AST node kinds expected — this pass is integration and
  polish, contingent on Pass 2 (expressions), Pass 3 (conditional
  expressions, if the fuller documented examples like
  `size={compact ? "sm" : "md"}` get included in the canonical example),
  and Pass 4 (`on.select` bindings) all already working.
- `mesh-compiler`: diagnostic rendering polish — a `render_diagnostic(source,
  diagnostic) -> String` producing a source snippet + caret, replacing the
  current bare `error: {message} ({start}..{end})` format. This piece is
  genuinely self-contained and doesn't depend on Pass 3/4's unresolved
  design questions — it could plausibly be planned and built earlier or in
  parallel if there's ever a reason to.
- `examples/` + fixture corpus + `mesh-cli` integration test, same shape as
  Pass 1's Task 8.

**Key risk:** mostly integration risk (do Pass 2-4's independently-built
pieces actually compose on the real canonical example), not new design
risk. The lowest-risk of the three outlined passes.

**Rough size:** smallest of the three, likely comparable to Pass 1's Task 8
alone plus the diagnostic-rendering piece.

## What Pass 2 already resolved that these passes build on

`docs/MPRX-SPEC.md` is now the source of truth for all of this (this
section just indexes it). Pass 2's plan
(`docs/superpowers/plans/2026-09-22-mesh-v0.1-pass-2-expressions.md`)
implements:

- `mesh_syntax::Expression` / `mesh_semantic::Expression` as enums with
  `Literal`/`Reference`/`MemberAccess` variants — Pass 3 extends these same
  enums with more variants rather than redesigning them.
- The `tag_name` (hyphens allowed, element names only) vs. `identifier`
  (no hyphens, everything else) token split from §2 — Pass 3's binary `-`
  operator is exactly why this split exists; confirm it's actually in
  place before assuming it.
- `Element.children: Vec<Child>` where `Child = Text | Expression` — Pass 4
  adds the third variant, `Element`, to this already-existing enum rather
  than introducing it from scratch (see the revised Pass 4 section above).
- String escape decoding and Boolean/Null literals, alongside String/Number
  — so `Literal` already has four variants by the time Pass 3 needs to
  reference it, not two.

Confirm all of the above actually shipped as described before assuming it
in Pass 3/4 planning — this is what Pass 2's plan intends, not yet what's
built.
