# MESH v0.2 — Outline

Date: 2026-09-24
Status: Draft outline, not an implementation plan. It has been revised
twice after architectural review.
- Decisions D1–D17 below are **settled** and each pass's plan must follow
  them.
- The few genuinely open items are listed at the end of "Open decisions".
  None of them is architectural.
- Nothing here is a Rust API or a file-level design; that belongs to each
  pass's plan.

Repo: `mesh`

## Where v0.1 left off

v0.1.0 (tagged 2026-09-24) is a walking skeleton. MPRX goes through the
whole native pipeline, from grammar to parser to AST to Semantic IR, with
structural validation and rustc-style diagnostics. What it checks is
*shape*, not *meaning*. `<user-card user={usr} />` passes. Every syntax
error is reported at `1:1`. The Semantic IR carries no source spans.

The v0.1 roadmap's "After v0.1" section ranked the next candidates:
component-model type checking, then `mesh-lsp`, then WASM + npm. This
outline follows that ranking. It also folds in v0.1's known limitations.

## Theme

**v0.2: checked against a component model.** `mesh check` goes from
"is this well-formed MPRX?" to "does this UI make sense for these
components?". Every component, prop, event, reference and command is
resolved against a declared model, and every error points at the exact
mistake.

This is the step that makes the core pitch true. Generated UI that
references something that doesn't exist, or passes the wrong kind of
value, gets rejected before it renders (see `docs/ARCHITECTURE.md`,
"Static verification" and "Built for generated UI").

## Goals

- Syntax errors point at the mistake, not at `1:1`.
- A MESH-owned, versioned, language-neutral **component manifest**, with
  structured JSON types, that the compiler receives as input.
- Name and interface resolution, plus a small type system, checked against
  that manifest. One explicit compatibility relation is used by every
  check.
- Diagnostic-granular source spans on the Semantic IR.
- Diagnostics with stable, machine-readable codes, and a JSON output
  format for pipelines that feed errors back to a generator.
- No semantic regressions: input checked without a manifest stays
  semantically compatible with v0.1 (D17).

## Non-goals (v0.2)

- `mesh-lsp`. It is the natural v0.3, once spans, types and coded
  diagnostics exist to serve.
- WASM build and the `packages/` npm wrappers (v0.3 or v0.4).
- Reading NEXUS's TypeScript `Component.define` directly. MESH never
  depends on NEXUS (see D1).
- **New MPRX syntax of any kind.** The language stays exactly v0.1's MPRX.
  This includes:
  - slots and control flow (`if`/`each`)
  - comments, optional chaining, subscripts
  - a presence test or an `undefined` literal
  - type annotations
  - additional operators

  v0.2 is purely about checking the existing language.
- **Type-system features beyond D5.** In particular:
  - unions, intersections, and nullable types separate from absence
  - `undefined`
  - generics beyond `list<T>`, and generic components
  - function types, overloads, inheritance, interfaces, constraints
  - nominal typing
  - recursive named types
  - open records, width subtyping, index signatures
  - implicit coercions, control-flow narrowing, and inference beyond
    D15's expression typing
- A state system. The manifest declares names in scope; it says nothing
  about where their values come from or how they change.
- Implicit or framework-provided names in expression scope (D8).
- A serialized IR format, formatter, rename, completion.
- Checking element children against the model. That needs slots, which
  are deferred.

## Definition of Done

**The examples pass.**
- With `examples/components.json` declaring the components the examples
  use, `mesh check --model examples/components.json
  examples/users-page.mprx` reports no errors.
- `examples/user-card.mprx` is a usage snippet rather than the `user-card`
  template, so its root is a `<user-card>` instance. It is checked with an
  explicit `--component` naming a manifest component whose scope and
  commands provide `user`, `layout` and `selectUser`, and it reports no
  errors.

**Semantic mistakes are caught precisely.** Each mistake in a fixture
corpus produces the right **diagnostic code**, at the narrowest span that
identifies it (D11). The corpus has one fixture per code in D14's
catalogue.

**Conformance fixtures pin the semantics.** At minimum:

*Requiredness and absence:*
- `compact={layout.compact}`, where `layout` has field `compact?:
  boolean`, so the expression is `boolean?`:
  - passes against a prop declared `compact: boolean?` or
    `compact?: boolean?`
  - fails with `type-mismatch` against `compact?: boolean`
- Omitting a prop declared `p: T?` fails with `missing-required-prop`.
- `p={null}` against `p: string?` fails with `type-mismatch`, because
  `null` is a value, not absence.

*`any`:*
- A value of type `any` passes against `p: string`.
- A value of type `any?` fails with `type-mismatch` against `p: string`,
  and passes against `p: string?`.
- A value of type `string?` fails with `type-mismatch` against `p: any`,
  and passes against `p: any?`.

*Equality:*
- `{name == 1}`, where `name: string`, fails with `no-common-type`.

*Records:*
- An object literal with a key the expected record doesn't declare fails
  with `unknown-field`, at the key.

*Other types:*
- `size={1}` against `size: string` fails with `type-mismatch`, pointing
  at `1`.

**Syntax errors are located.** Every v0.1 syntax-error fixture renders at
the mistake's line and column.

**v0.1 compatibility (D17).** Without `--model`:
- every v0.1 pass fixture still passes;
- every v0.1 fail fixture still fails, with the same severity and exit
  status.

Their expected-output files are regenerated for codes and locations.

**JSON diagnostics.** `--format json` exposes each diagnostic's code, and
no consumer needs to parse message text.

## Open decisions (brainstorm before planning)

D1–D17 are settled. Each records the decision, the reason, and the
consequences a plan must respect. The genuinely open items, none of them
architectural, are listed at the end of this section.

### D1. The component model is a MESH-owned manifest

- MESH defines and owns a declarative **component manifest**, and the
  compiler reads only that.
- MESH does not depend on NEXUS. NEXUS, or any other tool, may generate
  the manifest later.
- The manifest is the stable contract between the outside world and the
  compiler. It describes component *interfaces* only, not a NEXUS API
  representation.
- It carries `"version": 1` from day one. `version` identifies the **MESH
  manifest schema** version, not the version of NEXUS, PORT, or any
  component library.

Rejected alternatives:
- Parsing TypeScript. It couples MESH to NEXUS and needs a TS front end.
- Declaring the model inside `.mprx`. MPRX stays UI-only.

### D2. The manifest is JSON, with structured types and a JSON Schema

**Format:**
- The manifest is loaded through `serde` and `serde_json`, the workspace's
  first non-trivial dependencies.
- JSON is the machine-generated interchange format. TOML is not
  introduced for hand-editing convenience.
- A published JSON Schema validates the whole manifest, types included.

**Types are structured JSON values, not a type-string mini-language.**
Every type is an object with a `kind`:
- JSON Schema can validate every type directly.
- There is no second parser and no hidden language inside the manifest.
- NEXUS and other tools generate and inspect data rather than syntax.
- Future variants are added as new `kind`s.

**The set of `kind`s is closed** and matches D5 exactly:

| `kind` | Other properties | Meaning |
|---|---|---|
| `string`, `number`, `boolean`, `null`, `any` | none | Primitive types, plus `any`. |
| `list` | `element`: a type | `list<T>` |
| `record` | `fields`: name → field declaration | A record. |
| `named` | `name`: a type name | A reference to a top-level named type. |
| `optional` | `type`: a type | `T?` |

**A field declaration** is `{ "type": <type>, "required": <bool> }`.
- The same shape is used for props and record fields, so D5's
  requiredness rules apply identically to both.
- `required` has no default and must always be written.

**Other manifest entries:**

| Entry | Shape |
|---|---|
| Top-level `types` | name → type |
| Component `scope` | name → type |
| Event | an optional `payload` type |
| Command | an ordered `parameters` array of `{ "name", "type" }` |

`void` and `nothing` are not `kind`s. A manifest can't write them.

Illustrative only; Pass 3 finalises the exact property spelling with the
JSON Schema:

```json
{
  "version": 1,
  "types": {
    "User": { "kind": "record", "fields": {
      "name":   { "type": { "kind": "string" }, "required": true },
      "avatar": { "type": { "kind": "string" }, "required": false }
    } }
  },
  "components": {
    "user-card": {
      "props": {
        "user":    { "type": { "kind": "named", "name": "User" }, "required": true },
        "compact": { "type": { "kind": "boolean" }, "required": false }
      },
      "events":   { "select": { "payload": { "kind": "named", "name": "User" } } },
      "commands": {},
      "scope":    {}
    }
  }
}
```

**Duplicate JSON keys.** Names are JSON object keys, so the loader rejects
a duplicate key in any object as a manifest duplicate-name error. Many
JSON parsers silently keep the last duplicate; MESH doesn't.

### D3. One `.mprx` file is the template of one component

- A file's references resolve against *that* component's scope, and its
  commands against *that* component's commands.
- Every element in the file, the root included, is an **instance** of a
  manifest component. Its props and events are checked against that
  component.
- **Component identity is a compiler input, not a filesystem concern.**
  - The compiler receives the resolved component name through its compile
    options, alongside the manifest.
  - The compiler never looks at file names.
  - The CLI may infer the name from the file stem (`user-card.mprx` →
    `user-card`), and `--component <NAME>` overrides that.
- If the resolved name isn't in the manifest, that's a configuration
  error, reported before any MPRX checking.

### D4. No built-in elements

- `page`, `text`, `button`, `avatar` and every other tag are components
  declared in a manifest. PORT may ship a manifest for its primitive set
  later.
- MESH understands component interfaces, not renderer-specific primitive
  semantics. This keeps it renderer-independent.

### D5. The type system, absence, and requiredness

The type system is small and structural.

**Types a manifest can write** (D2 gives their JSON form):

| Type | Meaning |
|---|---|
| `string`, `number`, `boolean` | Primitive values. |
| `null` | The explicit value `null`. It is an ordinary value with its own type. It is **not** absence. |
| `any` | An unknown **present** value. It is the escape hatch for partially typed models (D9). It does not include absence; that's `any?`. |
| `list<T>` | A list whose elements are all `T`. |
| records | A set of named fields. Each field has a type and its own requiredness. Records are exact (D9). |
| named type references | A name defined in the manifest's `types`. |
| `T?` | **A value of type `T` that may be absent.** |

**Named types are aliases.** A named reference means exactly its
definition, and compatibility is structural (D9). There is no nominal
typing.

Named type definitions may not be recursive, directly or indirectly. That
is a manifest error, and it keeps every check finite.

**Absence** is a MESH language concept: "there is no value here".
- `T?` means "`T`, or absent". It does **not** mean nullable. `null` is a
  value, and absence is the lack of one.
- So, for example, `string?` accepts a string or absence. It does not
  accept `null`.
- MESH doesn't tie absence to a runtime representation such as
  JavaScript `undefined`. How a runtime represents it is that runtime's
  business. `undefined` is not added to the type system.
- An optional type directly wrapping another optional type (`T??`) is a
  manifest error, to keep manifests canonical.
- Absence is orthogonal to every other type, `any` included. That's why
  `any?` and `any` differ.

Consequences, accepted for v0.2:
- "a string or null" is not expressible without `any`, because there are
  no unions.
- MPRX has no presence test, so a `T?` value can only flow into a context
  that accepts `T?` (or `any?`).
- The only source of absent values is the manifest, through `T?`-typed
  scope names, fields and payloads. MPRX has no literal for absence.

**Requiredness belongs to the declaration, not the type.** It applies
the same way to props and record fields:

| Declaration | May be omitted? | If supplied, the value must satisfy |
|---|---|---|
| `p: T` | no | `T` |
| `p?: T` | yes | `T` |
| `p: T?` | no | `T?` (the value may be absent) |
| `p?: T?` | yes | `T?` |

Consequences:
- Omitting `p: T?` is `missing-required-prop`. Requiredness and
  absence are independent.
- Supplying a `T?`-typed expression to `p?: T` is a `type-mismatch`.
  Optional declaration does not make the *value* optional.

**Invariant: requiredness is erased on read.** Requiredness constrains
whether a field must be supplied. `T?` constrains whether the resulting
value may be absent. Field access exposes only the value-level
possibility, so requiredness is not represented in the resulting
expression type.
- When a declared field is read as an expression (member access on a
  record), the resulting type describes the values that may be observed,
  not whether the declaration was required.
- `f?: T`, `f: T?` and `f?: T?` all read as `T?`. `f: T` reads as `T`.
- Requiredness matters in exactly two places:
  - checking that required props are supplied;
  - comparing record *declarations* for assignability (D9 rule 8).

The four declarations stay distinct in records and prop interfaces;
only the *read* type is shared. There is no further optionality concept.

**Internal types**, which a manifest can never write:
- `void`: the result of a command invocation (D10). It is compatible with
  nothing, not even `any`, and has no `join`.
- `nothing`: the element type of the empty array literal `[]`. It is
  assignable to every type, so `[]` fits any `list<U>`.

No other internal types exist.

### D6. Checks run on the Semantic IR, which carries spans directly

- Source spans are added to the Semantic IR, and name resolution and
  type checking run on it, because the IR is what consumers get and what
  `mesh-lsp` will serve.
- Spans are **plain fields on IR nodes**, not a generic `Spanned<T>`
  wrapper around the whole IR, unless a pass plan finds a compelling
  reason otherwise.
- This breaks the IR's Rust types. The CHANGELOG must say so. Tests keep
  comparing IR through a span-insensitive helper.

### D7. Errors only; fail closed

- Everything new in v0.2 is an **error**: every unknown or missing
  construct, every type mismatch, every invalid use of a command or
  `$event`.
- v0.2 adds no warnings. v0.1's two existing warnings (duplicate attribute
  and duplicate event binding) are unchanged.
- Generated UI fails closed. `any` and `any?` are the only escape hatches
  for partially typed models.

### D8. The manifest's component shape and expression scope

A component declaration has five parts. Each serves one purpose:

| Part | Used when… | Contents |
|---|---|---|
| **name** | always | The component's identity: a tag name. |
| **props** | an instance appears in *another* template | Public inputs: field declarations (D2, D5). |
| **events** | an instance appears in another template with `on.<name>` | Name, plus an optional payload type. |
| **commands** | checking this component's *own* template | Name, plus ordered, typed parameters. Every parameter is required and the arity is exact. Commands return `void` (D10). |
| **scope** | checking this component's own template | The names an expression may reference, each with a type. |

**Invariant: scope is the complete lexical expression environment.**
- A reference resolves against the template component's `scope` and
  nothing else.
- Props are *not* implicitly in scope. If a template can see a prop's
  value, the manifest lists that name in `scope`, and a generator such as
  NEXUS decides that.
- There are no global, framework-provided or convenience names.
- `$event` is not a scope binding. It's a special value with its own
  rules (D10).
- The resolver doesn't know or care whether a scope name is backed by a
  prop, state, a local, or anything else. The manifest says nothing about
  state.
- Props, events, commands and scope are separate namespaces, because each
  appears in a syntactically distinct position:
  - `name=` for props
  - `on.name=` for events
  - `name(...)` for commands
  - a bare `name` for scope

  Sharing a name between them is allowed.
- The manifest's top-level named `types` are shared by all components.

### D9. One compatibility relation: `is_assignable(actual, expected)`

**Every contextual check uses this single relation.** So will future LSP
features. It covers:
- prop values
- command arguments
- `$event` against the payload type
- conditions
- operator operands

No checker contains its own compatibility logic.

**The rules.** Named references are expanded first. The first matching
rule decides.

1. Either side is `void` → **fail**, even against `any`. (`void` never
   reaches here in practice, because D10 rejects misplaced commands first.
   The rule is for completeness, and it comes first so that `any` can't
   absorb `void`.)
2. **Optionality is checked first, for every type, `any` included.**
   - `expected` is `U?`:
     - if `actual` is `T?`, the result is `is_assignable(T, U)`;
     - otherwise, the result is `is_assignable(actual, U)`.

     A present value satisfies "may be absent".
   - `expected` is not optional and `actual` is `T?` → **fail**, because
     the value may be absent. This is a `type-mismatch`, and its message
     says why.

   Beyond this rule, neither side is optional.
3. `expected` is `any` → pass.
4. `actual` is `any` → pass. `any` is deliberately unchecked against the
   value's type. That's the escape hatch. It is never unchecked against
   *absence*.
5. `actual` is `nothing` → pass.
6. Both primitive (`string`, `number`, `boolean`, `null`) → pass iff
   they're the same type. There are no coercions, so `null` is compatible
   only with `null` (and `any`).
7. `list<T>` → `list<U>`: pass iff `is_assignable(T, U)`. This is
   covariant, which is sound because MPRX values are never mutated.
8. record → record. This compares **declarations**, so requiredness
   counts here, unlike on read (D5). It passes iff **all** of the
   following hold:
   - every field declared *required* in `expected` is declared *required*
     in `actual`, and its declared type is assignable;
   - every field declared *optional* in `expected`, if declared in
     `actual` (required or optional), has an assignable declared type;
   - `actual` declares **no field that `expected` lacks**.

   So `f?: T` and `f: T?` are not interchangeable in either direction,
   even though both read as `T?`:
   - `f?: T` against expected `f: T?` fails the first condition.
   - `f: T?` against expected `f?: T` fails the second, because
     `T?` → `T` fails.
9. Anything else → **fail**.

So `any` → `T` passes, `any?` → `T` fails, and `any?` → `T?` passes.
Likewise `T?` → `any` fails and `T?` → `any?` passes.

**Records are exact, deliberately.** There is no width subtyping and no
open record.
- Object-literal checking is deterministic.
- A field the component model doesn't declare is never silently accepted,
  whether it's a typo or an invention by a generator.
- This is a v0.2 constraint, not an oversight. Shared named types are how
  two components agree on a shape.

**Common type**, written `join(A, B)`, is used for conditional branches,
array elements and equality. Named references are expanded first. The
first matching rule decides:
1. Anything involving `void` has no common type. This comes first so that
   `any`, `nothing` and identity can't produce a `void` join.
2. Optionality: `join(T?, U)`, `join(T, U?)` and `join(T?, U?)` are all
   `join(T, U)?`, if `join(T, U)` is defined. So optionality is never
   discarded, `any` included: `join(any, T?) = any?`.
3. `join(nothing, X) = join(X, nothing) = X`.
4. `join(any, X) = join(X, any) = any`.
5. Structurally identical types → that type. Records are identical only if
   they declare the same fields, each with the same requiredness and an
   identical declared type. So `{f?: T}` and `{f: T?}` don't join.
6. `join(list<T>, list<U>) = list<join(T, U)>`.
7. Anything else has no common type.

A missing common type is a `no-common-type` error.

`join` never invents compatibility that `is_assignable` would deny.
- It adds no coercions.
- It widens only through `any`, which is already unchecked against the
  value's type.
- It never widens across absence, `null` or `void`.

**Object literals.** Where an object literal meets an expected record
type, the checker reports field-level diagnostics instead of one
whole-value mismatch:
- `unknown-field` at the extra key
- `missing-required-field` at the literal
- `type-mismatch` at the offending value

The relation is the same; only the reporting is finer.

### D10. Commands are actions, not values; `$event`

**Commands:**
- A command invocation has type `void`.
- It is valid **only** as the complete handler expression of an `on.*`
  binding. That was already its documented use (MPRX-SPEC §6).
- Anywhere else (a prop value, an operand, an argument, a child), it is
  `command-outside-handler`.
- An `on.*` handler that isn't a command invocation is `handler-not-command`.
- No command-expression features are added.

**`$event`:**
- It exists only inside the arguments of an `on.*` handler's command.
  Elsewhere it is `event-value-outside-handler`.
- Its type is the payload type of the event being handled, taken from the
  **instance's** component, the element the `on.` sits on.
- If that event declares no payload, `$event` can't be used as a value;
  using it is `event-has-no-payload`.
- Any other `$` name is `unknown-special-value`.
- `$event` is never a scope binding (D8).

### D11. Spans are diagnostic-granular

**Invariant: every semantic construct that can independently produce a
diagnostic keeps its own narrow span, so a diagnostic can identify the
smallest useful source region.** One span around a whole expression or
element is not enough. At minimum these are distinct:
- an element's tag name (for `unknown-component`)
- an attribute's name (for `unknown-prop`), separately from its value
  expression (for `type-mismatch`)
- an event binding's event name (for `unknown-event`), separately from its
  handler
- a command's name (for `unknown-command`), separately from each argument
- a member access: the object (`layout`), the property name (`compact`,
  for `unknown-member`), and the whole expression (`layout.compact`, for
  `type-mismatch`)
- each object-literal key and value, and each array element

### D12. Semantic analysis never mutates the IR

```text
MPRX → Parser → AST → Semantic IR ─┬─ Name and interface resolution
                                   ├─ Expression typing
                                   └─ Contextual checking
                                           ↓
                                 structured facts (D13)
                                           ↓
                                   diagnostic layer
```

- **Semantic analysis does not change the Semantic IR's structure or
  meaning.** The IR stays what the source says, so it's equally useful to
  `mesh-lsp`, a formatter, or code generation.
- Analysis keeps its results (resolutions, types, facts) as **external
  state keyed by stable node identities**, such as node IDs or spans, and
  never writes them into the IR.
- If a later phase needs a typed IR, that is a **separate derived
  representation**. The Semantic IR is never rewritten into a different
  semantic form.
- Without a manifest, analysis doesn't run. The IR has the same meaning as
  v0.1's, plus spans.

### D13. Resolution produces facts; the diagnostic layer produces prose

```text
resolver / checkers → structured facts
                    → diagnostic layer
                    → code + message + labels + suggestions
```

- The resolver and checkers emit **structured facts**, with the context
  the diagnostic layer needs. For example:
  `UnknownIdentifier { name: "usr", span, candidates: <names in scope> }`.
- The facts contain no prose and no suggestions.
- The **diagnostic layer** chooses the code, writes the message, and
  computes suggestions. For example: `unknown reference "usr"; did you
  mean "user"?`.
- Edit distance lives only in that layer. JSON output and a future LSP can
  present the same facts differently.

### D14. Diagnostics have stable codes

**The shape of a diagnostic**, conceptually, before any serialization:
- severity
- a **stable code**
- a human message
- a primary span
- optionally, suggestions (a replacement and its span) and related spans,
  such as the declaration involved

**Code stability policy.** Codes are machine-readable API:
- Codes are kebab-case strings.
- A code is never renamed.
- A retired code is never reused for a different meaning.
- Messages may change freely.
- `syntax-error` is the **permanent** generic fallback code. More specific
  syntax codes may coexist with it; a syntax problem MESH can't classify
  more precisely keeps getting `syntax-error`.
- Better syntax classification or more precise locations in later versions
  don't change what an existing code means.

**The v0.2 catalogue.** Distinct mistakes get distinct codes; nothing
collapses into a generic "unknown reference".

| Code | Raised when |
|---|---|
| `syntax-error` | the permanent generic fallback; Pass 1 may add specific codes alongside it |
| `mismatched-closing-tag` | (v0.1) |
| `duplicate-attribute`, `duplicate-event-binding` | (v0.1, warnings) |
| `unknown-component` | tag not in the manifest |
| `unknown-prop` | attribute not a prop of the instance's component |
| `missing-required-prop` | required prop omitted |
| `unknown-event` | `on.<name>` not an event of the instance's component |
| `unknown-reference` | name not in the template's scope |
| `unknown-member` | field not on the record, or member access on a non-record |
| `possibly-absent-access` | member access on a `T?` value, `any?` included |
| `unknown-command` | command not declared for the template's component |
| `command-arity-mismatch` | wrong number of arguments |
| `command-outside-handler`, `handler-not-command` | D10 |
| `event-value-outside-handler`, `event-has-no-payload`, `unknown-special-value` | D10 |
| `type-mismatch` | `is_assignable` failed |
| `no-common-type` | conditional branches, array elements, or equality operands with no `join` |
| `unknown-field`, `missing-required-field`, `duplicate-object-key` | object literals |

Manifest errors (Pass 3) get their own `manifest-*` codes, under the same
stability policy.

### D15. Expression typing rules

`type_of(expression)` is defined for every v0.1 expression form. It
yields a type, or diagnostics plus an error marker that suppresses
cascading errors. "Needs `T`" always means `is_assignable(operand, T)`,
so `any` is accepted and any optional type, `any?` included, is rejected.

**Literals:**
- string → `string`; number → `number`; `true`/`false` → `boolean`;
  `null` → `null`
- a string attribute value (`title="Users"`) → `string`

**Names and members:**
- **Reference** → its scope type, or `unknown-reference`.
- **Member access `a.f`**:
  - `a` is a record → the field's type as read (D5: requiredness erased).
    A field that doesn't exist is `unknown-member`.
  - `a` is `any` → `any`.
  - `a` is `T?`, `any?` included → `possibly-absent-access`. MPRX has no
    optional chaining.
  - anything else (primitives, lists) → `unknown-member`. There are no
    built-in members in v0.2.

**Unary operators:**
- `!x` needs `boolean` and gives `boolean`.
- `-x` needs `number` and gives `number`.

**Binary operators:**

| Operators | Operands | Result |
|---|---|---|
| `+ - * / %` | `number` | `number` |
| `< <= > >=` | `number` | `boolean` |
| `&& \|\|` | `boolean` | `boolean` |
| `== !=` | see below | `boolean` |

- `+` is numeric only. There is no string concatenation, because text
  content already interleaves text and expressions.
- `&&` and `||` evaluate **left to right and short-circuit**. The right
  operand is evaluated only when the left doesn't decide the result.
  - MPRX-SPEC doesn't state this yet, and Pass 6 adds it there.
  - Because MPRX expressions are side-effect free and commands can't be
    operands (D10), short-circuiting never changes a result. It exists so
    runtimes agree.
  - Both operands are always type-checked. Types are never narrowed by
    evaluation order.
  - The result is a `boolean`, not one of the operands as in JavaScript.

**Equality, `==` and `!=`: strict, type-compatible, no coercion.**
- The operands must have a common type under `join`. Otherwise the
  expression is `no-common-type`.
- So `string == number` is rejected, and so is `string? == null`, because
  `null` is not absence.
- Because `join` preserves optionality, optional operands are allowed and
  their absence is taken into account. Absent equals absent, and absent
  never equals a present value. The result is still just a `boolean`.
- **Equality is not a presence test.**
  - MPRX can't express a value that is certainly absent. No literal or
    type means only "absent", and `null` is not absence.
  - The result never narrows an operand's type (D15 has no narrowing).
  - A `T?` stays `T?` after any comparison.
- Present values compare structurally, with no coercion:
  - primitives by value
  - lists element by element
  - records field by field
- A value of type `any` compares by its actual value, still without
  coercion.

**Other forms:**
- **Conditional `c ? a : b`**: `c` needs `boolean`, so a `boolean?`
  condition fails. The result is `join(a, b)`. Only the chosen branch is
  evaluated, but both are type-checked.
- **Array**:
  - `[]` → `list<nothing>`
  - otherwise `list<join of all elements>`, or `no-common-type`
- **Object** → an exact record with every key declared required, each
  typed by its value. A duplicate key is `duplicate-object-key`.
- **Command invocation** → `void`, with placement checked per D10.
  Arguments are checked with `is_assignable` against the parameter types.
- **`$event`** → the payload type, per D10.
- **Content expressions** (children) are resolved and typed but have no
  expected type, because children aren't modelled in v0.2.

### D16. Pass boundaries follow the analysis layers

- Resolution (Pass 4) turns names into declarations.
- Expression typing (Pass 5a) computes `type_of`.
- Contextual checking (Pass 5b) applies `is_assignable` against expected
  types.

Each layer consumes the previous layer's external results (D12) and emits
facts (D13). None of them writes prose, and none has its own
compatibility logic.

### D17. v0.1 compatibility

**Invariant: input checked without a manifest stays semantically
compatible with v0.1.**
- The same sources are accepted.
- The same mistakes are rejected, with the same severities and exit
  statuses.
- The IR has the same meaning.

v0.2 deliberately improves diagnostic *presentation* without that counting
as an incompatibility:
- diagnostic structure
- stable codes
- source locations
- message wording
- splitting one v0.1 syntax error into several located ones

MESH does not promise byte-for-byte identical diagnostic output.

- The exact property spellings within D2's settled representation. They

- The specific syntax-error codes Pass 1 adds alongside `syntax-error`.

### Pass 3 — The component manifest

**The invariant: a malformed manifest never reaches semantic checking.**
Load the manifest (D1, D2, D8) and validate it completely before any MPRX
checking. If the manifest has errors, only manifest errors are reported.

**Validation** covers everything the v0.2 model can get wrong, and nothing
beyond it:
- an unsupported `version`
- a document that doesn't match the JSON Schema, including:
  - an unknown `kind`, among them the internal `void` and `nothing`
  - a missing `required` flag
  - missing or extra properties
- duplicate JSON keys (D2), so duplicate names at every level:
  - components
  - props within a component
  - events
  - commands
  - scope names
  - named types
  - record fields
- duplicate command parameter names
- invalid identifiers:
  - component names must be valid MPRX tag names
  - props, scope names, commands, parameters and record fields must be
    valid MPRX identifiers
  - event names must be valid after `on.`
  - named-type names must be valid identifiers
- unknown `named` type references
- recursive named types
- an `optional` wrapping another `optional`

Manifest errors carry `manifest-*` codes and are rendered with
`file:line:col` from the JSON parser.

**Wiring:**
- Compile options carry the manifest and the resolved component name
  (D3). With no manifest, the options are empty and D17 holds.
- CLI: `mesh check --model <FILE> [--component <NAME>]`, with stem
  inference in the CLI only.
- `examples/components.json` declares the components the examples use.
- The manifest's JSON Schema is published.

**DoD:** the example manifest loads. A corpus of broken manifests gives
one precise, coded error per problem. No MPRX checks exist yet.

## Risks

- **Strict absence may push models to `any?`.** With no presence test,
  unions, or nullable-present types, a `T?` value can only go where `T?`
  is accepted. That is correct and fail-closed, but real models may lean
  on the escape hatches to cope. Watch for it in the examples; a presence
  test is a v0.3 language question, not a v0.2 patch.
- **Exact records may feel strict.** A caller can't pass a richer record
  to a prop typed with a subset. This is deliberate (D9). Shared named
  types are the intended answer; revisit only with evidence.
- **Manifest churn.** When NEXUS finalizes `Component.define`, the manifest
  may need to change. Mitigate by keeping it minimal and versioned from
  day one (D1). Structured `kind`s (D2) make additions non-breaking.
- **Breaking the IR API (Pass 2).** v0.1 embedders pin a tag, and the
  CHANGELOG spells out the change.
- **Recovery quality (Pass 1).** See the risk under Pass 1.
- **Cascading errors (Pass 5a).** One bad reference must not produce a
  chain of type mismatches. The error marker in D15 exists for this.
