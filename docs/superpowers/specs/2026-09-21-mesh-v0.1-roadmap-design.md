# MESH v0.1 Roadmap — Design

Date: 2026-09-21
Status: Approved
Repo: `mesh` (part of the VALENCE namespace; see `../ARCHITECTURE.md` and the
VALENCE-wide `docs/ARCHITECTURE.md` for full context)

## Context

MESH is currently pure scaffolding: six empty Rust crates (`mesh-syntax`,
`mesh-parser`, `mesh-semantic`, `mesh-compiler`, `mesh-lsp`, `mesh-cli`), a
placeholder Tree-sitter grammar directory, and three empty npm wrapper
packages. Nothing parses, validates, or compiles yet. `docs/ARCHITECTURE.md`
§23 sketches a VALENCE-wide vertical slice (MPRX → parser → semantic →
type-checking → IR → NEXUS → Web PORT → browser) but that scope spans three
independent repos and is not itself a MESH-scoped, versioned milestone.

This document defines what "v0.1" means specifically for the `mesh` repo,
and the order in which it gets built.

## Goals

- Prove the MESH pipeline (grammar → parser → semantic model → compiler)
  works end-to-end on real MPRX source, provable via `mesh-cli`.
- Establish the crate boundaries and diagnostic model that later milestones
  (type checking, LSP, WASM/npm distribution) build on, without having to
  re-architect them.
- Stay inside the `mesh` repo. No dependency on `nexus` or `port`.

## Non-goals (explicitly out of scope for v0.1)

- Component-model type checking (resolving `<user-card user={usr} />`
  against a real prop schema and flagging `usr` as undefined). Requires a
  typed component model that doesn't exist yet — deferred.
- `mesh-lsp`. It must reuse `mesh-compiler` rather than reimplement it
  (invariant, see `../ARCHITECTURE.md`), so it can't start until the
  compiler's diagnostic model is stable. Deferred to v0.2+.
- WASM build and wiring the `packages/` npm wrappers
  (`mesh-language`/`mesh-compiler`/`mesh-lsp`) to it. Deferred to v0.2+.
- Any NEXUS or PORT integration, rendering, or the full VALENCE vertical
  slice from `docs/ARCHITECTURE.md` §23.
- Formatter, rename, completion, hover, slots, optional chaining.

These are candidates for later milestones, not commitments — they are
listed here only to make v0.1's boundary explicit.

## Definition of Done

`mesh check examples/user-card.mprx` (the canonical example from
`docs/ARCHITECTURE.md`) runs via the native `mesh-cli` binary, parses
successfully, and reports zero errors. Running it against a small fixture
corpus of deliberately malformed MPRX (bad closing tag, disallowed
expression construct, duplicate attribute) produces correct, well-formatted
diagnostics with accurate source spans — not panics. Everything happens
through native Rust; no NEXUS/PORT, no WASM/npm wrapper wiring, no LSP, no
component-model type checking.

## Crate boundary for v0.1: mesh-semantic vs mesh-compiler

The docs describe these two crates with some overlapping language ("semantic
analysis" appears in both `mesh-semantic`'s and `mesh-compiler`'s
descriptions). For v0.1, since deep type checking is out of scope, the split
is:

- **`mesh-semantic`** builds the Semantic AST/IR from the `mesh-syntax` AST
  and performs *structural* validation only: well-formed element/attribute
  shape, valid expression node shapes, no cross-referencing against an
  external component model (that model is a NEXUS-side `.ts` concept that
  doesn't exist yet).
- **`mesh-compiler`** is a thin orchestration layer for v0.1: calls
  `mesh-parser` → `mesh-semantic`, exposes a single `compile(source) ->
  CompileResult { ir, diagnostics }` API, and owns diagnostic
  aggregation/rendering (rustc-style: source snippet + caret + span). It
  does not perform type checking in v0.1 — that capability is added in a
  later milestone without changing this boundary.

This keeps the crate separation the architecture docs call for intact,
without pretending v0.1 does work it doesn't do.

## Build order: walking skeleton

Rather than finishing each crate's full v0.1 scope before starting the
next (strict bottom-up), v0.1 is built as a walking skeleton: a trivial
end-to-end path through all six crates is wired up almost immediately, then
widened in passes. This mirrors the philosophy `docs/ARCHITECTURE.md` §23
already states for the VALENCE-wide slice ("build a vertical slice... prove
the fundamental architecture before building advanced capabilities"),
applied in miniature inside MESH. It means there is a runnable `mesh check`
from Pass 1 onward, and crate-boundary/API mismatches surface early instead
of at integration time.

### Pass 0 (optional, recommended) — Groundwork

Add CI (`cargo test`, `cargo clippy`, `cargo fmt --check`) to the existing
Cargo workspace so every subsequent pass is checked automatically. Also
establishes the Tree-sitter grammar tooling dependency (Node +
`tree-sitter-cli`) needed starting in Pass 1, on top of the Rust toolchain
that's already installed. Cargo pulls all Rust-side dependencies from
crates.io as each crate needs them (tree-sitter Rust bindings, a CLI arg
parser, etc.) — no dependency vendoring or preinstallation needed beyond
that.

**DoD:** CI green on the current (empty) workspace.

### Pass 1 — Skeleton wire-through

- Grammar: `grammar.js` parses only self-closing elements with
  string-literal attributes (`<tag attr="value" />`) and bare text content.
- `mesh-syntax`: AST types for Element, Attribute, StringLiteral, Text only.
- `mesh-parser`: lowers the Tree-sitter CST to that AST subset.
- `mesh-semantic`: passes the AST through to a minimal Semantic IR.
- `mesh-compiler`: wires parser → semantic, exposes `compile()`.
- `mesh-cli`: `check` command runs the full pipeline end-to-end.

**DoD:** `mesh check` on `<page title="Users" />` prints "no errors."

### Pass 2 — Expressions

Grammar adds `{...}` expression syntax for Literal, Reference,
MemberAccess. AST/parser/semantic/compiler updated to carry expression
nodes through.

**DoD:** `{user.name}` parses and round-trips through to the IR.

### Pass 3 — Full expression model

Grammar adds UnaryExpression, BinaryExpression, ConditionalExpression,
ArrayExpression, ObjectExpression, CommandInvocation — the full expression
node set from `docs/ARCHITECTURE.md` §5.

**DoD:** each node kind has a grammar test and a semantic IR fixture.

### Pass 4 — Bindings, structure, and errors

Grammar adds `on.eventName={...}` binding syntax, nested elements/children,
multiple attributes. `mesh-semantic` adds structural validation rules:
duplicate attributes, mismatched open/close tags, malformed `on.` bindings.
These produce diagnostics, not panics.

**DoD:** a fixture corpus of malformed MPRX produces correct diagnostics
with accurate spans.

### Pass 5 — Canonical example and polish

The full `user-card.mprx` example from `docs/ARCHITECTURE.md` §3/§5 parses
and checks clean. Diagnostic rendering is polished to rustc-style (source
snippet + caret). The example plus the fixture corpus are committed under
`examples/`, with an integration test asserting expected diagnostics for
each fixture.

**DoD:** this pass's completion is the v0.1 Definition of Done, above.

## Testing strategy

- Grammar: Tree-sitter's own corpus test format (`tree-sitter test`) per
  node kind, growing with each pass.
- `mesh-syntax`, `mesh-parser`, `mesh-semantic`, `mesh-compiler`: standard
  Rust unit tests per crate; fixture-driven tests using MPRX source strings
  as input and expected AST/IR/diagnostics as output.
- `mesh-cli`: integration tests (Pass 5) running the compiled binary against
  `examples/` fixtures and asserting on stdout/exit code.

## Open risks

- Tree-sitter grammar authoring is a new skill for this codebase even
  though the rest of the toolchain is Rust; Pass 0/1 needs the Node +
  `tree-sitter-cli` tooling in place before grammar work starts.
- The exact shape of the Semantic IR (`Component(...).bind(...).event(...)`
  in the docs) is illustrative, not a finalized API — Pass 1–5 will refine
  it as real cases are implemented. `docs/ARCHITECTURE.md` already warns
  against prematurely locking down a serialized IR format; this applies
  equally to the in-memory Rust representation during v0.1.

## After v0.1

Not committed, but the natural next candidates in rough priority order:
component-model type checking (the second option declined in the v0.1
scoping conversation), `mesh-lsp`, then WASM + npm package wiring. Each
gets its own brainstorming pass when v0.1 is closer to done, since priorities
may shift once the compiler's real diagnostic model exists.
