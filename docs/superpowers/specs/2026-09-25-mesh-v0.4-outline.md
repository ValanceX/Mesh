# MESH v0.4 — Outline

Date: 2026-09-25
Status: Final outline, written after an audit of v0.3.0 and revised
twice after review. It is not an implementation plan.
- The audit's findings are recorded below, E1–E12. None is fixed yet.
- The invariants I1–I5 carry over from v0.3 unchanged. I6–I10 are new,
  and **settled**. Every decision and every pass must respect them.
- Decisions D1–D11 are **settled**. The first draft left four questions
  open; the first revision settled them, and each resolution is recorded
  where it applies: E2 and D4 (no Semantic IR or AST in v0.4), E5 and D7
  (two npm packages), D8 (`mesh-lsp` binaries through npm), and E10 and
  D4 (the project file deferred).
- The project's identity is settled: **ValanceX** is the organisation
  and project name, and **`@valancex`** is the npm scope (D7). This
  replaces the scope D11 of v0.3 chose.
- Nothing here is a Rust or TypeScript API, or a file-level design;
  that belongs to each pass's plan.
- **Passes 0–2 are planned,** to be implemented one after another,
  0, 1, then 2. Each pass's section below names its plan.

Repo: `mesh`

## Where v0.3 left off

v0.3.0 (released 2026-09-24) brought MESH into the editor: `mesh-lsp`,
a client of the compiler, serves the compiler's own diagnostics, quick
fixes, hover, go-to-definition and completion, also on broken files. The
grammar ships highlighting queries, and a Neovim setup is verified by a
script.

Everything so far is Rust, installed with `cargo install` from a clone.
The v0.3 outline's "After v0.3" and the v0.3 release notes both name
v0.4 as the WASM build and the npm packages, including a launcher for
`mesh-lsp`; possibly a project file; possibly a thin VS Code extension.
The three packages under `packages/` are still placeholders that export
nothing.

## Audit of v0.3.0

**Method.** At `cac8517`:
- Ran everything CI runs: `cargo fmt --check`, clippy with warnings
  denied, 557 tests in 61 binaries, rustdoc with warnings denied, the
  MSRV check (`cargo +1.91.0 check --locked`), the grammar corpus
  (40/40), and `tree-sitter generate` (the committed parser is
  unchanged). All passed.
- Read the packages under `packages/`, CI, the build scripts of the
  grammar and of `tree-sitter` 0.27, the CLI's check flow, the JSON
  renderer and its schema, and the IR's types.
- **Built the compiler for WebAssembly**, in a throwaway `cdylib` outside
  the repo that depends on `mesh-compiler` and `mesh-manifest` and
  exports a few C-ABI functions (no `wasm-bindgen`). Findings E1–E3 and
  E9 come from that probe, and so does most of "What's healthy".
  - `cargo build --target wasm32-unknown-unknown -p mesh-compiler` builds
    unchanged on the pinned 1.98.1 and on the 1.91.0 MSRV. `tree-sitter`
    0.27 ships a libc shim and allocator for `wasm32-unknown-unknown`,
    and the grammar's `build.rs` already takes its headers
    (`DEP_TREE_SITTER_LANGUAGE_WASM_HEADERS`). The C is compiled by
    `clang`.
  - The linked module **imports nothing**. It instantiates with an empty
    import object in Node 22.
  - Size: 485 KB, 163 KB gzipped, at `opt-level = "z"` with LTO, before
    `wasm-opt`, and including the probe's own test code.
  - **It agrees with the CLI.** Replicating `mesh check`'s flow in the
    probe, 158 runs (every `.mprx` under `examples/` without a model,
    every `check` fixture and example with its manifest, and every
    broken-manifest fixture) printed exactly what `mesh check --format
    json` prints.
  - **The nesting limits hold in WASM.** `crates/mesh-compiler/tests/nesting.rs`'s
    thirteen sources, at exactly the limit and against its manifest, and
    its deep manifest type, all check at the default linker stack. With
    the stack forced down, a release build still passes them all at
    128 KiB and an unoptimized one at 256 KiB (it fails at 128 KiB), so
    the default leaves at least 4× headroom for those inputs. Every shape
    at 129, 5,000 and 100,000 levels is one `nesting-too-deep`, and
    nothing traps.
  - Checking `examples/users-page.mprx` takes 0.13 ms per call in Node.
- Checked the npm registry: no MESH package is published under any
  scope.

**What's healthy.**
- The layering pays off. No crate needed a change, a feature flag or a
  `cfg` to build for WASM. Only the CLI and the server touch the file
  system, threads or stdio, and neither is needed in WASM.
- The diagnostics document is already the right boundary. It is
  versioned, has a schema, and its promise already allows additive
  properties ("ignore any you don't know"), which E3 needs.
- The stack-safety work of v0.3 (A1, A2, and its D12) transfers to
  WASM's small, fixed stack without change.
- The probe shows the compiler is comfortably small enough for a JS/WASM
  package, so v0.4 treats size as a bounded release constraint (D2's
  budget) rather than an optimization project. Speed isn't a concern.

## Theme

**v0.4: MESH outside Rust.** The same compiler, built for WebAssembly,
behind a small JavaScript API that answers what the compiler's check
answers, and `mesh-lsp` installable from npm. The main user is a JS or
TS program that generates MPRX, often with a model, and has to check it
before using it: the generate-check-repair loop that the JSON
diagnostics were made for. The second is anyone who wants MESH in their
editor without a Rust toolchain.

## Architecture and invariants

```text
mesh CLI ───────┐
                │
mesh-wasm ──────┼──> mesh-compiler check  (one batch check, explicit inputs)
                │
future host ────┘

mesh-lsp ─────────> mesh-compiler compile_with  (D9 of v0.3's editor policy)
```

`mesh-compiler` owns the check. The CLI, `mesh-wasm` and any later host
are adapters around it: they gather its inputs and present its
diagnostics document, and none of them defines what a check is.
`mesh-lsp` stays different on purpose (D3). `@valancex/mesh-compiler`
wraps `mesh-wasm`; `@valancex/mesh-lsp` only launches the native
`mesh-lsp`.

I1–I5 carry over from v0.3 unchanged. They were written for the
server, and they apply to every new host.

**New invariants.**
- **I6. The JS wrapper is deliberately boring.** The JavaScript API is
  the Rust compiler compiled to WebAssembly, and this is an
  architectural boundary, not a preference. The wrapper must not parse
  MPRX, parse manifests, resolve components, calculate positions,
  normalize source coordinates, generate diagnostics, filter them,
  reinterpret their codes, or perform any MESH validation. It only
  transfers UTF-8 input, invokes the compiler, transfers the JSON
  output, parses the versioned diagnostics document, and exposes the
  documented JS API.
- **I7. Every batch-checking host answers what the compiler's check
  operation answers.** For the same source, manifest, component and
  paths, the CLI's `--format json` output and the JS API expose the
  same diagnostics document: the same diagnostics, codes, messages,
  positions and suggestions, in the same order. As in v0.3's I3, no
  host filters any out or adds any. The invariant is the document's
  content, not how a serializer lays out its bytes.
- **I8. Only published formats cross the boundary.** Nothing crosses
  from WASM into JavaScript unless it has a versioned, published shape.
  In v0.4 that's the diagnostics document
  (`schemas/diagnostics-v1.schema.json`) and nothing else. The Semantic
  IR and the AST don't cross (E2). D11 states the public compatibility
  boundary this implies.
- **I9. Deterministic check results.** Identical source, manifest,
  component, paths and compiler version produce an identical
  diagnostics document.
- **I10. The wrapper only drives a module of its own version.** Before
  relying on any other internal export, the wrapper checks that the
  WASM module it loaded is the version it was built for. An
  incompatible module fails clearly, with a documented error, before any
  check runs; the wrapper never calls exports it can't trust. How the
  version is read is internal (D2, D11).

## Goals

- A `mesh-wasm` crate that builds the compiler for
  `wasm32-unknown-unknown` in a Cargo-driven build, with no separate
  WASM toolchain (D1, D2).
- One check operation in `mesh-compiler`, with explicit inputs, that the
  CLI and the WASM build both host (D3, E1).
- `@valancex/mesh-compiler`: the WASM module and a thin, typed ESM
  wrapper (I6, I10). It checks a source string, with or without a
  manifest and an explicit component, and returns the diagnostics
  document (D4). It runs on the Node LTS releases the CI and release
  matrix names, and in browsers through an explicit initialization
  path.
- Positions JavaScript can use directly: UTF-16 positions beside
  today's bytes and `char` columns, in the JS API and in `mesh check
  --format json` alike, computed only by `SourceMap` (D5, E3).
- A failure contract at the WASM boundary: supported input gets
  diagnostics, an observed boundary failure is reported as one and never
  leaves a failed instance in use, and repeated checks keep memory
  bounded (D6, E9).
- `@valancex/mesh-lsp`: a launcher that starts a prebuilt `mesh-lsp` for
  the user's platform, with no LSP logic of its own, and one platform
  package per shipped target, each binary built and exercised natively
  on its target OS and architecture in CI (D8).
- A native CI baseline on Linux, macOS and Windows, and a release
  workflow that builds and publishes every artifact from the tag (D9,
  D10).
- Documentation: a guide to using MESH from JavaScript, package READMEs,
  the release notes.

## Non-goals (v0.4)

- **New MPRX syntax, or manifest format changes.** The language and
  manifest version 1 stay exactly v0.3's.
- **A serialized Semantic IR or AST** (E2). The JS API returns
  diagnostics only. A serialized IR is a separate, future design with
  NEXUS and PORT.
- **A `mesh-language` npm package** (E5, D7). It returns only when it
  has something to contain.
- **A project file** shared by the CLI, the server and the JS API
  (E10). Every host's inputs stay explicit.
- **Bundler integrations.** The module is browser-compatible and the
  JS API has an explicit browser initialization path (D4); automatic
  WASM loading in any particular bundler isn't part of v0.4's
  compatibility contract.
- **The language server in WASM,** in a browser or under WASI.
  `mesh-lsp` uses threads and stdio, and `wasm32-wasip1` has no threads.
  A browser editor can use the JS API for diagnostics; hover and
  completion in a browser are a later question.
- **Editor features.** E11's limitations, references, rename,
  formatting, symbols, semantic tokens. v0.4 is about distribution.
- **Publishing the Rust crates to crates.io,** or the grammar to npm or
  crates.io (E12). `cargo install --path` from a clone stays the Rust
  install.
- **A VS Code extension.** With D8's binaries it becomes a small later
  item (D8 of v0.3).
- **General package-manager compatibility.** D8's install behaviour is
  verified with npm; other package managers aren't promised.

## Definition of Done

**Batch hosts agree (I7).** A test in Node loads the built module
through `@valancex/mesh-compiler` and, for every `.mprx` fixture and
example, with and without a model, and every broken-manifest fixture,
compares the API's document with `mesh check --format json` run with the
same explicit `--model`, `--component` and paths. Both are parsed, and
the parsed documents are equal: every diagnostic, code, message,
position and suggestion, in order. The fuzzer's mutants are compared the
same way, for a fixed budget in CI and one recorded local run of at
least 100,000. (The CLI's own fixture tests keep pinning its printed
bytes, as they do today; that's a property of the CLI, not the
cross-host invariant.)

**Checks are deterministic (I9).** Within each host, checking the same
inputs repeatedly gives equal documents: in the CLI, on one JS API
instance, and after the wrapper has replaced a failed instance.

**Positions work in JavaScript (D5).** For sources with multi-byte UTF-8,
characters outside the Basic Multilingual Plane, CRLF and a leading BOM,
`source.slice(start.utf16, end.utf16)` in JS is exactly the text the
diagnostic's byte span covers (the property names are Pass 0's). The
CLI's JSON gains the same positions, the schema lists them, and the
schema test checks real output against it.

**The failure contract holds (D6).**
- `nesting.rs`'s sources run in WASM at the limit, against its
  manifest, at the default stack, and give diagnostics; past the limit,
  they give `nesting-too-deep`.
- A test-only export that panics shows that the wrapper observes the
  failure, throws `MeshInternalError`, never calls that instance again,
  and answers the next check correctly from a fresh one.
- The bounded-memory test of D6 passes: 100,000 checks, cycling a fixed
  set of fixtures on one instance, and the measured quantities are the
  same at the end as after the warm-up.

**The wrapper refuses a mismatched module (I10).** Given a module that
reports a different version, the API fails with its documented error
before any check runs.

**It runs where JavaScript runs.** The package's tests pass on every
Node LTS release the CI matrix names, and a smoke test checks a file in
headless Chromium through Playwright, using the explicit browser
initialization path.

**The packages are what we say they are.**
- `packages/` holds exactly `@valancex/mesh-compiler` and
  `@valancex/mesh-lsp`, plus D8's platform packages.
  `crates/mesh-cli/tests/packages.rs` pins the `@valancex/` scope, that
  list, and that every package's version equals the workspace version.
- Each packed package has every runtime file it needs and its required
  metadata, and none of the development or source files that mustn't
  ship. Each platform package has its executable. A very small platform
  package may be checked against an exact file list where that's
  simplest; that's a test choice, not a general invariant.
- Installed from its tarball into an empty directory, each package
  passes a smoke test of its documented behaviour, and nothing in it
  needs a Rust toolchain at runtime.
- The module's gzipped size is within D2's budget, checked in CI.

**The launcher starts a native binary on every shipped target (D8).**
For each of Linux x64, Linux arm64, macOS x64, macOS arm64 and Windows
x64, that target's binary, built on a native runner of its OS and
architecture, passes `mesh-lsp`'s transport tests
(`crates/mesh-lsp/tests/transport.rs`) through the launcher there,
installed from tarballs. Pass 2's install scenarios pass (D8).

**It's usable.** A "Using MESH from JavaScript" guide shows a
generate-check-repair loop, and its example is run by a test. The
editor setup guide gains the npm install path, verified in Neovim as in
v0.3.

## Decisions

### D1. Target `wasm32-unknown-unknown`, in a Cargo-driven build

- One target, `wasm32-unknown-unknown`: it runs in Node and in browsers
  with no imports, and the probe shows it builds today.
- **Cargo-driven** means: `cargo build` produces the module, and no
  separate WASM toolchain is required (no `wasm-bindgen`, no WASI SDK,
  no Emscripten). It doesn't mean Cargo is the only tool involved:
  Tree-sitter's C (its runtime and `parser.c`) is still compiled by
  `clang`, through the existing `cc` build path that `tree-sitter`'s
  build script arranges.
- Rejected: `wasm32-wasip1`, which needs a WASI host in the browser and
  gains nothing the compiler uses; and Emscripten, a second toolchain
  for C that `tree-sitter` no longer needs.
- CI's Ubuntu runner has `clang`. Contributors on macOS may need LLVM's
  `clang` rather than Apple's; the contributor checklist says so once
  Pass 1 knows.
- `tree-sitter` stays pinned to 0.27. A bump is a change to test like
  any other, because the WASM shim is its code, not ours.

### D2. A minimal boundary: JSON in, JSON out, no `wasm-bindgen`

- A new crate, `crates/mesh-wasm`, a `cdylib` that depends only on
  `mesh-compiler` and `mesh-manifest`, built as D1 describes. It has no
  file system access and no semantics of its own.
- `mesh-wasm` exposes the minimum C ABI necessary for the JS wrapper to
  transfer UTF-8 input and JSON output and perform required
  lifecycle/version operations (including I10's version check). Exact
  exports belong to the Pass 1 implementation plan. They are internal,
  not public API (D11).
- Input crosses as UTF-8; the result is the diagnostics document, already
  JSON and already specified. There is no second encoding of anything.
- Rejected: `wasm-bindgen`. Its CLI must match the crate's version
  exactly, which is one more tool to pin in CI and on every contributor's
  machine, and its generated glue is code we'd ship and not read. What
  it buys (rich types across the boundary) isn't needed while only JSON
  crosses (I8).
- **Size budget:** 300 KB gzipped for the module, checked in CI. The
  probe was 163 KB before `wasm-opt`. `wasm-opt` is optional and not a
  build requirement.

### D3. `mesh-compiler` owns the check operation (E1)

- `mesh-compiler` gains one compiler-level batch check, with explicit
  inputs: optional manifest text and its path, the component, the source
  and its path. It returns the diagnostics together with which document
  (the source or the manifest) they are reported against. Its rules are
  the ones `run_check` follows today: manifest errors stop the check; a
  missing component is reported on the manifest; otherwise the source
  is compiled.
- It is the authority; the CLI isn't. The CLI becomes a host of it:
  it reads files, derives `--component` from the file's stem when it
  isn't given (a convenience of the command line, as D6 of v0.3 allows),
  calls the check, and prints. Its output doesn't change, and every
  fixture test pins that already. `mesh-wasm` is another host and adds
  nothing (I6).
- The component is always explicit in the operation's inputs (I5).
- `mesh-lsp` keeps D9 of v0.3's different policy (a broken manifest
  moves dependents to model-less checking), because an editor needs the
  template's own syntax errors while the manifest is being fixed. That's
  editor-specific behaviour, not a batch check, so it keeps using
  `compile_with` directly and isn't a host of this operation.

### D4. The JS API returns the diagnostics document

- `@valancex/mesh-compiler` exports roughly one function: check a
  source at a path, optionally against a manifest (its text and path)
  and an explicit component, returning the diagnostics document of I7,
  typed from the JSON Schema. Also the version. Nothing else: no IR, no
  AST (E2). The pass plan fixes the names.
- **Inputs are explicit.** The caller passes every input; nothing is
  discovered or configured, and no project file is read (E10). The
  component is required whenever a manifest is given, and the API never
  derives it from a path (I5).
- **Paths are opaque source identifiers** supplied by the caller. They
  are used only to identify documents in diagnostics. The API performs
  no file system access, in Node or in a browser.
- The manifest is passed as **text**, not a JS object, so its
  diagnostics have positions, and so there is exactly one manifest
  parser (I6).
- **Loading.** The WASM module is browser-compatible. In Node the
  package loads it itself. In a browser, the JS API has an explicit
  initialization path that takes the module as a URL, bytes or a
  compiled `WebAssembly.Module`. Either way, I10's version check runs
  before the module is used. Bundler-specific auto-loading isn't part of
  v0.4's compatibility contract.
- ESM only, with TypeScript declarations.
- **Supported Node versions are named explicitly** by the CI and release
  matrix, and the package's documentation lists the same ones. The
  Pass 1 plan chooses them; nothing here depends on the release date.

### D5. UTF-16 positions in the diagnostics document (E3)

- Every position in the diagnostics document gains its UTF-16 code-unit
  offset from the start of the source, and its UTF-16 column, beside the
  existing `byte`, `line` and `column`. The exact property names are the
  Pass 0 plan's.
- The CLI's JSON output gains them too, so every host exposes the same
  document (I7). This is additive, as the document's promise allows
  ("properties may be added without changing it"): `version` stays 1,
  and the schema lists the new properties.
- `SourceMap` stays the single authority for coordinate conversion
  (I4), with its rules for a BOM and CRLF. TypeScript doesn't
  reimplement any of MESH's position rules, and there is no second,
  JS-side position model (I6). The human-readable output doesn't change.
- The test that matters is the Definition of Done's:
  `source.slice(start.utf16, end.utf16)` is exactly the diagnostic's
  span, for multi-byte UTF-8, non-BMP characters, CRLF and a leading
  BOM.

### D6. The failure contract at the WASM boundary (E9)

D7 of v0.3's contract, for a host that can't catch a panic.

| Case | Outcome |
|---|---|
| **Supported input, within the documented validation limits:** malformed MPRX, a malformed manifest, a missing component, and nesting up to and past the documented nesting limits | A diagnostics document. This is the validation domain the contract promises and the tests cover. |
| A JS string that isn't valid UTF-16 (a lone surrogate) | Encoded to UTF-8 by the platform, which replaces it with U+FFFD, as for any JS string written to UTF-8. The documentation says so. |
| **A boundary-level failure the wrapper can observe:** a call into the module that ends in a trap (a Rust panic, which aborts; `unreachable`; a failed memory growth surfaced as a trap), or a result that isn't a diagnostics document | The call throws `MeshInternalError`. |
| **After any boundary-level failure** | The affected instance is discarded and never reused, because its heap may be half-updated. A fresh instance is created lazily for the next operation. |

- **Nothing in Rust recovers from a trap.** `mesh-wasm` builds with
  `panic = "abort"`, which is all `wasm32-unknown-unknown` offers, and
  says so. A trap ends the call; only the JS wrapper, outside the
  module, observes it. The contract covers what the wrapper can observe.
  It doesn't promise that every failure is observable: a host-level
  out-of-memory, or the JS engine itself failing, is outside it.
- **The nesting tests prove less than "never traps".** They show that
  the documented nesting limits produce diagnostics rather than traps.
  They don't prove that arbitrary input can never trap. An internal
  failure is a bug, found by the fuzzer and fixed; that the wrapper
  contains one doesn't make it acceptable, as in D7 of v0.3.
- **Instances are the wrapper's internal business.** The public JS API
  has no instance lifecycle a caller must manage; a caller sees only
  checks, `MeshInternalError`, and I10's version error.
- **Memory stays bounded under repeated checks.** Concretely:
  - every buffer a call allocates in the module, for its input and its
    output, is released before the call returns, whatever the call's
    result;
  - the wrapper keeps no per-call resources after a call returns, and
    keeps no reference to a discarded instance;
  - repeated checks don't grow retained memory. Since linear memory
    never shrinks, its size is the retained high-water mark: after a
    warm-up pass over a fixed set of inputs, cycling the same inputs
    again doesn't grow the instance's linear memory, or the module's own
    count of live allocations, at all.

  Pass 1 turns this into the Definition of Done's deterministic test
  (100,000 checks, measured after the warm-up and at the end). The
  invariant is "no growth from repetition", not a byte threshold; how the
  live allocations are counted is the Pass 1 plan's.

### D7. The package family: two packages, scoped `@valancex` (E4, E5, E8)

- **Identity.** The project and organisation are ValanceX (the GitHub
  organisation's name). Every npm package is scoped **`@valancex/`**,
  all lowercase, as npm names must be. This replaces D11 of v0.3's
  scope, which the project no longer uses. No package uses an unscoped
  name.
- **v0.4 publishes two packages** (E5), plus D8's platform packages:
  - `@valancex/mesh-compiler`: the WASM module and its wrapper (D4).
  - `@valancex/mesh-lsp`: the launcher (D8).
- The `mesh-language` placeholder is removed from `packages/`. It was
  never published, so nothing is burned. It comes back only when there's
  something to put in it. Removing it also drops the compiler
  placeholder's dependency on it.
- The existing placeholders are renamed to `@valancex/*`, and
  `crates/mesh-cli/tests/packages.rs` is updated: it pins the
  `@valancex/` scope and the exact package list, instead of "at least
  three" packages.
- All packages are versioned in lockstep with the Rust workspace:
  v0.4.0 publishes `0.4.0`. The same test pins it.
- `packages/` becomes an npm workspace with a committed lockfile. CI
  typechecks, tests and packs it.

### D8. The `mesh-lsp` launcher ships native binaries

- **Five shipped targets,** settled: Linux x64, Linux arm64, macOS x64,
  macOS arm64 and Windows x64.
- **One platform package per target,** each holding one `mesh-lsp`
  binary and declaring its `os` and `cpu`, under `@valancex/`.
  `@valancex/mesh-lsp` lists them as `optionalDependencies`, so npm
  installs only the matching one. The expected names follow npm's
  `os`/`cpu` values, as in `@valancex/mesh-lsp-linux-x64`,
  `-linux-arm64`, `-darwin-x64`, `-darwin-arm64` and `-win32-x64`; the
  exact names are a Pass 2 detail, which Pass 2 may adjust after
  verifying them against npm's `os`/`cpu` behaviour and packaging
  constraints. The five targets and the approach don't change.
- **Native builds, natively exercised.** Every shipped binary is built
  on a CI runner of its own OS and architecture, and exercised there
  (D9). A binary cross-compiled on Linux is never the one shipped, and
  never the evidence that a target works.
- **The launcher.** Its `bin` finds the installed platform package,
  spawns its binary with the same arguments, passes stdio through
  untouched, and exits with its status. It has no LSP logic of its own:
  no protocol handling, no configuration, no messages (A11 of v0.3).
- On a platform with no package, it says which platforms are supported,
  and how to `cargo install` instead, and exits non-zero.
- **npm's behaviour is tested, not assumed.** esbuild and Biome ship
  binaries this way, but Pass 2 verifies it for these packages with
  npm: an install on each supported target gets exactly its binary;
  an install on an unsupported platform succeeds and the launcher gives
  the message above; `--ignore-scripts` changes nothing, because no
  package has install scripts; and an install from local tarballs, with
  no registry, works.
- Rejected: downloading the binary in a `postinstall` script, which fails
  offline, behind proxies, and under `--ignore-scripts`; and `mesh-lsp`
  under WASI in Node (see Non-goals).

### D9. CI: a native test baseline, native shipped binaries, optional cross-checks (E6)

Three OS-level test concerns, five shipped binary targets, and three
different kinds of CI work, kept apart:
- **Native platform test baseline.** `cargo test --workspace` runs
  natively on Linux, macOS and Windows on every push: one runner per
  OS, on whatever architecture that runner has. This is Pass 0's. The
  whole workspace suite doesn't run on every architecture just because
  a binary ships for it. The first Windows run is expected to find
  something (paths, line endings, `uri.rs`), and fixing it is part of
  Pass 0.
- **Native builds and execution of shipped binaries.** Each of D8's
  five targets is built in release mode on a native runner of its OS
  and architecture, and exercised there: the transport tests through
  the launcher, installed from tarballs (D8). This is Pass 2's.
- **Optional cross-compilation checks** may be used as a fast signal
  that a target still builds. They are never the sole evidence that a
  shipped binary works, and never produce a shipped binary.

Beside those:
- A WASM job builds `mesh-wasm`, runs the package's tests in Node on
  the named LTS releases (including the agreement test against a native
  `mesh` built in the same job), runs the Chromium smoke test, and
  checks the size budget.
- A packages job typechecks, tests and `npm pack`s every package, and
  installs each tarball into an empty directory to smoke-test it.
- The MSRV job also builds `mesh-wasm` for `wasm32-unknown-unknown` on
  1.91.

### D10. Releases are built from the tag (E7, E8)

- A workflow triggered by a `v*` tag builds every `mesh-lsp` binary
  natively (D9) and the WASM module from that commit, checks that every
  package's version equals the tag, packs everything, and publishes the
  `@valancex/*` packages to npm with provenance.
- It publishes with an npm token for the `@valancex` organisation that
  the maintainer adds as a repository secret. Verifying control of the
  organisation (E8), adding the secret, and pushing the tag are the
  maintainer's steps. No workflow in this repo publishes without them.
- Until the maintainer enables it, the workflow runs on a tag with
  publishing turned off and attaches the packed tarballs to the run, so
  it's exercised before the first real publish.
- A GitHub release under ValanceX, with the notes and the binaries
  attached, is the same workflow's job, for people who don't use npm.

### D11. The public compatibility boundary

- **The diagnostics schema is the public cross-host compatibility
  boundary.** What the CLI and the JS API promise is the diagnostics
  document, as `schemas/diagnostics-v1.schema.json` describes it, under
  its existing versioning promise.
- **`@valancex/mesh-compiler` v0.4 exposes only its documented JS API**
  (D4), with its two documented errors (D6, I10). Everything else in the
  package is internal.
- **`mesh-wasm`'s exports aren't public API,** including the version
  operation I10 uses. They may change in any release, and nothing
  outside the package may call them. I10 exists so that such a change
  fails clearly instead of silently.
- **Reachable isn't public.** A Rust compiler internal doesn't become
  part of any contract because it could be reached through WASM.

## Sequencing

- Pass 0 comes first, and its four items are the contracts everything
  else relies on. Pass 1's agreement test compares against the check
  operation and positions Pass 0 settles.
- Passes 1 and 2 are independent of each other, and can run in either
  order or together. Pass 2 needs Pass 0's test baseline and package
  clean-up.
- Pass 3 needs both, and E8 verified.

## Risks

- **E8 unverified at release time.** Publishing needs the maintainer's
  control of the `@valancex` organisation. It's cheap to verify now and
  expensive to discover at release, so it's worth doing long before
  Pass 3.
- **Windows (E6).** The first Windows run of 557 tests has never
  happened. Expect path, line-ending and URI failures in the tests, and
  maybe in `mesh-lsp`. Pass 0 does it first for that reason.
- **Native runners for every shipped target (D9).** Five targets need
  five kinds of native runner, including Linux arm64 and both macOS
  architectures. If one isn't available to the repository, that target
  isn't shipped in v0.4 rather than shipped untested.
- **`tree-sitter`'s WASM shim is someone else's code (D1).** A bump could
  break the WASM build, or its behaviour, silently. The agreement test
  catches the second; CI's WASM job catches the first.
- **Supply chain.** Publishing binaries under a scope makes it a target.
  The mitigations are provenance from CI (D10), 2FA on the npm account,
  and no install scripts in any package (D8).
- **Semantics creeping into the wrapper.** Convenience code in
  TypeScript (a path helper, a position tweak, a filtered diagnostic) is
  where a second implementation starts. I6 and D11 are the defence, and
  review against them.
- **Pressure to expose the IR early.** Once a JSON IR is published,
  NEXUS and PORT will depend on its shape, and ARCHITECTURE.md says that
  shape isn't ready. E2 keeps it out of v0.4; a request for it is a new
  design, not a v0.4 addition.
- **Scope creep toward a browser IDE.** The JS API tempts toward
  hover, completion and recovery in the browser. The Non-goals list is
  the defence; each addition needs an outline revision.

## After v0.4

- A serialized, versioned Semantic IR, designed with NEXUS and PORT
  (E2).
- The project file (E10), once configuration across the CLI, the server
  and the JS API has stabilized.
- A thin VS Code extension over D8's binaries (D8 of v0.3).
