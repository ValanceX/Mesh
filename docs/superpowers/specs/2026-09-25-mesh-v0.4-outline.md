# MESH v0.4 — Outline

Date: 2026-09-25
Status: Draft outline, written after an audit of v0.3.0. It is not an
implementation plan.
- The audit's findings are recorded below, E1–E12. None is fixed yet.
- The invariants I1–I5 carry over from v0.3 unchanged. I6–I8 are new,
  and **proposed**.
- Decisions D1–D10 are **proposed**. Four questions are open, under
  "Open decisions"; each has a recommendation. Pass 0 can start once
  open decisions 1 and 2 are answered.
- Nothing here is a Rust or TypeScript API, or a file-level design;
  that belongs to each pass's plan.

Repo: `mesh`

## Where v0.3 left off

v0.3.0 (released 2026-09-24) brought MESH into the editor: `mesh-lsp`,
a client of the compiler, serves the compiler's own diagnostics, quick
fixes, hover, go-to-definition and completion, also on broken files. The
grammar ships highlighting queries, and a Neovim setup is verified by a
script.

Everything so far is Rust, installed with `cargo install` from a clone.
The v0.3 outline's "After v0.3" and the v0.3 release notes both name
v0.4 as the WASM build and the `@valance/*` npm packages, including a
launcher for `mesh-lsp`; possibly a project file; possibly a thin VS
Code extension. The three packages under `packages/` are still
placeholders that export nothing.

## Audit of v0.3.0

**Method.** At `cac8517`:
- Ran everything CI runs: `cargo fmt --check`, clippy with warnings
  denied, 557 tests in 61 binaries, rustdoc with warnings denied, the
  MSRV check (`cargo +1.91.0 check --locked`), the grammar corpus
  (40/40), and `tree-sitter generate` (the committed parser is
  unchanged). All passed.
- Read the packages under `packages/`, CI, the build scripts of the
  grammar and of `tree-sitter` 0.27, the CLI's check flow, the JSON
  renderer and its schema, and the IR's types.
- **Built the compiler for WebAssembly**, in a throwaway `cdylib` outside
  the repo that depends on `mesh-compiler` and `mesh-manifest` and
  exports four C-ABI functions (no `wasm-bindgen`). Findings E1–E3 and E9
  come from that probe, and so does most of "What's healthy".
  - `cargo build --target wasm32-unknown-unknown -p mesh-compiler` builds
    unchanged on the pinned 1.98.1 and on the 1.91.0 MSRV. `tree-sitter`
    0.27 ships a libc shim and allocator for `wasm32-unknown-unknown`,
    and the grammar's `build.rs` already takes its headers
    (`DEP_TREE_SITTER_LANGUAGE_WASM_HEADERS`). The C is compiled by
    `clang`.
  - The linked module **imports nothing**. It instantiates with an empty
    import object in Node 22.
  - Size: 485 KB, 163 KB gzipped, at `opt-level = "z"` with LTO, before
    `wasm-opt`, and including the probe's own test code.
  - **It agrees with the CLI.** Replicating `mesh check`'s flow in the
    probe, 158 runs (every `.mprx` under `examples/` without a model,
    every `check` fixture and example with its manifest, and every
    broken-manifest fixture) printed exactly what `mesh check --format
    json` prints, byte for byte.
  - **The nesting limits hold in WASM.** `crates/mesh-compiler/tests/nesting.rs`'s
    thirteen sources, at exactly the limit and against its manifest, and
    its deep manifest type, all check at the default linker stack. With
    the stack forced down, a release build still passes them all at
    128 KiB and an unoptimized one at 256 KiB (it fails at 128 KiB), so
    the default leaves at least 4× headroom. Every shape at 129, 5,000
    and 100,000 levels is one `nesting-too-deep`, and nothing traps.
  - Checking `examples/users-page.mprx` takes 0.13 ms per call in Node.
- Checked the npm registry: nothing is published as
  `@valance/mesh-compiler`, and the `@valance` organisation already
  exists, with no public packages.

**What's healthy.**
- The layering pays off. No crate needed a change, a feature flag or a
  `cfg` to build for WASM. Only the CLI and the server touch the file
  system, threads or stdio, and neither is needed in WASM.
- The diagnostics JSON is already the right boundary. It is versioned,
  has a schema, and its promise already allows additive properties
  ("ignore any you don't know"), which E3 needs.
- The stack-safety work of v0.3 (A1, A2, D12) transfers to WASM's small,
  fixed stack without change.
- Performance and size aren't concerns for a JS package.

### Findings

| # | Finding | Severity | Status |
|---|---|---|---|
| E1 | **The check flow isn't the compiler's.** Load the manifest; if it has errors, report only those, against the manifest; else look up the component (`manifest-missing-component`, against the manifest); then `compile_with`. That orchestration is in `crates/mesh-cli/src/main.rs` (`run_check`), not `mesh-compiler`. `mesh-lsp` has its own variant, which D9 of v0.3 made different on purpose. A WASM entry point would be a third copy, and I1 wants one. The probe had to copy it to agree with the CLI. | Medium, blocking for Pass 1 | Open. D3. |
| E2 | **The Semantic IR has no serialized form.** Its types derive no `Serialize`, and ARCHITECTURE.md says "we're intentionally *not* locking down a binary or serialized IR format yet". Meanwhile the README says other layers consume MESH "through the Semantic IR", and `@valance/mesh-compiler`'s description promises "compilation". What a JS caller can get back from the WASM build is therefore undecided. | Blocking for scoping v0.4 | Open. Open decision 1. |
| E3 | **JSON positions are in units JavaScript can't index.** Each position has a UTF-8 `byte` offset and a `char` column. A JS string is indexed in UTF-16 code units, so a JS caller can't slice its own source at a diagnostic, or place a marker in Monaco or CodeMirror, without re-deriving the position. `SourceMap` already maps to UTF-16 (D2 of v0.3). | Medium, blocking for a usable JS API | Open. D5. |
| E4 | **The npm placeholders can't build what they declare.** `@valance/mesh-lsp` has `"bin": "./dist/cli.js"` but no `src/cli.ts`. None of the three has a test, a lockfile, or a workspace. CI never builds or typechecks them. They're at `0.0.1`, while the workspace is `0.3.0`. | Low now, blocking for publishing | Open. Pass 0. |
| E5 | **Three npm packages is the wrong shape for one WASM module.** `@valance/mesh-language` is to wrap "grammar, parser bindings, syntax nodes, and AST types". Like the IR (E2), the AST has no serialized form. And if `mesh-language` and `mesh-compiler` each shipped a module, Tree-sitter and the parser would ship twice, as two instances that can't share a tree. | Medium | Open. Open decision 2. |
| E6 | **MESH has only ever been built and tested on Linux.** CI runs on `ubuntu-latest` only. `.gitattributes` keeps fixtures LF for Windows, and `mesh-lsp`'s `uri.rs` handles Windows paths and drive letters, but neither has run on Windows, and nothing has run on macOS. Shipping prebuilt `mesh-lsp` binaries (Open decision 3) would ship binaries for systems no test has run on. | Medium, blocking for binary distribution | Open. D9, Pass 0. |
| E7 | **Releases are made by hand.** A release is a commit, and the maintainer pushes the tag afterwards. That's fine for a source-only release. It's not fine for several npm packages and per-platform binaries that must all carry the same version, built from the tagged commit. npm provenance also needs a CI publish. | Medium, for Pass 3 | Open. D10. |
| E8 | **The `@valance` npm organisation already exists.** The registry answers for it and lists no public packages. From here there's no telling whether the maintainer controls it. v0.3's Risks said the scope "must be registered on npm before v0.4 publishes anything". | Blocking for publishing | Open. A maintainer action, before Pass 3. If the scope isn't ours, D11 of v0.3 needs a new scope before anything is published. |
| E9 | **A panic in WASM is a trap, and it poisons the instance.** `wasm32-unknown-unknown` can't unwind, so a panic aborts the call mid-way, possibly with the allocator's state half-updated. D7 of v0.3 has no WASM counterpart: nothing says what a JS caller sees then, or that the instance is never reused. Nothing frees a call's input or output either, so a long-lived instance would grow without bound. The probe had both problems. | Medium | Open. D6. |
| E10 | **Where configuration lives is still undecided.** v0.3 settled on editor settings (`mesh.model`, `mesh.components`) and deferred a project file that `mesh check` could read too "to v0.4's packaging". A JS API adds a third reader of the same facts, since it also needs to know which manifest and component to check against. | Low | Open. Open decision 4. |
| E11 | **v0.3's accepted limitations are still there:** manifest edits aren't debounced (B5); closing tags (B8) and record fields (B9) have no definition; a diagnostic has one span (A13); a lone `\r` isn't a line break; the Helix configuration is untested. | Low | Carried. None is in v0.4's theme, so they stay non-goals (see "After v0.4"). |
| E12 | **The grammar's non-Rust bindings are untested.** `grammar/tree-sitter-mprx/bindings/` has C, Go, Node, Python and Swift bindings from the Tree-sitter CLI's template. None is built in CI; the Node binding's build is skipped (`npm ci --ignore-scripts`). | Low | Open. Non-goal for v0.4: the grammar isn't published to any registry, and the setup guide installs it from the repo. The grammar's README should say they're untested (Pass 3). |

## Theme

**v0.4: MESH outside Rust.** The same compiler, built for WebAssembly,
behind a small JavaScript API that answers what `mesh check` answers,
and `mesh-lsp` installable from npm. The main user is a JS or TS program
that generates MPRX, often with a model, and has to check it before
using it: the generate-check-repair loop that the JSON diagnostics were
made for. The second is anyone who wants MESH in their editor without a
Rust toolchain.

## Architecture and invariants

```text
                           ┌─ mesh check            (native)
mesh-compiler ── check ────┼─ mesh-wasm → @valance/mesh-compiler (JS)
                           └─ mesh-lsp              (native, D9 of v0.3)
                                 ↑
                         @valance/mesh-lsp (launcher only)
```

I1–I5 carry over from v0.3 unchanged. They were written for the
server, and they apply to every new host: the WASM build is one more
consumer of the compiler, with no semantics of its own.

**New invariants (proposed).**
- **I6. One compiler, every host.** The JavaScript API is the Rust
  compiler compiled to WebAssembly. No MPRX or manifest rule, no
  message and no position is computed in TypeScript. The wrapper moves
  bytes across the boundary and parses the JSON it gets back, nothing
  more.
- **I7. JS answers what `mesh check` answers.** For the same source,
  manifest and explicit component, the JS API returns exactly the
  diagnostics document `mesh check --format json --component` prints:
  the same codes, messages, positions and suggestions, in the same
  order. As in v0.3's I3, it filters none out and adds none.
- **I8. What isn't a format isn't exported.** Nothing crosses the WASM
  boundary unless it has a versioned, published shape. Today that's the
  diagnostics document (`schemas/diagnostics-v1.schema.json`). The IR and
  AST cross only if Open decision 1 gives them one.

## Goals

- A `mesh-wasm` crate that builds the compiler for
  `wasm32-unknown-unknown` with `cargo` alone (D1, D2).
- One check flow in `mesh-compiler`, used by the CLI and the WASM build
  (D3, E1).
- `@valance/mesh-compiler`: the WASM module and a thin, typed ESM
  wrapper. It checks a source string, with or without a manifest and an
  explicit component, and returns the diagnostics document (D4). It
  runs in current Node LTS releases and in browsers.
- Positions JavaScript can use directly: UTF-16 offsets and columns
  beside today's bytes and `char` columns, in the JS API and in `mesh
  check --format json` alike (D5, E3).
- A crash contract at the WASM boundary: no input makes the API hang,
  leak without bound, or return a wrong answer after a trap (D6, E9).
- `@valance/mesh-lsp`: a launcher that starts a prebuilt `mesh-lsp` for
  the user's platform, with no LSP code of its own (D8), if Open
  decision 3 says so.
- CI on Linux, macOS and Windows, and a release workflow that builds
  and publishes every artifact from the tag (D9, D10).
- Documentation: a guide to using MESH from JavaScript, package READMEs,
  the release notes.

## Non-goals (v0.4)

- **New MPRX syntax, or manifest format changes.** The language and
  manifest version 1 stay exactly v0.3's.
- **A serialized IR or AST**, unless Open decision 1 chooses otherwise.
- **The language server in WASM,** in a browser or under WASI.
  `mesh-lsp` uses threads and stdio, and `wasm32-wasip1` has no threads.
  A browser editor can use the JS API for diagnostics; hover and
  completion in a browser are a later question.
- **Editor features.** E11's limitations, references, rename,
  formatting, symbols, semantic tokens. v0.4 is about distribution.
- **Publishing the Rust crates to crates.io,** or the grammar to npm or
  crates.io (E12). `cargo install --path` from a clone stays the Rust
  install.
- **A VS Code extension.** It needs Open decision 3's binaries first;
  with them, it's a small v0.5 item (D8 of v0.3).
- **The project file,** if Open decision 4 takes the recommendation.

## Definition of Done

**WASM agrees with the CLI (I7).** A test in Node loads the built module
through `@valance/mesh-compiler` and, for every `.mprx` fixture and
example, with and without a model, and every broken-manifest fixture,
compares the API's document with `mesh check --format json` run with the
same explicit `--model` and `--component`. They are equal, byte for byte
before parsing. The fuzzer's mutants are compared the same way, for a
fixed budget in CI and one recorded local run of at least 100,000.

**Positions work in JavaScript (D5).** For sources with multi-byte UTF-8,
characters outside the Basic Multilingual Plane, CRLF and a leading BOM,
`source.slice(start.utf16, end.utf16)` in JS is exactly the text the
diagnostic's byte span covers. The CLI's JSON gains the same fields, the
schema lists them, and the schema test checks real output against it.

**It doesn't crash, hang or leak (D6).**
- `nesting.rs`'s sources run in WASM at the limit, against its
  manifest, at the default stack.
- A test-only export that panics shows that the API throws
  `MeshInternalError`, and that the next call answers correctly, from a
  new instance.
- 100,000 checks on one instance leave its memory bounded.

**It runs where JavaScript runs.** The package's tests pass on every
Node LTS release CI names, and a smoke test checks a file in headless
Chromium through Playwright.

**The packages are what we say they are.**
- `npm pack` of each package contains exactly the files a test lists.
- Installed from its tarball into an empty directory, each passes a
  smoke test, and nothing in it needs a Rust toolchain.
- Every package's version equals the workspace version, and a test pins
  that, beside the existing test that pins their names
  (`crates/mesh-cli/tests/packages.rs`, D11 of v0.3).
- The module's gzipped size is within D2's budget, checked in CI.

**The launcher starts the server (D8), on every platform CI runs.**
`mesh-lsp`'s transport tests (`crates/mesh-lsp/tests/transport.rs`)
pass through the launcher, on Linux, macOS and Windows.

**It's usable.** A "Using MESH from JavaScript" guide shows a
generate-check-repair loop, and its example is run by a test. The
editor setup guide gains the npm install path, verified in Neovim as in
v0.3.

## Decisions (proposed)

### D1. Target `wasm32-unknown-unknown`, built by `cargo`

- One target, `wasm32-unknown-unknown`: it runs in Node and in browsers
  with no imports, and the probe shows it builds today.
- Rejected: `wasm32-wasip1`, which needs a WASI host in the browser and
  gains nothing the compiler uses; and Emscripten, a second toolchain
  for C that `tree-sitter` no longer needs.
- The C (Tree-sitter's runtime and `parser.c`) is compiled by `clang`
  through `cc`, as `tree-sitter`'s build script arranges. CI's Ubuntu
  runner has it. Contributors on macOS may need LLVM's `clang` rather
  than Apple's; the contributor checklist says so once Pass 1 knows.
- `tree-sitter` stays pinned to 0.27. A bump is a change to test like
  any other, because the WASM shim is its code, not ours.

### D2. A hand-written boundary: JSON in, JSON out, no `wasm-bindgen`

- A new crate, `crates/mesh-wasm` (`cdylib`), depends only on
  `mesh-compiler` and `mesh-manifest`. It exports a few `extern "C"`
  functions: allocate and free a buffer, check, read the result, and the
  version.
- Strings cross as UTF-8 bytes in linear memory, and the result is the
  diagnostics document, already JSON and already specified. There is no
  second encoding of anything.
- The TypeScript wrapper is small: copy in, call, copy out, free,
  `JSON.parse`. Its tests are the Definition of Done's.
- Rejected: `wasm-bindgen`. Its CLI must match the crate's version
  exactly, which is one more tool to pin in CI and on every contributor's
  machine, and its generated glue is code we'd ship and not read. What
  it buys (rich types across the boundary) isn't needed while only JSON
  crosses (I8). If Open decision 1 exports the IR later, it's still
  JSON.
- **Size budget:** 300 KB gzipped for the module, checked in CI. The
  probe was 163 KB before `wasm-opt`. `wasm-opt` is optional and not a
  build requirement.

### D3. One check flow, in `mesh-compiler` (E1)

- `mesh-compiler` gains the whole check: optional manifest text and its
  path, the component, the source and its path, returning the
  diagnostics together with which document (the source or the manifest)
  they are reported against. Its rules are exactly `run_check`'s today:
  manifest errors stop the check; a missing component is reported on the
  manifest; otherwise the source is compiled.
- The CLI calls it, and its output doesn't change: every fixture test
  pins that already. `mesh-wasm` calls it and adds nothing.
- The component is always explicit in this API (I5). The CLI keeps
  deriving `--component` from the file's stem, before the call, as D6
  of v0.3 allows.
- `mesh-lsp` keeps D9 of v0.3's different policy (a broken manifest
  moves dependents to model-less checking), because an editor needs the
  template's own syntax errors while the manifest is being fixed. It
  keeps using `compile_with` directly.

### D4. The JS API returns the diagnostics document

- `@valance/mesh-compiler` exports roughly one function: check `source`
  at `path`, optionally against a manifest (its text and path) and an
  explicit component, returning the diagnostics document of I7, typed
  from the JSON Schema. Also `version`. The pass plan fixes the names.
- The manifest is passed as **text**, not a JS object, so its
  diagnostics have positions, and so there is exactly one manifest
  parser (I6).
- The component is required whenever a manifest is given. The API never
  derives it from `path` (I5).
- Loading: in Node the module loads itself. In a browser, the caller
  passes the `.wasm` file's URL, bytes or a compiled
  `WebAssembly.Module` to an explicit `init`. Bundler support beyond
  that is left to the pass plan's research, not promised.
- ESM only, with TypeScript declarations. The oldest Node release is
  the oldest active LTS release on the release date.

### D5. UTF-16 positions, added to the diagnostics document (E3)

- Every position in the diagnostics document gains its UTF-16 code-unit
  offset from the start of the source, and its UTF-16 column, beside the
  existing `byte`, `line` and `column`. The exact property names are the
  Pass 0 plan's.
- The CLI's JSON output gains them too, so I7 stays byte-for-byte. This
  is additive, as the document's promise allows ("properties may be
  added without changing it"): `version` stays 1, and the schema lists
  the new properties.
- They come from `SourceMap` (I4), with its rules for a BOM and CRLF.
  The human-readable output doesn't change.
- Rejected: converting positions in TypeScript. That would be a second
  definition of a position (I4), and it would need the source's
  encoding rules re-implemented in JS.

### D6. The crash contract at the WASM boundary (E9)

The contract of D7 of v0.3, for a host that can't catch a panic.

| Input | Outcome |
|---|---|
| Any source or manifest text | A diagnostics document. The nesting limits (A1, A2) bound every recursive stage, and the probe measured at least 4× stack headroom at the limit. |
| A string that isn't valid UTF-16 (a lone surrogate) | Encoded by `TextEncoder`, which replaces it with U+FFFD, as any JS string written to UTF-8 is. The documentation says so. |
| A trap (a panic, or running out of memory) | The call throws `MeshInternalError`. The wrapper drops that instance and makes a new one on the next call. A trapped instance is never called again, because its heap may be half-updated. |
| Many calls on one instance | Every buffer a call allocates is freed before the call returns, so memory stays bounded. |

- `mesh-wasm` builds with `panic = "abort"`, which is all
  `wasm32-unknown-unknown` offers, and says so, so no one expects
  unwinding.
- A trap is still a bug: it's found by the fuzzer and fixed. Recovering
  from one doesn't make it acceptable, as in D7 of v0.3.

### D7. The package family for v0.4 (E4, E5)

Assuming Open decision 2's recommendation:
- `@valance/mesh-compiler`: the WASM module and its wrapper (D4).
- `@valance/mesh-lsp`: the launcher (D8), if Open decision 3 says so.
- `@valance/mesh-language` is removed from `packages/`. It is not
  published, so no name is burned. It comes back when something would go
  in it: a serialized AST, or a JS parser API. Removing it also drops
  `@valance/mesh-compiler`'s placeholder dependency on it, and
  `crates/mesh-cli/tests/packages.rs` stops expecting at least three
  packages.
- All packages are versioned in lockstep with the Rust workspace:
  v0.4.0 publishes `0.4.0`. A test pins it (Definition of Done).
- The directory becomes an npm workspace with a committed lockfile. CI
  typechecks, tests and packs it.

### D8. The `mesh-lsp` launcher ships prebuilt binaries

Assuming Open decision 3's recommendation:
- One package per platform, each holding one `mesh-lsp` binary:
  `@valance/mesh-lsp-<os>-<arch>` for Linux x64 and arm64, macOS x64
  and arm64, and Windows x64. `@valance/mesh-lsp` lists them as
  `optionalDependencies`, with `os` and `cpu` fields, so npm installs
  only the matching one. esbuild and Biome ship their binaries this way.
- The launcher's `bin` finds the installed platform package, spawns its
  binary with the same arguments, passes stdio through untouched, and
  exits with its status. It has no LSP code of its own (A11 of v0.3).
- On a platform with no package, it says which platforms are supported,
  and how to `cargo install` instead, and exits non-zero.
- Rejected: downloading the binary in a `postinstall` script, which fails
  offline, behind proxies, and under `--ignore-scripts`; and `mesh-lsp`
  under WASI in Node (see Non-goals).

### D9. CI covers every platform we ship for (E6)

- `cargo test --workspace` runs on Linux, macOS and Windows. The
  first Windows run is expected to find something (paths, line endings,
  `uri.rs`), and fixing it is part of Pass 0.
- A WASM job builds `mesh-wasm`, runs the package's tests in Node
  (including the agreement test against a native `mesh` built in the
  same job), runs the Chromium smoke test, and checks the size budget.
- A packages job typechecks, tests and `npm pack`s every package, and
  installs each tarball into an empty directory to smoke-test it.
- The MSRV job also builds `mesh-wasm` for `wasm32-unknown-unknown` on
  1.91.

### D10. Releases are built from the tag (E7)

- A workflow triggered by a `v*` tag builds every `mesh-lsp` binary and
  the WASM module from that commit, checks that every package's version
  equals the tag, packs everything, and publishes to npm with
  provenance.
- It publishes with an npm token the maintainer adds as a repository
  secret. Adding the secret, confirming the scope (E8), and pushing the
  tag are the maintainer's steps. No workflow in this repo publishes
  without them.
- Until the maintainer enables it, the workflow can run on a tag with
  publishing turned off and attach the packed tarballs to the run, so
  it's exercised before the first real publish.
- A GitHub release with the notes and the binaries attached is the same
  workflow's job, for people who don't use npm.

## Passes

### Pass 0 — Groundwork

- D3: the check flow in `mesh-compiler`; the CLI moves onto it with
  unchanged output (E1).
- D5: UTF-16 positions in the diagnostics document, the schema, the CLI
  manual, and the JSON fixtures (E3).
- D9's OS matrix, and whatever the first macOS and Windows runs find
  (E6).
- D7's package clean-up: the npm workspace and lockfile, the removal of
  `@valance/mesh-language` if Open decision 2 agrees, the missing `bin`,
  and the version-lockstep test (E4, E5).

### Pass 1 — `mesh-wasm` and `@valance/mesh-compiler`

- The crate (D1, D2) and the wrapper (D4), with D6's crash contract.
- The agreement test, in Node against the native CLI, over fixtures and
  fuzzer mutants (I7).
- The nesting, trap and memory tests; the Chromium smoke test; the size
  budget. D9's WASM job.

### Pass 2 — The `mesh-lsp` launcher (if Open decision 3 is yes)

- Cross-built binaries for D8's platforms, the platform packages, and
  the launcher.
- `transport.rs`'s cases through the launcher on each OS.
- The editor setup guide's npm install path, checked by
  `editors/neovim/verify.sh`.

### Pass 3 — Release

- D10's release workflow, first run with publishing off.
- "Using MESH from JavaScript", the package READMEs, the grammar
  README's note on its untested bindings (E12), the CHANGELOG and the
  release notes.
- The maintainer confirms the npm scope (E8) and adds the token; then
  the tag publishes.

## Sequencing

- Pass 0 comes first. D3 and D5 change what the CLI prints (D5 only
  additively), and Pass 1's agreement test compares against that.
- Passes 1 and 2 are independent of each other, and can run in either
  order or together.
- Pass 3 needs both, and E8 settled.

## Risks

- **The npm scope may not be ours (E8).** It's cheap to check now and
  expensive to find out at release. If it isn't, the rename is the same
  mechanical change as A10 of v0.3, since nothing is published yet.
- **Windows (E6).** The first Windows run of 557 tests has never
  happened. Expect path, line-ending and URI failures in the tests, and
  maybe in `mesh-lsp`. Pass 0 does it first for that reason.
- **`tree-sitter`'s WASM shim is someone else's code (D1).** A bump could
  break the WASM build, or its behaviour, silently. The agreement test
  catches the second; CI's WASM job catches the first.
- **Supply chain.** Publishing binaries under a scope makes it a target.
  The mitigations are provenance from CI (D10), 2FA on the npm account,
  and no install scripts in any package (D8).
- **Scope creep toward a browser IDE.** The JS API tempts toward
  hover, completion and recovery in the browser. The Non-goals list is
  the defence; each addition needs an outline revision.
- **Exporting the IR too early (Open decision 1).** Once a JSON IR is
  published, NEXUS and PORT will depend on its shape, and ARCHITECTURE.md
  says that shape isn't ready.

## Open decisions

1. **Does the JS API return the Semantic IR (E2)?**
   - (a) **No, diagnostics only** in v0.4. The API checks; a JS program
     that wants to render uses the checked source. Keeps ARCHITECTURE.md's
     line, and I8 holds trivially. **Recommended**: the
     generate-check-repair loop needs only diagnostics, and an IR format
     deserves its own design, with NEXUS and PORT at the table.
   - (b) Return the IR as JSON, marked unstable, with no schema and no
     promise. Useful for experiments, but "unstable" formats get depended
     on anyway.
   - (c) Design and version an IR JSON format (`ir-v1.schema.json`) in
     v0.4. The right end state, but it roughly doubles v0.4, and it
     decides things (spans in the IR, how literals and operators are
     spelled) that NEXUS and PORT should weigh in on.

2. **Which npm packages exist in v0.4 (E5)?**
   - (a) **Two:** `@valance/mesh-compiler` and `@valance/mesh-lsp`;
     `@valance/mesh-language` is removed until it has contents.
     **Recommended.**
   - (b) Keep all three, with `mesh-language` a re-export of
     `mesh-compiler`'s parser-level API, so the family matches the Rust
     crates. It needs something to export, which (a) of Open decision 1
     doesn't give it.

3. **Does v0.4 ship `mesh-lsp` binaries through npm?**
   - (a) **Yes,** as D8 describes. Needs D9's OS matrix and D10's release
     workflow. **Recommended**: the v0.3 release notes promised a
     launcher, and without binaries a launcher does nothing that
     `cargo install` doesn't.
   - (b) No. v0.4 is the WASM package only. `mesh-lsp` stays
     `cargo install`, and Pass 2 moves to v0.5 with the VS Code
     extension, which needs the same binaries.

4. **The project file (E10).**
   - (a) **Defer to v0.5 again.** **Recommended**: v0.4 already has two
     new distribution channels, and the JS API takes its manifest and
     component explicitly, so it doesn't need one.
   - (b) Add a small, versioned project file at the workspace root, read
     by `mesh check`, `mesh-lsp` and optionally the JS API, naming the
     manifest and each file's component. It replaces repeated editor
     settings, and it's a new format to version and document.

## After v0.4

- A serialized, versioned Semantic IR, designed with NEXUS and PORT
  (Open decision 1), and `@valance/mesh-language` if it gives it
  contents.
- A thin VS Code extension over D8's binaries (D8 of v0.3).
- The project file, if Open decision 4 deferred it.
- v0.3's carried limitations (E11): definitions for closing tags and
  record fields, related spans, a debounced manifest, a lone `\r`,
  Helix verified.
- The language questions stay open: a presence test or optional
  chaining, slots and children typing, union or nullable-present types.
