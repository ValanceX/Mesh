## Where v0.2 left off

v0.2.0 (released 2026-09-24) checks what an MPRX file *means*. Given a
component manifest, `mesh check` resolves every tag, prop, event,
reference and command, types every expression, and reports each mistake
with a stable code at the exact span. `--format json` hands the same
diagnostics to programs.

Every piece an editor needs now exists: coded diagnostics, spans on the
IR, resolutions and types kept beside it (`mesh_analysis::Analysis`), and
suggestions with replacement spans. The v0.2 outline's "After v0.2" and
the v0.2 release notes both name the language server as v0.3, followed
by WASM and the npm packages.

## Audit of v0.2.0

**Method.**
- Ran everything CI runs: `cargo fmt --check`, clippy with warnings
  denied, all 33 test binaries, the MSRV check (`cargo +1.91.0 check
  --locked`), and the grammar corpus (40/40).
- Also ran what CI didn't: rustdoc with warnings denied, and
  `tree-sitter generate` to confirm the committed parser matches
  `grammar.js`. Both passed.
- Read every crate's source.
- Stress-tested with adversarial input: deep nesting of every construct,
  large files, deeply nested manifests, and a closed stdout.

**What's healthy.**
- The layering holds. `mesh-analysis` produces facts as data and never
  prose. `mesh-compiler` owns codes, messages and suggestions. The IR is
  never mutated.
- The test suite pins behaviour tightly:
  - fixture output is compared byte for byte;
  - the diagnostics reference and the model-checking guide are checked
    against the fixtures;
  - the code registry has a never-change test;
  - both JSON Schemas are checked against real output.
- Warnings are denied workspace-wide, and the MSRV is checked in CI.
- Performance is not a concern at editor scale. A 37 KB file checks
  against a manifest in about 25 ms, including process start.

## Theme

**v0.3: MESH in the editor.** A language server, `mesh-lsp`, that is a
client of the compiler, not a second one. Its diagnostics are the
compiler's own, and hover, go-to-definition and completion are answered
from the compiler's and the manifest's facts. The editor and `mesh check`
can't disagree about what a file means, because only the compiler
decides it.

## Architecture and invariants

```text
mesh-analysis → mesh-compiler → { mesh check, mesh-lsp, future consumers }
```

`mesh-compiler`, with `mesh-parser`, `mesh-semantic`, `mesh-analysis`
and `mesh-manifest` beneath it, is the single semantic authority. `mesh
check` and `mesh-lsp` are two consumers of it. Neither has semantics of
its own.

A document open in the editor has three kinds of state, and they never
mix:

1. **Canonical state.** The result of the canonical compile: exactly
   what `mesh_compiler::compile_with` returns for the document's text,
   with the manifest and component the configuration snapshot names
   (D6, D9). That is its diagnostics, and for a file that parses, its
   IR and analysis.
2. **Editor recovery state.** For a document whose canonical compile has
   no IR because of a syntax error, what a recovering parse can still
   find (D3). It exists only to answer hover, go-to-definition and
   completion.
3. **LSP presentation.** Turning either state into protocol messages:
   ranges through D2's source map, codes, quick fixes, hover text,
   completion items. It adds no semantic information of its own.

**Invariants.**
- **I1. One source of semantic truth.** The canonical compiler path is
  the only source of semantic truth. `mesh check` and `mesh-lsp` produce
  canonical diagnostics through the same compiler and analysis path.
- **I2. Recovery is editor-only.** Recovered or editor-only information
  never becomes an alternative compilation path, canonical IR, a source
  of diagnostics, or a source of facts that changes `mesh check`'s
  behaviour. It is never cached as canonical state or fed back into it.
  `parse`, `compile` and `compile_with`, and so `mesh check`, are
  unchanged by it.
- **I3. Diagnostics are the compiler's.** The diagnostics published for
  a document are exactly the canonical compile's diagnostics for that
  document's current snapshot: the same codes, messages, spans and
  suggestions, in the same order. The server filters none out and adds
  none.
- **I4. Positions have one definition.** Every line, column and LSP
  range derives from D2's source map. Neither the renderers nor
  `mesh-lsp` computes positions another way.
- **I5. Explicit component identity.** The compiler checks a document
  as the template of a component it is told explicitly. Nothing derives
  a component from a file name inside the compiler, and `mesh-lsp` never
  derives one from a URI or file name (D6).

## Goals

- A `mesh-lsp` binary that speaks LSP over stdio, as a client of
  `mesh-compiler` (I1).
- Canonical diagnostics for `.mprx` files and for the manifest itself,
  identical to `mesh check`'s (I3). Diagnostics are kept current as you
  type: each change is recompiled from the document's current snapshot,
  and a result is published only while that snapshot is still current
  (D10).
- Quick fixes from the suggestions diagnostics already carry ("did you
  mean `user`?").
- Hover: the type of an expression, and the declaration a name resolves
  to.
- Go to definition: from a tag, prop, event, command or scope name to
  its declaration in the manifest.
- Completion of tags, props, events, scope names, record members and
  commands, derived only from existing manifest and analysis facts, and
  deterministic, duplicate-free and stably ordered (D4).
- Hover and completion stay useful while the file is broken, which is
  most of the time while typing, through editor recovery state (D3),
  never through a second analysis.
- Syntax highlighting from Tree-sitter queries shipped with the grammar
  (D8), and setup instructions for editors that speak LSP and use
  Tree-sitter.
- No malformed or adversarial document, and no malformed LSP request,
  may cause an uncaught panic, an abort, or a crash of the server
  process (D7).

## Non-goals (v0.3)

- **New MPRX syntax of any kind.** The language stays exactly v0.2's.
  The deferred language questions stay deferred: a presence test,
  optional chaining, slots and children typing, unions.
- References, rename, formatting, document symbols, semantic tokens,
  inlay hints. Each is small once the pieces above exist, but none is
  needed to make MESH usable in an editor.
- A VS Code extension (D8). A future one will be a thin client and
  configuration layer with no MESH semantics in it.
- WASM, and publishing any npm package (v0.4). v0.3 only renames the
  placeholder packages to `@valance/*` and trims `packages/mesh-lsp` to a
  launcher's shape (A10, A11).
- Incremental compilation, whether salsa or Tree-sitter incremental
  reparsing. A full recompile per change is fast enough (see "What's
  healthy").
- Multi-root or cross-file analysis. One `.mprx` file is still the
  template of one component (v0.2 D3).
- Semantics from Tree-sitter queries. They highlight; they decide
  nothing (D8).
- A project file shared by the CLI and the server (D6, Open decisions).

## Definition of Done

**Canonical diagnostics agree with the CLI.** A test drives `mesh-lsp`
over every `.mprx` fixture, pass and fail, with and without a model, and
every broken-manifest fixture. For each document it compares the
published diagnostics with `mesh check --format json` run with the same
explicit `--model` and `--component` the server's configuration names
(D6), or with no `--model` where D9 says the document is checked without
one. They match exactly: codes, messages, ranges (through D2) and
suggestions, in order. For fixtures with syntax errors, the published
diagnostics are still exactly the CLI's syntax errors: editor recovery
state (D3) adds nothing to them. Hover, definition and completion may
additionally use recovery state; that isn't part of this comparison.

**Positions are exact.** The source map's tests cover, in each direction
and in `char`, UTF-8 and UTF-16 units:
- offsets inside a multi-byte UTF-8 sequence, and positions inside a
  UTF-16 surrogate pair;
- characters outside the Basic Multilingual Plane (such as emoji);
- offsets at and beyond the end of the file, and positions past the end
  of a line;
- zero-width spans;
- LF and CRLF line endings, and a leading byte-order mark.

Every range the fixture-agreement test compares is converted through the
source map, from the same byte spans the CLI renders.

**Navigation works on the examples.** On `examples/users-page.mprx`,
configured as the template of `users-page` against
`examples/components.json`:
- hovering `user.name` shows `string`, and hovering `compact` shows
  `boolean`;
- go-to-definition on `avatar` lands on the `"avatar"` key in the
  manifest, on `alt` on its prop, and on `selectUser` on its command;
- completion inside `<avatar ` offers `src`, `alt` and `size`, and marks
  the required ones.

**It works on broken files.**
- Completion after `user.` offers `name`, `avatar` and `active`, although
  `user.` is a syntax error.
- Completion after `<` offers every component.
- Hover still works on the parts of a file that parse, while another
  part has a syntax error.
- In all three cases, the published diagnostics are the canonical syntax
  errors and nothing else.

**Completion keeps its contract (D4).** Requesting completion twice on
the same snapshot gives identical lists. No list contains two items with
the same label and kind. Each list's order matches D4's ordering rule.
With a manifest that has errors, or a document with no configured
component, completion offers only what D4 allows and never fails.

**The lifecycle holds (D9, D10).** In-process tests show that:
- `didOpen` publishes the canonical diagnostics for that version;
- after a burst of `didChange`s, the last publication is for the latest
  version, and a result computed for an older version, delayed on
  purpose by the harness, is never published over a newer one;
- `didClose` clears the document's diagnostics;
- editing the manifest re-checks every open dependent document against
  the new manifest snapshot; breaking it publishes the manifest's errors
  and moves dependents to model-less checking; fixing it restores their
  model diagnostics;
- no response or publication mixes one document version with another,
  or one manifest snapshot with another.

**It doesn't crash (D7).** No uncaught panic, abort or process crash on:
- *documents:* every fixture, every prefix of every fixture (each
  position a user types through), the nesting stress inputs from A1 and
  A2, empty and whitespace-only files, and a fuzzing run of agreed length over `parse`, `compile_with` and the
  request handlers;
- *protocol boundary:* requests before `initialize` and after
  `shutdown`, unknown methods, malformed or missing parameters, requests
  and notifications for documents that aren't open, `didChange` with a
  version lower than the current one, positions past the end of a line
  or of the file and inside a surrogate pair, a manifest path that
  doesn't exist, can't be read or isn't valid UTF-8, and `exit` with or
  without `shutdown`;
- *transport:* stdin closing, stdout closing, and a message that isn't
  JSON-RPC (the server stops cleanly in each case).

Each case gets the outcome D7 defines for it.

**Highlighting doesn't rot.** The Tree-sitter queries compile against
the grammar and pass their highlight tests in CI (D8).

**It's usable.** The editor setup guide shows at least one editor
getting diagnostics, hover, definition, completion and highlighting from
a `cargo install`ed `mesh-lsp` and the shipped queries.

## Decisions

### D1. Transport: `lsp-server` and `lsp-types`, stdio only

- Use `lsp-server` (rust-analyzer's synchronous message loop) and
  `lsp-types`.
- No async runtime. The work is CPU-bound and takes milliseconds, and a
  synchronous loop is simpler to test in-process.
- Rejected: `tower-lsp`, which needs tokio and a larger dependency tree
  for nothing this server needs.
- Stdio only. Sockets and pipes can come later if a client needs them.

### D2. One source map for every presentation of a position

A6 is about positions, and I4 makes positions one piece of shared
infrastructure, not LSP behaviour.

- A **source map** is built once per source text. It maps a byte offset
  to a line and column, and back, in three column units: `char`s (the
  human and JSON output), UTF-16 code units (the LSP default) and UTF-8
  bytes. It also maps between those units directly.
- Its rules are total, so no lookup panics:
  - an offset inside a multi-byte UTF-8 sequence floors to the start of
    that character, as `locate` does today;
  - a UTF-16 position inside a surrogate pair floors to the start of
    that character;
  - an offset beyond the end of the file clamps to the end, and a column
    past the end of a line clamps to the end of that line's text;
  - a zero-width span maps to a zero-width range at the same place;
  - a line ends at `\n`, and a `\r` before it is not a column, so LF and
    CRLF files give the same columns;
  - a leading byte-order mark is not a column, and an offset on it is
    line 1, column 1.
- Supplementary-plane characters are one `char`, two UTF-16 code units
  and four bytes; the tests pin all three.
- `render_diagnostic` and `render_json` use it, which fixes A6's cost
  and keeps today's output byte for byte.
- `mesh-lsp` converts every range it sends, and every position it
  receives, through it (I4). The server negotiates `positionEncoding`
  (LSP 3.17): UTF-8 when the client offers it, otherwise UTF-16.
- It lives with the renderers, in `mesh-compiler`, unless Pass 0 finds a
  reason for its own crate. Either way it is compiler infrastructure
  that the server consumes.

### D3. Broken files: canonical diagnostics, editor recovery for navigation

This decision applies invariants I1–I3 to A7.

**Canonical state is unchanged.** The server compiles every snapshot
with the canonical compiler, exactly as `mesh check` does. A file with a
syntax error gets its syntax errors, no IR and no analysis. Its
published diagnostics are those syntax errors and nothing else.

**Editor recovery state is separate.** Only when the canonical compile
has no IR, hover, go-to-definition and completion may use a recovering
parse:
- `mesh-parser` gains a recovering entry point beside `parse`, clearly
  named and documented as editor-only. It keeps every element,
  attribute, event binding and child whose subtree has no error, and
  leaves out the ones that do.
- To type or resolve what it recovered, the server calls the same
  analysis code on the recovered tree. It never re-implements a check,
  a type rule or a lookup, so nothing like a second semantic engine can
  grow in `mesh-lsp`.
- What that yields lives only in the editor recovery store for that
  snapshot. It is never published as a diagnostic, never cached as
  canonical IR, never compared with or merged into canonical state, and
  discarded with its snapshot.
- When the canonical compile does have IR, navigation uses canonical
  state only, and recovery doesn't run.

Rejected alternatives:
- Keeping the last good analysis and shifting it through edits. Its
  spans go stale, and what it says about the part being typed is wrong.
- Publishing analysis diagnostics for recovered files. That breaks I3:
  the editor would disagree with `mesh check`, and report errors that
  are artifacts of recovery.

The exact recovery rules get their own short design spec, written
against real Tree-sitter recovery trees the way v0.2's located syntax
errors were, before Pass 3 is planned. That spec may choose *how* to
recover; it may not relax I1–I3.

**The spec is written** (`2026-09-24-mesh-v0.3-editor-recovery.md`). It
refines the first bullet above in two ways the observed trees forced
(B6): recovery is a *forest* (an unclosed block leaves no root element,
but every complete element before it), and it keeps a clean expression
from a pruned block as a part of its own, so `user` in `{user.}` can still
be hovered. It only trusts clean subtrees whose delimiters are real,
because clean-looking subtrees after a mistake are often misparsed
closing tags. Recovered parts are analyzed by `mesh_analysis::analyze`
and a new `analyze_expression`, the same walker; `mesh-lsp` computes
nothing.

### D4. Completion: context from the syntax tree, items from existing facts

**Context.** At the moment completion is wanted, the tree is almost
always broken (`<avatar `, `user.`, `on.`). So the question "what kind
of position is this offset in?" is answered by `mesh-parser` from the
Tree-sitter tree, recovery nodes included. The answer is a small enum:
a tag name; an attribute or event name on element *E*; an expression; a
member of expression *X*; a command name. The CST stays private to
`mesh-parser`, as the architecture requires; only the enum crosses the
crate boundary. Knowing *where* the cursor is is syntax. Everything
about *what* is valid there comes from the facts below.

The observed trees (B7) settle *how* the question is answered: from the
tokens **before** the cursor, and their parents' kinds, not from the node
the cursor is in, which is often the next text node or an `ERROR`. Where
the tokens don't say unambiguously, the answer is "no context", and
completion offers nothing. The Pass 4 plan's rule table cites an observed
shape for every rule.

**Contract.**
- **Derived, not invented.** Every item comes from facts that already
  exist: the manifest's declarations (components, props, events,
  commands, scope names, record fields), and the type of expression *X*
  from canonical state, or from D3's recovery state when there is no
  canonical IR. Completion adds no language rule. For example, it
  offers commands only in an `on.` handler because that is where
  analysis accepts them, not because of a rule of its own.
- **Deterministic.** The same snapshot, manifest snapshot and position
  always give the same list.
- **Duplicate-free.** At most one item per label and kind.
- **Stable order.** Required props before optional ones; otherwise the
  manifest's order, which is sorted by name. The client may re-sort by
  what has been typed.
- **Degrades to less, never to wrong.** With no manifest, a manifest
  that has errors, or no configured component, completion offers nothing
  that needs a model. When an expression has no type, member completion
  offers nothing. It never guesses.

### D5. The manifest keeps a span for every declaration

- `mesh-manifest` records the span of each declaration's key: component,
  prop, event, command, parameter, scope name, named type and record
  field.
- This is additive. The model's structs are `#[non_exhaustive]`, so new
  fields break no one.
- `mesh_analysis::Target` names are enough to look these spans up, so
  analysis doesn't change.

### D6. Component identity is explicit

The compiler already takes the component explicitly:
`compile_with(source, CompileOptions::with_template(template))`. v0.3
keeps it that way (I5).

- **The CLI** may keep deriving `--component` from the file's stem when
  it isn't given. That's a convenience of the command line, applied
  before the compiler is called.
- **The server never derives it** from a URI or file name. A file name
  isn't a stable identity in an editor:
  - an unsaved or untitled document has none;
  - renaming a file would silently change what it means;
  - generated or virtual documents have URIs, not meaningful names;
  - one file can be reached through two paths.
- **The server's configuration** names both answers:
  - `mesh.model`: the manifest, as a path relative to the workspace
    root;
  - `mesh.components`: a map from workspace-relative document path to
    component name.

  Both come in `initializationOptions` and are refreshed through
  `workspace/configuration`. For the examples, the map would hold
  `users-page.mprx` → `users-page` and `user-card.mprx` →
  `user-card-example`, which covers the per-file override case without
  a separate mechanism.
- **A document the map doesn't name,** including every untitled one, is
  checked without a model, exactly as `mesh check` without `--model`
  would check it. The server logs, once per document, that the document
  has no configured component. It adds no diagnostic for that (I3).
- With no `mesh.model` at all, every document is checked without a
  model.

Where this configuration should live long-term (editor settings, or a
project file the CLI reads too) is the one open decision below.

### D7. Crash safety

**Contract.** No malformed or adversarial document, and no malformed LSP
request, may cause an uncaught panic, an abort, or a crash of the server
process. Each kind of bad input has a defined outcome:

| Input | Outcome |
|---|---|
| A malformed or adversarial document | Canonical diagnostics, and empty or partial results for hover, definition and completion. |
| A malformed LSP request, or one the server can't serve | A protocol error response as LSP defines it: `ServerNotInitialized` before `initialize`, `InvalidRequest` after `shutdown`, `MethodNotFound` for an unknown request, `InvalidParams` for parameters that don't decode. Notifications are never answered: a malformed one is logged and ignored. |
| A request about a document that isn't open, or a position outside it | An empty result for a document that isn't open. A position is clamped through D2. |
| A broken or unreadable manifest | Manifest diagnostics, or a logged error for a path that can't be read, and model-less checking of dependents (D9). |
| stdin closes, or stdout closes | The server stops cleanly, without a panic, and exits with status 1, as LSP defines for exiting without `shutdown`. |
| A message that isn't JSON-RPC at all: not JSON, or JSON without a method or id | The server stops cleanly with status 1, as for a closed stdin. The transport (`lsp-server`'s stdio reader) can't read past such a message, and with no id there is no request to answer. Parameters that don't decode, in a well-formed message, are the "malformed LSP request" row above. (Pass 1 plan, "As built" 2.) |
| An internal programming bug | Found by tests and fuzzing and fixed. Defence in depth (below) contains one if it slips through, but containing a panic doesn't make it acceptable. |

**How.**
- The nesting limits (A1, A2) bound every recursive stage, and the tests
  added with them pin the whole pipeline to a 2 MiB stack.
- The server compiles on a thread it spawns with an explicit stack size,
  never less than those tests use.
- Each request handler runs under `catch_unwind`. A panic is logged and
  answered with an internal-error response, and the server keeps
  running. Request handlers only read state, so a panic in one leaves
  nothing half-changed to drop. A compile that panics publishes nothing
  and stores nothing for its snapshot (B3).
- A `cargo-fuzz` target (or a `proptest` suite, if CI can't run fuzzing)
  covers `parse`, `compile_with` and the request handlers.

### D8. Editor integration: Tree-sitter queries and setup guides, no VS Code extension

- **Highlighting.** `grammar/tree-sitter-mprx/queries/highlights.scm`
  ships in v0.3 (A12). It serves Neovim, Helix and Zed directly.
- **The boundary.** Tree-sitter queries decide how text is coloured and
  nothing else. No MESH feature reads a query capture: diagnostics,
  hover, definition and completion come only from the MESH parser,
  compiler and analysis. The queries may be approximate where
  highlighting is concerned; semantics may not.
- **They can't silently rot.**
  - Every query must compile against the grammar.
  - Highlight tests (Tree-sitter's `test/highlight/` assertions) pin the
    captures on a few representative files.
  - Both run in the grammar's existing CI step.
- **No VS Code extension in v0.3.** v0.3 ships `mesh-lsp`, the grammar
  with its queries, and setup instructions for editors that can run an
  LSP server and load Tree-sitter queries directly.
- **A future VS Code extension** is a thin client and configuration
  layer. It launches `mesh-lsp`, passes D6's configuration and provides
  highlighting. It contains no MESH semantics.

### D9. Manifest lifecycle

The invariant: every analysis runs against one coherent manifest
snapshot, and all of it (loading, validation and the diagnostics it
produces) comes from `mesh-manifest`, as it does for `mesh check`.

- **Source of truth.** The manifest's text is the editor's buffer while
  the manifest is open, and the file on disk otherwise.
- **Snapshots.** Each distinct manifest text is loaded and validated
  once, with `mesh_manifest::load`, into an immutable snapshot:
  - either a valid `Manifest`, or its complete list of manifest
    diagnostics;
  - the configuration it was loaded under.
- **Initial load.** The manifest named by `mesh.model` is loaded at
  `initialized`, before any document is checked against a model.
- **Changes.** A new snapshot is loaded and every open dependent
  document is recompiled when any of these happens:
  - an edit to the open manifest;
  - a change to the file on disk while it isn't open, through
    `workspace/didChangeWatchedFiles`;
  - closing the manifest, which reverts to the disk contents;
  - a change to `mesh.model` or `mesh.components`.

  A full recompile of each dependent document is fine; nothing is
  incremental.
- **A valid snapshot** is used for every dependent document with a
  configured component. If the manifest doesn't declare that component,
  the canonical `manifest-missing-component` diagnostic is published on
  the manifest, and that document is checked without a model.
- **Publishing on the manifest.** Whenever a snapshot is loaded, and
  whenever the set of missing components changes, the manifest's URI
  gets its current diagnostics, even when that's an empty list. A clean
  load publishes an empty list, which clears whatever an earlier session
  or an earlier broken version left there (Pass 1 plan, "As built" 3).
- **A broken snapshot** publishes its manifest diagnostics on the
  manifest file. While it is broken, dependent documents are checked
  without a model: their diagnostics are exactly `mesh check` without
  `--model`. Their diagnostics are never computed against an older, valid
  snapshot, which would be stale, or against a broken one. The CLI
  reports only the manifest's errors and stops. That's the right choice
  for a one-shot check, but an editor still needs the template's own
  syntax errors while the manifest is being fixed. The server chooses a
  different canonical compile for the document, not different content.
- **Coherence.** A document's result records the manifest snapshot it
  used, and D10's staleness rule applies to it: a result computed
  against a manifest snapshot that has since been replaced is never
  published.

### D10. Document snapshots, versions and diagnostic publication

**Snapshots.** Each open document's state is an immutable snapshot:
- its URI, its LSP version, and its full text (full text sync; see
  Non-goals);
- the configuration and manifest snapshot in force (D6, D9);
- once computed: its canonical state, its source map, and any editor
  recovery state.

Every request and every publication observes exactly one such snapshot.
Nothing mixes the text of one version with results of another.

**The staleness rule.** A result computed for a snapshot that is no
longer current, whether because of a newer document version, a newer
manifest snapshot or new configuration, is never published and never
replaces newer state. It is discarded. A request answered from a
snapshot answers from that snapshot alone.

**Publication lifecycle.**

| Event | What happens |
|---|---|
| `didOpen` | A snapshot is created, compiled, and its canonical diagnostics are published with its version. |
| `didChange` | A new snapshot replaces the old one. After a short debounce it is compiled and, if still current, its diagnostics are published with its version. A change with a version lower than the current one is logged and ignored. |
| `didClose` | The document's diagnostics are cleared (an empty publication) and its state is dropped. Closing the manifest reverts it to disk (D9). |
| Manifest or configuration change | Every open dependent document gets a new snapshot, is recompiled, and is published as above (D9). |
| A result for a stale snapshot | Discarded, as the staleness rule says. |

- Published diagnostics are exactly the canonical ones (I3): the MESH
  code as `code`, `codeDescription` linking to its entry in the
  diagnostics reference, and ranges through D2.
- Diagnostics are pushed (`textDocument/publishDiagnostics`), not
  pulled.
- Quick fixes: one `codeAction` per suggestion, replacing the
  suggestion's span.
- If A13's related spans exist, they become `relatedInformation`. If
  they don't, nothing else changes.

**Requests wait for their snapshot** (added after the audit, B2). A
request about a document is answered from the snapshot that is current
when it arrives. If that snapshot isn't compiled yet, the request is held
and the document's debounce is cut short; when the snapshot's result
arrives, the request is answered from it. If a newer snapshot replaces
it first, the request is answered with `ContentModified`, as LSP 3.17
prescribes, and a cancelled one with `RequestCanceled`. Holding is
bookkeeping: the loop never blocks. Without this, hover right after
typing, and completion almost always, would answer from nothing.
`codeAction` keeps its Pass 1 behaviour (an empty list while a newer
version is pending), since clients ask for it again on every cursor move.

This is a correctness contract, not a concurrency design. The pass
plans choose how the loop, the debounce and the compile thread meet it.

### D11. The npm package family is `@valance/*`

- Every MESH npm package is scoped `@valance/`, with the Valance
  spelling, as in `@valance/mesh-language`, `@valance/mesh-compiler` and
  `@valance/mesh-lsp`. That applies to the whole family, including any
  package added later, and to the dependencies between them.
- No package uses the unscoped name `mesh`.
- Pass 0 renames the placeholders under `packages/` and their references
  (the README's repository map). Nothing is published in v0.3.

### D12. Format validity is not the same as resource limits

- **Format validity** is what MPRX or manifest version 1 allows. It is
  defined by the spec, the manifest reference and the JSON Schema, and
  it has no depth limit.
- **Resource limits** are what this implementation supports. The
  128-level nesting limits (A1, A2) are resource limits. They keep a
  pathological input from exhausting the stack.
- Changing a resource limit is a behaviour change, recorded in the
  CHANGELOG, and breaking when it rejects something that was accepted.
  It does not need a new manifest version, and before 1.0 it doesn't
  need a major version either. The `[Unreleased]` breaking-change note
  stays.
- Pass 0 makes the wording say this:
  - **The manifest reference's "Versions" promise** gains a sentence
    saying the promise covers what a manifest means and whether the
    format allows it. Documented resource limits of an implementation,
    such as the nesting limit, are not part of the format, and a
    version of MESH may change them.
  - **The depth diagnostics** describe a supported limit, not a rule of
    the format. `nesting-too-deep` becomes "this is nested more than 128
    levels deep, the deepest MESH supports" (it now says "elements and
    expressions can't nest any deeper"). `manifest-nesting-too-deep`
    becomes "the manifest nests arrays and objects more than 128 levels
    deep, the deepest MESH supports". Their codes don't change (codes
    are stable; messages may improve), and their fixtures and
    diagnostics-reference entries are updated to match.

## Sequencing

- Pass 0 comes first; everything else uses it.
- Passes 1 and 2 use canonical state only, so they don't wait for D3's
  design spec.

- Pass 4 depends on Pass 3.

  time.

## Risks

- **Tree-sitter recovery trees are hard to predict** (the lesson of
  v0.2's located syntax errors). D3 and D4 depend on them. Mitigation:
  pin every recovered shape with a fixture, and fall back to "no answer"
  rather than a wrong one. Canonical diagnostics don't depend on
  recovery at all (I2), so the worst case is a missing hover or
  completion, never a wrong diagnostic.
- **A second semantic engine growing in `mesh-lsp`.** Hover and
  completion code is where rules get quietly re-implemented. Mitigation:
  I1, D3's rule that recovery reuses analysis code, D4's "derived, not
  invented" rule, and review against them.
- **Explicit component identity is more configuration.** Every checked
  document needs an entry in `mesh.components`. That's the price of
  identity that survives renames and untitled buffers (D6); the open
  decision below is about where that configuration lives.
- **Scope creep toward a full IDE.** The Non-goals list is the defence;
  each addition needs an outline revision.
- **The `@valance` scope must be registered on npm before v0.4
  publishes anything.** Nothing is published in v0.3.

## Open decisions

1. **D6: where the component map lives.** For v0.3 it is editor
   configuration: `mesh.model` and `mesh.components`, sent by the
   client. That's enough for the server, but every editor, and every
   team member's editor, has to repeat it, and `mesh check` can't read
   it. The alternative is a small project file at the workspace root
   that both the CLI and the server read. That means a new, versioned
   format, which is why it's listed as a non-goal for now. Recommended:
   ship editor configuration in v0.3, and decide on the project file
   with v0.4's packaging. This doesn't block Pass 0; Pass 1 needs an
   answer.
