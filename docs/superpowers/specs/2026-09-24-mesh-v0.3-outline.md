# MESH v0.3 — Outline

Date: 2026-09-24
Status: Draft outline, written after an audit of v0.2.0. It is not an
implementation plan.
- The audit's findings are recorded below. The ones fixed on the branch
  that carries this outline are marked **fixed**.
- Decisions D1–D10 are **proposed**, each with a recommendation. D3, D6
  and D8 need an answer before the pass that depends on them is planned;
  they are collected under "Open decisions".
- Nothing here is a Rust API or a file-level design; that belongs to each
  pass's plan.

Repo: `mesh`

## Where v0.2 left off

v0.2.0 (released 2026-09-24) checks what an MPRX file *means*. Given a
component manifest, `mesh check` resolves every tag, prop, event,
reference and command, types every expression, and reports each mistake
with a stable code at the exact span. `--format json` hands the same
diagnostics to programs.

Every piece an editor needs now exists: coded diagnostics, spans on the
IR, resolutions and types kept beside it (`mesh_analysis::Analysis`), and
suggestions with replacement spans. The v0.2 outline's "After v0.2" and
the v0.2 release notes both name the language server as v0.3, followed
by WASM and the npm packages.

## Audit of v0.2.0

**Method.**
- Ran everything CI runs: `cargo fmt --check`, clippy with warnings
  denied, all 33 test binaries, the MSRV check (`cargo +1.91.0 check
  --locked`), and the grammar corpus (40/40).
- Also ran what CI didn't: rustdoc with warnings denied, and
  `tree-sitter generate` to confirm the committed parser matches
  `grammar.js`. Both passed.
- Read every crate's source.
- Stress-tested with adversarial input: deep nesting of every construct,
  large files, deeply nested manifests, and a closed stdout.

**What's healthy.**
- The layering holds. `mesh-analysis` produces facts as data and never
  prose. `mesh-compiler` owns codes, messages and suggestions. The IR is
  never mutated.
- The test suite pins behaviour tightly:
  - fixture output is compared byte for byte;
  - the diagnostics reference and the model-checking guide are checked
    against the fixtures;
  - the code registry has a never-change test;
  - both JSON Schemas are checked against real output.
- Warnings are denied workspace-wide, and the MSRV is checked in CI.
- Performance is not a concern at editor scale. A 37 KB file checks
  against a manifest in about 25 ms, including process start.

### Findings

| # | Finding | Severity | Status |
|---|---|---|---|
| A1 | A valid `.mprx` file nested about 10,000 levels deep (elements, arrays; about 50,000 for unary operators or parentheses) overflowed the stack and aborted `mesh check` with `SIGABRT`: no diagnostic, and a signal instead of an exit status. Lowering, analysis and the tree types' derived `Clone`/`PartialEq`/`Drop` are all recursive, and nothing bounded their depth. This matters most for a toolchain meant for untrusted, generated input, and it would kill a long-running language server. | High | **Fixed.** `mesh-parser` checks the tree iteratively before lowering; deeper than 128 levels is `nesting-too-deep`. At 128 levels, every nesting shape compiles against a manifest, unoptimized, on a 2 MiB thread stack with more than 2× headroom. At 256, nested arrays needed up to 1.5 MiB. |
| A2 | A manifest nested about 50,000 levels deep overflowed the stack the same way, and loading was quadratic in depth: each level's raw JSON was re-parsed. | Medium | **Fixed.** Arrays and objects nested more than 128 levels deep are `manifest-nesting-too-deep`, found by a linear scan. The value matches `serde_json`'s own recursion limit. |
| A3 | Doc comments made stale by v0.2: `mesh-compiler` claimed "transformation, optimization, and code generation"; `mesh-semantic` said no component model exists yet; `EventValue` said names aren't validated; `Analysis::types` didn't mention that fixed-result operators keep their type after an error. | Low | **Fixed.** |
| A4 | CI didn't run rustdoc with warnings denied, or check that `src/parser.c` is regenerated from `grammar.js`. | Low | **Fixed.** Both are CI steps now, and the contributor checklist in `docs/README.md` lists them. |
| A5 | `mesh check --format json … \| head -c1` panics with exit status 101 ("failed printing to stdout: Broken pipe"), because `println!` panics when stdout closes. | A7 | A file with any syntax error gets no IR, so it gets no analysis at all. That's the right rule for `mesh check`, but while you type, a file is broken most of the time: `user.` is a syntax error at exactly the moment completion is wanted. | Blocking for hover and completion | Open. | A8 | The loaded `Manifest` keeps no spans for its declarations (only `"components"`), so nothing can jump from a name in a template to where it is declared. | Blocking for go-to-definition | Open. D5, Pass 0. |

The `mesh-lsp` crate's doc comment promises references, rename, document symbols and formatting, which no plan includes. | Low | Open. Trim both to v0.3's scope in Pass 1. |
| A12 | The grammar ships no Tree-sitter queries (`queries/highlights.scm`), so no editor gets syntax highlighting from it. | Medium for editor adoption | Open. D8. |
| A13 | Diagnostics carry one span only. `duplicate-object-key` already knows the occurrence that wins (`Fact::DuplicateObjectKey::last`), as `duplicate-attribute` could; LSP shows such spans as related information. | Low | Open, optional. An additive field on `Diagnostic`. |
| A14 | The manifest reference promises that version 1 never starts rejecting a manifest that is valid today. The A2 limit does, for manifests nested more than 128 levels deep. It is documented as a limit of this reader, not of the format. | Low | Open decision (below): confirm, or treat it as needing a version bump. |

A1's and A2's limits are, strictly, breaking for a file between 129
levels deep and the depth that used to crash. The CHANGELOG's
`[Unreleased]` section says so.

## Theme

**v0.3: MESH in the editor.** A language server, `mesh-lsp`, that
*is* the compiler. Diagnostics, hover, go-to-definition and completion
all come from the same `mesh-compiler` and `mesh-analysis` code as
`mesh check`, so the editor and the build can never disagree.

## Goals

- A `mesh-lsp` binary that speaks LSP over stdio.
- Diagnostics identical to `mesh check`, with the same codes, messages
  and spans, for `.mprx` files and for the manifest itself, updated as
  you type.
- Quick fixes from the suggestions diagnostics already carry ("did you
  mean `user`?").
- Hover: the type of an expression, and the declaration a name resolves
  to.
- Go to definition: from a tag, prop, event, command or scope name to
  its declaration in the manifest.
- Completion: tags, props, events, scope names, record members and
  commands, from the manifest.
- Useful while the file is broken, which is most of the time while
  typing.
- It never crashes, on any input.

## Non-goals (v0.3)

- **New MPRX syntax of any kind.** The language stays exactly v0.2's.
  The deferred language questions stay deferred: a presence test,
  optional chaining, slots and children typing, unions.
- References, rename, formatting, document symbols, semantic tokens,
  inlay hints. Each is small once the pieces above exist, but none is
  needed to make MESH usable in an editor.
- WASM and the npm packages (v0.4), beyond deciding A10's name and
  A11's shape.
- Incremental compilation (salsa or Tree-sitter incremental reparsing).
  A full recompile per change is fast enough (see "What's healthy").
- Multi-root or cross-file analysis. One `.mprx` file is still the
  template of one component (v0.2 D3).

## Definition of Done

**The server agrees with the CLI.** A test drives `mesh-lsp` over every
`.mprx` fixture, pass and fail, with and without a model, and every
broken-manifest fixture. It compares the published diagnostics with
`mesh check --format json` on the same file: the same codes, messages,
ranges and suggestions.

**Navigation works on the examples.** On `examples/users-page.mprx`
against `examples/components.json`:
- hovering `user.name` shows `string`, and hovering `compact` shows
  `boolean`;
- go-to-definition on `avatar` lands on the `"avatar"` key in the
  manifest, on `alt` on its prop, and on `selectUser` on its command;
- completion inside `<avatar ` offers `src`, `alt` and `size`, and marks
  the required ones.

**It works on broken files.**
- Completion after `user.` offers `name`, `avatar` and `active`, although
  `user.` is a syntax error.
- Completion after `<` offers every component.
- Hover still works on the parts of a file that parse, while another
  part has a syntax error.

**It doesn't crash.** No request panics or aborts the server on:
- any fixture;
- the nesting stress inputs from A1 and A2;
- every prefix of every fixture (each position a user types through);
- a fuzzing run of agreed length over `parse`, `compile_with` and the
  request handlers.

**It's usable.** The editor setup guide shows at least one editor
getting diagnostics, hover, definition and completion from a
`cargo install`ed `mesh-lsp` (D8).

## Proposed decisions

### D1. Transport: `lsp-server` and `lsp-types`, stdio only

- Use `lsp-server` (rust-analyzer's synchronous message loop) and
  `lsp-types`.
- No async runtime. The work is CPU-bound and takes milliseconds, and a
  synchronous loop is simpler to test in-process.
- Rejected: `tower-lsp`, which needs tokio and a larger dependency tree
  for nothing this server needs.
- Stdio only. Sockets and pipes can come later if a client needs them.

### D2. One line index for every presentation of a position

- A line index is built once per source text. It maps a byte offset to a
  line and column in three units, `char`s (the CLI and JSON output),
  UTF-16 code units (the LSP default) and UTF-8 bytes, and maps each of
  them back.
- It keeps `locate`'s rules exactly: a leading byte-order mark and a
  line's `\r` are not columns, and offsets are clamped and floored so a
  lookup never panics.
- `render_diagnostic` and `render_json` use it too, which fixes A6 and
  guarantees the three presentations agree.
- The server negotiates `positionEncoding` (LSP 3.17): UTF-8 when the
  client offers it, otherwise UTF-16.
- Where it lives: `mesh-compiler`, beside `position.rs`, unless Pass 0
  finds a reason for its own crate.

### D3. Broken files: recover what parses, but report only what `mesh check` reports

The server's **diagnostics** are always exactly `mesh check`'s: a file
with a syntax error reports its syntax errors and nothing else (v0.2
D17 still holds).

**Navigation** (hover, definition, completion) should still work on
the parts of a broken file that parse. Recommended approach:
- `mesh-parser` gains a recovering entry point beside `parse`. It lowers
  every element, attribute, event binding and child whose subtree has no
  error, and leaves out the ones that do, returning that partial AST
  alongside the same errors `parse` reports.
- The partial AST is lowered and analyzed as usual. The facts are used
  only to answer navigation requests, and are never published as
  diagnostics.
- `parse`, `compile` and `compile_with` are unchanged.

Rejected alternatives:
- Keeping the last good analysis and shifting it through edits. Its
  spans go stale, and what it says about the part being typed is wrong.
- Publishing analysis diagnostics for recovered files. That would make
  the editor disagree with `mesh check` and report errors that are
  artifacts of recovery.

This is the least settled decision in the outline. It gets its own short
design spec, written against real Tree-sitter recovery trees the way
v0.2's located syntax errors were, before Pass 3 is planned.

### D4. Completion context comes from the concrete syntax tree

- At the moment completion is wanted, the tree is almost always broken
  (`<avatar `, `user.`, `on.`). So the question "what kind of position
  is this offset in?" is answered by `mesh-parser` from the Tree-sitter
  tree, recovery nodes included.
- The answer is a small enum: a tag name; an attribute or event name on
  element *E*; an expression; a member of expression *X*; a command
  name. Any expression it carries is then typed with D3's recovered
  analysis.
- The CST stays private to `mesh-parser`, as the architecture requires.
  Only the enum crosses the crate boundary.

### D5. The manifest keeps a span for every declaration

- `mesh-manifest` records the span of each declaration's key: component,
  prop, event, command, parameter, scope name, named type and record
  field.
- This is additive. The model's structs are `#[non_exhaustive]`, so new
  fields break no one.
- `mesh_analysis::Target` names are enough to look these spans up, so
  analysis doesn't change.

### D6. How the server finds a file's manifest

The CLI takes `--model` and `--component`, and the component defaults to
the file's stem. The server needs the same two answers without flags.

Recommended:
- A workspace setting, `mesh.model`, is a path to the manifest relative
  to the workspace root. It is passed as `initializationOptions` and
  refreshed through `workspace/configuration`.
- The component is the file's stem, exactly as in the CLI.
- With no model configured, the server checks syntax and structure only,
  exactly as `mesh check` without `--model` does.

Rejected for now: a project file (such as `mesh.json`) read by both the
CLI and the server. It's the better long-term answer if `mesh check`
should find the model on its own, but it's a new format with its own
versioning. Revisit when the CLI wants it.

Needs an answer: whether a per-file component override (the
`user-card.mprx` → `user-card-example` case in the examples) is
required in v0.3, or waits for the project file.

### D7. The server never dies

- The nesting limits (A1, A2) bound every recursive stage, and the tests
  added with them pin the whole pipeline to a 2 MiB stack.
- The server compiles on a thread it spawns with an explicit stack size,
  never less than those tests use.
- Each request handler runs under `catch_unwind`, as defence in depth. A
  panic is logged and answered with an error response, and the server
  keeps running. That's a backstop, not a reason to tolerate panics: any
  panic found is a bug to fix.
- A `cargo-fuzz` target (or a `proptest` suite, if CI can't run fuzzing)
  covers `parse`, `compile_with` and the request handlers.

### D8. Editor integration

- **Highlighting:** `grammar/tree-sitter-mprx/queries/highlights.scm`
  (A12). It serves Neovim, Helix and Zed directly, and costs little.
- **VS Code** needs an extension to launch the server. Recommended: a
  minimal extension in `editors/vscode/` that finds `mesh-lsp` on `PATH`
  and adds a TextMate grammar for highlighting. It isn't published to
  the Marketplace in v0.3; that waits for v0.4's packaging.
- The editor setup guide documents VS Code (from source) and at least one
  generic LSP client.

Needs an answer: whether v0.3 includes the VS Code extension, or only
the generic client setup and the Tree-sitter queries.

### D9. The manifest is a document too

- The server publishes the manifest's own diagnostics on the manifest
  file, as `mesh check --model` reports them.
- While the manifest has errors, `.mprx` files get syntax and structure
  diagnostics only, as they would without a model, never model
  diagnostics against a broken model. The CLI's behaviour (report only
  the manifest's errors and stop) is right for a one-shot check but
  wrong for an editor, where the template is still being edited.
- Editing the manifest re-checks every open `.mprx` file.

### D10. What the server sends and accepts

- Text sync: full document on every change. Incremental sync can come
  later, without changing anything else (see Non-goals).
- Diagnostics: published by the server (`textDocument/publishDiagnostics`)
  after a short debounce, not pulled.
- Diagnostic `code` is the MESH code, and `codeDescription` links to its
  entry in the diagnostics reference.
- Quick fixes: one `codeAction` per suggestion, replacing the
  suggestion's span.

## Passes (proposed)

### Pass 0 — Groundwork and audit follow-ups

- The line index (D2), used by both renderers.
- An offset query over `Analysis` (A9): the innermost expression,
  resolution or fact at an offset.
- Declaration spans in the manifest (D5).
- A5: no panic on a closed stdout.
- A10 and A11: settle the npm scope, and trim `packages/mesh-lsp` and the
  `mesh-lsp` crate's doc to the actual plan.
- A13, if cheap: related spans on `Diagnostic`.

### Pass 1 — The server, and diagnostics

- The `lsp-server` loop (D1), the document store, full text sync, and
  configuration (D6).
- Diagnostics for `.mprx` and manifest files (D9, D10), and quick fixes.
- An in-process test harness: a client that drives the server over
  channels, with no subprocess.
- The fixture-agreement test from the Definition of Done.

### Pass 2 — Hover and go-to-definition, on files that parse

- Built on the resolutions and types v0.2 already records, D5's spans
  and Pass 0's offset query.

### Pass 3 — Broken-file recovery

- D3's design spec first, then the recovering parse and navigation on
  broken files.

### Pass 4 — Completion

- D4's position classifier, and completion items from the manifest and
  from D3's recovered analysis.

### Pass 5 — Editor integration and release

- Tree-sitter queries, and the editor extension or setup D8 settles.
- The "Editor setup" guide, and the release notes.
- The robustness items in the Definition of Done: the prefix test and
  the fuzzing run.

## Sequencing

- Pass 0 comes first; everything else uses it.
- Passes 1 and 2 need only files that parse, so they can ship before D3
  is settled.
- Pass 3's design spec can be written alongside Passes 1 and 2.
- Pass 4 depends on Pass 3.
- Pass 5's Tree-sitter queries depend on nothing and can land at any
  time.

## Risks

- **Tree-sitter recovery trees are hard to predict** (the lesson of
  v0.2's located syntax errors). D3 and D4 depend on them. Mitigation:
  pin every recovered shape with a fixture, and fall back to "no answer"
  rather than a wrong one.
- **Scope creep toward a full IDE.** The Non-goals list is the defence;
  each addition needs an outline revision.
- **The npm name.** If anything is published under `@valence` before A10
  is decided, renaming it later costs users a migration.

## Open decisions

1. **D3:** confirm "recover for navigation only, never for diagnostics".
   The exact recovery rules get their own design spec.
2. **D6:** is a per-file component override needed in v0.3, or does it
   wait for a project file?
3. **D8:** does v0.3 ship a VS Code extension (unpublished), or only
   Tree-sitter queries and generic client setup?
4. **A10:** the npm scope, `@valence` or `@valance`/`@valancex`.
5. **A14:** is the manifest nesting limit acceptable under version 1's
   compatibility promise, as a limit of the reader?

## After v0.3

- v0.4: the WASM build and the npm packages, including the language
  server launcher and, if D8 includes it, publishing the VS Code
  extension.
- NEXUS generating manifests, which v0.2 unblocked, is still NEXUS-side
  work.
- The language questions stay open: a presence test or optional
  chaining, slots and children typing, and whether union or
  nullable-present types are ever warranted.
