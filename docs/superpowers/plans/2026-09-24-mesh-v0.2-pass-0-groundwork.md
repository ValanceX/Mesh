# MESH v0.2 Pass 0: Groundwork Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Clear v0.1's loose ends before v0.2 feature work begins. This pass:
- pins the Rust toolchain and declares an MSRV;
- makes the fixtures line-ending-proof;
- stops a leading BOM from shifting columns;
- moves CI off Node 20 actions;
- adds `mesh --version`.

**Architecture:** There is no new code structure.
- **Task 1** is repository configuration: a `rust-toolchain.toml` pin, workspace `rust-version`, CI changes, and a new MSRV CI job.
- **Task 2** is one `.gitattributes` line, verified by a CRLF checkout.
- **Task 3** is a local change inside `render_diagnostic`. The span is still normalized to character boundaries first; only then does line 1's text start after a leading U+FEFF instead of at byte 0.
- **Task 4** is a single clap attribute.

**Tech Stack:**
- Rust: `rust-toolchain.toml` pins 1.98.1; the MSRV is 1.91.
- clap 4 derive.
- GitHub Actions: `actions/checkout@v7` and `actions/setup-node@v7`. These action versions run on the Actions runner's Node 24 runtime instead of the deprecated Node 20 one. Separately, `setup-node`'s `node-version: 22` installs Node 22 for the project's own grammar tests; it doesn't choose the runtime the actions themselves run on.
- Tests use `assert_cmd` and `predicates`, which are already dev-dependencies of `mesh-cli`.
- No new dependencies.

**Spec:** `docs/superpowers/specs/2026-09-24-mesh-v0.2-outline.md`, section "Pass 0 — Groundwork", and D17 ("v0.1 compatibility").

## Global Constraints

- **Pass 0 is infrastructure, not language behaviour.** It changes how the repo is built and checked (toolchain, MSRV, CI, line endings), how an already-produced diagnostic is *rendered* for a BOM source, and adds a CLI flag. It changes no language or diagnostic behaviour: the grammar, parser, AST, Semantic IR, diagnostic messages, spans, classification and order all stay exactly as they are. Diagnostic codes and located syntax errors belong to Pass 1 and must not appear here.
- **D17 holds.** The same valid sources are accepted and the same invalid sources are rejected, with the same exit statuses.
- **Rendering changes only for BOM sources.** For any source that doesn't start with U+FEFF, `render_diagnostic` output is byte-for-byte what it is today.
- **Toolchain and MSRV are v0.2-wide contracts,** not just Pass 0 details. Every later v0.2 pass builds, lints and tests on the pinned toolchain, and must keep compiling on the MSRV.
  - **The toolchain pin is exact:** `channel = "1.98.1"`, the version the repo is currently developed and linted with.
  - **The MSRV is `1.91`.** `render.rs` calls `str::floor_char_boundary`, which was stabilized in Rust 1.91, and the highest MSRV among the dependencies is 1.90 (`tree-sitter`).
  - **What the MSRV check proves:** `cargo +1.91.0 check --locked --workspace --all-targets` shows that the current workspace, with its committed `Cargo.lock`, builds on 1.91. It does not prove that 1.91 is the lowest version that would work, and the plan claims no more than that.
- **No new crates or dependencies.**
- **The renderer contract.** `render_diagnostic` accepts any diagnostic byte span and normalizes both offsets to valid UTF-8 character boundaries (`str::floor_char_boundary`, which also clamps past-the-end offsets) *before any string slicing*. No `source[...]` slice ever uses a raw span offset. BOM handling runs *after* that normalization, on the normalized boundaries, and must never bypass or replace it. The renderer never panics for any `(source, span)` pair: zero-width, reversed, past-the-end, or inside a multi-byte character, in sources with a BOM at byte 0, a BOM and nothing else, a BOM with CRLF, or any combination of these. This is the v0.1 contract, and the BOM change must keep it.
- **Pass 0 must be complete and merged before Pass 1 begins.** Pass 1 relies on what Pass 0 establishes: the pinned toolchain and MSRV, LF fixtures, the renderer contract above (including zero-width spans at byte 0 of BOM files), `mesh --version`, and the `CHANGELOG.md` `## [Unreleased]` section.
- **Changelog ownership.** Pass 0 creates `CHANGELOG.md`'s single `## [Unreleased]` section. Pass 1 and later passes add their entries to that section's existing `### Added`, `### Changed` and `### Fixed` subsections, and never create a second `Unreleased` section.
- **Commit authorship:** commit messages must follow the repository's established authorship and contributor convention. Don't invent, impersonate, or hard-code an agent or model identity in commit metadata.
- **Don't push or tag.** Publishing is the user's call.
- **Verification gate for every task.** Run the core Rust gate from the `mesh/` repo root. These are CI's Rust checks; CI also runs the grammar's npm tests and, from Task 1 on, the MSRV check, which the Final verification section covers:

  ```bash
  cargo fmt --all -- --check
  cargo clippy --workspace --all-targets -- -D warnings
  cargo test --workspace
  ```

### Task 3: Skip a leading byte-order mark when rendering

**Files:**
- Modify: `crates/mesh-compiler/src/render.rs`
- Test: `crates/mesh-compiler/tests/render.rs` (append)
- Test: `crates/mesh-cli/tests/check.rs` (append)
- Modify: `docs/manual/mesh-cli.md` (Limitations)
- Modify: `CHANGELOG.md` (Unreleased)

**Interfaces:**
- Consumes: `render_diagnostic(source: &str, path: &str, diagnostic: &Diagnostic) -> String`. It is unchanged.
- Produces: the same function. For sources starting with U+FEFF, the BOM is never echoed, counted as a column, or underlined.

Today, `fs::read_to_string` keeps a UTF-8 BOM as the character U+FEFF at bytes 0..3. The renderer counts it as a column, so everything on line 1 reports one column too far right. It also echoes the invisible character into the snippet.

**The contract this task must keep** (see Global Constraints): `render_diagnostic` takes any byte span and normalizes both offsets to character boundaries before it slices anything. The BOM handling added here runs after that normalization and works only on the normalized offsets. It never slices with a raw span offset, and never replaces the normalization.

**Why Pass 1 needs this now.** Pass 1 replaces v0.1's whole-document syntax error with precise spans, many of them zero-width. In particular, it reports an empty or BOM-only file as one diagnostic at `Span { start_byte: 0, end_byte: 0 }`, which starts on the BOM itself. That case must already render correctly, as `1 |` then `  | ^`, before Pass 1 lands. So must a zero-width span anywhere in a BOM, CRLF or multi-byte source. The last test below sweeps all of those.

- [ ] **Step 1: Write the failing renderer tests**

Append to `crates/mesh-compiler/tests/render.rs`:

```rust
#[test]
fn skips_a_leading_byte_order_mark() {
    // The BOM is bytes 0..3; `<div></span>` is bytes 3..15.
    let source = "\u{feff}<div></span>\n";
    let rendered = render_diagnostic(source, "bom.mprx", &diagnostic(Severity::Error, "m", 3, 15));
    assert_eq!(
        rendered,
        "error: m\n \
         --> bom.mprx:1:1\n  \
         |\n\
         1 | <div></span>\n  \
         | ^^^^^^^^^^^^"
    );
}

#[test]
fn a_span_starting_on_the_byte_order_mark_points_at_the_first_character() {
    // v0.1 syntax errors span the whole document (0..len), and an empty
    // span at 0 is also possible: both start on the BOM itself.
    let source = "\u{feff}<a>";
    for (start, end, carets) in [(0, 6, "^^^"), (0, 0, "^"), (1, 2, "^")] {
        let rendered = render_diagnostic(
            source,
            "bom.mprx",
            &diagnostic(Severity::Error, "m", start, end),
        );
        assert_eq!(
            rendered,
            format!("error: m\n --> bom.mprx:1:1\n  |\n1 | <a>\n  | {carets}"),
            "span {start}..{end}"
        );
    }
}

#[test]
fn renders_a_file_holding_only_a_byte_order_mark_like_an_empty_file() {
    let rendered = render_diagnostic(
        "\u{feff}",
        "bom.mprx",
        &diagnostic(Severity::Error, "m", 0, 0),
    );
    assert_eq!(
        rendered,
        "error: m\n \
         --> bom.mprx:1:1\n  \
         |\n\
         1 |\n  \
         | ^"
    );
}

#[test]
fn skips_a_byte_order_mark_in_a_crlf_source() {
    // `<a>` is bytes 3..6, then `\r\n`.
    let source = "\u{feff}<a>\r\n<b />";
    let rendered = render_diagnostic(source, "bom.mprx", &diagnostic(Severity::Error, "m", 3, 8));
    assert_eq!(
        rendered,
        "error: m\n \
         --> bom.mprx:1:1\n  \
         |\n\
         1 | <a>\n  \
         | ^^^"
    );
}

#[test]
fn a_byte_order_mark_does_not_shift_later_lines() {
    // `<b />` is bytes 7..12. This already passes; it pins that the BOM
    // handling only ever touches line 1.
    let source = "\u{feff}<a>\n<b />";
    let rendered = render_diagnostic(source, "bom.mprx", &diagnostic(Severity::Error, "m", 7, 12));
    assert_eq!(
        rendered,
        "error: m\n \
         --> bom.mprx:2:1\n  \
         |\n\
         2 | <b />\n  \
         | ^^^^^"
    );
}

/// The renderer's contract: any `(source, span)` pair renders without
/// panicking, and never echoes a byte-order mark or a line-ending `\r`.
/// Pass 1's located syntax errors add zero-width spans and spans at byte
/// 0 of BOM files, so this sweeps every span, zero-width, reversed and
/// out-of-range ones included, over sources that combine a BOM, CRLF line
/// endings and multi-byte characters.
#[test]
fn never_panics_for_any_span_over_bom_crlf_and_multi_byte_sources() {
    let sources = [
        "",
        "\u{feff}",
        "\u{feff}\r\n",
        "\u{feff}<a>\r\n<b />",
        "\u{feff}é\r\nü",
        "héllo\r\nwörld\n",
        "\r\n\r\n",
    ];
    for source in sources {
        for start in 0..=source.len() + 2 {
            for end in 0..=source.len() + 2 {
                let rendered = render_diagnostic(
                    source,
                    "p.mprx",
                    &diagnostic(Severity::Error, "m", start, end),
                );
                assert!(
                    !rendered.contains(['\u{feff}', '\r']),
                    "span {start}..{end} of {source:?}: {rendered:?}"
                );
            }
        }
    }
}
```

The span `1..2` in the second test splits the BOM's bytes. It floors to 0 and then behaves like a span that starts on the BOM.

- [ ] **Step 3: Implement the fix**

The order inside the function is the point of this step:
1. Normalize the span's offsets to character boundaries. This is today's code, unchanged.
2. Find the line from the normalized `start`. Also unchanged.
3. Only then work out where line 1's visible text starts, skipping a BOM.

Every slice uses the normalized `start`/`end` or offsets derived from them, never `diagnostic.span` directly.

In `crates/mesh-compiler/src/render.rs`, add a constant after the `use` line:

```rust
use mesh_syntax::Diagnostic;

/// The UTF-8 byte-order mark, as `fs::read_to_string` leaves it at the
/// start of a file saved "with BOM".
const BOM: char = '\u{feff}';
```

Extend the function's doc comment. Replace its last four lines:

```rust
/// line, and a trailing `\r` (CRLF sources) is never shown, counted, or
/// underlined. An out-of-range span, or one that splits a multi-byte
/// character, is clamped rather than panicking — a bad span should
/// degrade the snippet, not crash the CLI.
```

with:

```rust
/// line, and a trailing `\r` (CRLF sources) is never shown, counted, or
/// underlined; neither is a leading byte-order mark. An out-of-range
/// span, or one that splits a multi-byte character, is clamped rather
/// than panicking — a bad span should degrade the snippet, not crash
/// the CLI.
```

Then replace the whole function, from `pub fn render_diagnostic` to its closing `}`, with:

```rust
pub fn render_diagnostic(source: &str, path: &str, diagnostic: &Diagnostic) -> String {
    // Normalize the span before anything else. Every slice below uses
    // `start` and `end`, never the raw span offsets, so no span can make
    // this function slice mid-character or out of range.
    let start = source.floor_char_boundary(diagnostic.span.start_byte);
    let end = source
        .floor_char_boundary(diagnostic.span.end_byte)
        .max(start);

    let line_start = source[..start].rfind('\n').map_or(0, |i| i + 1);
    let line_end = source[start..]
        .find('\n')
        .map_or(source.len(), |i| start + i);
    // A leading byte-order mark is an encoding marker, not text: it is
    // never shown, counted as a column, or underlined. This only moves
    // where line 1's text starts; it works on the normalized `line_start`
    // and never replaces the normalization above.
    let text_start = if line_start == 0 && source.starts_with(BOM) {
        BOM.len_utf8()
    } else {
        line_start
    };
    let line_text = source[text_start..line_end].trim_end_matches('\r');
    let text_end = text_start + line_text.len();
    let line_number = source[..line_start].matches('\n').count() + 1;
    // A span starting inside the line ending (`\r` or `\n`) points just
    // past the last visible character, never into the line ending itself;
    // one starting on the byte-order mark points at the first character.
    let visible_start = start.clamp(text_start, text_end);
    let column = source[text_start..visible_start].chars().count() + 1;

    let indent: String = source[text_start..visible_start]
        .chars()
        .map(|c| if c == '\t' { '\t' } else { ' ' })
        .collect();
    let underline_end = end.min(text_end).max(visible_start);
    let carets = "^".repeat(source[visible_start..underline_end].chars().count().max(1));

    let gutter = " ".repeat(line_number.to_string().len());
    // Omit the separating space for an empty line so no output line ends
    // in trailing whitespace (fixture `.stderr` files must survive editors
    // that strip it, and `git diff --check`).
    let code = if line_text.is_empty() {
        String::new()
    } else {
        format!(" {line_text}")
    };

    format!(
        "{severity}: {message}\n\
         {gutter}--> {path}:{line_number}:{column}\n\
         {gutter} |\n\
         {line_number} |{code}\n\
         {gutter} | {indent}{carets}",
        severity = diagnostic.severity,
        message = diagnostic.message,
    )
}
```

Compared with today's function, only these change:
- the comment on the normalization lines;
- the new `text_start`;
- `line_text`, `text_end`, `column` and `indent` slice from `text_start` instead of `line_start`;
- `visible_start` uses `clamp` instead of `min`.

The normalization lines, `line_start`, `line_end`, `underline_end`, `carets`, `gutter`, `code` and the `format!` are unchanged.

Why this can't slice badly:
- `start` and `end` are character boundaries within the source, as before.
- `text_start` is either `line_start`, or 3 when line 1 starts with a BOM. Byte 3 is a character boundary, and `line_end >= 3` in that case, because the BOM holds no `\n`.
- `text_start <= text_end` always holds, because `text_end = text_start + line_text.len()`. So `clamp` never panics, and `visible_start` is a boundary.
- For a line without a BOM, `text_start == line_start <= start`, so `clamp` behaves exactly like the old `start.min(text_end)`.
