## Decisions this plan makes

1. **The manuals** are `docs/manual/templates.md` (the template format, compatibility, the fingerprint, programs and assembly) and `docs/manual/runtime.md` (render and dispatch, the render tree, keys and handler identifiers, the command intent, the host interface, the boundary's JavaScript encoding at the level a host needs, the runtime diagnostics' phases and order, and an implementation note saying number-to-text uses MESH's own exact digit generator, and why neither `std`'s formatting nor `ryu` is used (Pass 0's reviewed decisions)), with `docs/manual/diagnostics.md` holding every code and `docs/manual/mesh-cli.md` holding `mesh compile` and `mesh check-program`. Their status lines go.
2. **The spec** (`docs/MPRX-SPEC.md`): §9.7 and §9.8 lose any "specified, not implemented" wording, and §9.7 keeps citing the number-to-text table as normative, with the tie search's result; the v0.5 status table shows every pass shipped; the introduction says the spec now describes v0.5, whose syntax is v0.2's and whose evaluation is §9.7's; "Last updated" and §11 are updated.
3. **"Integrating MESH with NEXUS"** (`docs/guides/integrating-mesh-with-nexus.md`) is for whoever builds the adapter: what a host is (D5), the render and dispatch lifecycle, the obligation to keep each render while its tree is on screen and to dispatch with the render the renderer drew, telling the renderer when a tree comes from a different program, open scope and exact records (shape values to the manifest), how absence crosses, mapping an intent's command to a NEXUS command (`selectUser` → `"users.select"`) as the adapter's own table, and what to do with diagnostics (they are errors in the host's inputs or the program, never something to show end users as-is). Its example is a minimal host: it compiles the slice, renders from a stand-in store, keeps renders, dispatches a click with the right render after a re-render, and prints the intent and a mapped command.
4. **"Rendering MESH output"** (`docs/guides/rendering-mesh-output.md`) is for whoever builds a PORT renderer: the render tree's shape, that keys and handler identifiers are opaque but not secret (anyone with the templates can compute them, and dispatch's validation is what makes them safe), reconciling a new tree against the drawn one by key (D6), only between trees its host says come from one program (keys change when the program does, by design, so the host tells the renderer to draw a changed program's tree afresh), drawing props and text as given with nothing computed (I11, I13), reporting an event as its handler identifier and payload, surfacing a node of a component it doesn't know rather than dropping it (outline, "Risks": a missing template makes a composite a primitive), and that it never sees an intent. Its example is a tiny string renderer that draws the slice, then applies the second snapshot's tree as a list of updates by key.
5. **README and ARCHITECTURE:** the repository map gains `mesh-template`, `mesh-runtime`, `mesh-runtime-wasm` and `@valancex/mesh-runtime`; the README's pipeline shows compile → program → render → dispatch; ARCHITECTURE's rules gain I11–I15 in its own words, and its NEXUS and PORT sections point at the guides. `docs/README.md` links both guides and the new manuals, and its contributor checklist builds both modules and tests both packages.
6. **The release workflow:** the `javascript` job installs with npm 11 (see "Re-checked" 1), builds `mesh-runtime.wasm` beside `mesh.wasm` and packs `@valancex/mesh-runtime`; `publish.mjs`'s list appends `mesh-runtime` after `mesh-compiler` (neither depends on the other, so order between them doesn't matter, but a fixed order keeps runs comparable); the GitHub release attaches eight tarballs. The version check covers the new package through `packages.rs`, as it does the others.
7. **The release commit** bumps the workspace, the grammar and every npm package to 0.5.0 and regenerates both lockfiles with their tools (npm 11 for `packages/`); the CHANGELOG's `[Unreleased]` becomes `[0.5.0] - <date>`; `docs/releases/v0.5.md` says what v0.5 is, what it isn't (no NEXUS adapter, no PORT renderer, no editor work, no new syntax), what an upgrade from v0.4 changes (two new check errors; `mesh_compiler::SourceMap` now re-exported from `mesh-syntax`), and the known limitations (the outline's Risks that remain: absent list elements can't cross; whole-model fingerprints; exact records). They also state how number-to-text is verified, and by what: MESH's own exact digit generator, normatively by `docs/tables/number-to-text.tsv`, and differentially against V8, with the V8 versions compared and every entry of `number-text-differences.json`, or "none". A PORT renderer must draw MESH's text as given, never re-formatting it with its host's number formatting.
8. **The outline** gets its status (v0.5 released) and a "Definition of Done, as met" section, each item naming its test or document, as v0.4's does.
