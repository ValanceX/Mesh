## Decisions this plan makes

**Which open buffers are what (C1, C2, C3)**

1. **One map of open buffers.** The server keeps every `didOpen`ed text, whatever it is: `buffers: BTreeMap<String, Buffer { uri, language_id, version, text }>`. `didChange` and `didClose` update it first, for every URI. `Document` (MPRX snapshot state) and the manifest's open text are both *derived* from it, never stored apart from it, so they can't disagree with it.
2. **Classification, one rule, applied on every `didOpen` and on every configuration change:**
   - the buffer whose path is the configured manifest's path (`uri::to_path(uri) == manifest.path`) **is the manifest**, whatever its `languageId`;
   - otherwise a buffer whose `languageId` is `mprx` **is a document**, compiled and published as today;
   - otherwise it **is ignored**: kept in `buffers` (it may become the manifest later), never compiled, never published on.

   `languageId` decides what a buffer *is*, as LSP intends; it never decides what component a document is (I5, D6 unchanged). A client sends the `languageId` its user configured (Neovim sends the filetype), and the guide sets it to `mprx`.
3. **Reclassifying.** `configure()` (initial, pushed or pulled settings) recomputes the manifest path, then walks `buffers`:
   - a buffer that was a document and is now the manifest leaves `documents`, gets an empty publication (clearing its MPRX diagnostics), and becomes the manifest's source;
   - a buffer that was the manifest and no longer is becomes a document if its `languageId` is `mprx`, otherwise it's ignored; the manifest's old URI gets an empty publication (the existing `publish_manifest` rule already does this when the URI changes);
   - `reload_manifest` reads the buffer at the manifest's path if one is open, **else the disk**. There is no `manifest.open` state left to go stale (C1).
4. **What this changes for users:** a document whose `languageId` isn't `mprx` is no longer checked. That's a behaviour change for a client that sends another `languageId` for `.mprx` files; the manual and CHANGELOG say so. The harness and the agreement tests already send `mprx`.

**Configuration (C4)**

5. **Pull at `initialized`.** If the client supports `workspace/configuration`, `initialized` asks for section `mesh` once. Until the answer arrives, `initializationOptions` apply (so a client that sends both is configured at once, and the pull confirms or replaces it). An answer of `null` or `[null]` keeps the `initializationOptions`; anything else replaces them, through the existing `apply_settings`. A client without the capability behaves exactly as today.

**The watcher (B4, C5)**

6. **The pattern.** If the client's `didChangeWatchedFiles.relativePatternSupport` is true: `{ baseUri: <the manifest's directory>, pattern: <its file name, escaped> }`. Otherwise: `**/<its file name, escaped>`. Escaping wraps each of `*`, `?`, `[`, `]`, `{`, `}` in a one-character class (`[*]`); LSP globs have no other escape. A pattern broader than the one file costs nothing: `did_change_watched_files` already reloads only when a changed URI's path equals the manifest's.

**Highlighting (D8 as amended, C6, C7)**

7. **Captures.** `grammar/tree-sitter-mprx/queries/highlights.scm`, with nvim-treesitter's names:

   | Node | Capture |
   |---|---|
   | `tag_name` | `@tag` |
   | `attribute` `name:` | `@attribute` |
   | `event_binding` `name:` | `@attribute` (the `on.` prefix isn't a queryable node, E9, so it is uncaptured) |
   | `string` | `@string` |
   | `number_literal` | `@number` |
   | `boolean_literal` | `@boolean` |
   | `null_literal` | `@constant.builtin` |
   | `event_value` | `@variable.builtin` |
   | `reference` | `@variable` |
   | `member_access` `property:` | `@variable.member` |
   | `command_invocation` `command:` | `@function.call` |
   | `object_member` `key:` identifier | `@property` |
   | `unary_expression`/`binary_expression` `operator:`, `?`, `:` of a conditional | `@operator` |
   | `<`, `>`, `/>`, `</` of elements | `@tag.delimiter` |
   | `{`, `}` of an `expression_block` | `@punctuation.special` |
   | `(` `)` `[` `]`, and `{` `}` of an object | `@punctuation.bracket` |
   | `,`, `.`, `:` of an object member, `=` | `@punctuation.delimiter` |
   | `text` | uncaptured (plain text) |

   The capture names are a presentation choice (D8: approximate is fine for colour, never for meaning), but the test pins them, so changing one is a deliberate edit.
8. **The capture test.** In the grammar crate (`bindings/rust/lib.rs`'s test module, beside the generated tests, or a sibling `bindings/rust/highlight_tests.rs` it includes): for each `test/highlight/*.mprx`, parse it, run `HIGHLIGHTS_QUERY` with `QueryCursor::captures`, and render each capture as one line, `<row>:<col>-<row>:<col> <capture> <text>`, in document order; compare with the sibling `.captures` file exactly. With `MESH_BLESS=1` it writes the files instead (and still fails, so a bless is never a silent pass); the diff is reviewed by hand. Plus:
   - `the_highlights_query_is_built_in`: `cfg!(with_highlights_query)` is true, so an incremental build can't silently drop the constant (C7 is fixed by `println!("cargo:rerun-if-changed=queries")` in `build.rs`);
   - `every_node_kind_is_highlighted_or_listed`: every named node kind in `node-types.json` and every anonymous token appears in the query or in an explicit, commented "uncaptured on purpose" list in the test (`text`, `child`, `element`, …), so a grammar change that adds a node fails until someone decides how it's coloured.
9. **Samples:** `test/highlight/elements.mprx` (both element forms, nesting, strings with escapes, text), `expressions.mprx` (every operator, conditional, array, object with identifier and string keys, member chains, `null`, booleans, numbers), `events.mprx` (`on.` bindings, commands with arguments, `$event`), and `broken.mprx` (an unclosed `{user.` and a half-typed tag: captures still appear on the parts that parse, and nothing panics).
10. **`tree-sitter.json`** gains `"highlights": "queries/highlights.scm"`; `package.json`'s `files`/the crate's `include` already cover `queries/*`.

**Robustness (C10, D7 as amended, C11)**

11. **The every-fixture prefix walk** extends Pass 3's (`every_prefix_publishes_what_mesh_check_reports`) from `users-page.mprx` to every `.mprx` under `examples/` (the examples, `fixtures/{pass,fail}`, `fixtures/check/{pass,fail}`, `fixtures/manifest/template.mprx`), each opened as its configured component where it has one and model-less otherwise. For each prefix (every character boundary, as successive `didChange`s): the publication equals `mesh check --format json`'s, as today; and hover, definition and completion **at the end of the prefix and at three fixed earlier offsets** each return a result, never an error response. Cost: the existing walk runs `users-page.mprx`'s 212 prefixes in 0.93 s (debug), and every `.mprx` under `examples/` totals 6,418 bytes, so the whole walk is about 30 s. That fits Step 5's budget; if it doesn't in practice, the CLI comparison keeps every prefix of the examples and every third prefix of the fixtures, and the requests keep every prefix.
12. **The D7 cases no test covers** get one test each in `crates/mesh-lsp/tests/protocol.rs` or `transport.rs`: a hover and a completion at a UTF-16 position inside a surrogate pair (answers, no error); a `mesh.model` whose file isn't valid UTF-8 (logged, model-less); the A1 and A2 nesting stress inputs opened as a document and as the manifest (canonical `nesting-too-deep`/`manifest-nesting-too-deep`, no crash); an empty and a whitespace-only document (the CLI's diagnostics; hover, definition and completion answer).
13. **The fuzzer** (`crates/mesh-cli/tests/fuzz.rs`):
    - a xorshift PRNG seeded from `MESH_FUZZ_SEED` (default: a fixed constant, so CI is deterministic); iterations from `MESH_FUZZ_ITERATIONS` (default 2,000, a few seconds in debug);
    - corpus: every `.mprx` under `examples/`; each mutation applies one to six edits (insert one of a fixed token list including multi-byte, astral and BOM characters and `\r\n`; delete up to eight bytes; truncate), always at character boundaries;
    - each mutant goes through `parse`, `compile`, `compile_with` against `examples/components.json` (`users-page`), `editor::recover`, and `editor::candidates` and the offset queries at eight offsets (some past the end, and some that fall inside a multi-byte character, which the APIs must floor);
    - every 50th mutant also goes through an in-process server (`mesh_lsp::testing::Client`): `didChange` to it, then hover, definition and completion at three offsets; every response is a result or `ContentModified`, never an internal error;
    - all of it on a thread with the server's 8 MiB stack; a panic fails the test with the seed, the iteration and the mutant written to the failure message.
14. **The agreed length:** one local run with `MESH_FUZZ_ITERATIONS=1000000`, release build, recorded in "As built" with its seed, time and result. A failure it finds is fixed in this pass, and the mutant becomes a fixture or a named regression test.

## Review Focus

1. **Classification** (`crates/mesh-lsp/tests/manifest.rs`, `config.rs`), each a test:
   - `switching_the_model_while_the_old_manifest_is_open_loads_the_new_one` (E2): documents are checked against the new file; its errors are published on its URI; the old manifest's URI gets an empty publication;
