# MESH v0.4 Pass 3: Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release v0.4.0 (outline, "Pass 3"). This pass:
- adds D10's **release workflow**: triggered by a `v*` tag, it runs the whole of CI on the tagged commit, builds every `mesh-lsp` binary natively and the WebAssembly module, packs all seven npm packages, checks every version against the tag, publishes to npm with provenance, and makes a GitHub release with the binaries and tarballs attached;
- exercises that workflow **with publishing off** before any real publish;
- writes **"Using MESH from JavaScript"**, with an example a test runs, and the grammar README's note on its untested bindings (E12);
- makes the **release commit**: every version to 0.4.0, the CHANGELOG, the v0.4 release notes, and the README, docs index and outline updated.

**Architecture:**
- **`.github/workflows/release.yml`** has four jobs: `ci` (the whole of `ci.yml`, called as a reusable workflow), then `binaries` (a five-target matrix on the same native runners as CI) and `wasm`, which each upload their packed tarballs as artifacts, then `publish`, which downloads them all and publishes.
- **`ci.yml`** gains `workflow_call`, so the release can't publish a commit CI hasn't passed on.
- The npm token is the repository secret `NPM_ACCESS_TOKEN`, a granular access token the maintainer created for the `@valancex` organisation, which settles E8.
- Tasks **P3.1**–**P3.4**, in order.

**Tech Stack:** GitHub Actions (`actions/upload-artifact@v7`, `actions/download-artifact@v8`, `gh` on the runner). npm with `--provenance` (the repository is public). No new dependency.

**Spec:** `docs/superpowers/specs/2026-09-25-mesh-v0.4-outline.md`: D10, D11; E7, E8, E12; the Definition of Done's "It's usable" (the guide).

**Prerequisite:** Passes 0–2 are merged (pull request #1).

## Global Constraints

- **Nothing publishes without the maintainer's tag.** The workflow publishes only on a pushed `v*` tag, or on a manual run with `publish` set. Pushing `v0.4.0` is the maintainer's step, after this pass merges.
- **Every published file is built by the release workflow from the tagged commit.** Nothing is published from a developer's machine.
- **A shipped binary is built and tested on its own runner** (outline D9), exactly as CI does it.
- **Publishing can be retried.** A version already on the registry is skipped, not re-published, so a failed run can be run again.
- **Commit authorship and pushing:** as in the earlier passes. The maintainer asked for this pass; the branch is pushed and a pull request opened for CI.

## Decisions this plan makes

1. **Triggers:** `push: tags: ['v*']` publishes. `workflow_dispatch` with a `publish` boolean input, default `false`, runs everything but the publishing (a dry run: `npm publish --dry-run` for each tarball, and no GitHub release). `pull_request` on changes to the workflow itself runs the dry run too, so it is exercised before it merges.
2. **The version check:** the tag without its `v` must equal `[workspace.package] version`, which `packages.rs` already pins every package's version, dependency and `version.ts` to. On a dry run with no tag, the workspace version is used.
3. **Order of publishing:** the five platform packages, then `@valancex/mesh-lsp` (which depends on them), then `@valancex/mesh-compiler`. Each with `--access public --provenance`. Before each, `npm view <name>@<version>` skips a version the registry already has.
4. **The GitHub release** is `v<version>`, its notes the matching section of the release notes file (`docs/releases/v0.4.md`, whole), with the seven tarballs and the five `mesh-lsp` binaries (renamed `mesh-lsp-<target>[.exe]`) attached. It's made only after npm publishing succeeds.
5. **The guide's example is a test:** `docs/guides/using-mesh-from-javascript.md` has one complete ```js block, a generate-check-repair loop with a stand-in "generator" that applies suggestions. `packages/mesh-compiler/test/guide.test.mjs` extracts it, points its import at the built package, runs it, and checks its output.
6. **The release commit** bumps the workspace, the grammar (its manifests, and the one line of `src/parser.c` that `tree-sitter generate` writes the version into) and every npm package to 0.4.0, and regenerates both lockfiles with their tools.
7. **The token expires.** `NPM_ACCESS_TOKEN` has a 60-day expiration policy; the release notes' contributor section and `docs/README.md` say a release needs a current token.
