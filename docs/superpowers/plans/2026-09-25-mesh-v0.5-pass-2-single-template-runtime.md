# MESH v0.5 Pass 2: The Single-Template Runtime Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The runtime, natively, for programs of one template (outline, "Pass 2"): D3, D5, D6 and D8. This pass adds **`crates/mesh-runtime`**, with:
- **program validation** (D3's steps 1–3, and the two assembly rules a one-template program can break: its template must be the root's, and it must not contain itself);
- **input validation** of snapshots, payloads and handler identifiers against the boundary data model (D5);
- **evaluation** by §9.7, with **render** producing `render-v1`, and **dispatch** producing command intents;
- **keys and handler identifiers** (D4);
- the **three diagnostic phases**, and the runtime diagnostics document;
- a **test host** and a **reference renderer** (D10), natively;
- the evaluation, input and dispatch evidence for single templates.

**Architecture:**
- **`mesh-runtime`** depends on `mesh-syntax` (diagnostic spans and, after Decision 1, `SourceMap`), `mesh-manifest`, `mesh-template` and `mesh-analysis` (for `is_assignable`, which Pass 3's binding rule needs), and on nothing that parses MPRX (I12: the runtime accepts no source). No I/O, no clock, no randomness, no global state (D3).
- **Modules:** `value` (the host's values and the evaluator's values), `boundary` (host value → evaluator value, against a type: input validation, and evaluator value → output: the output checks), `fits` (D8's one relation), `number` (arithmetic, `%`, text conversion), `eval` (expressions), `program` (validation, identity, keys, handler table), `render`, `dispatch`, `diagnostic` (codes, locations, order, the document).
- **The public API** is two functions and their types (D3: "the whole conceptual surface is two operations"), sketched in Decision 3.
- **Tests use hand-written templates**, built by a small test-only builder, so the pass doesn't wait on Pass 1's compiler (outline, "Pass 2"). The corpus-wide property test runs as soon as Pass 1's P1.3 has merged.
- Tasks **P2.1**–**P2.8**, in order.

**Tech Stack:** Rust on the pinned toolchain (MSRV 1.91). No new dependency beyond Pass 1's (`sha2`, via `mesh-template`): number-to-text uses MESH's own exact digit generator, with its own small arbitrary-precision integer, and depends on neither `ryu` nor `core::fmt` (Pass 0 Decision 4c). `python3`, standard library only, in CI's `lint` job to check the number-to-text table. `mesh-compiler` only as a dev-dependency, for P2.8.

**Spec:** the outline's D3–D6, D8, D10 (native half), I11–I14; Pass 0's §9.7, §9.8, `docs/manual/runtime.md`, `schemas/render-v1.schema.json`, `schemas/runtime-diagnostics-v1.schema.json`. Definition of Done: "Inputs", "Evaluation" (including "number to text, normatively"), "Dispatch", "Structure, keys and handler identifiers" and "PORT sees only values", for single templates; "Fingerprints and versions", the runtime's half; "The property test" (P2.8).

**Prerequisite:** Pass 0 is merged and reviewed, and Pass 1's P1.1 (`mesh-template` and the fingerprint) has merged. Pass 1's other tasks may run alongside.

**Verification evidence:** checked at `33648f3`: `SourceMap` lives in `mesh-compiler`, which depends on `mesh-parser` and so on Tree-sitter, while `mesh-syntax` has no dependency at all; `mesh_manifest::load` gives `manifest-*` diagnostics with spans into the manifest; `mesh_analysis::is_assignable` needs only a `Manifest`; `mesh-manifest`'s JSON reader keeps each value's source text (`RawValue`), which is how a snapshot's out-of-range number can be told from a parse error; Rust's `f64` `%` is the truncated remainder (C's `fmod`), exact, with the dividend's sign. The standard library's float formatting (`Display`, `LowerExp`) documents no digit-generation guarantee, so this plan doesn't use it for text (outline D8). Which digit generator it uses is Pass 0's decision (Pass 0 Decision 4c), and this plan follows it. The API sketches are designs. Write each failing test first, see it fail, and treat any difference from what a step predicts as something to investigate.

## Global Constraints

- **I11: one evaluator.** Everything §9.7 and §9.8 define is implemented here and nowhere else. No other crate converts a value to text, coerces a value, or judges one at the boundary.
- **I14: every input is validated on every call,** including a render's contents on dispatch. Caching a validation result keyed on its inputs is allowed (D3); skipping validation is not.
- **Phases stop at the first that reports** (D3); program-validation steps stop at the first step that reports; input validation reports every mismatch in order; evaluation reports exactly one diagnostic.
- **No panic on any input.** A malformed template, a forged handler identifier or a hostile value is a diagnostic. The fuzz test (P2.7) runs every entry point on mutated inputs.
- **No existing behaviour changes,** apart from Decision 1's move, which keeps `mesh_compiler::SourceMap` working.
- **Changelog, commit authorship, pushing:** as in the earlier passes.
- **Verification gate for every task:** the Rust gate and the MSRV check, and `cargo build -p mesh-runtime --target wasm32-unknown-unknown` (so nothing native-only creeps in before Pass 3).

## Decisions this plan makes

**Structure (P2.1)**

1. **`SourceMap` moves to `mesh-syntax`,** and `mesh-compiler` re-exports it (`pub use mesh_syntax::source_map::{…}`), so its public path is unchanged. The runtime needs it for the model's diagnostics (Pass 0 Decision 28: manifest positions in the diagnostics document's form), and must not depend on Tree-sitter to get it. The move is one commit with no other change, so the review sees it's a move.
2. **The runtime diagnostic type is its own:** `RuntimeDiagnostic { code: RuntimeCode, message: String, location: Location }`, with `RuntimeCode` a `&'static str` newtype with an `ALL` list (as `DiagnosticCode` has), and `Location` one of Pass 0's six forms (Decision 28): `Model(span)`, `Program`, `Template { index, component }`, `Source { component, span }`, `Input(path)` and `Handler`. Each code has exactly one form, recorded beside it in `RuntimeCode`, and a test checks that every diagnostic the runtime builds uses its code's form. `manifest-*` diagnostics become `Location::Model`. `to_json(&[RuntimeDiagnostic], model_text)` renders `runtime-diagnostics-v1`.

**The API (P2.1)**

3. **Two operations and their data** (design):

   ```rust
   /// The parts of a program, as the host holds them: the root
   /// component's name and each template's text.
   pub struct Program<'a> { pub root: &'a str, pub templates: &'a [&'a str] }

   /// A value as the host supplies it, before validation.
   pub enum HostValue {
       Null, Boolean(bool), Number(f64), String(String),
       /// UTF-16 code units that aren't valid Unicode (an unpaired surrogate).
       Utf16(Vec<u16>),
       /// A number too large for binary64 (from JSON), as written.
       OutOfRange(String),
       /// `None` is an absent element: JavaScript's `undefined` or a hole.
       List(Vec<Option<HostValue>>),
       /// Absent fields are simply not here.
       Record(Vec<(HostKey, HostValue)>),
       Unsupported(UnsupportedKind),
   }

   pub fn render(program: &Program, model: &str, snapshot: &HostRecord) -> Result<Render, Vec<RuntimeDiagnostic>>;
   pub fn dispatch(render: &Render, handler: &str, payload: Option<&HostValue>) -> Result<Intent, Vec<RuntimeDiagnostic>>;

   /// One successful render: its tree, and the program, model and
   /// validated snapshot it came from (D5: kept as validated and encoded).
   pub struct Render { /* private */ }
   impl Render { pub fn tree(&self) -> &Tree; }
   ```

   `HostValue::from_json(&str)` is the native host's convenience: it keeps each number's text so an overflow becomes `OutOfRange` (Pass 0 Decision 8), and a duplicate key or a syntax error is an `Err` for the host, not a value. `Tree` and `Intent` serialize to `render-v1` and Pass 0's intent form.
4. **A render owns copies of everything it came from:** the template texts, the model text and the validated snapshot. Nothing a host does afterwards reaches it (D5: "later changes to host objects can't alter it"). Dispatch re-runs program validation and input validation on those copies (I14), then evaluates.

**Validation (P2.2)**

5. **Program validation's steps** (D3): (1) `mesh_manifest::load`; (2) each template: `mesh_template::from_json`, then every name checked against the model with the kind the template gives it (Pass 0 Decision 13), each failure `assembly-malformed-template` at the template, and an unsupported version `assembly-unsupported-format-version`; (3) each fingerprint against `mesh_template::fingerprint(model)`: `assembly-fingerprint-mismatch`; (4) in this pass: the template must be the root's (`assembly-missing-root`) and more than one template is refused as a limitation of this pass, with a test Pass 3 deletes; an occurrence of the root's own component inside it is `assembly-cycle`, so evaluation can't recurse.
6. **Input validation** converts a `HostValue` into an evaluator `Value` against a type, by §9.8, collecting every mismatch with its path: `runtime-missing-value` (a required name or field absent), `runtime-value-mismatch` (a present value that doesn't fit, reported at the deepest path where it stops fitting), `runtime-unknown-field`, `runtime-absent-element`, `runtime-number-out-of-range`, `runtime-non-finite-input`, `runtime-unpaired-surrogate`, `runtime-unsupported-value`. A snapshot name the root template doesn't declare is never looked at (D5, "Open scope"). For a payload: `runtime-unexpected-payload` for a payload given to an event without one; otherwise as a snapshot value, with paths from `$event`.
7. **`any` still has a shape to check:** a value of type `any` is walked for everything the boundary data model forbids (§9.8), at any depth, though no kind is required.

**Evaluation (P2.3, P2.4)**

8. **Values** are `enum Value { Absent, Null, Boolean(bool), Number(f64), String(Rc<str>), List(Rc<[Value]>), Record(Rc<BTreeMap<String, Value>>) }`; a record never stores an absent field (§9.7: "a record literal field whose value is absent is the same as no field"), and a list may hold `Absent` inside evaluation.
9. **`fits`** is one function over `Value` and `mesh_manifest::Type`, named types expanded, used by every runtime type check and by input validation (D8: "one relation").
10. **Numbers:** `+ - * /` and unary `-` are Rust's `f64` operations (IEEE 754, roundTiesToEven); `%` is Rust's `%` (truncated, exact); NaN's sign and payload are never observed, because nothing formats or compares a NaN's bits. `number::to_text(f64) -> String` implements §9.7's text conversion in two layers:
    - **digits:** the shortest, nearest, ties-to-even digit string and its exponent, from **MESH's own exact digit generator** (Pass 0 Decision 4c, reviewed). It is the reference generator's algorithm (`docs/tables/number_to_text.py`): decode the bits; compute the exact rounding interval (asymmetric at a power of two, ends included when the significand is even); find the smallest digit count with a candidate in it; choose the nearest candidate, then the even one. It does this over a small arbitrary-precision unsigned integer in `number.rs` (enough for 2^1074 × 10^k), with no new dependency. It never uses `core::fmt`, `ryu` or any other formatter;
    - **layout:** a MESH function that places those digits by §9.7's ECMA-262 steps.

    `-0` is `0`. It is only called on finite values: the output check runs first (D8), so NaN and the infinities reach `runtime-non-finite-output`, never text. The function's documentation names the generator and the guarantee it relies on.
11. **Order and the first error:** `eval` returns `Result<Value, RuntimeDiagnostic>` and `?`s through operands left to right, and `render` walks in document order (props in template order, then children), so the first error in D8's evaluation order is the one returned. Handlers are not evaluated at render.
12. **Checks, in D8's order at each point:** the type check (operands, member access, content, props against their declared types, arguments against parameter types), then the output check (no non-finite number, no absent list element, at any depth; `-0` becomes `0`). Each has its own code (Pass 0 Decision 27) and the span of the value checked.

**Trees, keys and handlers (P2.5)**

13. **Nodes and text runs** as D4 and Pass 0 Decision 22 say: adjacent text and interpolation children form one run, present even when empty; an absent prop is omitted; a `null` prop is `null`.
14. **Keys, program identity and handler identifiers** are Pass 0 Decisions 23–25: keys hash the program identity with the path, so they are stable within a program and change with it, and nothing here treats them as secret. The handler table (identifier → template, node path, event) depends only on the program, so it's built once per validation and could be cached with it. Every tree built is checked for duplicate keys (`runtime-key-collision`).

**Dispatch (P2.6)**

15. **Dispatch** is D5's lifecycle for one template: program validation of the render's copies; the handler identifier (`runtime-handler-other-program` if its program prefix isn't the render's program's; `runtime-unknown-handler` if the program has no such handler), which alone ends the phase if invalid; then the render's snapshot and the payload, together, every mismatch; then the handler's arguments, left to right, each checked against its parameter and at the output. The intent names the command and the template's component (D4).

**The test host and the reference renderer (P2.7)**

16. **In `crates/mesh-runtime/tests/common/`:** `host.rs` (reads a snapshot fixture with `HostValue::from_json`, renders, keeps every render by a number, dispatches an event with the render it names, records intents); `renderer.rs` (prints a tree as HTML-like text, one node per line, indented, props in code-point order, values as JSON, text runs quoted, keys not printed; and `compare(old, new)`, which lists, by key, each prop and text run whose value changed, and fails if the keys differ); `build.rs` (the template builder). Expected output is committed next to each test program, under `tests/programs/`.

## Review Focus

0. **Number to text is verified normatively:** `the_normative_table_holds` passes against the committed table, the table is unchanged by this pass (`git diff <base>..HEAD -- docs/tables/` is empty unless an outline amendment explains it), and `number.rs` generates no digits through `core::fmt`.
1. **Every rule of §9.7 and §9.8 has a test that names it** (by Pass 0's rule number), including each case the Definition of Done's "Inputs" and "Evaluation" lists spell out.
2. **The first error wins:** a template with several evaluation errors reports the first in evaluation order, and short-circuiting and the conditional skip an erroneous operand.
3. **Phases and order:** program validation stops at its first reporting step; input validation reports every mismatch, in path order; evaluation exactly one.
4. **Dispatch uses the render's snapshot,** never a new one; a mutated host object after render changes nothing; an absent argument is distinguished from `null`.
5. **I13:** a walk of every tree the tests produce finds only what I13 lists.
6. **No panic:** the fuzz test (P2.7) runs render and dispatch on mutated templates, snapshots, payloads and handler identifiers.
