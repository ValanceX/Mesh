# MESH v0.1 — Pass 3b (Array, Object, Command, EventValue) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Widen the MPRX grammar and pipeline (grammar → `mesh-syntax` → `mesh-parser` → `mesh-semantic` → `mesh-compiler`) to support array literals (`[1, 2, 3]`), object literals (`{{ key: value }}`), command invocations (`selectUser($event)`), and event values (`$event`) — the remaining four node kinds from `docs/MPRX-SPEC.md` §5's expression grammar. `<page items={[1, 2]} data={{ name: user.name }} action={selectUser($event)} />` must parse, lower, and compile cleanly. This completes MPRX's v0.1 expression grammar — after this pass, `mesh_syntax::Expression` has every variant §5 specifies.

**Architecture:** Bottom-up, one layer at a time (grammar → syntax → parser → semantic → compiler-test-coverage), same shape as Pass 3a. **Editing style differs from Pass 1-3a's plans**: those files have grown to 150-470 lines each, so this plan uses targeted insert/append instructions (exact anchor text to find, exact text to add) instead of "replace the full file contents" — full-file blocks would make this document large and error-prone to transcribe. Every insertion is still complete, literal code; nothing is left for the implementer to invent.

Two design points already fixed in `docs/MPRX-SPEC.md` (§2, §8) and `docs/superpowers/specs/2026-09-22-mesh-v0.1-pass-3-5-outline.md` during this pass's brainstorm — implementers should read those sections, not re-derive them:

1. **`event_value` is one atomic regex token** (`/\$[a-zA-Z_][a-zA-Z0-9_]*/`), not a structural `seq('$', $.identifier)` rule — a structural rule would let Tree-sitter's automatic whitespace-insertion accept `$ event` with a space, contradicting `event_value`'s placement in §2's *lexical* grammar (as opposed to `command_invocation`, which *is* structural and permits whitespace before its `(`, same as everywhere else in §5).
2. **Field-fallback convention, applying the lesson from Pass 3a's post-merge rust-skills audit**: that audit found `.unwrap_or(<arbitrary operator variant>)` was wrong for `UnaryOperator`/`BinaryOperator` specifically because *every* variant of those enums looks equally plausible — there's no way to tell a silently-defaulted operator from a correctly-parsed one. This pass introduces no enum with that problem: plain `String` fields (`command`, `EventValue.name`) keep the file's existing `.unwrap_or_default()` convention (an empty string is already a visibly-wrong, harmless sentinel — same spirit as the existing `Reference{name: String::new()}` in `missing_expression`); `ObjectKey`'s fallback gets the same harmless-empty-sentinel treatment for the same reason. `.kind()` dispatch (`lower_object_key`'s `identifier`/`string` match) uses `unreachable!()`, matching every other closed-set kind-dispatch already in the file.

`mesh-compiler`'s production code and `mesh-cli` are untouched — `compile()`'s signature doesn't change, same reasoning as every prior pass.

**Tech Stack:** Same as Pass 1-3a (Rust, Tree-sitter, `tree-sitter-cli` via npm). No new external crates. `grammar/tree-sitter-mprx/node_modules` should already be installed in whatever workspace this plan runs in (Pass 3a needed a one-time `npm install --ignore-scripts` + `node node_modules/tree-sitter-cli/install.js` workaround for a native-addon build issue unrelated to the CLI itself — if `node_modules` is missing, that's the recovery recipe; `npx tree-sitter --version` should print `tree-sitter 0.27.0` once it's in place).

**Spec:** `docs/MPRX-SPEC.md` (canonical grammar — this plan implements §5's remaining four node kinds, §2's `event_value` lexical clarification, and §8's Pass 3b rows) and `docs/superpowers/specs/2026-09-22-mesh-v0.1-pass-3-5-outline.md` (Pass 3b's place in the roadmap, including the grammar-technique rationale this plan implements).

## Global Constraints

- Scope is `ArrayExpression`, `ObjectExpression` (+ `ObjectMember`/`ObjectKey`), `CommandInvocation`, `EventValue` only. This completes §5's expression grammar for v0.1 — there is no Pass 3c.
- Do NOT add array/object subscript access (`a[0]`, `a["key"]`), nested elements (`Child::Element`), `on.` event bindings, comments, or structural-validation diagnostics — those are Pass 4/beyond or explicitly out of scope per `docs/MPRX-SPEC.md` §9.
- `command_invocation`'s argument list does **not** allow a trailing comma (`identifier '(' (expression (',' expression)*)? ')'` — no `','?`). `array_expression`/`object_expression` **do** allow one. This asymmetry is what `docs/MPRX-SPEC.md` §5's EBNF actually specifies — do not "fix" it for consistency.
- `event_value` is a single atomic regex token (`/\$[a-zA-Z_][a-zA-Z0-9_]*/`), not a `seq('$', $.identifier)` grammar rule. `mesh-parser`'s `lower_event_value` strips the leading `$` from the token text — there is no separate `name` field to read via `child_by_field_name`, unlike every other new node kind in this pass.
- `mesh-semantic::ObjectMember.key` is a plain `String` — `mesh_syntax::ObjectKey`'s `Identifier`/`String` distinction is flattened during lowering (both just name a field), not reused or mirrored as an enum. This matches the operator-enum-reuse precedent's *opposite* case: `ObjectKey`'s `String` variant carries a `Span` to strip, so it gets the normal mirror-and-strip treatment, not Pass 3a's reuse-directly treatment.
- Every dependency added via `cargo add` / `npm install` — never hand-pinned versions. This plan adds none.
- Generated Tree-sitter output (`grammar/tree-sitter-mprx/src/*`) is committed, same as every prior pass.
- `mesh-cli`'s production code (`crates/mesh-cli/src/main.rs`) is not expected to need any changes.
- Every task must end with `cargo test --workspace`, `cargo fmt --all -- --check`, and `cargo clippy --workspace --all-targets -- -D warnings` all still passing — **except** Tasks 2-3, where this is structurally impossible: extending `mesh_syntax::Expression` with new variants (Task 2) necessarily makes `mesh-semantic`'s match non-exhaustive (E0004) until Task 4 adds the corresponding arms, exactly like Pass 3a. Tasks 2-3 verify their own crate's tests only; Task 4 restores the exhaustive match and the full-workspace gate; Task 5 re-verifies it at the end.
