# MESH v0.4 Pass 2: The `mesh-lsp` Launcher and Platform Packages Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `mesh-lsp` from npm, with no Rust toolchain (outline, "Pass 2"). This pass:
- adds **five platform packages**, one per shipped target (Linux x64, Linux arm64, macOS x64, macOS arm64, Windows x64), each holding one native `mesh-lsp` binary (D8);
- fills **`@valancex/mesh-lsp`** with a launcher that starts the right binary and has no LSP logic;
- **builds each binary natively** on a CI runner of its own OS and architecture, and **exercises it there** through the launcher, installed from tarballs (D9);
- **verifies npm's behaviour** for these packages: platform filtering, an unsupported platform, `--ignore-scripts`, and an offline install from tarballs (D8);
- adds the **npm install path** to the editor setup guide, checked in Neovim.

**Architecture:**
- **Platform packages** live in `packages/mesh-lsp-<os>-<cpu>/`, in the npm workspace. Each is a `package.json` declaring `os` and `cpu`, a README, and a `bin/` directory that CI fills with the binary before packing. Binaries are never committed.
- **The launcher** is `packages/mesh-lsp/src/cli.ts`, compiled to `dist/cli.js` and declared as the package's `bin`. It resolves the platform package for `process.platform` and `process.arch`, spawns its binary with the same arguments and inherited stdio, and exits as the binary exits.
- **The transport tests** (`crates/mesh-lsp/tests/transport.rs`) learn to start the server through a launcher, so the same cases run against the native binary directly (every OS, every push) and through the installed launcher (each shipped target).
- **CI** gains a `native-binaries` job: a five-target matrix on native runners.
- Tasks **P2.1**–**P2.6**, in order.

**Tech Stack:** Rust on the pinned toolchain; Rust targets `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-pc-windows-msvc`. TypeScript for the launcher, with no runtime dependency. A local npm registry for the filtering test (`verdaccio`, pinned, run with `npx` in CI only). No new Rust dependency.

**Spec:** `docs/superpowers/specs/2026-09-25-mesh-v0.4-outline.md`: D7, D8, D9, D11; E6. Definition of Done items: "The launcher starts a native binary on every shipped target", the platform-package parts of "The packages are what we say they are", and the editor setup guide's npm path under "It's usable".

**Prerequisite:** Pass 0 is merged (the three-OS test baseline, and the `packages/` workspace with `@valancex/mesh-lsp` and no `bin`). Pass 1 need not be, though this plan assumes it is, since the passes run in order.

**Verification evidence:** checked at `7875097`: `transport.rs` spawns `env!("CARGO_BIN_EXE_mesh-lsp")` from one `spawn()` helper, so one seam covers every case; `editors/neovim/verify.sh` takes an installed server through `MESH_LSP` and copies it into a `bin/` on `PATH`; `crates/mesh-cli/tests/packages.rs` enumerates `packages/*/package.json`. Not checked here, and so the first thing each task confirms: the runner labels in Decision 7, npm's handling of the executable bit in packed binaries, and `verdaccio`'s behaviour on Windows. The sketches below are designs, not verified code.

## Global Constraints

- **The launcher has no LSP logic** (D8): no protocol handling, no configuration, no messages on stdout. Its only output is on stderr, and only when it can't start a binary.
- **A shipped binary is built and exercised on a native runner of its target** (D9). A cross-compiled binary is never packed or published. If a target has no native runner available to the repository, that target is not shipped in v0.4, and the user is told (outline, Risks); the other four still are.
- **The whole workspace suite doesn't run on every architecture** (D9). Each `native-binaries` job runs only the transport tests and the install scenarios.
- **No install scripts** in any package.
- **`mesh-lsp`'s behaviour doesn't change.** The only Rust source change is the transport tests' launcher seam.
- **Changelog, commit authorship, pushing:** as in Passes 0 and 1.
- **Verification gate for every task:** Pass 0's Rust gate, and in `packages/`: `npm ci`, `npm run build --workspaces`, `npm run typecheck --workspaces`, `npm test --workspaces --if-present`. P2.4 and P2.5 are verified in CI, on the five native runners.

## Decisions this plan makes

**Packages (P2.1)**

1. **Names follow npm's `os`/`cpu` values:** `@valancex/mesh-lsp-linux-x64`, `-linux-arm64`, `-darwin-x64`, `-darwin-arm64` and `-win32-x64`, in `packages/mesh-lsp-linux-x64/` and so on. P2.4 verifies that npm installs exactly one of them per target from a registry (outline D8: the names are this pass's to confirm). If that verification forces a change, the names change here, in `packages.rs` and in the launcher's table, and nowhere else.
2. **Each platform package** has `"os": ["<os>"]`, `"cpu": ["<cpu>"]`, `"files": ["bin"]`, a README saying it's installed by `@valancex/mesh-lsp` and not meant to be used directly, and no `bin` field (the launcher is the only entry point). Its binary is `bin/mesh-lsp`, or `bin/mesh-lsp.exe` on Windows. `.gitignore` ignores `packages/mesh-lsp-*/bin/`.
3. **`@valancex/mesh-lsp`** lists the five as `optionalDependencies`, each at exactly the workspace version, and declares `"bin": { "mesh-lsp": "dist/cli.js" }` again (Pass 0 removed it for want of a launcher).
4. **`packages.rs`** extends its exact list to the seven names, and checks: each platform package's `os` and `cpu` match its name; `@valancex/mesh-lsp`'s `optionalDependencies` are exactly the five, at exactly the workspace version; the launcher's table (Decision 6) names the same five packages. That last check reads `packages/mesh-lsp/src/targets.ts`, which holds only the table.

**Binaries (P2.4)**

5. **Linux binaries are static musl builds** (`*-unknown-linux-musl`), built on Linux runners of their own architecture with `musl-tools` installed for the C. A static binary runs on any Linux of that architecture, glibc or musl, old or new, so the package needs no `libc` field and no glibc floor. macOS binaries are built with `MACOSX_DEPLOYMENT_TARGET=11.0`. The Windows binary is built with `-C target-feature=+crt-static`, so it needs no Visual C++ runtime. Each is a `cargo build --release --locked -p mesh-lsp --target <triple>`.

**The launcher (P2.2)**

6. **`targets.ts`** maps `${process.platform}-${process.arch}` to a package name and a binary file name, for exactly the five targets.
7. **`cli.ts`**, with a `#!/usr/bin/env node` line:
   - look the key up in `targets.ts`; if it's missing, print to stderr which targets are supported and that `cargo install --path crates/mesh-lsp` from a clone of ValanceX/Mesh builds the server anywhere Rust runs, and exit 1;
   - resolve `<package>/package.json` with `createRequire(import.meta.url)`, and derive the binary's path from its directory; if the package isn't installed (an optional dependency npm skipped, or `--omit=optional`), print which package is missing and how to install it, and exit 1;
   - `spawn(binary, process.argv.slice(2), { stdio: "inherit" })`, with no shell;
   - forward `SIGINT`, `SIGTERM` and `SIGHUP` (where the platform has them) to the child;
   - when the child exits with a code, exit with that code; when it's killed by a signal, remove the forwarding handlers and kill the launcher with the same signal, so the parent sees the same death;
   - if spawning fails (for example, the binary lost its executable bit), print the error and exit 1.

   Everything else, including what the server writes on stdout, belongs to the binary: the launcher never reads its streams.
8. **The launcher's unit tests** (`packages/mesh-lsp/test/launcher.mjs`) use a fake platform package holding a small Node script as its "binary" (run with a `targets` override the tests inject through an environment variable read only in tests: `MESH_LSP_TEST_TARGETS`, a path to a JSON table). They check: arguments and stdin/stdout pass through byte for byte; exit codes pass through (0, 1, 3); a signal kills the launcher too; an unsupported platform and a missing package give their messages and exit 1. The variable is documented in `cli.ts` as test-only; it isn't part of the package's API (D11).

**The transport tests through the launcher (P2.3)**

9. **One seam in `transport.rs`:** `spawn()` starts `env!("CARGO_BIN_EXE_mesh-lsp")`, unless `MESH_LSP_LAUNCHER` is set, in which case it starts `node` with that path (the installed `node_modules/@valancex/mesh-lsp/dist/cli.js`) as its first argument. Every existing case then runs unchanged. Running through `node` directly, rather than npm's `.bin` shim, keeps the test independent of how npm spells shims on Windows; the shim itself is exercised in P2.5.

**npm's behaviour (P2.5)**

10. **Four scenarios, on each of the five native runners,** in `packages/mesh-lsp/test/install.mjs`, run by the `native-binaries` job (not by `npm test`, since it needs a real binary and a registry):
    - **Supported, from a registry.** Start `verdaccio` on a free port with a config that serves only `@valancex/*`, from local storage, with no uplink. Publish the launcher and all five platform packages: the native one with its real binary, the other four with a placeholder file in `bin/` (enough to test filtering). In an empty project, `npm install @valancex/mesh-lsp --registry <local>`. Exactly one platform package is installed, and it's the native one. `npx mesh-lsp` (the shim) completes an `initialize`/`shutdown`/`exit` round trip and exits 0.
    - **`--ignore-scripts`.** The same install with `--ignore-scripts` gives the same tree, and the same round trip.
    - **Offline, from tarballs.** In another empty project, `npm install --offline <launcher.tgz> <native-platform.tgz>` succeeds, and the round trip passes. The installed binary is executable (on Unix, its mode has the owner's execute bit), which settles whether npm keeps it.
    - **Unsupported.** In another empty project, `npm install --offline <launcher.tgz>` alone succeeds (the optional dependencies are skipped), and `npx mesh-lsp` exits 1 with the missing-package message, naming the platform package.
11. **The registry is a test tool only.** `verdaccio` is pinned and invoked with `npx`; it isn't a dependency of any package. Other package managers aren't tested (outline Non-goals).

**CI (P2.4)**

12. **The `native-binaries` job,** `fail-fast: false`, one entry per target:

    | Target | Runner (confirm the label is available) | Rust target |
    |---|---|---|
    | Linux x64 | `ubuntu-24.04` | `x86_64-unknown-linux-musl` |
    | Linux arm64 | `ubuntu-24.04-arm` | `aarch64-unknown-linux-musl` |
    | macOS x64 | `macos-15-intel` | `x86_64-apple-darwin` |
    | macOS arm64 | `macos-15` | `aarch64-apple-darwin` |
    | Windows x64 | `windows-2025` | `x86_64-pc-windows-msvc` |

    Each: install the toolchain and target; build the binary (Decision 5); `cargo test --release --locked --target <triple> -p mesh-lsp --test transport`, so the binary tested directly is the shipped build, same target and profile; copy the binary into its platform package's `bin/`; build and `npm pack` the launcher and that platform package; install both from tarballs into an empty project; run `transport.rs` again with `MESH_LSP_LAUNCHER` set; run `install.mjs`; upload the platform tarball as an artifact (Pass 3's release workflow reuses this job's steps).
13. **It runs on every push to `main` and every pull request,** like the rest of CI. Five release builds of one crate is minutes, and a platform break found at release time costs more.

**The guide (P2.6)**

14. **The editor setup guide** gains "Install with npm": `npm install -g @valancex/mesh-lsp`, which puts `mesh-lsp` on `PATH`, before the existing `cargo install` path, and says which five targets have binaries. The rest of the guide is unchanged: the editor starts `mesh-lsp` either way.
15. **`editors/neovim/verify.sh`** accepts `MESH_LSP` pointing at an npm-installed `mesh-lsp` shim. Today it copies `MESH_LSP` into its `bin/`, which breaks a shim that finds its package relative to itself; it now links it (a symlink on Unix) instead. The guide's verification section shows the npm case.

## Review Focus

1. **Five native binaries, natively exercised.** Every `native-binaries` job is green, and its log shows the binary built for its triple on its own runner, `transport.rs` passing directly and through the installed launcher, and the four install scenarios passing.
2. **The launcher is transparent.** Its unit tests show byte-for-byte pass-through of arguments and streams, exit codes, and signals.
3. **npm filters as claimed.** From the local registry, each runner installs exactly its own platform package.
4. **Failure is explained.** An unsupported platform and a missing package each give one clear stderr message and exit 1.
5. **The family is consistent.** `packages.rs` passes: seven names, `os`/`cpu` matching names, optional dependencies exactly the five at the workspace version, and the launcher's table naming the same five.
6. **Nothing cross-compiled ships.** No job packs a binary it didn't build for its own runner's OS and architecture.
7. **The guide's npm path works** in Neovim through `verify.sh` with an npm-installed server.
