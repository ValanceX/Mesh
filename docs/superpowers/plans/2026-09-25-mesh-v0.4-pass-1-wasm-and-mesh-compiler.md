# MESH v0.4 Pass 1: `mesh-wasm` and `@valancex/mesh-compiler` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The compiler in JavaScript (outline, "Pass 1"). This pass:
- adds **`crates/mesh-wasm`**, a `cdylib` that builds `mesh_compiler::check::run` for `wasm32-unknown-unknown` in a Cargo-driven build (D1, D2);
- fills **`@valancex/mesh-compiler`** with the module and a deliberately boring TypeScript wrapper (I6) that checks a source and returns the diagnostics document (D4);
- implements the **failure contract** (D6), the **version check** (I10) and the **size budget** (D2);
- proves **agreement** with `mesh check` (I7) and **determinism** (I9) from Node, over fixtures and fuzzer mutants, and runs in **headless Chromium**;
- adds D9's **WASM job** and the WASM build to the MSRV job.

**Architecture:**
- **`mesh-wasm`** is small: a safe core (`respond`) that turns five strings into the rendered diagnostics document by calling `check::run` and `Report::render_json`, and a thin `extern "C"` layer, compiled only for `wasm32`, that moves bytes in and out of linear memory. It has no semantics (I6) and touches no file system.
- **The wrapper** has three layers: `index.ts` (the public API: `check`, `init`, `version`, two error classes, the document's types), `engine.ts` (internal: loading, instances, the version handshake, memory transfer, failure handling), and `version.ts` (a constant). The package's `exports` map exposes only `index.js` and the `.wasm` asset (D11).
- **Two module builds.** The shipped `mesh.wasm` (profile `wasm`), and `mesh-test.wasm` (the same, plus the `test-hooks` feature: a panicking export and a live-allocation count). The failure and memory tests use the second; everything else uses the first.
- Tasks **P1.1**–**P1.6**, in order.

**Tech Stack:** Rust on the pinned toolchain, target `wasm32-unknown-unknown` (clang compiles Tree-sitter's C through `cc`, as today). TypeScript, ESM. Tests with Node's built-in `node:test`. Dev dependencies: `ajv` (schema checks in tests) and `playwright` (the browser smoke test). No runtime dependency. No new Rust dependency.

**Spec:** `docs/superpowers/specs/2026-09-25-mesh-v0.4-outline.md`: I6–I10; D1, D2, D4, D6, D9, D11; E2, E9. Definition of Done items: "Batch hosts agree", "Checks are deterministic", "Positions work in JavaScript" (the JavaScript half), "The failure contract holds", "The wrapper refuses a mismatched module", "It runs where JavaScript runs", and the `@valancex/mesh-compiler` parts of "The packages are what we say they are".

**Prerequisite:** Pass 0 is merged: `mesh_compiler::check`, D5's positions, the three-OS baseline and the `packages/` workspace exist.

**Verification evidence:** the audit's throwaway probe (outline, "Audit of v0.3.0") showed that the compiler builds for `wasm32-unknown-unknown` unchanged on 1.98.1 and 1.91, imports nothing, agrees with the CLI on 158 runs, and passes `nesting.rs`'s sources at the default stack with at least 4× headroom. Checked against `tree-sitter` 0.27's source: on `wasm32-unknown-unknown`, its C `malloc`/`free` are backed by Rust's global allocator (`binding_rust/wasm_allocator.rs`), so a counting global allocator sees every live allocation, C's included. The API sketches below are designs, not verified code. Write each failing test first, see it fail, and treat any difference from what a step predicts as something to investigate.

## Global Constraints

- **No semantics outside Rust (I6).** The wrapper validates only JavaScript argument types (a `TypeError` for a non-string `source`), which is JavaScript hygiene, not MESH validation. It never inspects a diagnostic.
- **Only the document crosses (I8).** No export returns anything but bytes of the diagnostics document, a status, or the version.
- **The Rust workspace's behaviour doesn't change.** `mesh-wasm` is a new consumer; no other crate changes, except a `[profile.wasm]` in the root `Cargo.toml`.
- **`panic = "abort"` only where it belongs.** It's set in the `wasm` profile, never in `dev` or `release`, because `mesh-lsp` relies on unwinding (`catch_unwind`, v0.3 D7).
- **Changelog, commit authorship, pushing:** as in Pass 0. CI changes need a push to verify; ask the user before pushing.
- **Verification gate for every task:** Pass 0's Rust gate, plus, from `packages/`:

  ```bash
  npm ci
  npm run build:wasm -w @valancex/mesh-compiler
  npm run build --workspaces
  npm run typecheck --workspaces
  npm test -w @valancex/mesh-compiler
  ```

  `npm test` needs a native `mesh` (`cargo build -p mesh-cli`) for the agreement test; it finds it at `../../target/debug/mesh[.exe]`, or at `MESH_BIN`.

## Decisions this plan makes

**The crate (P1.1)**

1. **`crates/mesh-wasm`**, a workspace member, `crate-type = ["cdylib", "rlib"]`: the `rlib` lets native tests call the safe core. Dependencies: `mesh-compiler` only (`mesh_compiler::check` owns manifest loading). A `test-hooks` feature, off by default.
2. **The safe core** is one function:

   ```rust
   /// Runs one check and renders its report: exactly
   /// `check::run(request).render_json(request)`.
   pub fn respond(source: &str, path: &str, model: Option<(&str, &str, &str)>) -> String;
   ```

   Native tests pin it to `check::run` on every corpus run, so the `extern` layer only has to move bytes.
3. **The `extern "C"` layer** is compiled only for `target_arch = "wasm32"`, so native builds of the workspace export nothing. Its exports are internal (D11), and this plan fixes them so Pass 1 can test them; they may change in any release:
   - `mesh_version_ptr() -> *const u8`, `mesh_version_len() -> usize`: the crate's `CARGO_PKG_VERSION`. **These two never change**, whatever else does, so any wrapper can always read any module's version (I10).
   - `mesh_alloc(len: usize) -> *mut u8` and `mesh_free(ptr: *mut u8, len: usize)`: input buffers, allocated and freed by the wrapper.
   - `mesh_check(source, source_len, path, path_len, manifest, manifest_len, manifest_path, manifest_path_len, component, component_len, has_model: u32) -> u32`: runs `respond`, keeps the document in a module-owned buffer, and returns `0`; returns `1`, keeping nothing, if an input isn't UTF-8 (`std::str::from_utf8`, never unchecked). The wrapper treats `1` as a boundary failure.
   - `mesh_result_ptr() -> *const u8`, `mesh_result_len() -> usize`, `mesh_result_clear()`: read the document, then release it.
   - With `test-hooks` only: `mesh_test_panic()`, which panics, and `mesh_live_allocations() -> usize`, from a counting `#[global_allocator]` over `std::alloc::System` that exists only under the feature.
4. **Module-owned state** is one result buffer, in a `thread_local!` `RefCell<Vec<u8>>` (WASM here is single-threaded; this keeps `static mut` and its lints out).
5. **The profile:** `[profile.wasm]` in the root `Cargo.toml`: `inherits = "release"`, `opt-level = "z"`, `lto = true`, `codegen-units = 1`, `panic = "abort"`. The build is `cargo build -p mesh-wasm --target wasm32-unknown-unknown --profile wasm`, giving `target/wasm32-unknown-unknown/wasm/mesh_wasm.wasm`. No `wasm-opt` (D2).

**The wrapper (P1.2)**

6. **The public API** (`index.ts`), all of it:

   ```ts
   export interface CheckInput {
     source: string;
     path: string;                       // an opaque identifier, never read (D4)
     model?: { manifest: string; path: string; component: string };
   }
   export function check(input: CheckInput): Promise<DiagnosticsDocument>;
   export function init(module: URL | string | BufferSource | WebAssembly.Module): Promise<void>;
   export const version: string;
   export class MeshInternalError extends Error {}   // D6: a boundary failure
   export class MeshVersionError extends Error {}    // I10: an incompatible module
   export type { DiagnosticsDocument, Diagnostic, Span, Position, Suggestion, Severity };
   ```

   The types mirror `schemas/diagnostics-v1.schema.json` by hand; a test validates real output against the schema with `ajv`, and a type-level test checks a parsed document is assignable to `DiagnosticsDocument`.
7. **`check` is async.** Instantiating a module is asynchronous in browsers, and after a failure the next check must create a fresh instance lazily (D6), so every check may need to await one. The check itself runs synchronously inside. Concurrent calls are serialized by the engine, one at a time, in call order.
8. **Loading (D4).** In Node, the first `check` loads `mesh.wasm` next to `index.js` (`new URL("./mesh.wasm", import.meta.url)`, read with `node:fs/promises`), unless `init` was called. In a browser, `check` before `init` rejects with an `Error` saying `init` is needed. `init` compiles the module once (`WebAssembly.compile`, or uses a given `Module`) and keeps it; instances are made from it. Nothing bundler-specific.
9. **The version handshake (I10).** Before using a new instance, the engine checks that it exports the two version functions and `memory`, reads the version, and compares it with `version.ts`'s constant. On any mismatch, or a missing export, it throws `MeshVersionError` naming both versions, and never calls another export of that module. A module that fails the handshake is dropped, so `init` can be called again with the right one.
10. **Transfer and release.** For each check: encode each string with one `TextEncoder`; `mesh_alloc` and copy each; call `mesh_check`; in a `finally`, `mesh_free` every input buffer; on status `0`, copy the result out with `TextDecoder` (`fatal: true`), call `mesh_result_clear`, and `JSON.parse`. A check without a model passes zero-length buffers and `has_model = 0`.
11. **Failure (D6).** Any exception thrown by a call into the instance, a non-zero status, invalid UTF-8 or JSON in the result, or a parsed value that isn't an object with `version` and `diagnostics`, becomes `MeshInternalError` (the original as `cause`). The engine then drops the instance (and every reference to it), and the next check instantiates a new one from the kept `Module`. `MeshInternalError` is never used for anything the check reports: those are diagnostics.
12. **`version.ts`** holds the package version as a constant. `crates/mesh-cli/tests/packages.rs` pins it to `package.json`'s version (and so to the workspace's).
13. **The package:** `"type": "module"`, `"exports": { ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" }, "./mesh.wasm": "./dist/mesh.wasm" }` (the asset path, so a browser caller can resolve its URL; it isn't API), `"files": ["dist"]`, `"sideEffects": false`, and `"engines": { "node": ">=22" }` from Decision 16. Scripts: `build:wasm` runs the cargo build of Decision 5 and copies `mesh_wasm.wasm` to `dist/mesh.wasm`, and the `test-hooks` build to `test/build/mesh-test.wasm`; `build` runs `tsc`; `test` runs `node --test test/`.

**Tests (P1.3–P1.4)**

14. **Tests are plain `.mjs` files** in `packages/mesh-compiler/test/`, importing `../dist/index.js`, or `../dist/engine.js` where they need the internal seam (injecting a module). Nothing outside the package imports `engine.js`; the `exports` map keeps it out of reach.
15. **The agreement fuzzer is the test's own,** a small seeded mutator (a `mulberry32` PRNG and a token list like `crates/mesh-cli/tests/fuzz.rs`'s), because it must write each mutant to a temporary file for the CLI. Budget: `MESH_FUZZ_ITERATIONS`, default 300 in CI; one local run of at least 100,000 is recorded in "As built" with its seed.
16. **Node versions: 22 and 24,** named in the CI matrix, `engines`, and the package README (outline D4). Both are LTS lines at the time of writing; a later release changes the matrix explicitly.
17. **The size budget is 300,000 bytes gzipped** (D2's 300 KB), measured with `node:zlib`'s `gzipSync` at level 9 on `dist/mesh.wasm`, in a test.
18. **The browser smoke test** serves `dist/` and a test page from a `node:http` server on a free port, drives headless Chromium through Playwright, calls `init(new URL("/mesh.wasm", location.href))`, checks `examples/fixtures/fail/mismatched-closing-tag.mprx`'s text, and compares the document with the CLI's, parsed. In CI, Playwright installs Chromium; locally it uses what's installed.

## Review Focus

1. **Boring wrapper (I6).** `engine.ts` and `index.ts` contain no MPRX, manifest, position or diagnostic logic. The only things they read from a document are `version` and `diagnostics` existing, in Decision 11's shape check.
2. **Agreement (I7).** Every corpus run, and every mutant, parses equal to `mesh check --format json`.
3. **Determinism (I9).** Twice on one instance, and again after a forced failure, the documents are equal.
4. **`source.slice(start.utf16, end.utf16)` (D5).** For every diagnostic and suggestion of every corpus run, and for sources with multi-byte UTF-8, astral characters, CRLF and a leading `﻿`, the slice equals the text the byte span covers (checked by slicing a `Buffer` of the same source).
5. **Failure (D6).** `mesh_test_panic` makes `check` reject with `MeshInternalError`; the trapped instance's exports are never called again (the test wraps them to count calls); the next check succeeds from a new instance.
6. **Memory (D6).** 100,000 checks cycling the fixture corpus on the `test-hooks` build: after a warm-up pass, `memory.buffer.byteLength` and `mesh_live_allocations()` measured after each call return are the same at the end as after the warm-up, and after the warm-up `mesh_live_allocations()` after every call equals its value before it. (The warm-up absorbs one-time, lazily initialized state; anything that still grows after it is a leak.)
7. **Version (I10).** A module reporting another version, and one missing the version exports, give `MeshVersionError` before any other export is called.
8. **Nesting (D6).** `nesting.rs`'s thirteen sources and its deep manifest, ported to the test, give diagnostics at the default stack; past the limit, one `nesting-too-deep`.
9. **The package ships what it should.** `npm pack` holds the compiled JavaScript and declarations of `index`, `engine`, `version` and `document` under `dist/`, `dist/mesh.wasm`, `package.json`, `README.md` and `LICENSE`; no `src/`, `test/`, `tsconfig.json`, source maps of test files or `mesh-test.wasm`. Installed from its tarball into an empty directory, `check` works with no Rust toolchain on `PATH`.
