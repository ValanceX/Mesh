**Goal:** Write down every contract v0.5 builds on, before any code implements one (outline, "Pass 0: Specifications, no code"). This pass:
1. corrects the **release record** (F2) and the **release checklist** (F3);
2. writes MPRX's **evaluation semantics** into the spec as **§9.7** (D8), with the **boundary data model** and its JSON and JavaScript mappings (D5), and the two new check-time diagnostics;
3. specifies **`template-v1`** (D1): its schema, and the model fingerprint's canonical form and digest;
4. specifies **programs and assembly** (D7): the rules, and the order of their diagnostics;
5. specifies **`render-v1` and the command intent** (D4): their schemas, and the properties and encodings of keys, handler identifiers and program identity;
6. specifies **diagnostics** (D3): every new code in the three families, the runtime diagnostics' document form, and their locations;
7. gets all of it **reviewed** before Pass 1 or Pass 2 starts.

**Architecture:** Nothing here runs. The pass produces documents, in the places the released v0.5 will keep them, so NEXUS and PORT can build on them as soon as the pass merges (outline, "Sequencing"):

Each carries a status line, "Specified for v0.5; not yet implemented", which Pass 4 removes.
- Tasks **P0.1**–**P0.7**, in that order. P0.2 comes before the formats because the formats encode its values.

**Tech Stack:** Markdown and JSON Schema (draft 2020-12, as `diagnostics-v1` and `manifest-v1` are). The only code is tests of documents (Decision 1), and the number-to-text table's reference generator, a standard-library Python 3 script that is part of the contract, not of the product (Decision 4b).

**Spec:** `docs/superpowers/specs/2026-09-25-mesh-v0.5-outline.md`: F2, F3; D1, D3, D4, D5, D7, D8; I11–I15; "Pass 0". The outline defines no API, serialized representation, encoding or file layout; this pass defines the serialized ones, and leaves the Rust and TypeScript APIs to the pass plans.

**Verification evidence:** checked against the code at `33648f3`:
- the Semantic IR (`mesh_semantic::Element`) keeps number literals as source text (`Literal::Number(String)`), drops whitespace-only text and shadowed attributes, and has spans only in bytes;
- analysis keeps resolutions beside the IR (`Analysis::resolutions`, `Target`), and `Target::Command` names only the command, since a template's commands are its own component's;

- the parser's `number` is `digit+ ('.' digit+)?`, unsigned;

Whether the standard library's or `ryu`'s documentation guarantees shortest, nearest and ties-to-even output is **not** established here. P0.2 reads both and records what they state (Decision 4c).

The encodings below are designs. Where a decision says "recommended", the review in P0.7 may change it, and the changed text is what later passes implement.

## Global Constraints

- **No product code.** No crate, package or workflow changes behaviour. The only code this pass adds is tests that keep documents honest (Decision 1), and the reference generator (Decision 4b).
- **Nothing contradicts the outline.** Where writing a document finds the outline wrong or incomplete, stop and amend the outline in the same commit, and say so in the commit message. The outline stays the contract.
- **Normative words** (*must*, *must not*, *only*, *exactly*) mean what the outline says they mean.
- **Every rule gets a name a test can cite.** Each numbered rule in §9.7, §9.8 and the manuals has an anchor, so Pass 1–3 tests can name the rule they pin (the outline's Definition of Done: "Every rule gets a test").
- **Additive-only promise stated once per format,** in its schema's `description`, with the diagnostics document's wording.
- **Changelog.** `CHANGELOG.md` gets an `[Unreleased]` section; P0.1 adds it. Specifications that change no behaviour get one line under `### Added` each ("specified, not yet implemented").
- **Commit authorship** follows the repository's convention. Don't invent or hard-code an agent or model identity in commit metadata.
- **Verification gate for every task,** from the repo root: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps`. Every existing test passes unedited.

## Decisions this plan makes

**Where the documents live**

1. **Documents, not code, but tested documents.** A schema nobody validates rots before its first reader. P0.3–P0.6 each add an example document to their manual, and one test file, `crates/mesh-compiler/tests/specifications.rs`, checks with the `jsonschema` dev-dependency that each new schema is a valid draft 2020-12 schema, that each manual's examples validate against it, and that each manual's counter-examples (marked in the manual) don't. It uses no product API, so it doesn't implement anything early. It moves to the crates that own each format in Passes 1–3.
2. **New diagnostic codes are listed in `docs/manual/runtime.md` and §9.7, not in `docs/manual/diagnostics.md`,** until the code that emits them exists. `diagnostics_reference.rs` requires the reference to list exactly `DiagnosticCode::ALL`; Pass 1 moves the two check-time codes there with their `DiagnosticCode`s, and Pass 2 and Pass 3 add the runtime and assembly families, with a test of their own (Decision 27).

**Evaluation (P0.2, D8)**

3. **§9.7 is written rule by rule,** in the outline's order: values and absence; *fits*; numbers (representation, literals, arithmetic, `%`, negative zero, non-finite values); equality and comparison; evaluation order (expressions, render, dispatch); runtime checks; text conversion; lists and records in content. Each rule is numbered (`9.7.1`…), and each example the outline gives is kept as an example in the spec.
   **Normative references are named exactly:** IEEE 754-2019 §4.3.1 (roundTiesToEven) and §5.4.1 (the arithmetic operations), and ECMA-262's Number::toString(x, 10) (§6.1.6.1.20 in ECMA-262 2025). The spec says which edition it cites and that the rule doesn't change with later editions.
4. **Text conversion is stated as an algorithm,** not only as prose: take the shortest digit string that round-trips; if several, the one nearest the exact value; if two are equally near, the one with an even last digit; then lay it out by ECMA-262's steps 6–12 (verify the step numbers against the cited edition). §9.7 says, citing the text, that ECMA-262's normative step 5 leaves the last digit open, and that MESH makes the note that recommends nearest-then-even normative. So V8, or any conforming engine, is not the authority for MESH output (outline D8, "Number to text"). Inline examples cover each layout branch (`k ≤ n ≤ 21`, `0 < n ≤ 21`, `−6 < n ≤ 0`, and both exponent forms) and the thresholds `1e21`/`123456789012345680000` and `0.000001`/`1e-7`. The full set of examples is the table (Decision 4a).

   **4a.** **The normative number-to-text table** is `docs/tables/number-to-text.tsv`, part of the v0.5 contract, which §9.7 cites as normative. One row per value, with these columns:
    - `bits`: the binary64 pattern, 16 hexadecimal digits, so the input is exact and never re-parsed;
    - `expected`: the exact MESH text; or, for NaN, `+∞` and `−∞`, `!runtime-non-finite-output`, since D8 stops them before text conversion;
    - `category`, from the list below;
    - `why`: one line saying what the row proves.

    The table has at least one row in every category, and a row for every value a category names:
    - `ordinary`: `1.5`, `100`, `0.1`, `-2.5`, `0.1 + 0.2`'s result, `1/3`, `123.456`, and their negations.
    - `zero`: `+0` gives `0`; `-0` gives `0`.
    - `integer-boundary`: 2^53 − 1, 2^53, 2^53 + 2, 2^54, and 2^n for n = 1, 52, 53, 63, 64, 1023, where the gap below is half the gap above, so the rounding interval is asymmetric; also both neighbours of each.
    - `layout-threshold`: both sides of 1e21 (`123456789012345680000`, `1e+21`, and the largest double below 1e21), 1e-6 and 1e-7 (`0.000001`, `1e-7`, and their neighbours), and one value in each layout branch.
    - `magnitude`: the largest finite value, `1e308`, `1e-300`, the smallest normal value (`2.2250738585072014e-308`) and its neighbours.
    - `subnormal`: the smallest subnormal (`5e-324`), the largest subnormal, and three with random mantissas.
    - `nearest-choice`: values where more than one shortest candidate round-trips, so choosing the nearest is what fixes the output. The smallest subnormal is one (every candidate from `3e-324` to `7e-324` reads back as it). The generator finds at least ten more, spread across magnitudes, including at least one where the nearest candidate is below the value and one where it is above.
    - `tie`: values whose two shortest candidates are exactly equally near, if binary64 has any, where the even one must be chosen. The generator searches for them (Decision 4b). If it finds none, the category holds no rows, and §9.7 records the search and its argument. The rule stays normative either way.
    - `non-finite`: NaN (a quiet one and one with a payload and the sign bit set), `+∞` and `−∞`, each giving `!runtime-non-finite-output`.

   **4b.** **The reference generator** is `docs/tables/number_to_text.py`: Python 3 with the standard library only, and exact arithmetic (`fractions.Fraction` and integers). For each value it decodes the bits exactly, computes the exact rounding interval (half-open or closed by the even-significand rule of round-to-nearest-even), and finds the smallest `k` for which some `k`-digit `s` falls in the interval. It enumerates every such `s`, chooses the nearest and then the even one, and lays the digits out by the §9.7 algorithm. It never calls a float formatter: not `repr`, `str`, `format` or `float.hex` for output, and it reads its values only from bits. It writes the table (`--write`), checks it (`--check`), and searches for ties (`--search-ties`, over every binary64 exponent with structured and random significands). It reports what it searched, and the report goes into §9.7. Because the table is computed from the rule alone, it can't encode what an implementation happens to print.

   **4c.** **The runtime's digit generator is chosen here,** with the documentation it relies on (outline D8, "The Rust implementation must not rely on undocumented behaviour"):
    - **Rejected:** `core`/`std` float formatting (`Display`, `Debug`, `LowerExp` for `f64`). Its documentation, read for the pinned toolchain (1.98.1), gives no algorithm and no guarantee of shortest output or of which shortest candidate is printed. Record the documentation read, with its URL and version.
    - **Candidate:** the `ryu` crate's `Buffer::format_finite`, under a MESH layer that splits its output into digits and exponent and lays them out by ECMA-262. It is adopted only if its documentation, or the paper it implements and cites (Adams, "Ryū: fast float-to-string conversion", PLDI 2018), states all three guarantees: shortest, correctly rounded (nearest), and ties to even. Record the exact statements relied on.
    - **Otherwise:** MESH's own exact generator in `mesh-runtime` (Pass 2): the same enumeration as the reference generator, over a small arbitrary-precision integer, with its correctness argument in its documentation. It's slower, and D6 sets no latency target.

    The choice, and the evidence for it, go into `docs/manual/runtime.md`'s implementation note and this plan's "As built". Whichever is chosen, it is correct because it passes the table in Pass 2, not because a library is trusted.
5. **The two check-time codes are named `content-not-text`** (an interpolation whose static type is a list, a record, `list<nothing>`, or an optional of one) **and `number-literal-out-of-range`** (a literal whose nearest binary64 value is infinite). Both are errors, in §9.7 with their spans: the interpolation, and the literal.
6. **§9.2's sentence "How a runtime represents absence is up to it"** is replaced by a pointer to §9.8: the boundary now says how absence crosses. §10 keeps slots and children out of scope and says composites without them are now defined (`docs/manual/templates.md`). The status table gains a "v0.5" table with Passes 0–4, "Planned".

**The boundary (P0.2, D5)**

7. **§9.8, "The boundary", is the boundary data model** and the table of how each value crosses, copied from the outline and made normative: absence crosses only as omission; `-0` becomes `0` on the way out; NaN and infinities never cross; strings are Unicode scalar values; lists have no absent elements; records are exact.
8. **The JSON mapping:** a snapshot or payload in JSON is decoded with each number's text converted to the nearest binary64 value, as a literal is (§9.7); a number whose nearest value is infinite is an input diagnostic, not a parse failure; `-0` in JSON is `-0`; a string with an escaped unpaired surrogate (`"\ud800"`) is an input diagnostic; a duplicate object key is a malformed document, which a host's JSON reader reports before the runtime sees a value. Outputs are written as JSON losslessly: every output number is finite and not `-0`, and every string is valid.
9. **The JavaScript mapping** is D5's list, made normative: missing and `undefined` properties are absent; `undefined` elements and holes are absent elements (so rejected on input); numbers keep their binary64 value; strings keep their UTF-16 code units; everything else, and any cycle, is *unsupported, with its kind*. The kinds are named: `function`, `symbol`, `bigint`, `object` (a non-plain object, with its constructor's name if it has one), `cycle`. The byte-level encoding is Pass 3's (outline D5: "The encoding is the pass plan's").

**The template (P0.3, D1)**

10. **`template-v1`'s top level** (recommended):

    ```json
    {
      "format": "mesh-template",
      "version": 1,
      "component": "user-card",
      "fingerprint": "sha256:<64 hex digits>",
      "compiler": "0.5.0",
      "root": { "…": "an element" }
    }
    ```

    `format` is a constant, so a stray JSON file is refused as malformed rather than as a version mismatch. `compiler` is provenance only (D1).
11. **Elements, children and handlers:**
    - An **element** is `{ "component", "span", "props": [...], "events": [...], "children": [...] }`. `props` holds only the attributes §3's duplicate resolution keeps, in source order, each `{ "prop", "value", "span" }`, where `value` is an expression, and a quoted attribute is a string literal.
    - An **event binding** is `{ "event", "command", "arguments": [...], "span" }`. The handler is not an expression: a template can hold a command only as a handler, and `$event` only inside a handler's arguments, so both rules of §9.5 are structural, and a template breaking them is malformed. The command's identity is `command` and the template's own `component` (D4).
    - A **child** is `{ "kind": "text", "value", "span" }`, `{ "kind": "expression", "expression" }` or `{ "kind": "element", "element" }`. Whitespace-only text is omitted (§3).
12. **Expressions** have a `kind` each: `literal` (`value`: a string, a finite number, a boolean or `null`), `scope` (`name`: the scope declaration it reads), `member` (`object`, `field`), `unary`, `binary`, `conditional`, `list`, `record` (`fields`: `[{ "name", "value", "span" }]`, shadowed keys omitted, as §3 omits shadowed attributes), and `event` (`$event`). Operators are named (`"not"`, `"negate"`, `"add"`, …, `"and"`, `"or"`), never spelt as source text. Every expression has a `span`.
13. **Resolution is by construction.** Every name in a template is a declaration name in the model: a `component` is a component, a `prop` a prop of the element's component, an `event` an event of it, a `command` a command of the template's component, a `scope` name a scope declaration of the template's component. `$event` resolves to the payload of its binding's event. So the template holds "what each name resolved to" without a resolution table, and the runtime checks each name against the model once, at validation: a name the model doesn't declare, with the kind the template gives it, makes the template malformed (`docs/manual/templates.md` says so; Pass 2 implements it).
14. **Numbers are JSON numbers** holding exactly the binary64 value. The compiler writes the shortest text that round-trips; a reader must convert with correct rounding (Rust: `serde_json`'s `float_roundtrip` feature, which Pass 1 enables; JavaScript's `JSON.parse` already does). A literal is never `-0`, NaN or infinite, so JSON can always hold it.
15. **Spans** are `{ "start": { "byte", "utf16" }, "end": { "byte", "utf16" } }`, offsets into the source as given, exactly as the diagnostics document counts them. Nothing depends on them for meaning (D1).

**The fingerprint (P0.3, D1)**

16. **The canonical form is a tree, digested bottom-up** (recommended). Named types are structural, so the fingerprint expands them (D1), and a manifest can nest named types so that a full expansion is exponential in the manifest's size. A digest computed per type, and memoized per named type, costs linear time and gives the same value as hashing the full expansion would:
    - `digest(type)` is SHA-256 of a tag byte and the digests or bytes of its parts: `string`, `number`, `boolean`, `null`, `any` (tag only); `list` (element digest); `optional` (inner digest); `record` (for each field in code-point order of name: the name as length-prefixed UTF-8, a required byte, the type digest). A named reference's digest is its definition's.
    - `digest(component)` covers props (name, type digest, required), events (name, payload digest or a none byte), commands (name, then each parameter's type digest in order, without its name) and scope (name, type digest), each map in code-point order of name.
    - The fingerprint is SHA-256 over a domain string, `mesh-model-v1`, then each component's name and digest in code-point order. It is written `sha256:` and 64 lowercase hexadecimal digits.
    - Excluded, as D1 requires: formatting, key order, `$schema`, `version`, the names of named types, unused named types, parameter names.
17. **SHA-256 comes from the `sha2` crate** (RustCrypto, `default-features = false`), added by Pass 1. A hand-written SHA-256 was considered and rejected: it's a correctness risk with no benefit, and `sha2` builds for `wasm32-unknown-unknown` with no imports. Pass 1 measures the module-size cost against v0.4's budget.
18. **The manual gives the byte layout exactly,** with a worked example: a two-component manifest, the digest of each step, and the final fingerprint. Pass 1's first test reproduces it.

**Programs (P0.4, D7)**

19. **The assembly rules are copied from D7 and numbered 1–7,** with D3's program-validation steps beside them (rule 3 is steps 2 and 3; the others are step 4), the binding soundness rule written with `is_assignable` (§9.3), and one example per rule.
20. **Assembly diagnostics are ordered** by the template's component in code-point order, then by span start, then by code. A diagnostic with no template (a missing root) comes first. Template-level diagnostics (a malformed template, which may have no readable component) are ordered by the template's position in the input.
21. **A program has no document,** and the manual says so: a host passes a root and a list of templates, and nothing else.

**Render tree, intents and identities (P0.5, D4)**

22. **`render-v1`** (recommended):

    ```json
    {
      "format": "mesh-render",
      "version": 1,
      "root": {
        "type": "node", "key": "k…", "component": "avatar",
        "props": { "src": "…", "alt": "Ada" },
        "events": { "click": "h…" },
        "children": [ { "type": "text", "key": "k…", "text": "Ada" } ]
      }
    }
    ```

    `props` is an object from prop name to value; an absent prop has no member (D4). `events` is an object from event name to handler identifier. Nothing else appears (I13); the schema sets `additionalProperties: false` everywhere below the root, so a renderer can rely on the shape, and says the additive-only promise lets a later version add properties.
23. **Program identity** is SHA-256 over `mesh-program-v1`, the root's name, and each template's canonical digest in code-point order of component. A template's canonical digest is SHA-256 over its canonical re-serialization (keys in a fixed order, numbers in shortest form, no whitespace), **excluding `compiler`**, so a recompile by a different compiler version that yields the same template gives the same program. It is never shown to a renderer.
24. **Keys** are `k` followed by 22 base64url characters: the first 128 bits of SHA-256 over `mesh-key-v1` and the structural path (for each step, the child position and the component, composites included). They reveal nothing recoverable (D4). Uniqueness is a property of the path, and the runtime checks it for each tree it builds, treating a collision as an internal error with its own code: at 128 bits it never happens, and the check makes "unique" hold rather than hold with high probability.
25. **Handler identifiers** are `h`, 11 base64url characters of the program identity's first 64 bits, `.`, and 22 of the first 128 bits of SHA-256 over `mesh-handler-v1`, the program identity, the node's key and the event name. The prefix lets dispatch tell "another program" (`runtime-handler-other-program`) from "no handler here" (`runtime-unknown-handler`), which the Definition of Done tests separately. Neither part reveals a command, its arguments, or anything they can be recovered from (D4).
26. **The command intent** (recommended):

    ```json
    {
      "command": { "component": "user-card", "name": "selectUser" },
      "arguments": [ { "value": { "name": "Ada", "active": true } }, { "absent": true } ]
    }
    ```

    One entry per parameter, in order: `{ "value": v }`, or `{ "absent": true }` where the parameter's type is optional. `{ "value": null }` is `null`. The intent is specified in `docs/manual/runtime.md`, and has its own schema definition inside `render-v1.schema.json` (`$defs/intent`), under the same promise.

**Diagnostics (P0.6, D3)**

27. **Three families, listed exactly** (recommended names; P0.7's review may rename):
    - **Check** (in `DiagnosticCode`, Pass 1): `content-not-text`, `number-literal-out-of-range`.
    - **Assembly** (rule 3 and step 2/3 of program validation, then rules 1, 2, 4–7): `assembly-malformed-template`, `assembly-unsupported-format-version`, `assembly-fingerprint-mismatch`, `assembly-duplicate-template`, `assembly-missing-root`, `assembly-unbound-scope-name`, `assembly-unsound-binding`, `assembly-cycle`, `assembly-composite-event`, `assembly-composite-children`.
    - **Runtime:** input: `runtime-missing-value`, `runtime-value-mismatch`, `runtime-unknown-field`, `runtime-absent-element`, `runtime-number-out-of-range`, `runtime-non-finite-input`, `runtime-unpaired-surrogate`, `runtime-unsupported-value`, `runtime-unexpected-payload`, `runtime-handler-other-program`, `runtime-unknown-handler`; evaluation: `runtime-operand-mismatch`, `runtime-not-a-record`, `runtime-missing-member`, `runtime-content-not-text`, `runtime-prop-mismatch`, `runtime-argument-mismatch`, `runtime-non-finite-output`, `runtime-absent-element-output`; internal: `runtime-key-collision`.
    - Program validation's step 1 reports the existing `manifest-*` codes.
28. **The runtime diagnostics document** mirrors the diagnostics document (`version`, `diagnostics`), with `severity` always `"error"` (D3: no warnings) and a `location` in one of four forms: `{ "kind": "model", "span" }` (a manifest diagnostic, with the diagnostics document's position form), `{ "kind": "template", "index", "component"? }`, `{ "kind": "source", "component", "span" }` (a template's span, in template-v1's span form), `{ "kind": "input", "root": "snapshot" | "payload" | "handler", "path": [...] }`, where a path segment is a string (a scope name or field) or an integer (a list index). The compiler's program check prints the same document (D7: "the same diagnostics, codes and locations").
29. **Diagnostic identity is code and location** (D3). The manual says, for each code, which location form it has and one example; message wording is not part of the contract.
30. **Order within a phase** is written once, in `docs/manual/runtime.md`: assembly by Decision 20; input by path (D3: segments in turn, names by code point, indices numerically, a path before its extensions; snapshot before payload for dispatch); evaluation, exactly one.
