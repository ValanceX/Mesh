# MESH v0.3 Pass 2: Hover and Go-to-Definition, from Canonical State — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Answer `textDocument/hover` and `textDocument/definition` for `.mprx` documents from the canonical compile's own resolutions and types (outline, "Pass 2 — Hover and go-to-definition, from canonical state"). This pass:
- makes the canonical compile **keep its analysis** (finding B1): `CompileResult` gains `analysis`, and the server stores it with each snapshot's canonical state;
- makes a request **wait for its snapshot** instead of answering from nothing (finding B2): a request about a document whose current snapshot isn't compiled yet is held until it is, and answered `ContentModified` if a newer snapshot replaces it first;
- serves **hover**: the type of the expression under the cursor, and the declaration a name resolves to;
- serves **go-to-definition**: from a tag, prop, event, command or scope name to its key in the manifest, through D5's spans;
- proves on every fixture that what it answers is exactly what `mesh_analysis::Analysis` says.

**It does not** answer on files with a syntax error (they return nothing until Pass 3), resolve closing tag names or member names (findings B8 and B9), or add completion (Pass 4).

**Architecture:**
- **`mesh-compiler`**: `CompileResult` gains `pub analysis: Option<mesh_analysis::Analysis>` and becomes `#[non_exhaustive]`. `compile_with` stores the analysis it already computes instead of dropping it. Nothing else in the compiler changes.
- **`mesh-lsp`**:
  - First, a pure move: `server.rs` (951 lines) splits into `documents.rs` and `manifest.rs`, the modules the Pass 1 plan named but the implementation folded into `server.rs` (finding B10).
  - `worker.rs` returns the whole `CompileResult` in an `Arc`, and the loop keeps it in `Compiled`, with the template it was checked as.
  - A new `requests.rs` holds the requests waiting for a snapshot (Decision 4).
  - A new `navigate.rs` answers hover and definition from a `Compiled` and the manifest snapshot. It reads `Analysis`'s offset queries, `Manifest::span_of` and `Manifest`'s declarations; it formats types only through `Ty`'s `Display`. It decides nothing about what a name means (I1).
- Tasks **P2.1**–**P2.7**, in order. Each leaves a working server.

**Tech Stack:** Rust 1.98.1, MSRV 1.91. `mesh-lsp` gains `mesh-analysis` as a dependency (for `Analysis`, `Target`, `Ty`); no crate from outside the workspace is added, so `Cargo.lock` changes only by that edge. `lsp-types` 0.97 has `Hover`, `HoverContents`, `MarkupContent`, `GotoDefinitionResponse` and `Location`. `lsp-server` 0.10's `ErrorCode` has `ContentModified` (-32801) and `RequestCanceled` (-32800).

**Spec:** `docs/superpowers/specs/2026-09-24-mesh-v0.3-outline.md`: invariants I1, I3, I4, I5; D5, D7, D10; findings B1, B2, B3, B8, B9, B10; the Definition of Done's "Navigation works on the examples" (hover and definition halves).

**Depends on:** Passes 0 and 1 (`47950dd`). Pass 0's `resolution_at`/`typed_at` and `Manifest::span_of` are this pass's inputs.

## Global Constraints

- **I1: no semantics in `mesh-lsp`.** Hover and definition read only `CompileResult::analysis` (its `resolution_at` and `typed_at`), `Manifest::span_of`, and the manifest's declarations. `mesh-lsp` still calls nothing below `mesh_compiler::compile`/`compile_with` and `mesh_manifest::load`. It never calls `mesh_analysis::analyze` itself.
- **I3 is untouched.** Published diagnostics don't change. The Pass 1 agreement test passes unedited.
- **I4:** every position in a hover or definition response goes through the source map: the document's for a hover range, the manifest snapshot's for a definition. The Pass 1 grep stays empty.
- **I5:** the component a `Scope` or `Command` resolution belongs to is the component the snapshot was compiled as, from its stored template; never from a file name.
- **Canonical state only.** A snapshot with no IR (a syntax error) or no model answers hover and definition with `null`. Pass 3 fills the first case; nothing fills the second.
- **The CLI's behaviour doesn't change.** `crates/mesh-cli/src` may change only if `CompileResult`'s new field forces it (it doesn't today: the CLI reads `diagnostics` and `ir` by name).
- **Never panic on input** (D7): unchanged from Pass 1, including the crate-level `unwrap_used`/`expect_used` denial.
- **Changelog, authorship, don't push,** as in Pass 0.
- **Verification gate for every task:** Pass 0's four commands, plus `cargo +1.91.0 check --locked --workspace --all-targets` for P2.2 (which changes `Cargo.lock`).

## Decisions this plan makes

**The canonical compile keeps its analysis (B1)**

1. **`CompileResult` gains `pub analysis: Option<mesh_analysis::Analysis>`**: `Some` exactly when `compile_with` had a template and the file had IR, which is exactly when it ran analysis. `compile` always gives `None`. The analysis diagnostics are still derived from it, in the same order, so `diagnostics` doesn't change.
2. **`CompileResult` becomes `#[non_exhaustive]`** in the same change. Adding a field already breaks code that builds a `CompileResult` or destructures it exhaustively; marking it now means the next field won't. The CHANGELOG records both under `### Changed` as breaking for the Rust API. `mesh-compiler` is pre-1.0, so a minor version may do this.
3. **Rejected: the server calling `mesh_analysis::analyze` on the IR itself.** It would give the same answer today, but it is a second call path that I1 exists to rule out, and it runs analysis twice per keystroke. The outline's own definition of canonical state is "exactly what `compile_with` returns … its IR and analysis"; after this pass, that is literally true.

**Requests wait for their snapshot (B2)**

4. **The readiness rule.** A request about document *D* is answered from *D*'s snapshot that is current when the request arrives:
   - If *D* isn't open, the answer is `null` at once.
   - If that snapshot is compiled (its `Compiled::identity` is the current identity and no debounce is pending), the answer is computed at once.
   - Otherwise the request is **held**. If *D* has a debounce pending, it is cut short: *D* is compiled now. When the result for that identity arrives, every request held on it is answered, in arrival order.
   - If the snapshot is replaced first (a `didChange`, a `didClose`, a manifest or configuration change), every request held on it is answered with `ContentModified` (-32801), as LSP 3.17 prescribes for a result the server knows is invalid.
   - `$/cancelRequest` for a held request answers it with `RequestCanceled` (-32800).
   - If the compile of that snapshot panicked, held requests get `null` (D7's "empty result for a malformed document").
   - `shutdown` first answers every held request with `null`.

   This is the only way hover works right after typing, and completion (Pass 4) always comes right after typing. The loop still never blocks: holding is bookkeeping.
5. **`codeAction` keeps its Pass 1 behaviour** (an empty list while a newer version is pending, `no_actions_while_a_newer_version_is_pending`). Clients re-ask for code actions on every cursor move, so an empty answer costs nothing, and changing a tested contract isn't this pass's job. Hover and definition use Decision 4.

**Hover**

6. **Capabilities:** `hoverProvider: true`, `definitionProvider: true`.
7. **What is hovered.** At byte offset *o* (the request position through the source map, clamped):
   - *r* = `analysis.resolution_at(o)`, *t* = `analysis.typed_at(o)`.
   - If *r* exists and *t* doesn't, or *r*'s span is no longer than *t*'s: a **declaration hover** for *r*, over *r*'s span.
   - Otherwise, if *t* exists: a **type hover** for *t*, over *t*'s span.
   - Otherwise `null`.

   So `compact` (a reference, where *r* and *t* share a span) is a declaration hover showing its type; the `n` of `user.name` is a type hover (`string`), because members don't resolve; and the `u` of it is a declaration hover for the scope name `user`.
8. **Hover text.** One fenced block, then at most one sentence. Types print with `Ty`'s `Display`, converting manifest types with `Ty::from`, which is the notation the docs and diagnostics already use. A `?` after a *name* means "not required", as in `Ty`'s record notation.

   | Hovered | Block | Sentence |
   |---|---|---|
   | `Component(c)` | `component avatar {` then one line per prop (`alt: string`, `size?: string`), then one per event (`on.click: any`, or `on.close` with no payload), then `}` | — |
   | `Prop { c, p }` | `alt: string` | "Required prop of `avatar`." or "Optional prop of `avatar`." |
   | `Event { c, e }` | `on.click: any`, or `on.close` | "Event of `button`." (or "…, with no payload.") |
   | `Scope(n)` | `user: User` | "In the scope of `users-page`." |
   | `Command(n)` | `selectUser(user: User)` | "Command of `users-page`." |
   | Type only | `string` | — |

   When the shown type is a named type, or an optional or list of one, a second line in the block gives its definition: `type User = { active: boolean, avatar?: string, name: string }`. Only the outermost named type is expanded, once.
9. **Markup.** Markdown (`MarkupKind::Markdown`, with a plain ```` ``` ```` fence) when the client's `textDocument.hover.contentFormat` lists `markdown`; otherwise plain text, the same lines without the fence.

**Definition**

10. **From a resolution to a declaration:**

    | `Target` | `Declaration` |
    |---|---|
    | `Component(c)` | `Component(c)` |
    | `Prop { c, p }` | `Prop { component: c, prop: p }` |
    | `Event { c, e }` | `Event { component: c, event: e }` |
    | `Scope(n)` | `Scope { component: <compiled as>, name: n }` |
    | `Command(n)` | `Command { component: <compiled as>, command: n }` |

    The answer is one `Location`: the manifest snapshot's URI, and `span_of`'s span converted through the manifest text's source map in the session's column unit. No resolution at *o*, or a declaration with no span (which a valid manifest can't have), is `null`.
11. **The manifest snapshot is the compiled one.** `Compiled` keeps the `Arc` of the manifest snapshot its compile used. Because Decision 4 answers only from a current snapshot, that is also the current manifest snapshot; keeping the `Arc` makes it impossible to mix the two by construction.
12. **Not in this pass:** closing tag names (the IR keeps no span for them, B8), member names to record fields (no `Target` for them, B9), type definitions (`textDocument/typeDefinition`), and definitions from inside the manifest. Each gives `null`. The manual lists them as limitations.

**Code layout (B10)**

13. **P2.1 is a pure move.** `Document`, `Compiled`, the document handlers and `compile`/`finish` move to `documents.rs`; `ManifestSnapshot`, `ManifestState`, `reload_manifest`, `publish_manifest` and `model_for` move to `manifest.rs`, as `impl Server` blocks in those modules. No logic changes; the gate proves it. The Pass 1 plan's "As built" gains an item recording that the split was deferred to here.

**Testing**

14. **The harness** (`mesh_lsp::testing::Client`) gains `send(method, params) -> RequestId` and `response(id, within) -> Response`, so a test can send a request, change the document, and then read the held request's answer. `request` stays as `send` then `response`. It also gains `hover(uri, position)` and `definition(uri, position)` helpers that return the decoded result.

## Review Focus

1. **Hover and definition agree with analysis** (`navigation_agrees_with_analysis_in_utf16` and `…_in_utf8`, in `crates/mesh-lsp/tests/navigation.rs`). For every `.mprx` file in `examples/fixtures/check/` and the two example templates, configured as the corpus test configures them, at **every byte offset** that starts a character:
