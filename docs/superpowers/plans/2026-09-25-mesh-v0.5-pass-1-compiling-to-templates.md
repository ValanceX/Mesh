# MESH v0.5 Pass 1: Compiling to the Template Format Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A template that checks clean compiles to `template-v1` (outline, "Pass 1"). This pass:
- adds **`crates/mesh-template`**: the template's Rust types, reading and writing `template-v1`, its canonical digest, and the **model fingerprint**, the one implementation the compiler and the runtime share (D1);
- adds the **two check-time diagnostics**, `content-not-text` and `number-literal-out-of-range` (D8);
- adds **compiling** to `mesh_compiler` (check, then emit), **`mesh compile`**, and **`compile()`** in `@valancex/mesh-compiler` (D2);
- proves the template, fingerprint and CLI–JS agreement evidence of the Definition of Done.

**Architecture:**
- **`mesh-template`** depends on `mesh-manifest` (for the fingerprint), `serde`, `serde_json` and `sha2`, and on nothing that parses MPRX, so Pass 2's runtime can depend on it without Tree-sitter. It owns: the types (`Template`, `Element`, `Prop`, `Handler`, `Child`, `Expression`, `Span`), `from_json` / `to_json`, structural validation (everything `template-v1.schema.json` says, and the structural rules of Pass 0's Decision 11), `canonical_digest`, and `fingerprint(&Manifest)`.
- **`mesh_compiler::check`** gains a compile phase beside `source`: it runs exactly `source`'s check and, only when that has no errors, emits the template from the IR. The emitter is a pure function of the IR, the model and the source (for UTF-16 offsets through `SourceMap`, I4).
- **The two new codes** come from the stages that already know what they need: `number-literal-out-of-range` from lowering (`mesh-semantic`), since it's a rule of the language with or without a model; `content-not-text` from analysis, since it needs a content expression's type.
- **`mesh-wasm`** gains a compile export; the wrapper gains `compile()`.
- Tasks **P1.1**–**P1.6**, in order. P1.1 is what Pass 2 needs, and it merges first, so Pass 2 can start (outline, "Sequencing").

**Tech Stack:** Rust on the pinned toolchain (MSRV 1.91). One new dependency, `sha2` (Pass 0 Decision 17), and `serde_json`'s `float_roundtrip` feature (Pass 0 Decision 14). TypeScript and `node:test` in `packages/`, as in v0.4.

**Spec:** the outline's D1, D2, D8 (literals, the two check-time diagnostics), I9, I12; Pass 0's `docs/manual/templates.md`, `schemas/template-v1.schema.json` and §9.7. Definition of Done: "Templates" and "Fingerprints and versions" (the compiler's half; the runtime's refusals are Pass 2's).

**Prerequisite:** Pass 0 is merged and reviewed. Where this plan and Pass 0's documents disagree, the documents win, and the difference goes into "As built".

**Verification evidence:** checked at `33648f3`: `check::source` and `Model::load` (`crates/mesh-compiler/src/check.rs`); `Model` keeps the `Manifest` and component privately; `CompileResult` carries `ir` and `analysis`; `SourceMap::utf16_offset` exists; `lower_child` drops whitespace-only text and `dedupe_last_wins` keeps the last attribute; `mesh-wasm`'s `respond` and its exports; the compiler package's `check()` and `engine.ts`; `fixtures.rs`'s corpus; `diagnostics_reference.rs`. Rust's `str::parse::<f64>` is correctly rounded (roundTiesToEven) and returns `inf` for an overflowing decimal, which is exactly what `number-literal-out-of-range` needs. The API sketches below are designs, not verified code. Write each failing test first, see it fail, and treat any difference from what a step predicts as something to investigate.

## As built: departures from this plan

Recorded as the pass goes.

1. **P1.1: a template's canonical digest moved to Pass 2.** The approved manual writes its numbers by §9.7.7.1, whose one implementation is the runtime's exact digit generator (Pass 2; I11). Implementing the digest here would need a second number-to-text implementation, or the generator a pass early. Pass 2 computes it beside the generator, in `mesh-runtime`'s program identity, and its plan now says so. Nothing in Pass 1 uses the digest.
2. **P1.1: the reader enforces two rules beyond the schema:** no repeated prop, event binding or record field name, and no `-0` literal. Both are things the compiler never writes, and the runtime would otherwise have to decide which duplicate wins. `docs/manual/templates.md` now lists them as part of being well-formed.
3. **P1.1: a document of the wrong shape reports one problem,** the first `serde` finds, since nothing after a shape error can be read. The structural checks after it (names, `$event`, duplicates, `-0`) report every problem, each at a JSON Pointer.
4. **P1.1: an integral literal is written as a JSON integer** (`2`, not `2.0`) when its integer is exact in binary64. It reads back as the same value either way.
5. **P1.1: Pass 0's template-schema tests stay in `crates/mesh-compiler/tests/specifications.rs`** rather than moving to `mesh-template`. They test the manual as a whole, and Pass 4 decides where they finally live. `mesh-template`'s own tests validate what `to_json` writes against the schema.

## Global Constraints

- **Check output doesn't change** for any source that has neither new diagnostic: every fixture `.stderr`, every JSON test and every LSP test passes unedited. A corpus source that newly fails would be a finding to stop on.
- **I12: no template from a source with errors.** The only path to a `Template` from source is the compile phase, and it returns one only when `has_errors` is false. `mesh_template::Template` has no public constructor from IR.
- **I9 extended:** compiling the same inputs with the same compiler twice gives byte-identical templates.
- **The IR and analysis APIs change only additively:** one new `Fact` variant, and no change to `mesh_semantic::Element`.
- **`mesh-lsp` gains the two diagnostics for free** (it calls `compile_with`), and nothing else. Its tests pass unedited.
- **Size:** the compiler module stays within v0.4's 300,000-byte gzipped budget (`size.test.mjs`); the pass records the new size.
- **Changelog, commit authorship, pushing:** as in v0.4. Ask the user before the first push.
- **Verification gate for every task:** v0.4's Rust gate, the MSRV check (`cargo +1.91.0 check --locked --workspace --all-targets`), and, from P1.5, v0.4's package gate (`npm ci`, `build:wasm`, `build`, `typecheck`, `npm test -w @valancex/mesh-compiler`).

## Decisions this plan makes

**`mesh-template` (P1.1)**

1. **The types mirror `template-v1` one to one,** with `serde` derives and `#[serde(deny_unknown_fields)]` nowhere: the additive-only promise means a v1 reader must accept properties a later v1 adds. Structural validation is a separate function, not a side effect of deserializing, so it can report every problem with a location:

   ```rust
   pub struct Template { pub component: String, pub fingerprint: Fingerprint, pub compiler: String, pub root: Element }

   /// Reads a template document. A document that isn't JSON, isn't
   /// `mesh-template`, or has an unsupported version is refused with the
   /// reason; a structurally invalid one is refused with every problem.
   pub fn from_json(text: &str) -> Result<Template, Refusal>;
   pub fn to_json(template: &Template) -> String;          // canonical: fixed key order, no whitespace
   pub fn canonical_digest(template: &Template) -> Digest;  // over to_json, without `compiler`
   pub fn fingerprint(manifest: &mesh_manifest::Manifest) -> Fingerprint;

   pub enum Refusal { Malformed(Vec<Problem>), UnsupportedVersion(u64) }
   ```

   `Refusal` maps onto `assembly-malformed-template` and `assembly-unsupported-format-version` in Pass 2; this crate has no diagnostic codes of its own.
2. **Numbers** are `f64` in the types and read with `float_roundtrip`. Enabling the feature in the workspace changes `mesh-manifest`'s number parsing too, which only makes it exact; `manifest-*` tests confirm nothing changes.
3. **The fingerprint is Pass 0's Decision 16,** memoized per named type. `Fingerprint` and `Digest` are newtypes over `[u8; 32]` that display as `sha256:` and hex, and parse from it.

**The check-time diagnostics (P1.2)**

4. **`number-literal-out-of-range`** is reported by `mesh_semantic::lower` for each `Literal::Number` whose text parses to an infinity, at the literal's span, as an error. The IR keeps the text (a later stage converts), and lowering still produces IR, as it does for every lowering diagnostic.
5. **`content-not-text`** is a new `Fact::ContentNotText { ty, span }`, reported by analysis for an interpolation in content whose type, after expanding named references and stripping one optional, is a list or a record, `list<nothing>` included. `any` and `any?` are allowed (their failures are the runtime's, D8). An interpolation with no type (an error inside it) gets no second diagnostic, as §9.4's "errors don't cascade" requires. `mesh-compiler`'s diagnostic layer gives it a message and no suggestion.
6. Both codes join `DiagnosticCode::ALL`, move from Pass 0's placeholder into `docs/manual/diagnostics.md` with fixtures (`examples/fixtures/check/fail/content-not-text.mprx`, `number-literal-out-of-range.mprx`), and `diagnostics_reference.rs` passes as it is.

**Compiling (P1.3)**

7. **`check::template`,** beside `check::source`:

   ```rust
   /// Checks `source` as the template of `model`'s component, and, only if
   /// the check has no errors, compiles it. Warnings don't stop it.
   pub fn template(source: &str, model: &Model) -> Compiled;

   #[non_exhaustive]
   pub struct Compiled { pub diagnostics: Vec<Diagnostic>, pub template: Option<mesh_template::Template> }
   ```

   `diagnostics` is exactly what `check::source(source, Some(model))` returns (a test pins it). The model is required: a template needs a component and a fingerprint.
8. **Emitting is a straight walk** of the IR: element → component and props (IR order is already §3's), event bindings → handlers (a clean check guarantees each handler is a command invocation), children → text, expression or element, operators → Pass 0's names, number text → `f64` by `str::parse`, spans → byte and UTF-16 offsets through one `SourceMap`. Names need no lookup: a clean check means every name is the declaration it resolved to (Pass 0 Decision 13). A debug assertion checks each name against `Analysis::resolutions`, and `emit.rs`'s tests run with it.
9. **The compiler version** written is `env!("CARGO_PKG_VERSION")` of `mesh-compiler`.

**`mesh compile` (P1.4)**

10. **`mesh compile <FILE> --model <MANIFEST> [--component <NAME>] [--output <PATH>] [--format human|json]`,** with `check`'s model and component rules (the stem default stays in the CLI). With no errors it writes the template to `--output`, or to stdout without it, and exits 0; with errors it prints the diagnostics exactly as `check` does and writes no template, and exits 1. `--format json` requires `--output`, since stdout then carries the diagnostics document; clap enforces it.
11. **Warnings print as `check` prints them** (stderr in human form), and don't stop the template.

**The JavaScript API (P1.5)**

12. **`mesh-wasm` gains `mesh_compile`,** with `mesh_check`'s inputs (the model required) and one result document: `{"diagnostics": <diagnostics document>, "template": <template-v1> | null}`, rendered in Rust. The wrapper parses it once; it adds no rule (v0.4's I6).
13. **`compile(input: CompileInput): Promise<CompileResult>`,** where `CompileInput` is `CheckInput` with `model` required and `CompileResult` is `{ diagnostics: DiagnosticsDocument; template?: Template }`. `Template` is exported as a TypeScript type mirroring the schema (`template.ts`), documented as data to store and pass on, not to interpret. Errors, the version check and the failure contract are `check()`'s.

## Review Focus

1. **No template from an erroneous source,** anywhere: the fixtures' fail corpus and the fuzzer's mutants never produce one, and `Template` can't be built from IR outside `check::template`.
2. **Fingerprints:** the worked example from `docs/manual/templates.md` reproduces; every "doesn't count" case gives equal fingerprints; every counted declaration changes it.
3. **Templates validate against `template-v1`** for every clean corpus source, and read back equal (`from_json(to_json(t)) == t`).
4. **The CLI and the JS API agree** on templates and diagnostics for every corpus run, byte for byte on the template.
5. **Literals:** `1`, `1.0` and `1.00` compile to the same value, `1.5` and `1.50` too, and a tie rounds to even.
6. **The two new codes** fire exactly where §9.7 says, and nowhere in the existing corpus.
