# MESH v0.1 Pass 4b: Event Bindings & Structural Validation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship event bindings (`on.click={handler}`) end-to-end (grammar → AST → semantic IR) and add the three Pass 4b structural-validation rules — duplicate-attribute warnings, duplicate-event-binding warnings, and open/close tag-name-mismatch errors — to `mesh-semantic::lower`.

**Architecture:** Event bindings get their own `event_binding` grammar rule, lexically disambiguated from a plain attribute literally named `on` via a `token(seq('on', '.'))` atomic prefix token (no `prec`/`conflicts` needed). `mesh-syntax::Element` gains an `event_bindings: Vec<EventBinding>` field alongside the existing `attributes` field — parallel, independently-ordered namespaces, never merged. `mesh-parser` lowers the new CST node the same way it lowers `attribute`. `mesh-semantic::lower` is restructured so every lowering function returns `(T, Vec<Diagnostic>)` instead of just `T`/`Option<T>`, threading diagnostics up from children in source order; a new `dedupe_last_wins` helper implements last-occurrence-wins deduplication for both `attributes` and `event_bindings` independently, and a new tag-name-mismatch check compares `Element.closing_name` against `Element.name`. All diagnostics stay non-fatal — `ir: Some(..)` is always produced alongside them.

**Tech Stack:** Rust (workspace: `mesh-syntax`, `mesh-parser`, `mesh-semantic`, `mesh-compiler`), tree-sitter grammar (`grammar/tree-sitter-mprx`, JS grammar DSL + generated C parser), `tree-sitter-cli` for `generate`/`parse`/`test`, `cargo test` per-crate and workspace-wide.

**Spec:** `docs/superpowers/specs/2026-09-23-mesh-v0.1-pass-4-design.md`

## Global Constraints

- **Source order is authoritative within every ordered collection.** Attributes, event bindings, children, and diagnostics each preserve the relevant source order for that collection. Attributes and event bindings are independent namespaces and therefore do not share a cross-namespace ordering contract — there is no guarantee, and no requirement, that their relative interleaving in source is preserved across the two separate `attributes`/`event_bindings` collections. Diagnostics preserve their own explicitly defined semantic traversal order (see the "Diagnostic ordering" rule below), not raw source position. `HashMap`/`HashSet` may be used for O(1) lookup only — hash-iteration order must never determine IR or diagnostic ordering. Do not introduce a merged attribute/event-binding collection merely to preserve source interleaving; they stay two separate `Vec`s in both the AST and the IR.
- **Duplicate-survivor ordering (explicit invariant).** After deduplication, surviving entries preserve the source order of their **winning occurrences** — not the order in which names were first encountered, not a grouped-by-name order, and never `HashMap` iteration order. `dedupe_last_wins` must keep satisfying this even if its internal implementation changes; Task 2's ordering test exists specifically to make this observable (see below), since first-encountered order and winning-occurrence order can disagree once 3+ distinct names are involved.
- **Diagnostic ordering (global invariant).** `LowerResult.diagnostics` (and any nested `Vec<Diagnostic>` threaded up during lowering) is ordered, per element, as: (1) that element's own duplicate-attribute diagnostics, in shadowed-occurrence source order; (2) that element's own duplicate-event-binding diagnostics, in shadowed-occurrence source order; (3) that element's own tag-name-mismatch diagnostic, if any (at most one per element); (4) then, for each child in `children: Vec<Child>` in their own source order, that child's diagnostics recursively, computed by the same rule. This order falls directly out of `lower_element`'s traversal — **no sorting pass ever runs after lowering**, and no step in any task may introduce one.
- **Diagnostics are data, not presentation.** `mesh_syntax::Diagnostic` holds only `severity`, `message`, `span` — no renderer/CLI/LSP-specific fields.
- **Severity does not determine recoverability (explicit invariant).** Pass 4b's three structural diagnostics are all non-fatal — `ir: Some(..)` is always produced alongside them, regardless of severity:

  | Condition | Severity | `ir` |
  |---|---|---|
  | duplicate attribute | `Warning` | `Some` |
  | duplicate event binding | `Warning` | `Some` |
  | mismatched closing tag | `Error` | `Some` |

  No later task may make any Pass 4b diagnostic force `ir: None`. `mesh_compiler::compile`'s signature and `CompileResult`'s fields stay exactly as they are today.
- **Grammar defines syntax; semantic analysis defines meaning.** Duplicate-attribute, duplicate-event-binding, and tag-name-matching rules live in `mesh-semantic::lower`, never in `grammar.js`.
- **Semantic namespaces are explicit.** `attributes` and `event_bindings` are deduplicated independently of one another — an attribute named `click` and an `on.click` event binding never collide.
- **`EventBinding.name` excludes the `on.` prefix (explicit invariant).** `on.click={handler}` produces `EventBinding.name == "click"`, never `"on.click"` — the prefix is surface syntax consumed by the grammar's `token(seq('on', '.'))`, not semantic data. Event names are **not** validated against any known-event registry in Pass 4b: `on.click`, `on.foo`, and `on.whatever` are all syntactically and semantically valid event bindings at this stage. The only Pass 4b semantic rule for event bindings is duplicate detection; event existence, handler signature/type checking, and framework-specific event semantics are future work and must not be added by any task in this plan.
- **Tag-mismatch diagnostic span.** Pass 4b reports a tag-name mismatch against the enclosing `Element.span` (the *opening* element's span) — the current AST exposes no dedicated closing-tag span, and adding one is out of scope for Pass 4b. This is a deliberate scope boundary, not an oversight; a future diagnostic-span refinement may introduce a closing-tag-specific span, but not here.
- **Determinism.** No hash-based iteration order may ever affect diagnostics, IR, or emitted output.
- **No preemptive `prec`/`conflicts`.** `token(seq('on', '.'))` is the intended, and sufficient, lexical disambiguation mechanism for event bindings vs. a plain attribute named `on`. Do not add `prec`, `conflicts`, or other precedence machinery unless a fresh `tree-sitter generate` actually reports a conflict. If a conflict does appear, stop and investigate the grammar rather than mechanically adding precedence — the generated parser and a zero-conflict `tree-sitter generate` result remain the authority on whether any such declaration is needed.
- **No recursion-depth guard**, no unified `Vec<ElementModifier>` merging attributes and event bindings, no event-binding semantic validation beyond duplicate detection, no changes to `mesh_compiler::compile`'s signature or `CompileResult`'s fields, no `mesh-cli`/`mesh-lsp` consumption changes — all explicitly out of scope per the spec.
- **Pass 4b scope boundary.** This plan implements exactly: event bindings (grammar/AST/parser/IR) + duplicate-attribute warnings + duplicate-event-binding warnings + open/close tag-name-mismatch errors + the diagnostic-propagation infrastructure those rules require. It does not implement, and no task may introduce: event registries, event-handler type checking, runtime event dispatch, event-modifier syntax beyond `on.<name>={...}`, recursion-depth guards, a unified `ElementModifier` abstraction, grammar-level duplicate detection, grammar-level tag matching, diagnostic sorting, `mesh-cli`/`mesh-lsp` consumption changes, `mesh_compiler::compile` API-shape changes, or unrelated parser/semantic refactors.

#### Step 1: Add the `event_binding` grammar rule and corpus tests

Edit `grammar/tree-sitter-mprx/grammar.js`. Extract `_element_modifier` so both `selfClosingElement` and `containerElement` accept either `attribute` or the new `event_binding`, replacing the current `repeat($.attribute)` in both helper functions:

```js
const selfClosingElement = $ => seq(
  '<',
  field('name', $.tag_name),
  repeat($._element_modifier),
  '/>',
);

const containerElement = $ => seq(
  '<',
  field('name', $.tag_name),
  repeat($._element_modifier),
  '>',
  repeat($.child),
  '</',
  $.tag_name,
  '>',
);
```

Add the `_element_modifier` and `event_binding` rules to the `rules` object, immediately after the existing `attribute` rule:

```js
    attribute: $ => seq(
      field('name', $.identifier),
      '=',
      field('value', choice($.string, $.expression_block)),
    ),

    _element_modifier: $ => choice($.attribute, $.event_binding),

    event_binding: $ => seq(
      token(seq('on', '.')),
      field('name', $.identifier),
      '=',
      field('handler', $.expression_block),
    ),
```

`_element_modifier` is a hidden rule (leading `_`): tree-sitter inlines its children directly into the parent's `children` list, so `attribute` and `event_binding` nodes still appear as direct children of `self_closing_element`/`container_element`, exactly like `attribute` does today. `token(seq('on', '.'))` makes the `on.` prefix one atomic token, lexically distinct from the `identifier` token `on` by longest-match — this needs no `prec`/`conflicts` declaration.

**`token(seq('on', '.'))` is the intended, and sufficient, disambiguation mechanism** — do not add `prec`, `conflicts`, or any other precedence machinery to this rule preemptively. Step 2 below runs `tree-sitter generate` fresh; if and only if it reports a conflict, stop and investigate the grammar (most likely the `token(...)` wrapping was dropped or narrowed) rather than mechanically silencing the conflict with a `prec`/`conflicts` declaration. A zero-conflict `tree-sitter generate` is the authority that no such declaration is needed.

    fn string_attribute(name: &str, value: &str, start: usize, end: usize) -> mesh_syntax::Attribute {
        mesh_syntax::Attribute {
            name: name.to_string(),
            value: mesh_syntax::AttributeValue::String(mesh_syntax::StringLiteral {
                value: value.to_string(),
                span: mesh_syntax::Span { start, end },
            }),
            span: mesh_syntax::Span { start, end },
        }
    }

    // are both first seen before title). Winning-occurrence order is
    // [class, title, id] instead, because id's *winning* occurrence
    // (pos 4) comes after title's only occurrence (pos 3) — this is the
    // case that actually distinguishes the two orderings.
    let ast = mesh_syntax::Element {
        name: "div".to_string(),
        closing_name: None,

            string_attribute("id", "x", 2, 3),
            string_attribute("class", "b", 4, 5),
            string_attribute("title", "y", 6, 7),
            string_attribute("id", "z", 8, 9),

        children: vec![],
        span: mesh_syntax::Span { start: 0, end: 10 },

    let element = result.ir.expect("should lower");

    assert_eq!(element.attributes.len(), 3);
    assert_eq!(element.attributes[0].name, "class");
    match &element.attributes[0].value {

        other => panic!("expected a string attribute value, got {other:?}"),

#### Step 7: Implement `dedupe_last_wins`

In `crates/mesh-semantic/src/lib.rs`, add near the top of the file (after the IR type definitions, before `pub fn lower`):

```rust
fn dedupe_last_wins<'a, T>(
    items: &'a [T],
    name: fn(&T) -> &str,
    span: fn(&T) -> mesh_syntax::Span,
    kind: &str,
) -> (Vec<&'a T>, Vec<mesh_syntax::Diagnostic>) {
    let mut last_index_for_name: std::collections::HashMap<&str, usize> = std::collections::HashMap::new();
    for (index, item) in items.iter().enumerate() {
        last_index_for_name.insert(name(item), index);
    }

    let mut survivors = Vec::new();
    let mut diagnostics = Vec::new();

    for (index, item) in items.iter().enumerate() {
        if last_index_for_name[name(item)] == index {
            survivors.push(item);
        } else {
            diagnostics.push(mesh_syntax::Diagnostic {
                severity: mesh_syntax::Severity::Warning,
                message: format!(
                    "duplicate {kind} {:?}: this occurrence is shadowed by a later one",
                    name(item)
                ),
                span: span(item),
            });
        }
    }

    (survivors, diagnostics)
}
```

Check `mesh_syntax::Diagnostic`'s exact field names in `crates/mesh-syntax/src/lib.rs` before finalizing — adjust `severity`/`message`/`span` field names if they differ.

The `HashMap` is used only to look up, for each forward-pass index, whether it is that name's last occurrence — both `survivors` and `diagnostics` are built by iterating `items` in its own index order, never by iterating the `HashMap`, so ordering stays fully deterministic and source-order-derived.

    LowerResult {
        ir: Some(element),
        diagnostics,
    }
}

fn lower_element(ast: &mesh_syntax::Element) -> (Element, Vec<mesh_syntax::Diagnostic>) {
    let mut diagnostics = Vec::new();

    let (attributes, attribute_diagnostics) = dedupe_last_wins(
        &ast.attributes,
        |a| a.name.as_str(),
        |a| a.span,
        "attribute",
    );
    diagnostics.extend(attribute_diagnostics);

    let (event_bindings, event_binding_diagnostics) = dedupe_last_wins(
        &ast.event_bindings,
        |e| e.name.as_str(),
        |e| e.span,
        "event binding",
    );
    diagnostics.extend(event_binding_diagnostics);

    let mut children = Vec::new();
    for child in &ast.children {
        let (lowered, child_diagnostics) = lower_child(child);
        children.extend(lowered);
        diagnostics.extend(child_diagnostics);
    }

    let element = Element {
        name: ast.name.clone(),
        attributes: attributes.into_iter().map(lower_attribute).collect(),
        event_bindings: event_bindings.into_iter().map(lower_event_binding).collect(),
        children,
    };

    (element, diagnostics)
}

fn lower_child(child: &mesh_syntax::Child) -> (Option<Child>, Vec<mesh_syntax::Diagnostic>) {
    match child {
        mesh_syntax::Child::Text(text) if text.value.trim().is_empty() => (None, Vec::new()),

        mesh_syntax::Child::Expression(expression) => {

        mesh_syntax::Child::Element(element) => {
            let (lowered, diagnostics) = lower_element(element);
            (Some(Child::Element(Box::new(lowered))), diagnostics)
        }
    }

#### Step 5: Add the tag-name-mismatch check to `lower_element`

In `crates/mesh-semantic/src/lib.rs`, extend `lower_element` (the version from Task 2's Step 8) by inserting a new block between the `event_bindings` deduplication and the `children` loop — this ordering matches the spec's diagnostic-ordering rule (own attribute warnings → own event-binding warnings → own tag-mismatch error → recurse into children):

```rust
fn lower_element(ast: &mesh_syntax::Element) -> (Element, Vec<mesh_syntax::Diagnostic>) {
    let mut diagnostics = Vec::new();

    let (attributes, attribute_diagnostics) = dedupe_last_wins(
        &ast.attributes,
        |a| a.name.as_str(),
        |a| a.span,
        "attribute",
    );
    diagnostics.extend(attribute_diagnostics);

    let (event_bindings, event_binding_diagnostics) = dedupe_last_wins(
        &ast.event_bindings,
        |e| e.name.as_str(),
        |e| e.span,
        "event binding",
    );
    diagnostics.extend(event_binding_diagnostics);

    if let Some(closing_name) = &ast.closing_name {
        if closing_name != &ast.name {
            diagnostics.push(mesh_syntax::Diagnostic {
                severity: mesh_syntax::Severity::Error,
                message: format!(
                    "mismatched closing tag: opened with {:?}, closed with {:?}",
                    ast.name, closing_name
                ),
                span: ast.span,
            });
        }
    }

    let mut children = Vec::new();
    for child in &ast.children {
        let (lowered, child_diagnostics) = lower_child(child);
        children.extend(lowered);
        diagnostics.extend(child_diagnostics);
    }

    let element = Element {
        name: ast.name.clone(),
        attributes: attributes.into_iter().map(lower_attribute).collect(),
        event_bindings: event_bindings.into_iter().map(lower_event_binding).collect(),
        children,
    };

    (element, diagnostics)
}
```

The resulting `Element.name` is always the opening tag's name (`ast.name`), never the closing tag's — the mismatch is reported but does not change which name lowering uses.

The diagnostic's `span` is deliberately `ast.span` — the opening element's span, covering the whole `<name ...>...</other>` construct — not a dedicated closing-tag span. This is a Pass 4b scope boundary, not an oversight: `mesh_syntax::Element` doesn't currently expose a separate span for the closing `tag_name` token (the grammar captures it as a bare, unfielded `$.tag_name` — see `containerElement` in `grammar/tree-sitter-mprx/grammar.js`), and adding one is out of scope for this pass per the Global Constraints list of things not to introduce. Editors/LSPs consuming this diagnostic will underline the entire element for a mismatch in Pass 4b; a future pass can narrow it once the AST carries a closing-tag span.
