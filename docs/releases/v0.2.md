# MESH v0.2.0 release notes

*Released 2026-09-24.*

v0.2 makes MESH check what a UI **means**, not just its shape. v0.1 could tell you a file was well-formed MPRX; `<user-card user={usr} />` passed even if nothing named `usr` existed. v0.2 checks a file against a **component manifest** that declares your components and the names each template may use. Every component, prop, event, name and command must be declared, and every value must have the right type. Each mistake is an error with a stable code, at the exact place it happens.

That's what makes MESH safe for UI you didn't write by hand. When a model generates MPRX that invents a prop, misspells a name, or passes a value that might not be there, `mesh check` rejects it before it renders, and `--format json` hands the errors back as data, so the generator can fix them.

The language itself hasn't changed: every v0.1 file means the same thing in v0.2.

## Highlights

- **Component manifests.** A MESH-owned JSON format declares each component's props, events, commands and scope, with structured types. It's versioned, published as a JSON Schema, and validated completely before any file is checked. See the [manifest reference](../manual/manifest.md).

  ```console
  $ mesh check --model examples/components.json examples/users-page.mprx
  no errors
  ```

- **Checking against the model.** With `--model`, `mesh check` resolves every tag, attribute, `on.` binding, reference and command, types every expression, and checks every prop value and command argument against its declaration. Misspelled names get a suggestion:

  ```text
  error[unknown-reference]: unknown reference "usr": it isn't in the template's scope
   --> examples/fixtures/check/fail/unknown-reference.mprx:1:14
    |
  1 | <page title={usr.name} />
    |              ^^^
    = help: did you mean "user"?
  ```

- **A small, strict type system.** Absence (`T?`) is distinct from `null`, and whether a prop must be written is distinct from whether its value may be absent. `any` is an escape hatch for partly typed models, but it never hides absence. Records are exact. Nothing is converted implicitly. One mistake gets one error, never a cascade. See [Checking against a component model](../guides/checking-against-a-component-model.md), and the exact rules in the [language spec](../MPRX-SPEC.md#9-checking-against-a-component-model).
- **JSON diagnostics.** `mesh check --format json` prints every diagnostic as one JSON document, with its code, message, path, span (as bytes and as lines and columns) and suggestions. See the [CLI manual](../manual/mesh-cli.md#json-output).
- **Syntax errors point at the mistake.** v0.1 reported every syntax error at `1:1`. v0.2 reports most of them where the mistake is, reports each one in a file with several, and gives common mistakes their own code and message: a `<` in text, a hyphenated attribute name, an unclosed tag, a trailing comma, a single-brace object, a malformed `on.` binding.
- **Stable diagnostic codes.** Every diagnostic has a kebab-case code, such as `error[type-mismatch]`. A code is never renamed or reused for a different meaning, so programs can match on it. The [diagnostics reference](../manual/diagnostics.md) lists all of them.
- **`mesh --version`**, a pinned toolchain with a declared minimum Rust version (1.91), and fixtures that work on Windows checkouts.

## Upgrading from v0.1

- **Without `--model`, nothing changes.** The same files pass and fail, with the same exit statuses. Diagnostics look a little different: each has a code in its header (`error[mismatched-closing-tag]: ...`), and syntax errors have real locations and more specific messages.
- **To start checking against a model,** write a manifest declaring every component your files use, `page` and `text` included: MESH has no built-in elements. [`examples/components.json`](../../examples/components.json) is a complete example. Each file is the template of the component named like the file; use `--component` to name another.
- **Rust API.** The Semantic IR now carries source spans, which changes several `Expression` and `AttributeValue` variants from tuple to struct form. `Diagnostic` has two new fields, `code` and `suggestions`, and `ParseError` has `code`. `compile_with` and `CompileOptions` check against a manifest, from the new `mesh-manifest` crate; the new `mesh-analysis` crate exposes the analysis as data; and `render_json` builds the JSON document. The [CHANGELOG](../../CHANGELOG.md) lists every change, and the [embedding guide](../guides/embedding-the-compiler.md) shows the new API.

## Known limitations

- **No presence test.** MPRX can't test whether a value that may be absent is there, and has no optional chaining, so such a value can only be passed on to somewhere that accepts absence. If that's too strict, change the manifest's types.
- **No union types.** "A string or `null`" can only be written as `any`.
- **Children aren't checked against components.** A component can't declare what content it accepts yet, so any children are allowed. Expressions inside them are still checked.
- **One file per `mesh check`**, and no `compile` command or IR output.
- **Columns count characters,** not display width, in both output formats.
- **Native Rust only.** The language server (`mesh-lsp`) and the npm packages under `packages/` are still placeholders, and there's no WASM build yet.

## What's next

1. Editor support through `mesh-lsp`, reusing the compiler: diagnostics with codes, hover with types, go-to-definition, and completion from the manifest.
2. A WASM build and the npm packages.
3. NEXUS generating manifests from its component definitions.
