# MESH v0.5.0 release notes

*Released 2026-09-26.*

v0.5 makes MESH render. The compiler turns each checked component into a **template**, and the new **MESH runtime** renders a program of templates against a host's values to a **render tree**, and turns the events a renderer reports into **command intents**. NEXUS's adapter and PORT's renderers can now build against it, in their own repositories.

The runtime is MPRX's one evaluator. It's written in Rust, and `@valancex/mesh-runtime` is that same runtime in WebAssembly, not a second implementation: its JavaScript only encodes values and carries results. Only what the compiler checked runs, and every value a host supplies is checked on every call.

The language's syntax hasn't changed. Two new check errors can reject files v0.4 accepted (see "Upgrading from v0.4").

## Highlights

- **Compiling to templates.** `mesh compile`, and `compile()` in `@valancex/mesh-compiler`, emit a checked component's template (`template-v1`), and only when it has no error. A template is compatible with a runtime by its format version and its model's fingerprint, never by the compiler's version. `mesh check-program` and `checkProgram()` check a program of them. See the [templates manual](../manual/templates.md).
- **The runtime.** `render({ program, model, snapshot })` validates everything, evaluates, and returns a render whose tree holds only primitive components, final values, text, keys and handler identifiers. `dispatch(render, handler, payload)` returns the command intent, evaluated against the render's own snapshot. Errors are diagnostics, never exceptions. In Rust it's the `mesh-runtime` crate; in Node 22 and later and in browsers it's `@valancex/mesh-runtime`, about 185 KB gzipped, with no dependencies. See the [runtime manual](../manual/runtime.md).
- **Composition.** A program is a root and its templates. A component with a template is a composite, expanded in place; any other is a primitive, for the renderer.
- **Evaluation is specified.** [§9.7 of the spec](../MPRX-SPEC.md#97-evaluation) defines MPRX's values, numbers, equality, evaluation order, runtime checks and text, and §9.8 the boundary between the runtime and its host.
- **Two guides,** each with an example a test runs: [Integrating MESH with NEXUS](../guides/integrating-mesh-with-nexus.md), for a host, and [Rendering MESH output](../guides/rendering-mesh-output.md), for a renderer.
- **The slice,** `examples/slice/`: a page that uses a composite `user-card` twice, with its committed render tree, intent and changes, checked natively and in Node.

## Number to text

MPRX's text for a number is MESH's own: the shortest digits that read back, the nearest of those, and the even one on a tie (§9.7.7.1). The runtime computes it with its own exact digit generator, not Rust's float formatting (which fails 4 rows of the table on Rust 1.98.1) and not a library. It's verified two ways:
- **normatively,** by the table [`docs/tables/number-to-text.tsv`](../tables/number-to-text.tsv), computed from the rule alone by its reference generator. The runtime reproduces every row, natively and in WebAssembly;
- **differentially,** against V8's `String(x)`: the WebAssembly build's text for 1,000,000 generated values, compared on V8 12.4.254.21 (Node 22.22.2), and on Node 22 and 24 in CI. There are no differences: `number-text-differences.json`, the reviewed list of intentional ones, is empty.

The comparison is evidence of compatibility, not the definition. A renderer draws MESH's text as it's given, and never formats the number again with its platform's formatting.

## Try it

```console
$ npm install @valancex/mesh-compiler @valancex/mesh-runtime
```

Then follow [Integrating MESH with NEXUS](../guides/integrating-mesh-with-nexus.md), which compiles the slice, renders it, and dispatches a click.

## Upgrading from v0.4

- **Two new check errors** (§9.7): `content-not-text`, for an interpolation in content whose type is a list or a record, which has no text; and `number-literal-out-of-range`, for a number literal too large to be finite. A file with either checked clean in v0.4, and doesn't now. `mesh-lsp` reports both.
- **Rust API:** `SourceMap` moved to `mesh-syntax`, so the runtime needn't depend on the parser. `mesh_compiler::SourceMap` re-exports it, so its path still works. Additions: `check::template` and `check::program` in `mesh_compiler`, and the `mesh-template` and `mesh-runtime` crates.
- **`mesh check` hasn't changed,** and neither has its JSON document.
- **The grammar is versioned with MESH,** at 0.5.0.

## Known limitations

- **Absent list elements can't cross.** A list holding an absent element, from an array literal, can't be rendered or passed as an argument. It fails closed.
- **Fingerprints cover the whole model.** Every template must be recompiled after any change of meaning to the component model, even to an unrelated component.
- **Records are exact.** A host's value may hold only the fields its type declares, so a host shapes its values to the manifest.
- **Composites have no events, children or slots.**
- **MESH ships no NEXUS adapter and no PORT renderer.** Those belong to their repositories.
- From v0.4, still: no language server in the browser, and bundlers aren't handled for you.
- From v0.3, still: configuration lives in each editor, closing tags and record fields have no definition, a diagnostic has one location, manifest edits aren't debounced, and only Neovim's setup is verified.
- From v0.2, still: no presence test for a value that may be absent, no union types, and children aren't checked against components.

2. Composite events, and children and slots for composites.
