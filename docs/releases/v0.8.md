# MESH v0.8.0 release notes

*Prepared 2026-10-04. Not yet released: the tag and the publication are the maintainer's, after review.*

v0.8 lets a host ask a program which events it declares. It adds no MPRX syntax and changes no format: the runtime gains one operation, in Rust, in the WebAssembly module and in `@valancex/mesh-runtime`.

## Highlights

- **Declared events.** `mesh_runtime::declared_events(&program, model)` in Rust, and `declaredEvents({ program: { root, templates }, model })` in `@valancex/mesh-runtime`, return the event bindings the program's templates declare. Each is a `DeclaredEvent`: the **component** whose template declares the binding (the component of the command's intent), the **event**, the **command** it raises, and the binding's **span** in that template's source (UTF-8 bytes and UTF-16 code units). The runtime manual's [declared events](../manual/runtime.md#the-declared-events) section is the contract.
- **A fact about the program, not a render.** An event inside a `mesh-if` alternative the snapshot doesn't choose is declared, and so is an event inside a composite's template. An event inside a `mesh-each` body is declared once, whatever the items: a rendered handler needs the item's values, a declared event doesn't, so it has no handler identifier. Nothing is deduplicated: two bindings that raise the same command are two declared events, with their own spans.
- **The same validation.** The program is validated exactly as `check_program`, render and dispatch validate it, and a program that isn't valid gives that program's diagnostics. The order is fixed: components in order of name, then each template's bindings in document order, whatever order the templates were supplied in.
- **One new export, one new function.** The runtime module exports `mesh_declared_events`, and the package requires it: a 0.8 package refuses a module without it, as it refuses one of another version. `mesh_runtime::declared_events_to_json` writes the result as the array the manual documents; the module returns `{"events": [...]}` or `{"diagnostics": ...}`, as render does.

## Compatibility

- **Additive.** `check_program`, render, dispatch, the compiler, `template-v1`, `render-v1`, the manifest format and model fingerprints are unchanged. A program gets the same render trees, handler identifiers and intents.
- **A component with no template is a primitive,** as it always was, so the commands the manifest declares for it are not declared events.
- **Rust API:** `mesh_runtime` has `DeclaredEvent`, `declared_events` and `declared_events_to_json`.
- **npm:** `@valancex/mesh-runtime` has `declaredEvents()` and the types `DeclaredEvent`, `DeclaredEventsInput` and `DeclaredEventsResult`. Its WebAssembly module grew by about 4.2 KB (about 1.6 KB gzipped, to about 193.7 KB: within the budget of 277,126 bytes gzipped).
- **Ranges.** Before 1.0 a minor version is a new range: a package that depends on `@valancex/mesh-runtime` `^0.7.0` does not receive 0.8. A host that wants one runtime copy needs every package that depends on it to accept 0.8.

## Not decided

Whether a declared event should carry its arguments; how a diagnostic should name the source file of a template, which the program doesn't carry; and whether the compiler package should expose the same operation for build-time tools.
