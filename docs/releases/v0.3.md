# MESH v0.3.0 release notes

*Released 2026-09-24.*

v0.3 brings MESH into the editor. The new `mesh-lsp` language server shows MESH's diagnostics as you type, offers their suggestions as quick fixes, and answers hover, go to definition and completion from your component manifest. The grammar now ships Tree-sitter highlighting queries.

The server is a **client of the compiler**, not a second implementation of it. The diagnostics it shows are exactly the ones `mesh check` reports for the same text, manifest and component: the same codes, messages, locations and suggestions, in the same order. A test compares the two on every fixture, and on every prefix of every fixture as it would be typed. Your editor and your build can't disagree about what a file means.

The language hasn't changed: every v0.2 file means the same thing in v0.3.

## Highlights

- **Diagnostics as you type, identical to `mesh check`.** For `.mprx` documents, and for the manifest itself. A manifest with errors shows them on the manifest, and your templates keep their own syntax errors meanwhile.
- **Quick fixes.** `did you mean "user"?` becomes a one-click replacement.
- **Hover:** the type of any expression, such as `string` for `user.name`, and what a component, prop, event, scope name or command is declared as.
- **Go to definition:** from a tag, prop, event, command or scope name to its key in the manifest.
- **Completion** of tags, props (required ones first), events, commands, scope names and record fields, each offered only where the compiler accepts it, and derived only from the manifest. Every item it offers is, once inserted, accepted by the compiler; a test checks that for every kind.
- **It works while the file is broken,** which it almost always is while you type. After `user.`, after `<avatar `, after a bare `<`, completion still answers, and hover and definition work on the parts that parse. None of this touches the diagnostics: they stay exactly the compiler's.
- **Syntax highlighting** from `grammar/tree-sitter-mprx/queries/highlights.scm`, for any editor that loads Tree-sitter queries. The queries only colour text; nothing in MESH reads them.
- **An editor setup guide,** with a Neovim 0.11 configuration that a script checks in a real, headless Neovim: diagnostics, hover, definition, completion on broken text, highlighting and manifest edits.

## Try it

```console
$ git clone https://github.com/ValanceX/Mesh.git
$ cd Mesh
$ cargo install --path crates/mesh-cli
$ cargo install --path crates/mesh-lsp
$ mesh --version
mesh 0.3.0
```

Then follow the [editor setup guide](../guides/editor-setup.md). The server needs to know which manifest to check against and which component each file is the template of; it never guesses a component from a file's name, because an editor's file names aren't stable. See [configuring `mesh-lsp`](../manual/mesh-lsp.md#configuring).

## Upgrading from v0.2

- **`mesh check` hasn't changed,** except that a file or manifest nested more than 128 levels deep is now an error (`nesting-too-deep`, `manifest-nesting-too-deep`) instead of a crash, or instead of being accepted if it was shallow enough not to crash. These are limits of this implementation, not rules of MPRX or of manifest version 1. No handwritten file comes near them.
- **Rust API: `CompileResult` has a new field, `analysis`, and is `#[non_exhaustive]`.** Code that builds a `CompileResult` or destructures every field must change; code that reads its fields by name doesn't.
- **Rust API, additions:** `mesh_compiler::SourceMap` for positions in characters, UTF-8 or UTF-16; offset queries on `Analysis`; declaration spans in the manifest; and the editor-only `mesh_compiler::editor` module (`recover`, `candidates`). See the [embedding guide](../guides/embedding-the-compiler.md#files-with-syntax-errors-for-editors).
- **The grammar is versioned with MESH,** at 0.3.0.

## Known limitations

- **Configuration lives in each editor.** Every editor, and everyone's editor, names the manifest and each file's component; `mesh check` can't read that configuration. A project file both could read is a question for v0.4.
- **One workspace root,** and paths compare exactly, so on a case-insensitive file system write `components` keys with the case your editor uses.
- **Closing tags and record fields have no definition.** Go to definition works from an opening tag's name, and from `user` in `user.name` but not from `name`, which hover still types.
- **Diagnostics have one location each.** A duplicate object key doesn't point at the occurrence that wins.
- **Manifest edits aren't debounced:** each keystroke in the manifest re-checks every open document. It's fast enough, but a half-typed manifest shows its errors as you type.
- **Disk changes to the manifest** are seen automatically only by clients that let servers watch files. Neovim doesn't on Linux; there, the manifest is reloaded when you open it or change the settings.
- **A lone `\r`** (a classic Mac line ending) isn't a line break to MESH, so positions in such a file disagree with the editor's.
- **Only Neovim is verified.** The guide's Helix configuration is untested, and there's no VS Code or Zed extension yet.
- From v0.2, still: no presence test for a value that may be absent, no union types, and children aren't checked against components. The npm packages are unpublished placeholders, and there's no WASM build.

## What's next

2. Possibly a project file that both `mesh check` and the server read, and a thin VS Code extension that only starts `mesh-lsp` and passes its settings.
3. NEXUS generating manifests from its component definitions.
