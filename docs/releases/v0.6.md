# MESH v0.6.0 release notes

*Draft, 2026-09-27. Not yet released: the version numbers are bumped and the tag pushed in the release step, after review.*

v0.6 settles the semantic questions PORT raised when it built MESH's first real renderer, so that a renderer, and later server rendering and hydration, can realize a render tree without deciding anything about what it means. It adds no syntax, and changes no evaluation.

The questions, the evidence and the decisions are in [`docs/superpowers/specs/2026-09-27-mesh-port-semantic-resolution.md`](../superpowers/specs/2026-09-27-mesh-port-semantic-resolution.md).

## Highlights

- **A value, its text, and its realization are three steps, and MESH owns the first two.** A render tree's prop value is the semantic value: evaluated and checked, and not realized for any target. Its MESH text is defined by [§9.7.7](../MPRX-SPEC.md#977-the-text-of-a-value) and made by the runtime. Realization is the renderer's, in exactly two ways ([§9.8.7](../MPRX-SPEC.md#987-realization)): natively, in a target slot that holds a value of its kind exactly, or as its MESH text in a slot that holds only text. No platform coercion, host-language formatting or JSON, ever.
- **`propText`.** A render tree's node now carries the MESH text of each number, boolean and `null` prop. A renderer copies it into a text-only slot and never makes a text itself, in any language, with no MESH code. Strings need no copy; lists and records have no text, and can only be realized natively. A `null` prop has the text `null`; an absent prop has neither value nor text.
- **Event resolution** ([§9.9](../MPRX-SPEC.md#99-event-resolution)). One interaction reaches at most one binding, and so gives at most one intent: from the innermost interacted node towards the root, the first node whose primitive has the interaction's applicable event, and which binds it, receives the interaction. It is not DOM bubbling: there are no phases, and no second binding fires. A primitive's event contract is MESH-level and the same on every target; a PORT maps its target's interactions onto it, and resolution takes the resulting applicable event.
- **Conformance vectors,** [`examples/conformance/`](../../examples/conformance/README.md): real programs, their trees, and named cases for `propText` (including absent, `null` and a string as three distinct node shapes) and for event resolution, in JSON and MPRX, for a renderer in any language to test itself against, without a browser or MESH's code.

## Compatibility

- **`render-v1` keeps `version: 1`.** Its schema has always said a later MESH may add properties without a new version, and that renderers must ignore properties they don't know. `propText` is optional, so every v0.5 tree is still valid against the new schema. A consumer that validates trees against the *v0.5* schema file will reject nodes with `propText`, since `$defs/node` lists its properties exactly: use the new schema.
- **`template-v1`, the manifest format, model fingerprints and runtime diagnostics are unchanged.** v0.5 templates run on v0.6.
- **Rust API:** `mesh_runtime::Node` has a new field, `prop_text`, and is `#[non_exhaustive]`, so code outside the crate can't build it with a struct literal or destructure it exhaustively. `resolve`, `Interaction`, `Resolved` and `ResolveError` are new: `resolve` returns `Ok(Some(Resolved))`, `Ok(None)` when no node qualifies, or `Err(ResolveError::UnknownTarget)`. `number_to_text` is still exported, for Rust hosts; no new formatting function is exported, and a renderer needs none.
- **Renderers:** a renderer that lets one interaction reach more than one binding no longer conforms to §9.9; one that converts values to text itself never conformed to MESH's one-evaluator rule, and §9.8.7 now says so directly.

## Upgrading from v0.5

- **Renderers:** where a prop goes into a text-only slot, use the value when it's a string and `propText` otherwise; refuse a list or record there. Resolve each interaction to at most one binding, and check against `examples/conformance/`.
- **Hosts:** nothing changes. Dispatch is as before, once per reported handler identifier.
- **Rust code building `mesh_runtime::Node` values:** trees come from `render`; read their fields rather than constructing them.
